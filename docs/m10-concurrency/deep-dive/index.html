Deep Dive — What Actually Overlaps When You Run Checks Concurrently

The lab built check_many() and check_many_async() and proved, by timing them, that concurrency overlaps the wait instead of queuing it. This page opens up the machinery underneath that result: what the GIL actually blocks and why a thread pool still speeds up I/O-bound work in CPython, what happens inside the asyncio event loop on every await, what changes in a connection pool once eight requests share it instead of one, and the fleet-checking patterns you reach for once "check everything at once" stops being good enough on its own. You will use this the day you are asked why a concurrent script did not get faster, why a shared client behaved unexpectedly under load, or why checking two hundred endpoints every thirty seconds during an incident is not actually the right design.

Where this picks up

You need ~/platformops at v0.8 from the lab, with check_many(), check_health_async() and check_many_async() in place. Every command below runs a short, disposable script in its own scratch folder -- none of them touch httpclient.py, cli.py or your project's git history.

mkdir -p ~/platformops/dd-scratch && cd ~/platformops/dd-scratch

Re-running any command on this page is safe.

1 -- The GIL blocks Python bytecode, not a network wait​

Picture a single-lane bridge with one toll booth: only one car crosses at a time, no matter how many cars are queued on either side. That is the Global Interpreter Lock (GIL) -- only one thread in a CPython process may execute Python bytecode at any given instant, even on a machine with sixteen cores. The lesson already stated this; what it did not show is when a thread gives up its place at the booth. A thread blocked inside a C-level system call -- waiting on a socket for httpx to receive bytes back from a server -- has already stepped off the bridge. It released the GIL before it started waiting, specifically so another thread can cross while it does nothing but wait.

dd-scratch/gil_release_demo.py
import threading
import time

N_THREADS = 4
ITERATIONS = 5_000_000


def cpu_bound_spin():
    total = 0
    for i in range(ITERATIONS):
        total += i


def io_bound_wait():
    time.sleep(0.5)


def time_it(target, label):
    threads = [threading.Thread(target=target) for _ in range(N_THREADS)]
    start = time.perf_counter()
    for t in threads:
        t.start()
    for t in threads:
        t.join()
    elapsed = time.perf_counter() - start
    return elapsed


single_start = time.perf_counter()
cpu_bound_spin()
single_elapsed = time.perf_counter() - single_start

cpu_elapsed = time_it(cpu_bound_spin, "cpu")
io_elapsed = time_it(io_bound_wait, "io")

print(f"1 CPU-bound thread:  {single_elapsed:.2f}s")
print(f"{N_THREADS} CPU-bound threads: {cpu_elapsed:.2f}s  (GIL forces them to take turns)")
print(f"{N_THREADS} I/O-bound threads: {io_elapsed:.2f}s  (GIL released during the wait)")
uv run python3 dd-scratch/gil_release_demo.py

Expected output

1 CPU-bound thread:  0.13s
4 CPU-bound threads: 0.53s  (GIL forces them to take turns)
4 I/O-bound threads: 0.50s  (GIL released during the wait)

One thread counts to five million in about 0.13 seconds. Four threads doing the same work take about four times as long (0.53s) -- the GIL forces them to take turns through the same single-lane bridge, so threading buys nothing for CPU-bound work. Four threads each sleeping for half a second finish in about half a second total, because time.sleep() (like a real socket read inside httpx) releases the GIL for the duration of the wait, letting the other three threads run during that same window. check_health()'s call to client.get(url) spends almost all of its time in exactly this released state -- which is the entire reason ThreadPoolExecutor(max_workers=8) in check_many() produces a real speedup in CPython, despite the GIL, for this specific kind of work.

This is also why the module's guidance draws a hard line between I/O-bound and CPU-bound work: ThreadPoolExecutor speeds up check_health() because the wait happens outside the GIL, but the exact same pool would give you no speedup at all wrapped around a CPU-heavy function -- parsing a huge JSON payload, computing a checksum over a large file -- because that work never releases the GIL in the first place. multiprocessing (separate processes, separate GILs each) is the tool for that case, not ThreadPoolExecutor.

2 -- What actually happens on await​

A single receptionist juggling three calls only works because the receptionist has a clear signal for "this call is on hold, check the next line" -- otherwise they would just stare at a silent phone. await is that signal for asyncio. When check_health_async() hits await client.get(url, timeout=timeout), the coroutine does not block the thread -- it suspends itself and hands control back to the event loop, a single loop running in the one thread that owns every task in check_many_async(). The event loop looks at every other task that is not currently suspended waiting on I/O and runs whichever one is ready to make progress, until that task also hits an await and suspends. When the operating system tells the event loop that URL A's socket has data ready to read, the loop resumes exactly the coroutine that was waiting on it, picking up right after that await line.

dd-scratch/event_loop_interleave.py
import asyncio
import time


async def labeled_wait(name: str, seconds: float) -> None:
    print(f"{time.perf_counter():.3f} {name}: starting, about to await")
    await asyncio.sleep(seconds)
    print(f"{time.perf_counter():.3f} {name}: resumed after await")


async def main() -> None:
    await asyncio.gather(
        labeled_wait("A", 0.3),
        labeled_wait("B", 0.1),
        labeled_wait("C", 0.2),
    )


asyncio.run(main())
uv run python3 dd-scratch/event_loop_interleave.py

Expected output

1167104.894 A: starting, about to await
1167104.894 B: starting, about to await
1167104.894 C: starting, about to await
1167104.994 B: resumed after await
1167105.095 C: resumed after await
1167105.195 A: resumed after await
Your timestamps will differ

The exact numbers come from time.perf_counter() on the machine that ran this -- yours will be completely different. The important shape: all three "starting" lines print first, then the "resumed" lines appear in a different order (B, C, A), matching the shortest sleep first.

All three "starting" lines print first, back to back, before any "resumed" line -- each coroutine runs up to its own await, suspends, and hands control back immediately, rather than running to completion one at a time. The "resumed" lines then print out of order, B first, then C, then A -- in the order each one's wait actually finished, not the order they were started in. This is exactly the mechanism check_many_async() relies on: every check_health_async() call reaches its await client.get(...) almost immediately, all of them suspend together, and the event loop wakes each one up independently as its own response arrives.

asyncio.Semaphore(max_concurrency) gates entry to this same suspend/resume cycle, not raw parallelism -- there is only ever one thread here. async with semaphore: in check_many_async()'s _bounded_check() suspends a coroutine at the semaphore itself if the cap is already full, exactly the same "await, then get resumed later" mechanism, just resumed by another task calling semaphore.release() (implicitly, on exiting the async with block) instead of by a socket becoming readable. A ninth coroutine waiting on Semaphore(8) is parked in the same event loop queue as one waiting on a slow server -- neither one is spending a thread doing nothing, because there is only the one thread to begin with.

3 -- One shared connection pool behaves differently than eight separate clients​

A single shared taxi rank with eight cabs on call behaves very differently from eight commuters each owning a private car: the rank can reuse a cab the moment it drops someone off, while eight private cars each sit idle between trips, and each one had to be bought (a handshake) before it could be used at all. check_many_async() opens exactly one httpx.AsyncClient() for the whole batch and passes it into every check_health_async() call -- every request in that batch shares one connection pool, and a repeated request to the same host can reuse an already-open, already TLS-handshaked connection instead of paying for a new one.

dd-scratch/shared_pool_demo.py
import time
import httpx

N = 6
URL = "https://example.com"


def shared_client() -> float:
    start = time.perf_counter()
    with httpx.Client() as client:
        for _ in range(N):
            client.get(URL, timeout=10.0)
    return time.perf_counter() - start


def fresh_client_per_request() -> float:
    start = time.perf_counter()
    for _ in range(N):
        with httpx.Client() as client:
            client.get(URL, timeout=10.0)
    return time.perf_counter() - start


shared = shared_client()
fresh = fresh_client_per_request()
print(f"one shared Client, {N} sequential requests: {shared:.2f}s")
print(f"fresh Client per request, {N} sequential requests: {fresh:.2f}s")
uv run python3 dd-scratch/shared_pool_demo.py

Expected output

one shared Client, 6 sequential requests: 0.46s
fresh Client per request, 6 sequential requests: 0.89s
Your exact times will differ

Network conditions change the numbers each run. The important shape: the shared client is measurably faster than the fresh-client-per-request run, typically close to twice as fast, because it pays the TCP-plus-TLS handshake only once and reuses the open connection for every later request to the same host.

The shared client finishes roughly twice as fast -- the first request against a host pays the TCP-plus-TLS handshake, and every later request to that same host inside the shared pool reuses the connection that handshake already opened. The fresh-client run pays that handshake cost six times over, once per throwaway client, even though every request targets the identical host. This is the concrete reason check_many_async()'s spec insisted on "one shared httpx.AsyncClient() across every URL in the batch" instead of letting each call open its own -- opening a fresh client per URL inside a concurrency-bounded loop throws away exactly the efficiency the concurrency was meant to buy.

httpx.Client is documented as thread-safe, so check_many()'s thread pool could share one client across its eight threads the same way -- the lab's version does not do this (each check_health() call opens its own short-lived httpx.Client()), which is a real, deliberate cost: every threaded check pays its own handshake, where a shared-client version would not. The trade-off is code simplicity -- check_health() stays a single-purpose, dependency-free function usable outside a batch context, at the price of losing pool reuse when it is called inside one. DNS resolution follows the same shared-vs-fresh pattern: a resolved hostname is cached by the OS resolver (and, for the lifetime of a connection, by the connection pool itself) for a short window, so a shared client issuing many requests to the same host resolves DNS once and reuses that answer, where opening a fresh client per request re-resolves it every single time.

4 -- Progressive health checks and circuit breakers: what "check everything" grows into​

Checking three hundred endpoints with max_concurrency=8 every time is honest and bounded, but it treats every endpoint as equally worth a full check on every pass -- which stops being true the moment part of the fleet is degraded. Three patterns show up in real fleet-checking tools once the naive "check everything, every time" version starts costing too much:

  • Progressive checks. Run a fast, cheap pass first (a lightweight HEAD or a shallow /healthz) across the whole fleet, then only run a slower, deeper check (a full dependency check, a synthetic transaction) against the endpoints the fast pass flagged. This is the same idea as triage in an incident -- you do not run a full diagnostic on every service, only on the ones the quick pass already said are suspect.
  • Circuit breakers. Once an endpoint has failed enough consecutive checks, stop sending it new requests for a cooldown window and report it as "known bad" from cache instead. This protects two things at once: it stops a batch of checks from repeatedly hammering a service that is already known to be down, and it stops that one dead endpoint's timeout from eating a slot in your concurrency cap on every single pass.
  • Exponential fan-out. Rather than always checking the full fleet at a fixed concurrency, widen the cap when everything is healthy (cheap to check fast) and narrow it automatically when failures start appearing (avoid adding load to a system that is already struggling) -- the concurrency cap becomes a dial the checker itself adjusts, not a constant.
dd-scratch/circuit_breaker_sketch.py
from dataclasses import dataclass, field


@dataclass
class CircuitState:
    consecutive_failures: int = 0
    open_until: float = 0.0  # a perf_counter() timestamp; 0 means "closed"


FAILURE_THRESHOLD = 3
COOLDOWN_SECONDS = 30.0


def record_result(state: CircuitState, ok: bool, now: float) -> None:
    if ok:
        state.consecutive_failures = 0
        state.open_until = 0.0
        return
    state.consecutive_failures += 1
    if state.consecutive_failures >= FAILURE_THRESHOLD:
        state.open_until = now + COOLDOWN_SECONDS


def should_skip(state: CircuitState, now: float) -> bool:
    # "Open" means the breaker has tripped -- skip real checks until the cooldown passes.
    return now < state.open_until


breakers: dict[str, CircuitState] = {}


def circuit_for(url: str) -> CircuitState:
    return breakers.setdefault(url, CircuitState())
uv run python3 -c "
from importlib import util
spec = util.spec_from_file_location('cb', 'dd-scratch/circuit_breaker_sketch.py')
cb = util.module_from_spec(spec)
spec.loader.exec_module(cb)

state = cb.circuit_for('https://flaky.example')
now = 1000.0
for i in range(3):
    cb.record_result(state, ok=False, now=now)
    print(f'after failure {i + 1}: consecutive={state.consecutive_failures}, skip={cb.should_skip(state, now)}')
print(f'skip 10s later: {cb.should_skip(state, now + 10)}')
print(f'skip 31s later: {cb.should_skip(state, now + 31)}')
"

Expected output

after failure 1: consecutive=1, skip=False
after failure 2: consecutive=2, skip=False
after failure 3: consecutive=3, skip=True
skip 10s later: True
skip 31s later: False

Three consecutive failures trip the breaker (should_skip flips to True); ten seconds into the thirty-second cooldown it is still tripped; past thirty-one seconds it has reset. This sketch is intentionally not wired into check_many_async() -- it is the shape you would layer on top of it once a fleet checker runs continuously (a monitoring loop, not a one-shot CLI command) and starts spending most of its concurrency budget re-checking endpoints everyone already knows are down.

Teardown​

cd ~/platformops
rm -rf dd-scratch

This removes only the scratch folder this page created. Your real httpclient.py, cli.py and the rest of ~/platformops are untouched.

Where you will use this
  • The GIL blocks Python bytecode, not a thread that is parked in a socket read. Use it when: deciding whether to reach for ThreadPoolExecutor or multiprocessing for a new batch job -- a thread pool speeds up work that spends its time waiting on I/O; it does nothing for a CPU-heavy loop that never releases the GIL.
  • await suspends a coroutine and hands the single thread to whichever other task is ready to run; nothing runs in true parallel inside one event loop. Use it when: debugging why an asyncio script feels stuck -- a coroutine that never hits an await (a long synchronous call slipped into async code) blocks the entire event loop, not just itself.
  • A shared httpx.Client/httpx.AsyncClient reuses TCP and TLS handshakes across requests to the same host; a fresh client per request pays that cost every time. Use it when: writing or reviewing any batch or fan-out HTTP code -- confirm one client object is built once and passed down, not constructed inside the loop that calls it.
  • Progressive checks and circuit breakers exist because checking every endpoint the same way, every time, wastes capacity on endpoints already known to be down. Use it when: a health checker is asked to run continuously rather than once -- before widening max_concurrency further, check whether the real fix is skipping known-bad endpoints instead of checking them faster.
