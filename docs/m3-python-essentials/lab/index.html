Lab — Build PlatformOps v0.1: the Infrastructure Inventory Reporter

This lab has two phases. In Phase A you write the inventory data and the checking functions yourself, by hand, so you know exactly what every line does. In Phase B you hand a short, written request to a coding agent to extend that same file, then you review its change before accepting it — the same review habit you will use every time an agent touches this project for the rest of the course.

You need the ~/platformops project from the M2 lab, already tagged v0.0, and a coding agent installed (claude --version should print a version — see the Environment page if it does not).

cd ~/platformops

Phase A — write the inventory reporter by hand​

1. Write the inventory and the check functions​

Create src/platformops/inventory.py with this content:

"""Infrastructure inventory reporter — PlatformOps v0.1.

A small, in-memory list of servers, and a few checks a platform team runs
on it by hand today: who forgot to tag a server with an owner, which prod
servers are under-provisioned on memory, and how many servers sit in each
environment.
"""

MIN_PROD_MEMORY_GB = 8

INVENTORY = [
    {"name": "web-01", "env": "prod", "cpu": 4, "memory_gb": 16,
     "tags": {"owner": "web-team", "tier": "frontend"}},
    {"name": "web-02", "env": "prod", "cpu": 4, "memory_gb": 6,
     "tags": {"tier": "frontend"}},
    {"name": "api-01", "env": "prod", "cpu": 8, "memory_gb": 32,
     "tags": {"owner": "platform-team", "tier": "backend"}},
    {"name": "api-02", "env": "prod", "cpu": 8, "memory_gb": 4,
     "tags": {"owner": "platform-team", "tier": "backend"}},
    {"name": "db-01", "env": "prod", "cpu": 16, "memory_gb": 64,
     "tags": {"owner": "data-team", "tier": "database"}},
    {"name": "cache-01", "env": "staging", "cpu": 2, "memory_gb": 8,
     "tags": {"owner": "platform-team", "tier": "cache"}},
    {"name": "worker-01", "env": "staging", "cpu": 4, "memory_gb": 8,
     "tags": {}},
    {"name": "worker-02", "env": "dev", "cpu": 2, "memory_gb": 4,
     "tags": {"owner": "dev-team"}},
    {"name": "build-01", "env": "dev", "cpu": 4, "memory_gb": 8,
     "tags": {"owner": "ci-team", "tier": "ci"}},
    {"name": "monitor-01", "env": "prod", "cpu": 4, "memory_gb": 8,
     "tags": {"owner": "sre-team", "tier": "observability"}},
]


def find_missing_owner(inventory):
    """Return the names of servers that have no `owner` tag."""
    missing = []
    for server in inventory:
        if "owner" not in server["tags"]:
            missing.append(server["name"])
    return missing


def find_low_memory_prod(inventory, min_memory_gb=MIN_PROD_MEMORY_GB):
    """Return the names of prod servers with less than `min_memory_gb` memory."""
    flagged = []
    for server in inventory:
        if server["env"] == "prod" and server["memory_gb"] < min_memory_gb:
            flagged.append(server["name"])
    return flagged


def count_by_environment(inventory):
    """Return a dict mapping each environment name to its server count."""
    counts = {}
    for server in inventory:
        env = server["env"]
        counts[env] = counts.get(env, 0) + 1
    return counts


def print_report():
    """Print a plain-text infrastructure inventory report."""
    print("PlatformOps Inventory Report")
    print("=============================")
    print(f"Total servers: {len(INVENTORY)}")

    print("\nServers by environment:")
    for env, count in count_by_environment(INVENTORY).items():
        print(f"  {env}: {count}")

    print("\nMissing owner tag:")
    missing = find_missing_owner(INVENTORY)
    if missing:
        for name in missing:
            print(f"  - {name}")
    else:
        print("  (none)")

    print(f"\nProd servers with low memory (< {MIN_PROD_MEMORY_GB}GB):")
    low_memory = find_low_memory_prod(INVENTORY)
    if low_memory:
        for name in low_memory:
            print(f"  - {name}")
    else:
        print("  (none)")


if __name__ == "__main__":
    print_report()

Ten servers, ten small facts each. Three of them break a rule on purpose: web-02 and worker-01 have no owner tag in their tags dict, and web-02 and api-02 are in prod with less memory than MIN_PROD_MEMORY_GB. Your three functions are written to catch exactly that — each one loops over the same INVENTORY list and returns a plain list of names.

The if __name__ == "__main__": guard is what lets this same file be both a script you run directly and, later, a module other code can import without it printing anything on import.

2. Write the tests​

Create tests/test_inventory.py:

from platformops.inventory import (
    INVENTORY,
    count_by_environment,
    find_low_memory_prod,
    find_missing_owner,
)


def test_find_missing_owner_flags_servers_without_an_owner_tag():
    missing = find_missing_owner(INVENTORY)
    assert "web-02" in missing
    assert "worker-01" in missing
    assert "web-01" not in missing


def test_find_low_memory_prod_flags_only_underpowered_prod_servers():
    flagged = find_low_memory_prod(INVENTORY)
    assert "web-02" in flagged
    assert "api-02" in flagged
    # a low-memory server outside prod must not be flagged
    assert "worker-02" not in flagged
    # a well-provisioned prod server must not be flagged
    assert "db-01" not in flagged


def test_count_by_environment_matches_the_inventory():
    counts = count_by_environment(INVENTORY)
    assert counts == {"prod": 6, "staging": 2, "dev": 2}
    assert sum(counts.values()) == len(INVENTORY)

Each test checks one function against the real inventory data — not a fake, simplified version of it. This is deliberate: the data itself carries the interesting cases (a server missing a tag, a prod server that is under-provisioned), so the tests read almost like plain English questions about that data.

3. Run the quality gates​

uv run ruff format .

Expected output

1 file reformatted, 4 files left unchanged

Ruff reformatted inventory.py — most likely it rewrote the wide dictionary entries in INVENTORY onto one line per field, which is Ruff's standard style for a dict that does not fit on one line. Open the file and take a look; it still behaves exactly the same, just laid out more consistently. Run the same command again and it will report nothing left to change.

uv run ruff check .

Expected output

All checks passed!
uv run pytest -q

Expected output

Five tests: the two from test_foundation.py in M2, plus the three you just wrote.

Phase B — extend it with your coding agent​

Everything from here is delegated. You will write a short, exact request, hand it to your coding agent (this lab shows Claude Code; any repository-aware coding agent — Codex, OpenCode and others — works the same way), and then review what comes back before you accept it.

5. Ask your coding agent to extend the report​

Open your coding agent in the project folder:

claude

Paste this request exactly as written:

I'm working in this uv-managed Python project. Please update
src/platformops/inventory.py and its tests with these requirements:

1. Add a function filter_by_environment(inventory, env) that returns only
   the servers whose env field matches the one given.
2. Add a function build_summary(inventory) that returns a dict with
   total_servers, total_cpu, total_memory_gb, and by_environment (a count
   per environment).
3. Add a function sort_by_name(inventory) that returns a NEW list of
   servers sorted by name, without changing the original INVENTORY list.
4. Update print_report() so the printed report also shows a summary
   section with the new totals, a section listing the prod servers (use
   filter_by_environment for it), and a section listing all servers
   sorted by name.

Constraints:
- Do not add any new third-party dependencies.
- Do not change the behavior of the existing functions: find_missing_owner,
  find_low_memory_prod, count_by_environment.
- All existing tests in tests/test_inventory.py must stay green.
- Add tests for the new functions.
- Run `uv run pytest -q` yourself before you finish, and tell me the result.

This is a spec, not a conversation: what to add, and what must not change. Stating the constraints (no new dependencies, existing behavior untouched, existing tests green) up front is what makes the result reviewable — you are not guessing what "good" looks like after the fact.

Why does requirement 3 say "a NEW list"?

Python gives you two ways to sort. inventory.sort(key=...) sorts the list in place — it changes the original. sorted(inventory, key=...) leaves the original alone and returns a new sorted list. Requirement 3 demands the second kind. If sort_by_name quietly reordered INVENTORY itself, every other function reading that list would suddenly see a different order — the shared-data trap from this module's lesson, hiding inside a one-word choice. When you review the agent's diff, check which one it used.

Let the agent work. It will report back once it has made the change and run the tests itself.

No coding agent on this machine?

You can still finish this lab. The instructor's finished version of this extension lives in your labs clone at ~/307-aipython-labs/labs/checkpoints/v0.1/src/platformops/inventory.py (and its tests at ~/307-aipython-labs/labs/checkpoints/v0.1/tests/test_inventory.py). Copy those two files into your project, then treat them exactly as if an agent wrote them: run the review checklist below, read the diff, and run the gates yourself. The review skill is the point of this phase — not who typed the code.

6. Review what changed — before you trust it​

Do not skip this step because the agent said it ran the tests. Check for yourself.

git add -A && git diff --cached

Stage first, then diff the staged snapshot against your last commit (v0.0). This is not optional cosmetics: inventory.py and test_inventory.py are brand-new files that Phase A created and never committed, so plain git diff (which only compares already-tracked files) shows nothing at all for them — you would see an empty diff and wrongly conclude nothing changed. Staging with git add -A first makes git diff --cached show the full new-file content as an addition, alongside any change to a file that was already tracked.

Read the diff. Your agent's exact wording, variable names and code layout will differ from anyone else's — that is expected and fine. What you are checking for:

  • The three original functions (find_missing_owner, find_low_memory_prod, count_by_environment) are still there, unchanged in behavior.
  • The new functions match what you asked for: a filter, a summary, a sort.
  • Nothing you did not ask for got added — no new dependency in pyproject.toml, no rewrite of parts you did not mention.

Then run the gates yourself, independently of whatever the agent claimed:

uv run ruff format .
uv run ruff check .
uv run pytest -q

Expected output (the exact test count depends on how many tests your agent added; your own numbers may differ from this capture — what must be true is zero failures)

5 files left unchanged
All checks passed!
........                                                                 [100%]
8 passed in 0.01s

If you asked for four things and reviewed the diff, this checklist is your acceptance test:

  • Did the three original functions keep their exact names and behavior? (the original tests answer this — if they still pass unmodified, the answer is yes)
  • Do all tests pass, with zero failures?
  • Does ruff check . still report All checks passed!?
  • Is pyproject.toml unchanged (no new dependency snuck in)?
  • Does the printed report now show a summary section and a sorted section?

Only once every box is checked do you accept the change. This is the review habit this course keeps coming back to: an agent's own claim that "it works" is not evidence — the same three gates you already trust are the evidence, and you are the one who reads the diff.

7. Bump the version and tag the release​

Open pyproject.toml and change the version line:

version = "0.1.0"

Update the README.md line that names the current release:

Current release: **v0.1 — Infrastructure Inventory Reporter**.

This module does not touch src/platformops/__init__.py — its __version__ string and about() tagline stay at 0.0.0 for now. That is expected: this module's work is the inventory reporter, not the toolkit's version wiring, which a later module ties together properly. pyproject.toml's version field is the one the Release Ladder tool reads, and that one you have just bumped.

Bring the environment back in step with the version change:

uv sync

Troubleshooting
  • KeyError: 'owner' when running your own code — you wrote server["tags"]["owner"] directly somewhere instead of checking "owner" in server["tags"] first. Some servers in INVENTORY have no owner key at all; that gap is deliberate. Check for the key before reading it, or use server["tags"].get("owner"), which returns None instead of raising. .get() also takes a fallback value: server["tags"].get("owner", "unassigned") returns "unassigned" when the key is missing — handy for reports.
  • count_by_environment returns wrong numbers — a common cause is comparing server["env"] == "Prod" (capital P) somewhere; Python string comparison is case-sensitive, and every environment name in INVENTORY is lowercase.
  • Your agent's diff touches pyproject.toml — this means it added a dependency you did not ask for. Reject that part of the change: ask the agent to solve the requirement using only the standard library, since nothing in the spec needs a third-party package.
  • Test count in Step 6 does not match the capture above — expected. It depends on how many tests your own agent chose to add for the three new functions. What matters is 0 failed.
  • uv run python -m platformops.inventory prints nothing — you are most likely running it from outside the platformops folder, or the if __name__ == "__main__": guard is missing or mis-indented at the bottom of inventory.py.
