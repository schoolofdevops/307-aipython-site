Python Essentials — Written by Hand

Module slides​

Walk this short whiteboard deck for the big picture, or open it fullscreen.

▶ Module 3 — Python EssentialsOpen fullscreen ↗

Your ~/platformops project can already run three quality checks and print one line of text. This module gives it something real to work with: a small list of servers, and code that reads through that list and flags problems — a missing owner tag, a prod server that is short on memory, how many servers sit in each environment. Every idea below is something you will type into inventory.py in the lab that follows.

1. A name for a value — variables and basic types​

A shipping label stuck on a box does not become the box — it just points at it, so you (or anyone else) can find that box later by reading the label. A Python variable works the same way: cpu = 4 does not create a box called cpu that holds the number 4 inside it. It sticks the label cpu onto the value 4, so your code can refer to it by name.

Four basic types cover almost everything you will store about a server:

TypeExampleWhat it holds
str (string)"web-01"Text, always in quotes
int (integer)4A whole number, no decimal point
float2.5A number with a decimal point
bool (boolean)True / FalseExactly one of two states
name = "web-01"
cpu = 4
memory_gb = 16
is_prod = True

2. Lists — an ordered shelf of items​

Think of a list as a numbered shelf: item 1, item 2, item 3, in a fixed order, and you can point at any one of them by its shelf number. In Python, that shelf number is called an index, and it starts at 0, not 1.

servers = ["web-01", "web-02", "api-01"]
print(servers[0])   # "web-01" -- the first shelf spot

A list can grow (servers.append("db-01")) or shrink, and it always keeps the order you put things in. That order is exactly what you want for a server inventory: you read it top to bottom, the same way every time.

3. Dictionaries — a labeled folder, not a numbered shelf​

A dictionary (dict) is a filing folder with a labeled tab on every page, instead of a numbered shelf. You do not ask for "page 3" — you ask for the page labeled "name", or the one labeled "memory_gb", and the folder hands you that exact page, called a key, paired with what is written on it, called a value.

server = {"name": "web-01", "env": "prod", "cpu": 4, "memory_gb": 16}
print(server["env"])   # "prod"

This fits one server record perfectly: a handful of named facts about one machine, each one easy to find by its label.

4. Putting it together — an inventory is a list of dictionaries​

A real server inventory is both ideas at once: an ordered shelf of folders. One list holds every server; each server is its own labeled folder.

INVENTORY = [
    {"name": "web-01", "env": "prod", "cpu": 4, "memory_gb": 16,
     "tags": {"owner": "web-team", "tier": "frontend"}},
    {"name": "web-02", "env": "prod", "cpu": 4, "memory_gb": 6,
     "tags": {"tier": "frontend"}},
    {"name": "cache-01", "env": "staging", "cpu": 2, "memory_gb": 8,
     "tags": {"owner": "platform-team"}},
]

Notice web-02 has a tags folder with no "owner" label in it at all — a real, common gap in a real inventory, and exactly the kind of thing your lab code will catch.

5. Tuples — a pair that is not meant to change​

A tuple looks like a list but is written with parentheses, and once you create it, you cannot add, remove, or replace an item in it. Think of a printed shipping label with a fixed region code stamped on it: ("us-east-1", "us-east-1a"). Nobody edits a printed label — if the region changes, you print a new one. Use a tuple for facts that belong together and are not supposed to move once set, like a (region, availability_zone) pair.

location = ("us-east-1", "us-east-1a")
region, az = location   # unpacking: two names for the two values

6. Sets — a guest list, not a seating chart​

A set holds items with no fixed order and, importantly, no duplicates — asking it twice to add the same environment name changes nothing. Think of a guest list at the door: the question is only "is this name on the list?", never "which position is this name in?".

environments_seen = {"prod", "staging", "prod"}
print(environments_seen)             # {"prod", "staging"} -- the repeat collapses
print("prod" in environments_seen)   # True

Reach for a set when you only care whether something is present, not where.

One rule to remember: a set can only hold simple, unchangeable values — strings, numbers, tuples. Lists and dictionaries cannot go inside a set; Python refuses them with a TypeError: unhashable type. So "a set of servers" (dictionaries) is not possible — but a set of server names (strings) works perfectly.

7. Conditions, loops and membership — checking every server against a rule​

A loop walks down your list one server at a time, the same way a checkpoint guard checks one badge at a time instead of glancing at the whole line at once. Inside the loop, a condition (if / else) decides what to do with each one, and in asks a plain yes-or-no question: "is this key present?"

for server in INVENTORY:
    if "owner" not in server["tags"]:
        print(f"{server['name']} has no owner tag")

in on a dictionary checks its keys, not its values — "owner" in server["tags"] asks "does this folder have a page labeled owner?", regardless of what is written on that page.

8. Indexing, slicing and f-strings​

Indexing (servers[0]) picks one item by its shelf position. Slicing (servers[0:2]) picks a range — "give me the first two", the way you might photocopy pages 1 and 2 of a folder without touching the rest. Both work the same way on strings, since a string is really an ordered sequence of characters.

An f-string is a template with blanks that Python fills in for you at the point you write f"..." — like a form letter that inserts each reader's own name:

name = "web-01"
memory_gb = 16
print(f"{name} has {memory_gb}GB of memory")

9. Mutable vs immutable — why this bites in automation​

Some Python values can be changed after they are created; others cannot. Lists, dicts and sets are mutable — you can add to them, remove from them, edit them in place. Strings, numbers, booleans and tuples are immutable — once created, that exact value never changes; any "change" actually builds a brand new value and gives it the same name.

Picture a shared whiteboard in an operations room versus a printed status report. Two people can walk up to the same whiteboard and both scribble on it — whoever looks at it next sees both sets of changes, whether they meant to or not. A printed report, once handed out, stays exactly as it was printed; a second person marking up their own copy never changes yours.

This matters the moment two names point at the same list or dict, which happens more often in real code than it looks:

inventory = [{"name": "web-01"}]
backup = inventory          # backup is not a copy -- it is the same whiteboard
backup.append({"name": "web-02"})
print(len(inventory))       # 2 -- the "backup" name changed the original too

backup = inventory did not make a second list. It put a second label on the exact same one — the way cpu = 4 earlier put one label on one value, except here two labels point at one mutable object. Append through either name, and both names see it, because there is only one whiteboard. This is the single most common reason a script "mysteriously" sees data it should not — a function received the same mutable list another part of the program is still holding, and changed it out from under it. The lab's report-writing code, and the Deep Dive after it, both come back to this.

Common pitfalls
  • Confusing a dict's in check with checking its values. "owner" in server["tags"] checks keys only. To check a value, look it up first: server["tags"].get("owner") == "web-team".
  • Assuming a list index starts at 1. It starts at 0. servers[1] is the second item, not the first.
  • Writing a tuple and expecting it to grow. location.append(...) fails — tuples have no append. If you need to add items later, you wanted a list.
  • Passing a mutable list into a function and being surprised it changed. If a function appends to or edits a list you handed it, your original list changes too — they are the same object, not a copy. Copying it first (list(original)) avoids this when you need the original left alone.
  • Using = where you meant ==. = assigns a value; == compares two values. Python's syntax rejects if env = "prod": outright, which catches this one early — but the habit is worth naming, since it carries over from other languages.
