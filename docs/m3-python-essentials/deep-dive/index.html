Deep Dive — How Python Actually Stores Your Data

The lab had you write lists, dicts and tuples and trust that they behaved the way the lesson described. This page opens up what a Python variable really is underneath, why two variables can quietly share one mutable object, why copying a nested structure is not always as safe as it looks, and why a dict lookup on a ten-thousand-server inventory is not slower than one on a ten-server inventory. You reach for this the day a copy of your inventory data changes when you only meant to touch the copy, or a teammate asks why server in big_list is timing out a health check under load.

Where this picks up

You need your ~/platformops project from the lab, with its .venv present — none of the commands below touch inventory.py itself, so they work the same whether you are at v0.0 or v0.1. If you removed the project, rebuild the minimum in under a minute:

cd ~
[ -d platformops ] || (uv init --package --vcs none --python 3.12 platformops && cd platformops && uv python pin 3.12 && uv add --dev ruff pytest)
cd ~/platformops

Every command below runs a throwaway Python session with a heredoc — nothing it does writes to a file, so re-running any of them is always safe.

1 — A variable is a sticky note, not a box​

The lesson's shipping-label analogy for a single variable extends to two variables at once: a sticky note is cheap to write and stick onto any box you like, including a box someone else already labeled. Nothing stops two sticky notes — two different variable names — from pointing at the exact same box. is and id() are how you check that in Python: is asks "do these two names point at the same object?", and id() gives you that object's actual identity — its address in memory for the length of the program.

uv run python3 - <<'EOF'
inventory = [{"name": "web-01"}]
backup = inventory
backup.append({"name": "web-02"})
print("length of inventory:", len(inventory))
print("same object?", inventory is backup)
print("same id?", id(inventory) == id(backup))
EOF

Expected output

length of inventory: 2
same object? True
same id? True

backup = inventory copied a sticky note, not a box. Both names point at the one list that exists in memory, so appending through backup is the same operation as appending through inventory — there was only ever one list to change. This is the exact mechanism behind the lesson's "why this bites in automation" pitfall, now with the tool (is and id()) to prove it instead of just describing it.

2 — Shallow copy copies the shelf, not what is on it​

A shallow copy is like photocopying the cover sheet of a folder but leaving the same physical inner folder clipped inside it. The outer folder is new — a genuinely different object — but anything nested inside (another folder, another list, another dict) is still the original, shared object. A deep copy photocopies everything, all the way down, so nothing inside is shared with the original anymore.

uv run python3 - <<'EOF'
import copy

original = [{"name": "web-01", "tags": {"owner": "web-team"}}]

shallow = copy.copy(original)
shallow[0]["tags"]["owner"] = "changed-via-shallow"
print("after editing the shallow copy's nested tag:", original[0]["tags"]["owner"])

deep = copy.deepcopy(original)
deep[0]["tags"]["owner"] = "only-in-deep-copy"
print("after editing the deep copy's nested tag:  ", original[0]["tags"]["owner"])
EOF

Expected output

after editing the shallow copy's nested tag: changed-via-shallow
after editing the deep copy's nested tag:   changed-via-shallow

The outer list got copied both times — shallow is not original and deep is not original are both true. But shallow's inner tags dict is the same dict object original points at, so editing it through shallow shows up in original too. The deep copy rebuilt every nested object, so editing it never reaches back into original. A server inventory is exactly this kind of nested structure — a list of dicts, each with its own nested tags dict — which is why copy.copy() on an inventory is rarely what you actually want; copy.deepcopy(), or building a fresh structure explicitly, is.

3 — Why a dict or set lookup does not get slower as your inventory grows​

A list membership check (name in server_names) walks the list from the front until it finds a match or reaches the end — like scanning a shelf of unsorted folders one by one. A dict or set lookup works more like a library's card catalog: a hash function turns the key into a number, and that number tells Python almost exactly which shelf to go to directly, without scanning anything. That is why in on a set or dict stays fast even as the collection grows into the thousands, while in on a list gets slower in direct proportion to its size.

uv run python3 - <<'EOF'
import timeit

names_list = [f"server-{i}" for i in range(5000)]
names_set = set(names_list)
target = "server-4999"

list_time = timeit.timeit(lambda: target in names_list, number=2000)
set_time = timeit.timeit(lambda: target in names_set, number=2000)

print(f"list membership check: {list_time:.4f}s for 2000 lookups")
print(f"set membership check:  {set_time:.4f}s for 2000 lookups")
EOF

Expected output

list membership check: 0.0763s for 2000 lookups
set membership check:  0.0001s for 2000 lookups

The exact seconds vary by machine; the shape does not — the set (and a dict, which uses the same underlying mechanism for its keys) finishes in a small fraction of the list's time, because it never scans. This is the concrete reason find_missing_owner and find_low_memory_prod in your lab loop over INVENTORY (a list, because order and duplicates both matter for a server inventory) but check "owner" not in server["tags"] against a dict, not a list — dict-key membership is the cheap operation, by construction.

4 — A tuple is a sealed container, not a sealed cargo​

A tuple blocks one specific thing: replacing what sits in one of its own slots. Think of a shipping container welded shut after loading — you cannot swap crate 1 for a different crate once it is sealed. But if crate 1 itself is an open box (a list) rather than a sealed one, you can still reach in and rearrange what is inside that box; the container's seal never promised anything about what is inside each crate, only that the crates themselves cannot be swapped or reordered.

uv run python3 - <<'EOF'
record = ("web-01", ["prod"])
record[1].append("critical")
print("after mutating the list inside the tuple:", record)

try:
    record[0] = "web-02"
except TypeError as exc:
    print(f"TypeError: {exc}")
EOF

Expected output

after mutating the list inside the tuple: ('web-01', ['prod', 'critical'])
TypeError: 'tuple' object does not support item assignment

Appending to the list at record[1] works — nothing about the tuple's immutability stops the list itself from changing, since the tuple only holds a sticky note pointing at that list, the same as any other variable. Reassigning record[0] fails outright, because that is the one operation a tuple actually blocks: replacing what one of its own slots points to. "Immutable" describes the tuple's own slots, never what a mutable object living in one of those slots can still do.

Where you will use this
  • Two variable names can point at the same mutable object, and mutating through one shows up through the other. Use it when: a function you pass a list or dict into seems to change data you still hold elsewhere — check with is before assuming a copy happened; often none did.
  • A shallow copy only copies the outer container; nested mutable objects (like a tags dict inside each server) stay shared with the original. Use it when: you copy an inventory before a dry run and the "original" changes anyway — reach for copy.deepcopy, not copy.copy or list(...), whenever the structure has nesting.
  • Dicts and sets look up by a computed hash, not by scanning, so membership checks on them stay fast as an inventory grows. Use it when: you are checking membership against a list of thousands of server names or IDs on every request — build a set once instead of scanning a list repeatedly.
  • A tuple blocks reassigning its own slots, but a mutable object stored in one of those slots can still be changed from underneath it. Use it when: you pick a tuple for a fixed (region, az) pair specifically so it cannot change, and you need to remember that only holds if nothing mutable is nested inside it.
