Observability Automation

Module 26 built a tool that reads GitHub's own records to answer one question: is this release ready? Module 28 and 29 read a Kubernetes cluster's own records. Every one of those tools reads state something else already computed and hands back a report. This module reads a different kind of record: the metrics, logs and alerts a running system produces about itself while it is running. And it does one more thing none of the earlier modules had to do -- it makes PlatformOps's own automation produce that same kind of record about itself, so a run of release-check or restart-execute that misbehaved in production can be reconstructed later, not just guessed at.

Why this matters at work

Something goes wrong in production. A script that usually finishes in nine seconds took nine minutes. A restart command ran, but nobody on the team remembers triggering it. By the time anyone notices, the terminal that ran the command is gone, and "add a print statement and run it again" does not work, because the problem already happened once and may not happen the same way twice. What is actually left behind -- a log line here, a metric there, a trace span somewhere else -- is only useful if it is possible to connect all three back to the one run that caused them. This module builds that connection on purpose, instead of hoping someone remembers the right timestamp to search for later.

1. The claim number, not five separate folders​

Imagine you call an insurance company about a car accident. The call center agent does not go searching for "your case" by your name -- they ask for your claim number first. Every department that ever touches your case -- the adjuster who inspected the car, the repair shop that filed an invoice, the accounts team that issued a payment -- files its own paperwork under that same claim number. Months later, anyone can pull that one number and see every step of the story in order, even though five different departments, none of whom talk to each other daily, each only ever saw their own small piece.

A correlation ID is that claim number, for one run of an automated script. This module generates one short ID (req- plus a few random characters) at the start of a run, and threads it through everything that run touches: every structured log line it writes, and the trace span that records how long the whole run took. Grep that one ID afterward, across the log file and the trace output, and every piece of the story from that run comes back together -- without anyone having had to remember a timestamp or guess which of a hundred similar-looking runs it was.

2. Vitals, chart notes and the alarm -- three signals, one patient​

A hospital patient is monitored three different ways at once. A vital-signs monitor prints a continuous stream of numbers -- heart rate, blood pressure -- moment by moment. A nurse's chart notes are a narrative: "9:00am, patient reported pain, gave medication." An alarm only makes noise when one of those numbers crosses a threshold that actually needs a person's attention right now. All three describe the same patient, but they answer different questions, and a nurse checking on a patient usually needs more than one of them together.

A running service works the same way. Metrics are the vital-signs monitor -- a continuous numeric stream ("http requests per second", "error rate") a metrics backend stores and can be queried, in the same shape Prometheus's own query API uses: ask a question like "how many requests tagged service=payments and status=5xx happened", and get back a list of numbers. Logs are the chart notes -- one line per event, in plain or structured text, that a log-search backend can be asked to filter by service, level or (crucially for this module) correlation ID. Alerts are the alarm -- a separate system watches metrics against thresholds a team already agreed on, and reports which ones are currently firing, in the shape Prometheus's own Alertmanager returns them.

This module's observability-inspect command asks all three questions for one service, under one correlation ID, and reports what each one found. The fetch/aggregate split this course has used since Module 24's cloud audit carries over unchanged: three small functions each talk to exactly one backend and hand back plain facts; one separate, pure function turns those facts into a report. None of the three fetch functions decides whether what they found is good news.

3. A quiet backend and a broken one are not the same fact​

Ask a metrics backend "how many errors happened for this service in the last five minutes" and it can honestly answer two very different ways. It might answer with a real number -- even zero. Zero is still an answer: the backend is working, it checked, and it found nothing. Or the request might never get an answer at all -- the backend is down, the network is broken, the request timed out after every retry. Those are not the same fact, and treating them the same is the easiest mistake to make when automating an observability check.

This module keeps them apart everywhere it reports anything. A section that fetched successfully but found nothing is reported EMPTY -- a real, known answer, the same honest-unknown discipline this course has used since Module 19's service-readiness report, applied here in the opposite direction: a quiet result is not a missing one. A section that could not be reached at all is reported UNKNOWN, and its name is added to sources_failed. An automated check, or an agent reading this tool's --json output, needs to be able to tell "this service is healthy and quiet" apart from "I have no idea what this service is doing right now" -- and only the second one should ever make a script stop trusting its own report.

4. Instrumenting the instrument​

Every tool this course has built so far produces evidence about something else. This module's observability-inspect command is also, itself, something worth being able to debug later. Every fetch it makes writes a structured log line -- one JSON object per line, the shape a log-search backend can actually index, instead of a sentence a person has to re-parse. The whole run is wrapped in one OpenTelemetry span, the same kind of record a trace backend like Jaeger or Tempo visualizes.

The part that ties the two together is traced_operation(). For the length of one run, it makes the same correlation ID appear as an attribute on the span and on every log line written underneath it -- without every function in between having to accept and pass along a correlation_id parameter by hand. It does this with a contextvars.ContextVar, a value that travels with the current call stack automatically, the same way a claim number travels with a case file no matter which desk it lands on next. This is the module's central point: a human staring at a dashboard can eyeball which signals look related. An agent or a script correlating signals automatically needs them tagged with something it can match on exactly -- that is what makes telemetry something automation can act on, not just something a person can look at.

5. Why this lab runs against fixtures, not a real backend​

This course's lab environment has no metrics backend, no log-search backend and no alerting system running -- check course.config.json's tool list, and none of Prometheus, Grafana, Loki or Datadog are on it. Standing one up is a real, valuable skill, and it is out of scope for a laptop lab meant to run on an 8 GB machine.

So this module does what Module 26 already did for GitHub's API: it defines the exact JSON shape a real backend returns -- Prometheus's own query API envelope for metrics, Alertmanager's own v2 shape for alerts, and a small shape this project defines itself for log search -- and tests every function against recorded fixtures of that shape, replayed with respx, entirely offline. The functions this module writes are the same functions that would call a real backend in production; only the transport underneath them is swapped out for the lab.

Common pitfalls​

  • Reporting "no data found" the same way as "could not check." This is the mistake Section 3 exists to prevent. An EMPTY section answered the question; an UNKNOWN section never got asked. Confusing the two turns a genuinely healthy, quiet service into a false alarm -- or worse, a real outage into "everything's fine, nothing to report."
  • Calling configure_tracing()'s underlying trace.set_tracer_provider() more than once and expecting a fresh exporter. OpenTelemetry installs one tracer provider per process; a second install attempt is silently ignored, with only a warning logged. configure_tracing() in this module checks for that and skips re-installing instead of quietly failing -- see the Deep Dive for this working, and failing, both proven live.
  • Writing a log line outside any traced_operation() block and expecting it to carry a correlation ID. The ContextVar only has a value while a traced_operation() block is open; a log line written before or after one gets correlation_id: null, which breaks the "grep one ID, see the whole story" promise for that line.
  • Assuming one base URL serves metrics, logs and alerts. In real infrastructure these are almost always three separate systems on three separate addresses (a metrics backend, a log-search backend, an alerting system) -- this module's functions each take their own base_url for exactly that reason, the same way platformops.releasecheck never assumed GitHub and a deployment target shared one host.
  • Assuming every observability backend speaks the exact same wire shape. This module models query_metrics() on Prometheus's own query API and list_alerts() on Alertmanager's v2 API, because both are widely used, well-documented shapes -- but Datadog, CloudWatch and Elasticsearch each shape the same kind of answer differently. A real integration against one of those confirms its actual response shape first, the same way this module's own docstrings say plainly which real API each function's shape is modeled on.
