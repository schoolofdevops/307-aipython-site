Deep Dive — Observability Automation

The lab proved observability-inspect produces a full-pass report against healthy fixtures, an honest EMPTY report against a quiet service, and an honest UNKNOWN report when a source is unreachable. This page goes one level deeper on three claims the lesson made but did not fully prove on their own: that the fetch/aggregate split really has zero judgment on one side and zero network calls on the other, what "quiet" and "broken" actually look like side by side from the exact same function, and a real trap in OpenTelemetry's own API that this module's configure_tracing() was written specifically to avoid.

Where this picks up

This page assumes ~/platformops at v2.5.0, with src/platformops/observability.py and the observability-inspect CLI command in place from the lab.

cd ~/platformops
uv run platformops version

Expected output

platformops 2.5.0

1. Fetch and aggregate, proven mechanically​

The lesson claimed the three gather_*_evidence() functions never decide whether what they found is good news, and evaluate_observability_snapshot() never touches the network. "We tried to keep them apart" is not the same claim as "they really are apart" -- the same discipline Module 26's Deep Dive used to prove releasecheck.py's fetch and aggregate halves were really separate. Grep the fetch functions for a status word:

awk '/^def gather_metrics_evidence\(/{p=1} /^@dataclass/{exit} p' src/platformops/observability.py | rg -i '"ok"|"empty"|"firing"|"unknown"'; echo "exit=$?"

Expected output

exit=1

rg exits 1 when it finds zero matches. Across all three fetch functions -- gather_metrics_evidence(), gather_logs_evidence() and gather_alerts_evidence() -- not one of them contains the string "OK", "EMPTY", "FIRING" or "UNKNOWN" anywhere in its body. Each one only ever returns a "fetched" flag plus the raw facts it found.

Now the other half -- evaluate_observability_snapshot(), the function that does all the judging, checked for the two things that would prove it secretly depends on the network:

awk '/^def evaluate_observability_snapshot\(/{p=1} /^def inspect_observability\(/{exit} p' src/platformops/observability.py | rg 'httpx|gather_'; echo "exit=$?"

Expected output

exit=1

Zero matches. evaluate_observability_snapshot()'s entire body -- building sources_ok/sources_failed, running each _evaluate_* helper, assembling one ObservabilitySnapshot -- never mentions httpx and never calls a gather_* function. A stronger check confirms the whole module never even imports the HTTP library at all:

rg '^import httpx|^from httpx' src/platformops/observability.py; echo "exit=$?"

Expected output

exit=1

That third check is the strongest of the three. evaluate_observability_snapshot() is not merely a function that happens not to call the network today -- it could not call the network even if a future edit tried to add a shortcut, because the module doing the judging never holds a reference to httpx in the first place. Adding a network call there would require adding a new import first, a far more visible change in review than adding one more line to a function that already has httpx in scope.

2. A quiet backend and a broken one, from the exact same function​

The lesson stated the rule: an answered-but-empty result is EMPTY; an unreachable one is UNKNOWN. Here it is proven directly -- the exact same function, gather_metrics_evidence(), called twice with the exact same query, against two different fixture scenarios.

cat > /tmp/m30_empty_vs_unknown.py << 'PYEOF'
import json
from pathlib import Path

import httpx
import respx

import platformops.httpclient as httpclient
from platformops.observability import gather_metrics_evidence, evaluate_observability_snapshot

httpclient.time.sleep = lambda _seconds: None

FIXTURES = Path("tests/fixtures/observability")
METRICS_URL = "http://localhost:9090"


def _fixture(name):
    return json.loads((FIXTURES / name).read_text())


# Scenario A: the backend answers, and genuinely has nothing to report.
with respx.mock:
    respx.get(f"{METRICS_URL}/api/v1/query").mock(
        return_value=httpx.Response(200, json=_fixture("metrics_query_empty.json"))
    )
    quiet_evidence = gather_metrics_evidence(METRICS_URL, "up")

# Scenario B: the backend cannot be reached at all -- every retry refused.
with respx.mock:
    respx.get(f"{METRICS_URL}/api/v1/query").mock(
        side_effect=httpx.ConnectError("connection refused")
    )
    broken_evidence = gather_metrics_evidence(METRICS_URL, "up")

print("--- scenario A: quiet backend ---")
print("evidence:", quiet_evidence)
print("section: ", evaluate_observability_snapshot(
    service="payments", correlation_id="req-demo",
    metrics_evidence=quiet_evidence,
    logs_evidence={"fetched": True, "query": "q", "total": 0, "logs": []},
    alerts_evidence={"fetched": True, "total": 0, "active": []},
).metrics)

print()
print("--- scenario B: broken backend ---")
print("evidence:", broken_evidence)
print("section: ", evaluate_observability_snapshot(
    service="payments", correlation_id="req-demo",
    metrics_evidence=broken_evidence,
    logs_evidence={"fetched": True, "query": "q", "total": 0, "logs": []},
    alerts_evidence={"fetched": True, "total": 0, "active": []},
).metrics)
PYEOF
uv run python /tmp/m30_empty_vs_unknown.py

Expected output

http://localhost:9090/api/v1/query: attempt 1/5 failed (connection refused), retrying
http://localhost:9090/api/v1/query: attempt 2/5 failed (connection refused), retrying
http://localhost:9090/api/v1/query: attempt 3/5 failed (connection refused), retrying
http://localhost:9090/api/v1/query: attempt 4/5 failed (connection refused), retrying
--- scenario A: quiet backend ---
evidence: {'fetched': True, 'query': 'up', 'sample_count': 0, 'samples': []}
section:  {'status': 'EMPTY', 'detail': "no data points found for query 'up'"}

--- scenario B: broken backend ---
evidence: {'fetched': False, 'error': 'http://localhost:9090/api/v1/query unreachable after 5 attempt(s): connection refused'}
section:  {'status': 'UNKNOWN', 'detail': 'http://localhost:9090/api/v1/query unreachable after 5 attempt(s): connection refused'}

Scenario A's backend answered with a real 200 and an empty result array -- fetched: True, and the section is EMPTY. Scenario B's backend never answered at all, even after four retries -- fetched: False, and the section is UNKNOWN. Both scenarios end with sample_count-shaped evidence that looks almost identical at a glance (both "no samples"), and yet the report keeps them in two completely different categories -- because they are, in fact, two completely different situations for an operator to act on.

3. The once-per-process trap, and how this module avoids it​

OpenTelemetry's own API has a real trap this module was written specifically to sidestep: a process can install exactly one global TracerProvider. Calling trace.set_tracer_provider() a second time does not raise -- it silently does nothing, after printing one warning.

cat > /tmp/m30_tracerprovider_trap.py << 'PYEOF'
from opentelemetry import trace
from opentelemetry.sdk.trace import TracerProvider
from opentelemetry.sdk.trace.export import SimpleSpanProcessor
from opentelemetry.sdk.trace.export.in_memory_span_exporter import InMemorySpanExporter

# The trap: calling trace.set_tracer_provider() directly, twice.
exp1 = InMemorySpanExporter()
p1 = TracerProvider()
p1.add_span_processor(SimpleSpanProcessor(exp1))
trace.set_tracer_provider(p1)

exp2 = InMemorySpanExporter()
p2 = TracerProvider()
p2.add_span_processor(SimpleSpanProcessor(exp2))
trace.set_tracer_provider(p2)  # second call -- does this actually take effect?

tracer = trace.get_tracer("demo")
with tracer.start_as_current_span("s1"):
    pass

print("exp1 (first provider) recorded:", len(exp1.get_finished_spans()), "span(s)")
print("exp2 (second provider) recorded:", len(exp2.get_finished_spans()), "span(s)")
print("the installed provider is p2:", trace.get_tracer_provider() is p2)
PYEOF
uv run python /tmp/m30_tracerprovider_trap.py

Expected output

Overriding of current TracerProvider is not allowed
exp1 (first provider) recorded: 1 span(s)
exp2 (second provider) recorded: 0 span(s)
the installed provider is p2: False

The warning line comes straight from OpenTelemetry's own SDK, not from this project. The span landed in exp1 -- the first provider installed -- even though p2 was the one asked for last. Any code that assumed the second configure-style call would "reset" tracing for a fresh test or a fresh CLI invocation within the same process would be wrong, and would not even get an exception to tell it so.

configure_tracing() in platformops.telemetry avoids this by checking what is already installed before ever calling trace.set_tracer_provider():

rg -A3 'current = trace.get_tracer_provider\(\)' src/platformops/telemetry.py

Expected output

    current = trace.get_tracer_provider()
    if isinstance(current, TracerProvider):
        logger.debug(
            "tracing already configured for this process -- reusing the existing TracerProvider"
        )

Proven directly -- calling configure_tracing() twice in the same process never hits the trap, and never prints the warning:

cat > /tmp/m30_tracerprovider_fix.py << 'PYEOF'
from platformops.telemetry import configure_tracing

provider_a = configure_tracing("platformops-demo")
provider_b = configure_tracing("platformops-demo")

print("provider_a is provider_b:", provider_a is provider_b)
print("no warning printed above this line")
PYEOF
uv run python /tmp/m30_tracerprovider_fix.py

Expected output

provider_a is provider_b: True
no warning printed above this line

This is exactly why tests/test_telemetry.py and tests/test_observability.py never call configure_tracing() for a test that needs an isolated exporter -- they build their own TracerProvider and pass a tracer from it straight to traced_operation()'s tracer parameter instead, which never touches the global registry at all, and so never runs into this trap either way.

Where you will use this
  • A fetch function proven never to judge, and a judgment function proven never to touch the network. Use it when: you are reviewing a pull request that adds a new evidence source to a report like this one -- check which side of the split the new code landed on before approving it.
  • "No data" and "could not check" are never the same report, even when the evidence looks similar. Use it when: you are debugging an automated observability check that says nothing is wrong -- check whether every source actually answered (sources_failed) before trusting a quiet report.
  • A library's own global-state API can have a "only once per process" trap with no exception to warn you. Use it when: you are wiring any SDK that installs a process-wide singleton (a tracer provider, a default HTTP client, a logging config) -- check what happens on a second call before assuming it behaves like a normal function call, especially inside a test suite that invokes your code more than once in one process.

Teardown​

cd ~/platformops
rm -f /tmp/m30_empty_vs_unknown.py /tmp/m30_tracerprovider_trap.py /tmp/m30_tracerprovider_fix.py

Nothing else from this page persists -- every scenario here ran against respx-mocked fixtures or an in-memory span exporter already committed to the project from the lab. There is no real observability backend, container, or cluster this page touched.
