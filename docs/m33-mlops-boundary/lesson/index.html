Python at the MLOps Boundary

Your team ships support-assistant, a chatbot that answers customer questions. One morning, support tickets shoot up. The assistant keeps giving wrong answers. Someone on the on-call channel asks three plain questions: which model version is actually live right now, did the training run behind it finish cleanly, and is the serving endpoint even healthy? You do not need to be a data scientist to answer any of these. You need to know where this information lives, and how to pull it into one report — the same way platformops release-check (Module 26) already pulls together a release verdict without re-running anyone's tests.

This module teaches you the vocabulary a machine-learning (ML) team uses for this, and builds a small, read-only inspector for it: platformops ai-inspect. It never trains, tunes, or judges a model's accuracy. It answers operational questions — is the right version deployed, and is it up — the same way platformops workload-inspect (Module 28) answers "is this Kubernetes app healthy" without touching a single line of the app's own code.

Why this matters at work

MLOps (Machine Learning Operations) is the discipline of running machine-learning systems in production, the way DevOps runs everything else. As more products ship an AI feature, on-call engineers get paged for AI incidents whether or not they trained the model. You are not expected to retrain it. You are expected to answer "what changed, and is it up" in minutes — exactly the skill this module builds.

1. The vocabulary: from one training attempt to a live version​

Picture a bakery that keeps trying new bread recipes. Every attempt at baking a batch — a specific set of ingredients, a specific oven temperature, a specific result — gets written down in a logbook. In machine learning, that logbook is called tracking, and each attempt is called a run. A run has a status: it finished, it failed, or it is still baking. Related runs (all the attempts at one recipe) are grouped into an experiment.

When a run produces bread worth selling, the bakery does not put the whole logbook on the shelf — it puts the finished loaf on the shelf, with a label. In machine learning, that finished loaf is a model: the trained file a program can actually use to make predictions. The shelf itself is called a model registry — a catalog that tracks every model, and every numbered version of it, along with which run produced it. support-assistant-intent-classifier:4 names one exact version, the same way a medicine bottle's batch number names one exact batch — not "the drug", but this specific manufactured lot, made on this date, from this exact process. MLflow is one popular, open-source tool that implements this whole vocabulary as a real product — it tracks runs, stores models, and runs a registry. This module talks about it because it is the tool you are most likely to meet at work, not because this lab installs one.

2. Why this lab never starts a real MLflow server​

This course lists its lab tools on the Environment page, and it is a fixed list: git, Docker, uv, kind, kubectl, claude, Floci, syft, grype. MLflow is not one of them, and this course will not ask you to install and run a full tracking server just to read three fields back from it.

Instead, this module does what Module 26 (releasecheck.py, reading GitHub's API) and Module 30 (observability.py, reading a metrics/logs/alerts backend) already did. It writes a small, typed client against MLflow's own REST API, and tests it against saved example responses instead of a live server. The client code is the same code that would work against a real MLflow server later — only the tests stay offline. This keeps the lab fast and repeatable on a laptop, and it proves your client code is correct, not that one specific server happens to be reachable right now.

3. A new kind of service definition: ai-service​

Module 5 gave every normal service a ServiceDefinition: a name, a repository, a namespace, an owner. A model-serving workload carries a few fields a web service never needs: which registry it comes from, which exact model version it must be running, which serving runtime runs it (the program that loads the model and answers requests — for example vllm or torchserve), and its inference mode.

Inference mode is either:

  • Online — a live endpoint answers one request at a time, the moment it arrives. Think of a corner shop: you walk in right now, and someone serves you immediately.
  • Batch — a job reads a large pile of work, processes all of it on a schedule, and writes the results somewhere. Think of a wholesaler who fills one large overnight order and delivers it in the morning — there is no counter to walk up to at 2pm and ask if they are open.

This module adds AIServiceDefinition as its own, separate model next to ServiceDefinition — not new fields bolted onto the old one. A plain web service will never have a model_version; a model-serving workload always does. Keeping them separate means neither model carries fields that sit empty for its own kind of service.

4. Three honest questions, not one guess​

platformops ai-inspect asks exactly three questions about a deployed AI workload, and reports each one honestly instead of collapsing them into a single "good" or "bad":

  1. Is the exact model version ready? Read the registry entry for registered_model_name:model_version. READY is good news; FAILED_REGISTRATION is bad news; anything else (a version still mid-registration) is reported as unknown, not guessed at.
  2. Did the run behind it finish cleanly? The registry entry names the run that trained this version. FINISHED is good news; FAILED or KILLED is bad news.
  3. Is the serving endpoint healthy — when it has one? An online service gets a real health check, reusing the same check_health() this course built in Module 9. A batch service has no standing endpoint, so this question is marked not applicable — never reported as "down", because it was never meant to answer there in the first place.

This is the same fetch-then-judge shape you have already used twice: releasecheck.py (Module 26) fetches evidence from GitHub and judges it separately; observability.py (Module 30) fetches metrics, logs and alerts and judges them separately. Here, the fetch functions only reach MLflow's API or a health-check URL, and hand back plain facts. A separate, pure function turns those facts into a verdict. 5. What this module deliberately does not do​

ai-inspect never registers a model version, never moves a version between stages (for example, promoting a version from "staging" to "production"), and never restarts a serving process. It reads three things and reports them. Deciding whether a model's predictions are good enough to ship — accuracy, bias, drift — is data-science work this toolkit stays out of on purpose, the same way cloudaudit.py (Module 24) only ever detects a policy violation and never fixes one itself.

Common pitfalls​

  • Treating "model version is READY" as "the model is good." READY only means the registry finished storing this version — it says nothing about whether its predictions are accurate.
  • Health-checking a batch workload's non-existent endpoint. A batch job answering "connection refused" is not evidence of an outage — it may simply have no endpoint to check. That is exactly why inference_mode decides whether this module even attempts the check.
  • Expecting "the model version does not exist" to look different from "could not reach MLflow." It does not, and that is on purpose. Both come back as an HTTP error this module cannot tell apart without guessing, so both honestly report UNKNOWN — never a confident-looking FAIL built on a guess. The one model failure this module DOES report with confidence is FAILED_REGISTRATION: a version that exists, but whose own registration process failed. Do not read UNKNOWN as "the version is missing" — read it as "this module could not tell."
  • Assuming this module talks to a live MLflow server. It talks to a small, typed client tested against saved example responses — see Section 2 for why, and the Deep Dive for the mechanical proof that this module never sends a write call to MLflow.
