Deep Dive — Python at the MLOps Boundary

The lab proved ai-inspect reports HEALTHY for a good deployment, unhealthy for a failed training run, and NOT_APPLICABLE for a batch workload's endpoint. This page goes one level deeper on three claims the lesson made but did not fully prove on their own: that the fetch/aggregate split really has zero judgment on one side and zero MLflow write calls anywhere in the module, that the run lookup is genuinely chained from the registry's own answer rather than guessed, and what "could not check" and "checked, and it is down" actually look like side by side from the exact same function.

Where this picks up

This page assumes ~/platformops at v2.8.0, with src/platformops/aiservice.py, src/platformops/ai_inspect.py, and the three MLflow-shaped functions in httpclient.py in place from the lab.

cd ~/platformops
uv run platformops version

Expected output

platformops 2.8.0

1 — Read-only, proven mechanically​

The lesson claimed ai-inspect never registers a model version, never transitions a stage, and never restarts a serving process. "We only wrote GET functions" is not the same claim as "there is no write call anywhere in this module" -- the same discipline Module 24's Deep Dive used to prove cloudaudit.py never calls a write-mode AWS API. Start with the MLflow section itself: every one of the three functions issues exactly one request, and every one of them is a GET.

awk '/# MLflow.s own REST API shape/,0' src/platformops/httpclient.py | rg -c '"GET"'

Expected output

3

Three matches -- one per function. Now check for the four verbs that would mutate something on a real MLflow server:

awk '/# MLflow.s own REST API shape/,0' src/platformops/httpclient.py | rg '"POST"|"PUT"|"DELETE"|"PATCH"'; echo "exit=$?"

Expected output

exit=1

rg exits 1 when it finds zero matches. Not one write verb appears anywhere in the section -- this is not "we didn't happen to write one today", it is "the section cannot issue one without a future edit adding a new function".

The same fetch/aggregate split every other read-only inspector in this project uses (cloudaudit.py, M24; releasecheck.py, M26; observability.py, M30) holds here too. Grep the three gather_*_evidence() functions for a verdict word:

awk '/^def gather_model_evidence\(/{p=1} /^@dataclass/{exit} p' src/platformops/ai_inspect.py | rg -i '"pass"|"fail"|"unknown"|"not_applicable"'; echo "exit=$?"

Expected output

exit=1

Zero matches. Now the other half -- evaluate_ai_workload(), the function that does all the judging, checked for the two things that would prove it secretly depends on the network:

awk '/^def evaluate_ai_workload\(/{p=1} /^def inspect_ai_workload\(/{exit} p' src/platformops/ai_inspect.py | rg 'gather_|check_health|httpx\.(get|post|put|delete)'; echo "exit=$?"

Expected output

exit=1

Zero matches again. evaluate_ai_workload()'s entire body -- building sources_ok/sources_failed, running each _evaluate_* helper, assembling one AIWorkloadReport -- never mentions gather_, check_health, or an httpx request verb.

This matters the moment someone asks, during an incident review, "could this inspector have accidentally changed something in MLflow while it was checking status?" The answer is not "we trust the code" -- it is "here is the grep that proves it," the same evidence a security review or an audit would ask for before granting this command broader read access in a real environment.

2 — The run lookup is chained, never guessed​

A model version's registry entry names the run that trained it (run_id). inspect_ai_workload() reads that id and passes it straight into gather_run_evidence() -- but what happens when the registry lookup itself fails? A naive implementation might fall back to a default, a cached value, or simply skip the check silently. This module does neither: when the model version cannot be fetched, there is no run_id to chain from, and the run section reports its own honest "fetched": False -- it never invents a run to ask about.

Proven live, with a spy wrapped around gather_run_evidence() to count real calls -- once when the registry answers, zero times when it does not:

cat > /tmp/m33_chaining_proof.py << 'PYEOF'
import json
import logging
from pathlib import Path
from unittest.mock import patch

import httpx
import respx

import platformops.ai_inspect as ai_inspect_module
import platformops.httpclient as httpclient
from platformops.ai_inspect import inspect_ai_workload
from platformops.aiservice import GOOD_AI_EXAMPLE, validate_ai_service

httpclient.time.sleep = lambda _s: None
logging.getLogger("platformops.httpclient").setLevel(logging.ERROR)

MLFLOW_URL = "http://localhost:5000"
ENDPOINT_URL = "https://support-assistant.internal.example.com/v1/predict"
service = validate_ai_service(GOOD_AI_EXAMPLE)
real_gather_run_evidence = ai_inspect_module.gather_run_evidence

# Scenario A: the model version lookup itself fails (MLflow unreachable).
# gather_run_evidence() must never be called -- there is no run id to chain from.
with patch.object(
    ai_inspect_module, "gather_run_evidence", wraps=real_gather_run_evidence
) as spy_run, respx.mock:
    respx.get(f"{MLFLOW_URL}/api/2.0/mlflow/model-versions/get").mock(
        side_effect=httpx.ConnectError("connection refused")
    )
    respx.get(ENDPOINT_URL).mock(return_value=httpx.Response(200))
    report = inspect_ai_workload(service, mlflow_base_url=MLFLOW_URL)
    print("Scenario A -- model lookup failed:")
    print("  gather_run_evidence call count:", spy_run.call_count)
    print("  run section status:", report.run["status"])
    print("  run section detail:", report.run["detail"])

print()

# Scenario B: the model version lookup succeeds -- gather_run_evidence() must be
# called exactly once, with the exact run_id the registry entry named.
with patch.object(
    ai_inspect_module, "gather_run_evidence", wraps=real_gather_run_evidence
) as spy_run, respx.mock:
    model_fixture = json.loads(
        Path("tests/fixtures/mlflow/model_version_ready.json").read_text()
    )
    respx.get(f"{MLFLOW_URL}/api/2.0/mlflow/model-versions/get").mock(
        return_value=httpx.Response(200, json=model_fixture)
    )
    run_fixture = json.loads(Path("tests/fixtures/mlflow/run_finished.json").read_text())
    respx.get(f"{MLFLOW_URL}/api/2.0/mlflow/runs/get").mock(
        return_value=httpx.Response(200, json=run_fixture)
    )
    respx.get(ENDPOINT_URL).mock(return_value=httpx.Response(200))
    report = inspect_ai_workload(service, mlflow_base_url=MLFLOW_URL)
    print("Scenario B -- model lookup succeeded:")
    print("  gather_run_evidence call count:", spy_run.call_count)
    called_run_id = spy_run.call_args.args[1] if spy_run.call_args else None
    print("  run_id passed to gather_run_evidence:", called_run_id)
    print("  matches registry's run_id:", called_run_id == "a1b2c3d4e5f647a8b9c0d1e2f3a4b5c6")
PYEOF
uv run python /tmp/m33_chaining_proof.py

Expected output

Scenario A -- model lookup failed:
  gather_run_evidence call count: 0
  run section status: UNKNOWN
  run section detail: no run id available -- model version evidence unavailable

Scenario B -- model lookup succeeded:
  gather_run_evidence call count: 1
  run_id passed to gather_run_evidence: a1b2c3d4e5f647a8b9c0d1e2f3a4b5c6
  matches registry's run_id: True

Scenario A: gather_run_evidence is called zero times, and the run section's detail says plainly that no run id was available -- not a fabricated status for a run this code never actually looked up. Scenario B: gather_run_evidence is called exactly once, with the exact run_id string the registry fixture returned. This is what protects a report from ever showing a confident-looking FINISHED/FAILED verdict for the wrong run, or for no run at all, if the registry lookup that was supposed to identify it never actually succeeded.

3 — "Could not check" and "checked, and it is down" from the exact same function​

gather_endpoint_evidence() calls the same check_health() this course built in Module 9, and check_health() never raises -- a timeout, a refused connection, and a 503 all come back as a normal HealthResult, never an exception. That single fact is exactly what makes it possible for _evaluate_endpoint() to tell two very different real-world situations apart from the same function call, instead of collapsing both into one generic "unhealthy":

cat > /tmp/m33_endpoint_contrast.py << 'PYEOF'
import logging

import httpx

from platformops.ai_inspect import _evaluate_endpoint, gather_endpoint_evidence

logging.getLogger("platformops.httpclient").setLevel(logging.ERROR)

ENDPOINT_URL = "https://support-assistant.internal.example.com/v1/predict"

# Same function, two real HTTP outcomes.
unreachable = gather_endpoint_evidence(
    ENDPOINT_URL,
    "online",
    transport=httpx.MockTransport(
        lambda request: (_ for _ in ()).throw(httpx.ConnectError("connection refused"))
    ),
)
overloaded = gather_endpoint_evidence(
    ENDPOINT_URL,
    "online",
    transport=httpx.MockTransport(lambda request: httpx.Response(503)),
)

print("No response at all (DNS/network failure) judged as:")
print(" ", _evaluate_endpoint(unreachable))
print()
print("A real 503 response (service answered, overloaded) judged as:")
print(" ", _evaluate_endpoint(overloaded))
PYEOF
uv run python /tmp/m33_endpoint_contrast.py

Expected output

No response at all (DNS/network failure) judged as:
  {'status': 'UNKNOWN', 'detail': 'endpoint unreachable -- connection failed: connection refused'}

A real 503 response (service answered, overloaded) judged as:
  {'status': 'FAIL', 'detail': 'endpoint answered 503 -- not healthy'}

A connection error -- no response came back at all -- is judged UNKNOWN: this module genuinely could not check. A 503 is judged FAIL: the endpoint answered, and the answer was bad news. These are two different incidents that need two different responses. A DNS or networking failure between your inspection tooling and the model's serving cluster is an infrastructure problem, possibly unrelated to the model at all. A 503 from a reachable server is a real capacity or backpressure signal from the serving runtime itself -- the process is up, and it is telling you it cannot keep up right now. Routing both to the same generic "unhealthy" bucket would send whoever is paged down the wrong troubleshooting path half the time.

Where you will use this
  • A read-only inspector proven read-only by grep, not by trust. Use it when: you are reviewing a pull request that adds a new adapter function against an external system with both read and write endpoints -- confirm the section only issues the HTTP verb it claims to, the same way this page confirmed httpclient.py's MLflow section never issues a POST, PUT, DELETE or PATCH.
  • Chained evidence that never falls back to a guess when an earlier lookup fails. Use it when: you are debugging a report that shows a confusing or seemingly-random result for a dependent lookup -- check whether the code that produced it actually had the identifier it needed, or whether an earlier failure silently left it working from a stale or default value instead.
  • "Could not check" and "checked, and it is down" as two different, actionable incidents. Use it when: an on-call alert fires for a service and the first report back is ambiguous -- look for which of the two your tooling actually means before you start troubleshooting the wrong layer (the network path versus the application itself).

Teardown​

cd ~/platformops
rm -f /tmp/m33_chaining_proof.py /tmp/m33_endpoint_contrast.py

Nothing else from this page persists -- every scenario here ran against respx-mocked or httpx.MockTransport-mocked calls already committed to the project from the lab. There is no real MLflow server, no container, and no cluster this page started.
