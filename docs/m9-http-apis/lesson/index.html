HTTP APIs and Integration Automation

▶ M9 — HTTP APIs and Integration AutomationOpen fullscreen ↗

So far, platformops has read data that sits still: a YAML file on disk (M5-M6), a fixed inventory in memory (M3-M4). A lot of the data you need during a real incident does not sit still — it lives behind an HTTP API. Is the payments service actually reachable right now? What does the source-control host say about a repository's last build? You could open a browser and click through five dashboards to answer both questions. Or platformops could ask the APIs directly and print the answer in one command. This module adds that capability: an HTTP client you can trust, and two new commands — http-check and repo-info — built on it.

1. Timeouts: the setting that quietly isn't set​

Picture calling a colleague's desk phone. If nobody picks up, you do not stand there holding the receiver for an hour — you hang up after a while and try something else. A well-behaved HTTP client needs the same habit: give up waiting after a fixed time, instead of hanging forever on a server that will never answer.

This is where a popular but older Python HTTP library, requests, has a trap: it has no default timeout at all unless you set one on every single call. Forget once, and a script that should fail fast in five seconds can hang for the length of your CI job's timeout instead — the worst possible way to discover a downstream service is unreachable. This course uses httpx instead, in part because it makes you set an explicit timeout policy up front, and its own default (five seconds) is at least a real number, not "wait forever."

import httpx

TIMEOUT = httpx.Timeout(connect=5.0, read=10.0, write=5.0, pool=5.0)

with httpx.Client(timeout=TIMEOUT) as client:
    response = client.get("https://api.github.com")

Splitting the timeout into connect, read, write and pool phases matters because they fail for different reasons — a slow DNS lookup is a different problem from a server that connects instantly but drips its response one byte at a time.

2. Two different ways a call can fail​

A phone call can fail in two different ways: the line rings and rings with nobody there, or someone picks up and says "no, we don't do that here." Both are failures, but you would not treat them the same — one means "try a different number," the other means "you called the right place, but the answer is no."

HTTP calls fail the same two ways, and httpx gives you two different exception families for them:

  • The request never got an answer — a DNS failure, a refused connection, or a timeout. httpx raises httpx.ConnectError or httpx.TimeoutException for this.
  • The request got an answer, and the answer is a problem — a 404 (not found), a 401 (unauthorized), a 500 (the server broke). The request succeeded as far as the network is concerned; the status code is what tells you something is wrong.
try:
    response = client.get(url)
    response.raise_for_status()  # turns a 4xx/5xx into an exception
except httpx.ConnectError:
    ...  # never reached the server at all
except httpx.HTTPStatusError as exc:
    ...  # exc.response.status_code tells you what went wrong

Collapsing both into one generic except Exception throws away exactly the information you need during an incident: "is the network broken, or is the service up and actively reporting a problem?" check_health() in this module's lab keeps that distinction — a health check that cannot even reach a host reports a different reason than one that reaches a host returning a 503.

3. Trust the shape, not just the bytes​

A JSON response is text, not proof. response.json() turns valid JSON text into a Python dict or list, but nothing stops a server from changing a field's name, dropping a field, or sending a response that is not valid JSON at all. M5 taught you to never trust a raw dict from a YAML file past the point where it entered your program — ServiceDefinition.model_validate(...) turns a dict into something typed and checked. An HTTP response deserves exactly the same discipline: this module validates a repository response against a small Pydantic model before your code touches any of its fields, so a surprising API response fails loudly, right where it entered the program — not three functions later as a confusing KeyError.

4. Pagination: when one page is not the whole answer​

A library with ten thousand books does not hand you every card in the catalog in one stack — it hands you a drawer, and a note on the back of the last card says "see the next drawer." GitHub's list endpoints (repositories, workflow runs, issues) work the same way: one response is capped at a page's worth of results, and a Link header in the response names the URL for the next page — if there is one.

A client that reads only the first page silently under-reports — ninety recent workflow runs looking like the only thirty that exist. Following Link until the server stops sending a next relation is how you get the true count, capped by your own page limit so a surprising history does not page forever.

5. Retrying: knowing when trying again is safe​

Pressing an elevator button five times in a row does not make the elevator arrive faster — but if the elevator briefly stalls and then recovers, waiting a moment and pressing again is exactly the right move. The same judgment applies to a failed HTTP request: a 429 (rate limited) or a 5xx (server trouble) is often temporary, and retrying a moment later, with a short wait that grows each time, is the right response. A 404 or 401 will not change if you ask again in half a second — retrying those just wastes time and makes the failure slower to report. This lab's client retries only the transient cases and gives up immediately on the permanent ones; the Deep Dive covers the backoff math and the specific rule for which HTTP methods are even safe to retry at all.

6. Credentials never appear in a log line​

Think of a hotel front desk: the receptionist confirms your room number out loud to the whole lobby, but never reads your keycard's access code aloud — the number identifies you, the code is what actually lets you in, and only one of those is safe to say where anyone can hear it. A request header carrying Authorization: Bearer <token> works the same way — the request being made is fine to log, the token's value is not. This lab's calls are against GitHub's public, unauthenticated endpoints, so no token is required to make them work — but the pattern still matters, because the moment you point this client at a private repository or an internal API, a token appears, and every log line in this module is written so that value never leaks into one.

7. One client, wired into the CLI you already have​

None of this needs a new interface. http-check and repo-info are two more @app.command() functions next to validate and inspect from M8, following the exact same shape: an argument for what to check, --json for a script, and the same 0/1/2 exit-code contract — 0 for a clean result, 1 for a genuine problem (an unhealthy endpoint, a 404), 2 for a usage error (a URL with no scheme, a repo slug with no slash) you catch before making a single network call.

Common pitfalls
  • Leaving the timeout at its library default and assuming it means "reasonable." Set it explicitly, in code you can read later, instead of trusting a default you have not checked.
  • Treating every failure the same way in one broad except Exception. A connection failure and a 404 need different handling, and often a different message to whoever reads your logs.
  • Calling response.json() and using the result immediately, with no shape check. A field that changed name or vanished should fail loudly right there, not surface as a KeyError two functions later.
  • Reading only the first page of a paginated endpoint. GitHub, and most list APIs, cap a single response — check the Link header before you trust a count.
  • Retrying a 404 or a 401 as if it might succeed on the next try. Only retry a failure that is actually likely to be transient — a permanent client error will not fix itself.
  • Logging a header dict that includes Authorization. Build headers in one place, and make sure that one place is the only place a token's value is ever touched.
