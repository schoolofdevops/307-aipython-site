Deep Dive — Packaging Python Automation with Containers

The lab proved the image builds, runs non-root, passes its healthcheck, and runs as a Kubernetes Job that reads a real Secret. This page goes one level deeper on three claims the lesson made but the lab did not have to prove directly: exactly what makes up the image's size layer by layer, whether a resources.limits value in a YAML file is actually enforced by the kernel or just recorded as a number, and what a kind Job's Pod really is underneath — a Docker container, or something else.

Where this picks up

This page assumes ~/platformops at v2.2.0, with Dockerfile, .dockerignore and k8s/ in place from the lab.

cd ~/platformops
uv run platformops version

Expected output

platformops 2.2.0

1. What is actually inside 277MB — a real layer-by-layer breakdown​

docker images reported this image at 277MB. That number is not one block — it is the sum of every layer in the image, including the layers python:3.12-slim itself already had before this project's Dockerfile added anything. docker history shows each layer with its own size and the command that created it:

docker history platformops:2.2.0 --no-trunc --format '{{.Size}}\t{{.CreatedBy}}' | head -8

Expected output (trimmed to the size-relevant lines — command text shortened)

0B      USER platformops
4.1kB   WORKDIR /app
0B      ENV PATH=/app/.venv/bin:...
53.1MB  COPY --chown=platformops:platformops /app/.venv /app/.venv # buildkit
49.2kB  RUN groupadd --gid 1000 platformops && useradd ...
16.4kB  RUN ... (python3 symlink setup, part of the base image)
44.6MB  RUN apt-get install ... build Python from source ... (part of python:3.12-slim itself)
4.99MB  RUN apt-get install ca-certificates netbase tzdata ... (part of python:3.12-slim itself)

Two layers here are this project's own: the useradd layer (49.2kB — the cost of one dedicated user) and the .venv copy (53.1MB — platformops itself plus its five pinned dependencies and every one of their own transitive dependencies). Every other layer above — the compiled Python interpreter, ca-certificates, tzdata — is inherited unchanged from python:3.12-slim; this Dockerfile never asked for any of it directly. The multi-stage build's actual saving is not visible in this list at all: it is everything from the builder stage that is not here — no uv, no C compiler, no apt package-manager cache, no tests/ folder. Those layers exist in the builder stage's own history, and never cross into the image you just inspected.

2. A resources.limits value is enforced by the kernel, not just recorded​

The lesson's apartment-building analogy claimed a resource limit is a "hard ceiling the kernel enforces," not merely a number Kubernetes remembers. This session proved that live, from inside a running pod with the lab's exact resources.limits (cpu: 200m, memory: 128Mi):

kubectl run platformops-cgroup-debug --image=platformops:2.2.0 --restart=Never \
  --overrides='{"spec":{"containers":[{"name":"platformops","image":"platformops:2.2.0","command":["sleep","120"],"resources":{"requests":{"cpu":"50m","memory":"64Mi"},"limits":{"cpu":"200m","memory":"128Mi"}}}]}}'
kubectl wait --for=condition=Ready pod/platformops-cgroup-debug --timeout=60s
kubectl exec platformops-cgroup-debug -- sh -c 'cat /sys/fs/cgroup/memory.max; echo ---; cat /sys/fs/cgroup/cpu.max'
kubectl delete pod platformops-cgroup-debug

Expected output

134217728
---
20000 100000

Both numbers are the kernel's own cgroup v2 accounting, read directly from inside the container — not Kubernetes reporting back its own YAML. 134217728 bytes is exactly 128 * 1024 * 1024 — 128Mi, byte for byte. 20000 100000 is cgroup v2's cpu.max format, <quota> <period> microseconds: 20,000 microseconds of CPU time allowed per 100,000-microsecond period, which is exactly 200m (0.2 of one CPU core). Kubernetes did not just remember these numbers — it wrote them into the container's cgroup, and the Linux kernel is the one that will actually kill the process if memory usage crosses 134217728 bytes.

3. A kind Job's Pod is a containerd container, not a Docker container​

kind runs each cluster node as a Docker container on your host — but everything inside that node is managed by its own containerd, completely separate from your host's Docker daemon. This session proved the split live, right after the lab's Job completed:

docker ps --format '{{.Names}}\t{{.Image}}'

Expected output

platformops-m27-control-plane   kindest/node:v1.32.2

Your host's Docker only sees the node itself — one container running the entire Kubernetes control plane and everything scheduled onto it. The platformops container the Job actually ran is invisible to docker ps because it was never created by your host's Docker daemon at all. Looking from inside the node instead:

docker exec platformops-m27-control-plane crictl ps -a | grep platformops

Expected output

32fb6fe4e37b1   54d99b390e119   52 seconds ago   Exited   platformops   0   675247664b3fb   platformops-validate-tf2zn

crictl — the CRI (Container Runtime Interface) debugging tool — talks to the node's own containerd, and that is where the Job's actual container lives, managed entirely independently of your host's Docker. This is exactly why Module 28's Kubernetes automation talks to the cluster through kubeconfig and the Kubernetes API, never through a Docker socket: from the API's point of view, which container runtime a node happens to use underneath — containerd, CRI-O, or (as here) containerd wrapped inside a kind node that is itself a Docker container — is exactly the detail Kubernetes exists to abstract away.

4. Two SBOM formats, two different pictures of the same image​

syft can emit the same image's contents in more than one standard format. This session generated both from the identical image and compared them. As in the lab's Phase 3, syft needs DOCKER_HOST pointed at your actual Docker socket if you are not on Docker Desktop's default setup (export DOCKER_HOST=unix:///Users/gshah/.rd/docker.sock on this machine — run docker context inspect -f '{{.Endpoints.docker.Host}}' to find yours):

syft platformops:2.2.0 -o spdx-json 2>/dev/null | python3 -c "import json,sys; print('SPDX packages:', len(json.load(sys.stdin)['packages']))"
syft platformops:2.2.0 -o cyclonedx-json 2>/dev/null | python3 -c "import json,sys; print('CycloneDX components:', len(json.load(sys.stdin)['components']))"

Expected output

SPDX packages: 123
CycloneDX components: 2839

Same image, wildly different counts — not because one format is wrong, but because SPDX and CycloneDX answer a different question by convention. SPDX here reports package-level entries (one row per installed deb or python package) — the shape procurement and legal teams typically ask for: "what packages, at what versions, are in this artifact." CycloneDX's default output goes more granular, down toward individual files and embedded binary components — the shape most vulnerability-scanning pipelines (Dependency-Track and similar tools) prefer, because a vulnerability can live in a specific file, not just "the package as a whole." Neither number is "the real one" — pick the format your downstream tool actually consumes, and do not be alarmed when two SBOMs of the same image disagree on how many things it contains.

Common pitfalls​

  • Assuming docker images' SIZE column and docker inspect --format='{{.Size}}' always agree. They can differ by container-engine implementation detail (this session saw both, and they did not match exactly) — treat docker images as the number a learner will actually see.
  • Believing a resource limit is "just Kubernetes bookkeeping." It is a real cgroup value the kernel reads and enforces — Section 2 above reads it directly from /sys/fs/cgroup, not from kubectl describe.
  • Trying to docker exec into a Job's Pod after it completes. A completed container has no running process left to exec into — this deep dive used a separate, short-lived debug Pod for that reason, not the lab's own Job.
  • Expecting an SBOM's package count to be a fixed, format-independent fact about an image. It depends entirely on which format (and which of syft's catalogers) produced it.
Where you will use this
  • Layer-by-layer docker history review. Use it when: a teammate asks "why is our image so big" and the honest answer requires seeing exactly which layer is responsible, not guessing.
  • Reading cgroup values directly from inside a container. Use it when: a pod is being OOM-killed or throttled and you need to confirm the limit Kubernetes actually applied, not just the limit written in the YAML you think is deployed.
  • crictl/ctr on a node, instead of docker ps on the host. Use it when: debugging why a workload isn't visible to Docker tooling on a machine that runs Kubernetes — common on any managed node pool, not just kind.
  • Choosing an SBOM format deliberately, not by default. Use it when: wiring an SBOM into a compliance process (SPDX) versus a vulnerability-management pipeline (CycloneDX) — picking whichever your downstream tool actually parses.

Teardown​

This page's only addition beyond the lab was one debug Pod, already deleted at the end of Section 2 (kubectl delete pod platformops-cgroup-debug). If you stopped partway through, confirm it is gone:

kubectl get pod platformops-cgroup-debug 2>&1

Expected output

Error from server (NotFound): pods "platformops-cgroup-debug" not found
