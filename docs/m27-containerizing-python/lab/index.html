Lab — Packaging Python Automation with Containers

This lab has six phases. Phase 0 verifies your tools, including two new ones this module adds: syft and grype. Phase 1 writes the Dockerfile and .dockerignore, then bumps the version to v2.2.0 — the Containerized PlatformOps release — before anything gets built, so the image itself carries the right version. Phase 2 builds that image and runs it as a plain container. Phase 3 generates a real SBOM and runs a real vulnerability scan. Phase 4 runs the exact same image as a Kubernetes Job on a kind cluster, using a ConfigMap and a Secret. Phase 5 runs this project's full quality gate and closes out the release.

Before you start

You need ~/platformops at v2.1.0, with src/platformops/releasecheck.py in place from Module 26, and the labs repo cloned at ~/307-aipython-labs.

cd ~/platformops
uv run platformops version

Expected output

platformops 2.1.0

If this already shows 2.2.0, you have already completed this lab — every step below is still safe to re-run.

Phase 0 — Verify your tools​

docker, kind and kubectl are already part of this course's lab environment. syft and grype are new for this module — install them if which syft grype comes back empty:

brew install syft grype   # macOS
# Linux: curl -sSfL https://raw.githubusercontent.com/anchore/syft/main/install.sh | sh -s -- -b /usr/local/bin
#        curl -sSfL https://raw.githubusercontent.com/anchore/grype/main/install.sh | sh -s -- -b /usr/local/bin
docker --version
kind --version
kubectl version --client
syft version
grype version

Expected output

Docker version 29.5.3-rd, build 5d9ffe3
kind version 0.27.0
Client Version: v1.35.0
Kustomize Version: v5.7.1
Application:   syft
Version:       1.49.0
...
Application:         grype
Version:             0.116.0

docker scout is not used in this lab

Some Docker CLI builds ship a bundled docker scout command that does SBOM and scanning too. This course's reference environment does not have that subcommand installed (docker scout returns unknown command) — this lab uses syft/grype, which are separately installed, real tools that work the same way regardless of which Docker CLI build you have.

Phase 1 — The Dockerfile and .dockerignore​

Step 1 — Write .dockerignore​

cd ~/platformops
cat > .dockerignore << 'EOF'
# Never ship the source tree's own virtual environment or caches into a
# build context -- they are large, platform-specific, and the image builds
# its own venv from uv.lock instead.
.venv
.mypy_cache
.pytest_cache
.ruff_cache
__pycache__/
*.py[oc]

# Version control and editor metadata -- never useful inside the image, and
# .git in particular can be large and carries full history, not just the
# working tree.
.git
.gitignore
.github

# Course/tooling metadata that has nothing to do with what the container
# runs. README.md stays IN the context -- pyproject.toml's `readme` field
# points at it, and the builder's `uv sync --no-editable` step fails without
# it.
.claude
skills
AGENTS.md
CLAUDE.md
CHANGELOG.md

# Local scratch files this project's own .gitignore already excludes from
# git -- excluding them from the build context too means a stray resolved
# config or audit log on a contributor's machine never leaks into an image
# layer.
*.resolved.yaml
remediation-audit.jsonl

# Tests are not part of what ships -- they run against the source tree in
# CI, never inside the built image.
tests

# Kubernetes manifests are applied with kubectl from outside the image, not
# baked in.
k8s
EOF

Step 2 — Write the Dockerfile​

cat > Dockerfile << 'EOF'
# syntax=docker/dockerfile:1

# ---------------------------------------------------------------------------
# Stage 1: builder -- has uv, pyproject.toml, uv.lock and source. Resolves
# and installs the exact locked dependency set into a throwaway virtualenv.
# Nothing from this stage except that one .venv folder crosses into the
# final image.
# ---------------------------------------------------------------------------
FROM python:3.12-slim AS builder

ENV PYTHONDONTWRITEBYTECODE=1 \
    UV_LINK_MODE=copy

WORKDIR /app

RUN pip install --no-cache-dir uv==0.6.12

# Copy only the dependency manifests first -- Docker caches this layer, so a
# source-only change later does not force a full dependency re-install.
COPY pyproject.toml uv.lock README.md ./
COPY src/ ./src/

# --frozen: fail instead of silently re-resolving if uv.lock is out of date.
# --no-dev: skip pytest/mypy/ruff -- the running container never needs them.
# --no-editable: install platformops as a normal package, so the final
# image needs the .venv only, not a copy of /app/src alongside it.
RUN uv sync --frozen --no-dev --no-editable

# ---------------------------------------------------------------------------
# Stage 2: runtime -- a fresh, minimal base with nothing but the Python
# interpreter and the .venv copied in from the builder. No uv, no build
# tools, no uv.lock, no test suite -- none of that ships to production.
# ---------------------------------------------------------------------------
FROM python:3.12-slim AS runtime

# A dedicated, unprivileged user. If an attacker ever breaks out of the
# platformops process itself, they land as this user -- not root -- with no
# home directory and no shell worth using.
RUN groupadd --gid 1000 platformops \
    && useradd --uid 1000 --gid platformops --no-create-home --shell /usr/sbin/nologin platformops

COPY --from=builder --chown=platformops:platformops /app/.venv /app/.venv

ENV PATH="/app/.venv/bin:$PATH" \
    PYTHONDONTWRITEBYTECODE=1 \
    PYTHONUNBUFFERED=1

WORKDIR /app
USER platformops

# No network call and no cluster credentials required -- local-status only
# inspects the git and Docker state already visible inside the container.
# A container that cannot even run this is not healthy no matter what else
# is going on.
HEALTHCHECK --interval=30s --timeout=5s --start-period=5s --retries=3 \
    CMD platformops local-status --path . --json > /dev/null || exit 1

ENTRYPOINT ["platformops"]
CMD ["--help"]
EOF

Step 3 — Bump the version and update the changelog​

The image Phase 2 builds next should carry the right version — platformops --version reads it from the installed package's own metadata, set at build time from pyproject.toml. Bump it now, before building anything:

uv run python -c "
import re
path = 'pyproject.toml'
text = open(path).read()
text = text.replace('version = \"2.1.0\"', 'version = \"2.2.0\"', 1)
open(path, 'w').write(text)
"
uv sync
uv run platformops version

Expected output

platformops 2.2.0

Add a ## [2.2.0] - Containerized PlatformOps section to CHANGELOG.md, above the previous release, following the same ### Added structure every prior release entry already uses — mention the Dockerfile, .dockerignore and k8s/ manifests this phase added.

Phase 2 — Build the image and run it as a container​

Step 1 — Build​

docker build -t platformops:2.2.0 .

Expected output (trimmed to the parts that matter — your layer IDs and timings will differ)

#15 [builder 6/6] RUN uv sync --frozen --no-dev --no-editable
#15 6.386 Installed 27 packages in 859ms
#15 6.386  + boto3==1.43.63
#15 6.386  + httpx==0.28.1
#15 6.386  + platformops==2.2.0 (from file:///app)
#15 6.386  + pydantic==2.13.4
#15 6.386  + pyyaml==6.0.3
#15 6.386  + typer==0.27.1
...
#18 naming to docker.io/library/platformops:2.2.0 done
This install list is point-in-time

The exact set of transitive packages (27 here) and their versions come from uv.lock at the time you run this — the five direct dependencies (boto3, httpx, pydantic, pyyaml, typer) plus platformops itself are the ones that matter; the rest are their own dependencies, pinned by the lockfile, not something you choose by hand.

Step 2 — Check the image​

docker images platformops:2.2.0

Expected output

IMAGE               ID             DISK USAGE   CONTENT SIZE   EXTRA
platformops:2.2.0   7539f822d311   277MB         64.5MB
Column layout, ID and size are point-in-time

Docker's own image listing shows a different set of columns depending on which image store your Docker install uses — this is a containerd-backed install (Rancher Desktop), so docker images prints IMAGE/ID/DISK USAGE/CONTENT SIZE here instead of the classic REPOSITORY/TAG/IMAGE ID/SIZE table. Look for whichever column is the SIZE-equivalent in your own output — around 277MB here (DISK USAGE; CONTENT SIZE is a smaller, deduplicated figure that shares bytes with other images already on your machine). Your exact ID and size will differ — Debian security patches inside python:3.12-slim change over time. Most of this size is the base OS and the Python interpreter python:3.12-slim already includes, not anything this Dockerfile added — the .venv layer copied in from the builder (all five dependencies plus platformops itself) is a small fraction of the total. The Deep Dive breaks the layers down.

Step 3 — Confirm it runs as a non-root user​

docker run --rm --entrypoint id platformops:2.2.0

Expected output

uid=1000(platformops) gid=1000(platformops) groups=1000(platformops)

Step 4 — Run the CLI against a real file​

docker run --rm -v "$(pwd)/service.yaml:/data/service.yaml:ro" platformops:2.2.0 validate /data/service.yaml

Expected output

/data/service.yaml: OK -- checkout-api [prod/us-east-1] ns=checkout owner=payments-team alerts=#checkout-alerts

Step 5 — See it degrade honestly with no network and no Docker socket​

docker run --rm --entrypoint platformops platformops:2.2.0 local-status --json

Expected output

WARNING platformops.local_ops: git is not installed or not on PATH
WARNING platformops.local_ops: docker is not installed or not on PATH
WARNING platformops.local_ops: docker is not installed or not on PATH
{
  "status": "ok",
  "path": ".",
  "git": {
    "clean": false,
    "changed_files": [],
    "error": "git is not installed or not on PATH"
  },
  "docker": {
    "available": false,
    "error": "docker is not installed or not on PATH"
  },
  "containers": []
}

The three WARNING lines go to stderr (from Python's own logging module), and the JSON goes to stdout — a script piping --json output through | jq or similar sees only the clean JSON on stdout; the warnings show up in your terminal because it shows both streams together.

local_ops.py's never-raises contract (Module 11) holds here exactly the way it holds on your own laptop when git or docker is missing — status: ok, with the individual git/docker sections reporting what actually happened. This is the exact command the image's HEALTHCHECK runs.

Step 6 — Watch the healthcheck actually pass​

docker run -d --name platformops-health-demo --entrypoint sh platformops:2.2.0 -c "sleep 120"
sleep 40
docker inspect platformops-health-demo --format='{{.State.Health.Status}}'
docker inspect platformops-health-demo --format='{{json .State.Health.Log}}'
docker rm -f platformops-health-demo

Expected output

healthy
[{"Start":"2026-08-05T22:45:12+05:30","End":"2026-08-05T22:45:13+05:30","ExitCode":0,"Output":"WARNING platformops.local_ops: git is not installed or not on PATH\nWARNING platformops.local_ops: docker is not installed or not on PATH\nWARNING platformops.local_ops: docker is not installed or not on PATH\n"}]
platformops-health-demo

The sleep 120 override exists only so the container stays alive long enough to watch the healthcheck cycle — normal use of this image is the one-shot docker run --rm ... from the steps above, where HEALTHCHECK is still baked into the image's metadata but the container exits before a second check would ever run.

Phase 3 — SBOM and vulnerability scan​

Step 1 — Point syft and grype at the right Docker socket​

syft and grype both talk to the Docker daemon at its default socket path (/var/run/docker.sock) unless told otherwise — they do not read docker context the way the docker CLI itself does. If you are on Docker Desktop's default setup this is already correct; if you are on Rancher Desktop, Colima, or any setup with a non-default socket, point both tools at the same socket your docker CLI is actually using:

docker context inspect -f '{{.Endpoints.docker.Host}}'

Expected output (yours may show unix:///var/run/docker.sock if you are on Docker Desktop — use whatever this command prints)

unix:///Users/gshah/.rd/docker.sock
export DOCKER_HOST=unix:///Users/gshah/.rd/docker.sock

Without this, syft/grype fail with docker not available: failed to connect to Docker daemon even though docker build and docker run both work fine — those two read the active docker context correctly, syft/grype do not.

87 of the roughly 118 packages listed are deb — operating-system packages that came from python:3.12-slim, not from anything platformops added. The remaining 28 are python packages — platformops itself, its five direct dependencies, and their own transitive dependencies.

Step 3 — Scan for known vulnerabilities​

grype platformops:2.2.0

Expected output (trimmed — real, current CVE data; your exact counts will differ as CVE databases update)

NAME          INSTALLED    FIXED-IN  TYPE    VULNERABILITY   SEVERITY
python        3.12.13                binary  CVE-2026-7210   Critical
perl-base     5.40.1-6               deb     CVE-2026-8376   Critical
libc6         2.41-12+deb13u3        deb     CVE-2026-5450   Critical
libncursesw6  6.5+20250216-2         deb     CVE-2025-69720  Critical
...
201 matches across 37 packages: 7 Critical, 30 High, 66 Medium, 8 Low, 54 Negligible, 36 Unknown
Read this before you panic about "7 Critical"

Every single one of these findings is in a package python:3.12-slim brought in — python (the interpreter binary itself), libc6, perl-base, libncursesw6, libsqlite3-0, and similar base-OS packages. None of the 201 findings are in platformops's own code or in any of its five pinned dependencies (boto3, httpx, pydantic, pyyaml, typer) — check with:

grype platformops:2.2.0 -o json | python3 -c "
import json, sys
d = json.load(sys.stdin)
app = {'boto3','httpx','pydantic','pydantic-core','pyyaml','typer','platformops'}
hits = [m['artifact']['name'] for m in d['matches'] if m['artifact']['name'] in app]
print('findings in platformops or its pinned dependencies:', hits or 'none')
"

Expected output

findings in platformops or its pinned dependencies: none

The honest response to this scan is not "get to zero findings" — that is rarely realistic for any image built on a general-purpose base. It is: know what is there, rebuild on a fresh base regularly so the next scan reflects the base image's latest patches, and keep this check — "nothing here is in code my own team maintains" — as the one that actually gates a release.

Phase 4 — Run it as a Kubernetes Job​

Step 1 — Write the manifests​

mkdir -p k8s
cat > k8s/configmap.yaml << 'EOF'
# Non-secret configuration: the service definition the Job validates. A
# ConfigMap is the right place for this because none of it is confidential
# -- a repository URL, an environment name, an owning team -- the same kind
# of value platformops has read from service.yaml on disk since Module 6.
apiVersion: v1
kind: ConfigMap
metadata:
  name: platformops-service-config
data:
  service.yaml: |
    name: checkout-api
    repository: github.com/example/checkout-api
    environment: prod
    team_owner: payments-team
    kubernetes_namespace: checkout
    deployment_name: checkout-api
    aws_account: "111122223333"
    region: us-east-1
    observability:
      dashboard_url: https://grafana.example.com/d/checkout-api
      alert_channel: "#checkout-alerts"
EOF

cat > k8s/secret.yaml << 'EOF'
# A stand-in for a real secret (an API token, a database password). Its
# actual value here is not confidential -- it just overrides
# `environment: prod` to `environment: staging` so the Job's output proves
# the Secret was really read. In production the same `envFrom.secretRef`
# wiring is exactly how you hand platformops a real GitHub token or AWS
# key: never in the Dockerfile, never in the image, injected at deploy
# time and readable only by pods this namespace's RBAC allows.
#
# `kubectl apply -f secret.yaml` is fine for a course lab. A real cluster
# manages this file with something that keeps it out of git history
# entirely (sealed-secrets, External Secrets Operator, or your platform's
# secret store) -- never commit a real secret.yaml.
apiVersion: v1
kind: Secret
metadata:
  name: platformops-demo-secret
type: Opaque
stringData:
  PLATFORMOPS_ENVIRONMENT: staging
EOF

cat > k8s/job.yaml << 'EOF'
# Runs platformops once, to completion, inside a kind cluster -- a Job, not
# a Deployment. A Deployment keeps a process running forever and restarts
# it if it dies; a Job runs a task to completion and stops. Validating a
# service definition is a task with a clear end, so a Job is the right
# primitive -- the same way a CI pipeline step is a Job, not a service.
apiVersion: batch/v1
kind: Job
metadata:
  name: platformops-validate
spec:
  backoffLimit: 0 # a validation failure is real output, not a flake worth retrying
  ttlSecondsAfterFinished: 300
  template:
    spec:
      restartPolicy: Never
      automountServiceAccountToken: false # this Job never calls the Kubernetes API
      containers:
        - name: platformops
          image: platformops:2.2.0
          imagePullPolicy: IfNotPresent
          # Overrides the image's `ENTRYPOINT ["platformops"]` -- this Job
          # runs the config loader directly so it can prove the
          # environment-variable override (PLATFORMOPS_ENVIRONMENT, from
          # the Secret below) actually reaches the resolved config.
          command: ["python", "-m", "platformops.config"]
          args: ["/config/service.yaml", "--check", "--json"]
          envFrom:
            - secretRef:
                name: platformops-demo-secret
          volumeMounts:
            - name: service-config
              mountPath: /config
              readOnly: true
          securityContext:
            runAsNonRoot: true
            runAsUser: 1000
            runAsGroup: 1000
            allowPrivilegeEscalation: false
            readOnlyRootFilesystem: true
            capabilities:
              drop: ["ALL"]
          resources:
            requests:
              cpu: 50m
              memory: 64Mi
            limits:
              cpu: 200m
              memory: 128Mi
      volumes:
        - name: service-config
          configMap:
            name: platformops-service-config
EOF

Step 2 — Create a kind cluster and load the image​

kind clusters run their own containerd, separate from your host's Docker daemon — an image you built with docker build is not automatically visible inside the cluster. kind load docker-image copies it in explicitly.

kind load docker-image platformops:2.2.0 --name platformops-m27

Step 4 — Read the real logs​

kubectl logs job/platformops-validate

Expected output

{
  "status": "ok",
  "dry_run": true,
  "would_write": "/config/service.resolved.yaml",
  "service": {
    "name": "checkout-api",
    "repository": "github.com/example/checkout-api",
    "environment": "staging",
    "team_owner": "payments-team",
    "kubernetes_namespace": "checkout",
    "deployment_name": "checkout-api",
    "aws_account": "111122223333",
    "region": "us-east-1",
    "observability": {
      "dashboard_url": "https://grafana.example.com/d/checkout-api",
      "alert_channel": "#checkout-alerts"
    }
  }
}

"environment": "staging" — not "prod", the value the ConfigMap's service.yaml actually contains. That value came from the Secret's PLATFORMOPS_ENVIRONMENT env var, read the same way config.py's apply_env_overrides() (Module 11) already reads any PLATFORMOPS_* variable — this is the real, live proof the Secret was actually wired in, not just declared.

"would_write" and no actual file — that is --check, and readOnlyRootFilesystem, both working

The Job runs python -m platformops.config ... --check, a dry run that reports what it would write without writing it — deliberately, so the container never needs a writable filesystem. Pair that with readOnlyRootFilesystem: true in the Pod spec and you get defense in depth: even if --check were dropped by mistake, the kernel itself would refuse the write.

Phase 5 — Full quality gate​

uv run pytest -q
uv run ruff check src/ tests/
uv run mypy src/
uv run platformops version

Expected output

365 passed in 42.07s
All checks passed!
Success: no issues found in 22 source files

git add -A
git commit -m "platformops v2.2.0 -- Containerized PlatformOps"

docker rmi platformops:2.2.0
rm -f sbom.spdx.json
docker image prune -f

Expected output

Deleting cluster "platformops-m27" ...
Deleted nodes: ["platformops-m27-control-plane"]
Untagged: platformops:2.2.0
Deleted: sha256:...

This removes the kind cluster this lab created and the image this lab built — it does not touch ~/platformops itself, service.yaml, or any other module's containers or clusters.
