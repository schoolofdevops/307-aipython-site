Packaging Python Automation with Containers

Every module so far ran platformops the same way: uv run platformops ..., on your own laptop, with uv making sure the right Python version and the right library versions were in place. That works well while you are the only person running it. It stops working the moment someone else needs to run the exact same tool — a teammate on a different laptop, a CI job, a scheduled task in Kubernetes — and their machine does not have uv, does not have Python 3.12, or has a slightly different version of pydantic installed for some other project.

Why this matters at work

A platform team ships a CLI like platformops to dozens of engineers and to CI. "Works on my laptop" is not good enough — the tool has to run the same way everywhere, without every user first installing the exact right Python version and every dependency by hand. This module packages platformops as a container image: one file that carries everything the tool needs to run, built once, run anywhere Docker or Kubernetes runs.

1. A shipping container, not a moving truck packed by hand​

Before shipping containers existed, loading a cargo ship meant carrying loose boxes, barrels and crates up the gangplank by hand, one at a time, packed differently for every ship. A shipping container changed that: goods go into a standard steel box once, at the factory, and that exact box moves by truck, train and ship without ever being unpacked and repacked — because every crane, every truck bed and every ship's hold was built to handle that one standard shape.

A container image does the same job for software. platformops and everything it needs — the right Python interpreter, the right library versions — get packed into one standard box once, when you build the image. That same box then runs unchanged on your laptop, in CI, or inside a Kubernetes cluster, because Docker (and every tool that speaks the same standard) knows how to run that one shape of box, regardless of what is inside it.

A Dockerfile is the packing list — a plain text file of instructions that says exactly what goes into the box and in what order. docker build reads it and produces the image; the image is the thing that actually ships and runs.

2. Multi-stage builds — the construction site never ships with the building​

Building a house needs scaffolding, a concrete mixer, a crane, and a crew of workers on site. None of that ships with the finished house — once the last wall is painted, the scaffolding comes down and only the building itself is handed to the owner. Shipping the scaffolding along with the house would be pointless weight: expensive to move, and useless to whoever lives there.

Building platformops's image has the same two phases. Turning pyproject.toml and uv.lock into a working set of installed Python packages needs uv itself, and — for some of platformops's dependencies — a C compiler to build native extensions. None of that is needed to run platformops afterward; only the already-installed packages are. A multi-stage build keeps these two phases in separate, named stages inside one Dockerfile, and only copies the finished result from the first stage into the second:

uv itself, uv.lock, the C compiler apt pulled in to build a native extension, and the project's own tests/ folder never reach the final image — they only ever existed in the builder stage, which is thrown away once the build finishes. The final image is built fresh from python:3.12-slim again, with nothing in it except the one .venv folder copied across.

3. Running as a guest, not as the building's owner — USER, not root​

A hotel gives every guest a key card that opens their own room, the gym and the pool — never the staff areas, the server room, or another guest's room. If a guest's key card were somehow copied and misused, the damage is limited to what a guest can reach. Handing every guest a master key "just in case it's more convenient" would turn one stolen card into a hotel-wide problem.

A container that runs as root by default is the master-key version. If an attacker ever finds a way to run their own code inside that container — through a bug in one of platformops's dependencies, for example — root inside the container is a much bigger prize than an ordinary, unprivileged user would be. This module's Dockerfile creates one dedicated user (platformops, uid 1000) with no home directory and no usable shell, and switches to it with USER platformops before the image is done — every process this image ever runs, runs as that one limited user, never as root.

4. Configuring at run time, not baking config into the box​

A hotel room's thermostat lets each guest set their own temperature without the hotel rebuilding the room for every guest. The room itself — walls, wiring, the thermostat unit — is identical for everyone; only the setting changes, and it changes without touching the building at all.

platformops already works this way — src/platformops/config.py (Module 11) reads PLATFORMOPS_ENVIRONMENT, PLATFORMOPS_REGION, PLATFORMOPS_TEAM_OWNER and PLATFORMOPS_KUBERNETES_NAMESPACE from the environment and lets any of them override the matching field in a service definition file. None of that had to change for containers: docker run -e PLATFORMOPS_ENVIRONMENT=staging ... and a Kubernetes env/envFrom block both work by setting environment variables the exact same way a shell export does — the image itself never changes per environment. Baking one team's region or environment name into the image itself would mean building a separate image per team, per environment — the opposite of "build once, run anywhere."

5. Secrets — handed over at the door, never printed on the blueprint​

A hotel's guest key cards are not manufactured into the building's blueprint — they are encoded and handed to each guest individually at check-in, and revoked the moment they check out. Printing a permanent master key into the blueprint itself would mean every copy of that blueprint, forever, carries a working key.

A Dockerfile is exactly that permanent, widely-copied blueprint — anyone who can see the image (or the Dockerfile in source control) can see anything baked into it. A real credential (a GitHub token, a database password, a cloud access key) must never appear in a Dockerfile, an ENV instruction, or a layer that gets committed. Kubernetes's Secret object is the equivalent of handing the key card over at check-in: the value lives outside the image, injected as an environment variable only when the container actually starts, readable only by pods the namespace's access rules allow. This lab's Job reads PLATFORMOPS_ENVIRONMENT from a Secret — not because that particular value is confidential, but because the wiring (envFrom.secretRef → environment variable → os.environ inside the running process) is exactly how you would hand the same container a real API token in production, with zero code changes.

6. Health checks — a periodic "are you actually working" check​

A hospital does not wait for a patient to say something is wrong — a nurse checks vital signs on a fixed schedule, catching a problem before the patient even notices it. A container that only gets checked when something visibly breaks is the opposite: by the time anyone notices, it may have been silently broken for a while.

Docker's HEALTHCHECK instruction runs a command inside the container on a repeating schedule and records whether it exits 0 (healthy) or not. This image's healthcheck runs platformops local-status --path . --json — a command already guaranteed, by local_ops.py's own contract (Module 11), to never raise and always exit 0, reporting git and docker as simply unavailable inside a minimal container rather than crashing. A container that cannot even run that command is not healthy, no matter what else is going on inside it.

7. Resource limits — a fence, not a suggestion​

An apartment building gives each unit a fixed electrical and water allotment, not an unlimited draw from the building's shared supply. One apartment running every appliance at once draws only its own allotment — it cannot starve the rest of the building of power or water, because the limit is enforced at the meter, not just written in the lease.

Kubernetes resources.requests and resources.limits do the same job for CPU and memory. A request is what the scheduler reserves for a container up front — a promise the node has that much spare capacity before the pod is even placed. A limit is a hard ceiling the kernel enforces while the container runs — exceed the memory limit and the container is killed, not merely slowed down. Without limits, one runaway process can consume an entire node's memory and take every other pod on it down too. The Deep Dive proves, live, that this limit is enforced by the Linux kernel itself, not just recorded as a number in a YAML file.

8. Scanning and SBOM — an ingredient label for a container image​

A packaged food's ingredient label lists everything inside it, including preservatives and additives nobody in your own kitchen added — because they came from an ingredient you bought, not from your own recipe. You did not choose to add them, but you are still the one eating them, so you get to know they are there.

python:3.12-slim, the base this image builds on, brings its own operating-system packages — things like libc6, perl-base, tar — that platformops's own code never imports and never calls, the same way a can of tomato sauce carries preservatives the home cook never personally added. An SBOM (Software Bill of Materials) is that ingredient label for a container image: every package inside it, where it came from, and what version. A vulnerability scanner checks that list against databases of known security problems (CVEs) and reports which packages — yours or the base image's — have one.

This module uses two real, separately installed tools for this: syft generates the SBOM; grype scans for vulnerabilities. (Some Docker CLI builds ship a bundled docker scout command that does something similar — this course's reference environment does not have it installed, so the lab uses syft/grype directly, which work the same way on every platform.)

Running both against this image for real (this module's own lab, captured live — see the lab for the exact numbers) turns up a real, current list of CVEs — almost all of them in python:3.12-slim's own operating-system packages, not in platformops's own five pinned dependencies. That is not a failure to fix before shipping; it is the scanner doing its job, and it is completely normal for any image built on a general-purpose base. The response is not "reach zero findings" — that is rarely achievable — it is "know what's there, keep the base image current, and make sure nothing critical sits in code your own team actually maintains."

9. Running the same image two ways: a one-off errand and a scheduled shift​

Asking a friend to grab groceries once is a different kind of task from putting them on a recurring Tuesday shift. Both use the same person and the same skills, but one runs once and is done; the other is expected to repeat, or to be supervised while it runs.

The exact same platformops:2.2.0 image runs both ways in this lab:

  • docker run — a one-off errand. You run the CLI once, on your own machine, for a single command like platformops validate service.yaml, and the container exits when the command finishes.
  • A Kubernetes Job — the same one-off idea, but scheduled and supervised by a cluster instead of typed by hand. A Job runs a container to completion exactly like docker run does — it is not a Deployment, which keeps a process running forever and restarts it if it dies. Validating a service definition has a clear end, the same way a CI pipeline step does; a Job is the Kubernetes primitive built for exactly that, not for a long-running service.
Why this Job never touches the Kubernetes API

This Job's own container talks to nothing but its own filesystem and environment variables — it never calls kubectl, never imports a Kubernetes client library, and its Pod spec sets automountServiceAccountToken: false so it cannot even if it tried. Reading Kubernetes state from Python — the Kubernetes client library, kubeconfig, listing Pods and Deployments programmatically — is Module 28's job, not this one. This module only teaches you to package and run a container on Kubernetes with plain kubectl; automating Kubernetes itself from Python comes next.

Common pitfalls​

  • Forgetting .dockerignore and shipping .venv, .git, or tests/ inside the image. A host .venv can carry host-specific binaries that break on a different machine; .git can be large; none of it is needed to run the tool. Exclude them explicitly.
  • Running as root because it is the default. Add a dedicated user and switch to it with USER before the image is finished — do not defer this "for later."
  • Building a single-stage image with the C compiler and uv still inside it. That works, but ships build tools nobody needs at run time, inflating the image and its attack surface for no benefit. Multi-stage keeps only the finished .venv.
  • Baking a secret into an ENV instruction or a docker build --build-arg. Both end up readable in the image's layer history, forever, to anyone who can pull the image. Inject secrets at run time only — a Kubernetes Secret, or docker run -e from a value that was never written to a file.
  • Treating a HEALTHCHECK command that talks to the network as safe by default. This image's healthcheck deliberately calls local-status, which never raises even with no network and no Docker socket present — a healthcheck that can itself fail for reasons unrelated to the container's actual health produces false alarms.
  • Skipping resources.limits "because the tool is lightweight." A limit protects every other pod on the node from a bug in this one container, regardless of how light the tool normally is.
  • Reading a vulnerability scan's Critical/High count as a verdict on your own code. Check which package each finding is in first — a finding in the base image's perl-base or libc6 is not a defect in code your team wrote.
  • Using a Deployment for a task that has a clear end. A Deployment restarts a finished process forever, treating a successful, completed validation run as a crash to recover from. Use a Job for anything that is meant to finish.
