Multi-Region Cloud Inventory

Module 21 built a scanner that answers one question well: "what EC2 instances are running in us-east-1?" A real account almost never lives in one region. A company might run its US traffic out of us-east-1, its European traffic out of eu-west-1 for data-residency reasons, and a disaster-recovery copy of everything in a third region nobody thinks about until the day it matters. "What is actually running, across every region we use, right now" is a much more useful question — and a much harder one to answer safely.

This module extends the Module 21 scanner into multiregion.py: a scanner that checks several regions at once, without waiting for the slowest one to finish before starting the next, and without one broken or unreachable region silently taking down the whole report. It also widens what gets counted per region — not just EC2 instances, but EBS volumes, security groups, and Elastic IPs — and adds S3 buckets, which turn out to need a genuinely different discovery approach.

Why this matters at work

During a security incident, "list every EC2 instance, volume, security group and public IP address across every region we operate in, right now" is exactly the kind of request that shows up in the first ten minutes. Doing that by hand, region by region, in the AWS console, is slow exactly when speed matters most. A scanner that checks every region at once, and still gives you a usable answer even if one region's credentials happen to be expired that day, turns a fifteen-minute manual sweep into one command.

1. The health inspector who covers many branches​

Picture a city health department that has to inspect every branch of a restaurant chain — one branch downtown, one on the north side, one across town, and so on. The department could send one inspector to visit every branch, one at a time, driving across the city between each stop. That works, but it is slow, and it gets slower every time the chain opens a new branch.

A better-run department sends out a small team of inspectors at once — say, three inspectors, covering three branches at the same time — instead of one inspector doing everything alone, and instead of trying to send twenty inspectors out on twenty branches simultaneously, which would mean twenty cars converging on the city's streets and twenty reports landing on the coordinator's desk all at once. Three or five inspectors working in parallel, drawn from a fixed pool, is enough to move fast without overwhelming the city.

And if one branch is closed that day, or the inspector cannot get in touch with the manager, that one branch gets marked "not inspected — could not reach" on the final report. It does not stop the other inspectors from finishing their branches, and it does not blank out the whole city's report just because one branch had a problem.

This module's scanner works exactly the same way. Each AWS region is a branch. A small, fixed pool of workers (not one per region, and never unlimited) scans several regions at once. A region that cannot be reached — expired credentials, a permissions problem, a network failure — gets marked as failed in the final report, and every other region's results still come back.

Only three inspectors are ever out on the road at once here, even if the chain has twenty branches — the pool is small and fixed, not "one inspector per branch." And ap-south-1 failing does not stop us-east-1 and eu-west-1 from reporting back.

2. Bounded concurrency — a small pool, never one thread per region​

"Concurrency" means doing more than one thing at the same time. Module 10 already covered why an unbounded amount of concurrency is dangerous: creating one operating-system thread per item of work (one thread per region, if an account operates in twenty regions) means twenty threads all opening network connections, all competing for CPU time, and all of that overhead growing every time a new region gets added — completely independent of how much actual work each thread is doing.

scan_regions() uses Python's concurrent.futures.ThreadPoolExecutor with an explicit max_workers argument — five by default, and always a small, fixed, configurable number, the same discipline httpclient.check_many() (Module 10) already established for concurrent HTTP checks. No matter how many regions get passed in, no more than max_workers region-scans ever run at the same time. The Deep Dive measures this live, with a lock-protected counter that proves the pool never exceeds its cap — not just documents that it should.

3. Five AWS APIs, five different response shapes, one record​

This module discovers five kinds of resource, and every one of AWS's APIs nests its response differently:

  • EC2 instances: Reservations[].Instances[] — a list of lists.
  • EBS volumes: a flatter Volumes[] list.
  • Security groups: SecurityGroups[].
  • Elastic IPs: Addresses[].
  • S3 buckets: a plain list of bucket dicts, with no tags at all unless you ask for them separately.

Code that kept each of these shapes around as-is would need five different sets of logic everywhere downstream — building a report, filtering by tag, writing to a file. Instead, every lister function in multiregion.py ends by producing the same shape: a ResourceRecord with resource_type, resource_id, region, tags, and state. A security group has no natural "state" — it exists or it does not — so its state is simply None. That is a real, correct value for that resource type, not a missing field or a bug.

Both output formats — Markdown and CSV — are built from this one normalized list. Neither one re-runs any discovery logic; they only differ in how they render the same records.

4. Elastic IPs — a real AWS quirk, not a bug​

EC2 instances, EBS volumes and security groups are all listed through a paginator (client.get_paginator(...)) — the same discipline Module 21 established, because a real account can hold more of any of these than one API response page returns.

Elastic IPs are the exception. client.can_paginate("describe_addresses") returns False — AWS never registered a paginator for this operation at all, because one account's Elastic IPs are capped low enough by AWS itself that they never span more than one response. list_elastic_ips() calls describe_addresses() directly, once, with no paginator — calling get_paginator("describe_addresses") here would raise an error, because the operation genuinely does not support it. This is a fact about the API, not a shortcut this module is taking.

5. S3 is not region-scoped — a different discovery shape entirely​

The other four resource types are scanned once per region, inside the health-inspector pool. S3 cannot work that way, because S3 buckets are not region-scoped the way EC2 instances are. list_buckets() always returns every bucket in the account, no matter which region the S3 client was built for.

--- EC2: one call PER region, each returns only that region's instances ---
describe_instances() in us-east-1: ['i-9924a44b31d56fe7a']
describe_instances() in us-west-2: ['i-56c6741e4c8fd5380']

--- S3: ONE call, account-wide, from a client built for us-east-1 ---
list_buckets() (client region=us-east-1): ['bucket-in-east', 'bucket-in-west']
-> both buckets came back, even the one whose real data lives in us-west-2

A design that looped S3 the same way as the other four resource types — calling list_buckets() once inside every region's scan — would call it once per region and get back the exact same full account-wide list every single time, N times over, while never actually learning which region each bucket's data lives in. list_s3_buckets() is called exactly once, outside the per-region pool. Each bucket's real region is a second, separate call, get_bucket_location():

--- each bucket's REAL region only comes from a second, per-bucket call ---
get_bucket_location(Bucket='bucket-in-east'): us-east-1
get_bucket_location(Bucket='bucket-in-west'): us-west-2

One more S3-specific quirk: get_bucket_location() returns an empty result for a bucket in us-east-1 specifically — every other region names itself in the response. list_s3_buckets() treats an empty result as "us-east-1", the one region AWS itself treats as a historical default.

6. Partial regional failure — the report always returns what succeeded​

A multi-region scan touching real infrastructure will, sooner or later, hit a region that fails: temporary credentials that expired between the start of the scan and when that region's turn came up, a permissions boundary that only applies to one region, or a genuine network problem. The scanner's whole design exists so that one such failure does not take down the report for every other region.

Every region's scan runs inside its own try/except, inside its own worker. A failure there never propagates up and crashes the whole scan — it becomes one entry in a failed_regions list, alongside the reason, while every other region's results still make it into the report.

{
  "status": "partial",
  "regions_scanned": ["us-east-1"],
  "failed_regions": [
    {"region": "eu-west-1", "error": "expired-token", "message": "..."}
  ],
  "count": 12,
  "resources": [ /* everything us-east-1 found */ ]
}

status is "ok" only when every region succeeded, and "partial" the moment even one region failed — a caller (a human reading the CLI output, or a script reading --json) can always tell the difference between "everything is fine" and "most of this is fine, but not all of it."

7. Expired credentials are not the same problem as "access denied"​

scan_regions() catches botocore.exceptions.ClientError the same way cloudinventory.py already does — by name, never with a bare except Exception. But not every ClientError means the same thing operationally, and this module draws one specific line: an expired security token (AWS's ExpiredToken, ExpiredTokenException or RequestExpired error codes) is reported as its own "expired-token" reason, distinct from every other ClientError.

The reason this distinction matters: "your temporary credentials expired mid-scan" has a completely different fix than "this account does not have permission for this region" or "this region does not support this resource type." An expired token means re-authenticate and re-run the scan — the region itself may be perfectly healthy. Lumping it in with every other rejected request under one generic "ClientError" reason would hide that distinction from whoever reads the report next.

8. Missing tags are not errors​

A resource with no tags is a completely normal, expected state — not a failure. Two different shapes of "no tags" show up across these five APIs, and both must be handled the same way:

  • EC2, EBS, security groups, EIPs — an untagged resource can come back with its Tags key missing entirely, or present as an empty list. _tags_from_ec2_list() treats both the same way, producing {} either way.
  • S3 — an untagged bucket does not return an empty tag set at all. Calling get_bucket_tagging() on it raises a ClientError with the code NoSuchTagSet. This module catches exactly that code and treats it as "no tags" ({}) — anything else is left to raise, the same discipline every other exception handler in this project follows.

Common pitfalls​

  • Spawning one thread per region. It looks like it works fine in a two-region test and becomes a real problem the moment an account operates in ten or twenty regions. Always pass a small, explicit max_workers to ThreadPoolExecutor.
  • Assuming Elastic IPs paginate the same way EC2 instances do. describe_addresses has no paginator at all — check client.can_paginate(...) before assuming every "list" operation works the same way.
  • Looping list_buckets() once per region. It returns the same account-wide list every time, wasting API calls without ever learning which region each bucket actually lives in.
  • Treating a missing Tags key as an error instead of "no tags." A resource with nothing tagged on it is normal, expected, everyday state — not a reason to crash a scan. NoSuchTagSet on an untagged S3 bucket is the same situation, just a different shape.
  • Treating an expired-token failure the same as an access-denied failure. They call for completely different next steps — re-authenticate versus fix a permissions policy — and a report that cannot tell them apart makes the person reading it guess.
  • Letting one failed region blank out the whole report. The whole point of failed_regions is that a scan is still useful even when it is incomplete — never let one region's exception abort every other region's already-successful work.
