Deep Dive — Multi-Region Cloud Inventory

The lab proved multiregion.py works, and Phase 2's diff review proved you can catch an unbounded-concurrency bug and a pagination bug by reading code and running a targeted demo against it. This page goes one level deeper on three things the lab used but did not fully prove on their own: exactly why S3's discovery shape has to be different from the other four resource types, exactly what a real multi-page pagination bug looks like side by side with the fix, and exactly how many region-scans are running at once, measured live, not just asserted.

Where this picks up

This page assumes ~/platformops at v1.8.0, with src/platformops/multiregion.py and its multi-region-scan CLI command in place from the lab. Nothing here depends on any file being left over from the lab — every script below is created fresh, in a scratch location outside the project.

cd ~/platformops
uv run platformops version

Expected output

platformops 1.8.0

1. Why S3 discovery is structurally different from the other four​

The lesson stated the rule: EC2, EBS, security groups and Elastic IPs are all region-scoped — a client built for us-east-1 only ever sees us-east-1's resources. S3 is not. list_buckets() on a client built for us-east-1 returns every bucket in the account, including ones whose actual data lives in us-west-2. Two live calls, side by side, make the difference concrete instead of asserted.

cat > /tmp/s3_shape_demo.py << 'PYEOF'
import boto3
from moto import mock_aws


@mock_aws
def demo():
    ec2_east = boto3.client("ec2", region_name="us-east-1")
    ec2_west = boto3.client("ec2", region_name="us-west-2")
    ec2_east.run_instances(ImageId="ami-12345678", MinCount=1, MaxCount=1, InstanceType="t2.micro")
    ec2_west.run_instances(ImageId="ami-12345678", MinCount=1, MaxCount=1, InstanceType="t2.micro")

    s3 = boto3.client("s3", region_name="us-east-1")
    s3.create_bucket(Bucket="bucket-in-east")
    s3.create_bucket(
        Bucket="bucket-in-west", CreateBucketConfiguration={"LocationConstraint": "us-west-2"}
    )

    print("--- EC2: one call PER region, each returns only that region's instances ---")
    for region, client in [("us-east-1", ec2_east), ("us-west-2", ec2_west)]:
        ids = [
            i["InstanceId"]
            for r in client.describe_instances()["Reservations"]
            for i in r["Instances"]
        ]
        print(f"describe_instances() in {region}: {ids}")

    print()
    print("--- S3: ONE call, account-wide, from a client built for us-east-1 ---")
    all_buckets = [b["Name"] for b in s3.list_buckets()["Buckets"]]
    print(f"list_buckets() (client region=us-east-1): {all_buckets}")
    print("-> both buckets came back, even the one whose real data lives in us-west-2")

    print()
    print("--- each bucket's REAL region only comes from a second, per-bucket call ---")
    for name in all_buckets:
        location = s3.get_bucket_location(Bucket=name).get("LocationConstraint") or "us-east-1"
        print(f"get_bucket_location(Bucket={name!r}): {location}")


demo()
PYEOF
uv run python /tmp/s3_shape_demo.py

Expected output

--- EC2: one call PER region, each returns only that region's instances ---
describe_instances() in us-east-1: ['i-9924a44b31d56fe7a']
describe_instances() in us-west-2: ['i-56c6741e4c8fd5380']

--- S3: ONE call, account-wide, from a client built for us-east-1 ---
list_buckets() (client region=us-east-1): ['bucket-in-east', 'bucket-in-west']
-> both buckets came back, even the one whose real data lives in us-west-2

--- each bucket's REAL region only comes from a second, per-bucket call ---
get_bucket_location(Bucket='bucket-in-east'): us-east-1
get_bucket_location(Bucket='bucket-in-west'): us-west-2

This is the concrete argument against looping S3 the same way as the other four resource types. If list_s3_buckets() were called once inside every region's per-region loop, a two-region scan would call list_buckets() twice and get the exact same two-bucket list back both times — bucket-in-west would appear to belong to whichever region asked last, and the account would be reported as having twice as many buckets as it actually does, the moment naive deduplication was skipped. scan_regions() calls list_s3_buckets() exactly once, outside the per-region pool, for exactly this reason.

2. Proving the pagination fix, not just claiming it​

Phase 2 of the lab showed the diff's buggy list_ec2_instances() returning 5 records instead of 12. This section builds both versions side by side — the buggy version (a single describe_instances(MaxResults=...) call, first page only) and the fixed version (the real list_ec2_instances() from multiregion.py, which walks every page) — against the exact same fixture, in the same run, so there is no question of the two being tested under different conditions.

cat > /tmp/pagination_proof.py << 'PYEOF'
import boto3
from moto import mock_aws

from platformops.multiregion import list_ec2_instances


def buggy_list_instances(client, *, page_size):
    """The mistake: ask the paginator for a small page size, then only read the FIRST page it yields."""
    paginator = client.get_paginator("describe_instances")
    first_page = next(iter(paginator.paginate(PaginationConfig={"PageSize": page_size})))
    return [i["InstanceId"] for r in first_page["Reservations"] for i in r["Instances"]]


@mock_aws
def demo():
    client = boto3.client("ec2", region_name="us-east-1")
    for _ in range(12):
        client.run_instances(
            ImageId="ami-12345678", MinCount=1, MaxCount=1, InstanceType="t2.micro"
        )

    buggy_result = buggy_list_instances(client, page_size=5)
    fixed_result = list_ec2_instances(client, page_size=5)

    print("instances actually created: 12")
    print(f"buggy (paginator built, but only the first page read): {len(buggy_result)} returned")
    print(f"fixed (list_ec2_instances(), walks every page): {len(fixed_result)} returned")


demo()
PYEOF
uv run python /tmp/pagination_proof.py

Expected output

instances actually created: 12
buggy (paginator built, but only the first page read): 5 returned
fixed (list_ec2_instances(), walks every page): 12 returned

Both functions ran against the same 12 mocked instances, in the same process. The buggy version is not wrong because it fails to build a paginator — it does build one — it is wrong because it only ever reads the object the paginator yields first, instead of looping over every page the paginator yields. list_ec2_instances() in this module's real code loops (for page in paginator.paginate(...)), which is the entire difference between 5 and 12 here. Against a fixture with 3 or 4 instances, both versions would return the same number — the bug is invisible until the account (or a deliberately forced small page_size, exactly as this demo does) genuinely spans more than one page.

3. Proving bounded concurrency, not just claiming it​

scan_regions()'s docstring says max_workers bounds how many regions scan at once. A lock-protected counter, incremented when a region-scan starts and decremented when it ends, measures the real peak concurrency directly — not by reading the code and trusting it, but by watching it happen.

cat > /tmp/concurrency_proof.py << 'PYEOF'
import threading
import time
from unittest import mock

from platformops.multiregion import scan_regions

lock = threading.Lock()
state = {"current": 0, "peak": 0}


def fake_scan_region(*, region, profile=None, page_size=None):
    with lock:
        state["current"] += 1
        state["peak"] = max(state["peak"], state["current"])
    time.sleep(0.1)  # long enough that overlap is measurable, not a race
    with lock:
        state["current"] -= 1
    return []


def demo():
    regions = [f"region-{i}" for i in range(12)]

    with mock.patch("platformops.multiregion.scan_region", fake_scan_region), mock.patch(
        "platformops.multiregion.list_s3_buckets", lambda client: []
    ), mock.patch(
        "platformops.multiregion.get_aws_client", lambda *a, **k: object()
    ):
        for max_workers in (3, 5):
            state["current"] = 0
            state["peak"] = 0
            scan_regions(regions, max_workers=max_workers)
            print(
                f"max_workers={max_workers}: {len(regions)} regions scanned, "
                f"peak concurrent region-scans observed = {state['peak']}"
            )


demo()
PYEOF
uv run python /tmp/concurrency_proof.py

Expected output

max_workers=3: 12 regions scanned, peak concurrent region-scans observed = 3
max_workers=5: 12 regions scanned, peak concurrent region-scans observed = 5
This output is point-in-time

The exact peak concurrency figure depends on real OS thread scheduling and can vary run to run and machine to machine — the guarantee ThreadPoolExecutor(max_workers=...) makes is an upper bound, not an exact figure. What stays true on every run: the observed peak never exceeds max_workers, and it climbs above 1, proving the regions genuinely overlap instead of running one at a time. Compare this against Phase 2 Step 3 of the lab, where the same measurement against the buggy raw-threading.Thread version showed a peak of 10 out of 10 regions — every single one running at once, completely ignoring max_workers=3.

Twelve regions, max_workers set once to 3 and once to 5 — the observed peak never exceeds whichever cap was requested for that run, no matter how many regions were passed in. This is the same measurement Phase 2 Step 3 of the lab ran against the diff's buggy version, where the peak hit 10 out of 10 regions regardless of max_workers. The difference between the two runs is the entire argument for ThreadPoolExecutor(max_workers=...) over a raw threading.Thread per region: one enforces the cap as a real constraint on how many workers exist; the other accepts the argument and does nothing with it.

Where you will use this
  • Use it when: you are asked to add a new resource type to an inventory scanner and are deciding whether it belongs in the per-region loop or needs its own pass — check whether the underlying AWS API is region-scoped first (describe_* operations usually are; account-wide list_* operations like S3's sometimes are not).
  • Use it when: you are reviewing someone else's pagination code and see a paginator object created but only its first page ever read — this looks completely correct against a small test fixture and silently drops data on a real, larger account.
  • Use it when: a coding agent hands you a "concurrent" extension to review — check whether the concurrency primitive itself enforces the stated limit (a real ThreadPoolExecutor(max_workers=...)) rather than just accepting a max_workers parameter that nothing in the implementation actually consults.
  • Use it when: you need to prove a concurrency claim to a reviewer or in an incident postmortem — a lock-protected counter around the concurrent section is a small, honest way to measure real peak concurrency instead of asserting it from reading the code.

Teardown​

cd ~/platformops
rm -f /tmp/s3_shape_demo.py /tmp/pagination_proof.py /tmp/concurrency_proof.py

No AWS state, real or faked, survives past these scripts' own runs — nothing else to clean up.
