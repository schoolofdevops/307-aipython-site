Lab -- Build PlatformOps v0.4: the Service Configuration Validator

This lab has two phases. In Phase A you add pyyaml and hand-build a small module that loads a service.yaml file and validates it through the ServiceDefinition model from the last module -- so you know exactly how a file problem and a data problem are told apart. In Phase B you hand a short, written request to a coding agent to add environment-variable overrides, a --json output flag, and a --check dry-run flag on top of that, then you review its diff before accepting it -- the same review habit as the last two modules.

You need the ~/platformops project from the M5 lab, already tagged v0.3, with uv run pytest -q passing and git log showing that tag.

3. Create the config-loading module​

Create src/platformops/config.py:

src/platformops/config.py
"""Load service definitions from YAML files -- PlatformOps v0.4.

`servicedef.py` validates a service definition once it is already a Python
dict. Most of the time that dict starts life as a YAML file a team keeps in
its repository -- `service.yaml`, checked in next to the code it describes.
This module is the bridge between the two: it turns a path on disk into a
validated `ServiceDefinition`, and it is careful about the two ways a file
can fail before validation ever gets a chance to run -- the file might not
exist, or it might not be valid YAML.
"""

from pathlib import Path

import yaml

from platformops.servicedef import ServiceDefinition, validate_service


class ConfigError(Exception):
    """A problem with the config file itself, not with the data in it.

    `validate_service` already reports data problems (a missing field, a
    bad environment value) as a list of error dicts. `ConfigError` is for
    everything upstream of that: the file was not where we looked, or what
    was in it was not YAML at all.
    """


def load_yaml_dict(path: Path) -> dict:
    """Read a YAML file and return its top-level mapping as a dict.

    Raises `ConfigError` with a plain-English message for the two failures
    a learner (or a script) will actually hit: a missing file, or text that
    is not valid YAML.
    """
    path = Path(path)
    if not path.exists():
        raise ConfigError(f"config file not found: {path}")

    text = path.read_text(encoding="utf-8")

    try:
        data = yaml.safe_load(text)
    except yaml.YAMLError as exc:
        raise ConfigError(f"invalid YAML in {path}: {exc}") from exc

    if not isinstance(data, dict):
        raise ConfigError(f"{path} does not contain a YAML mapping (a service definition)")

    return data


def load_service_yaml(path: Path) -> ServiceDefinition | list[dict]:
    """Load a service definition YAML file and validate it.

    Returns a validated `ServiceDefinition` on success, or the list of
    Pydantic error dicts on a data problem -- the same contract as
    `validate_service`. A file problem (missing file, broken YAML) raises
    `ConfigError` instead, so the two failure modes are never confused with
    each other.
    """
    data = load_yaml_dict(path)
    return validate_service(data)


def _print_result(path: Path) -> None:
    try:
        result = load_service_yaml(path)
    except ConfigError as exc:
        print(f"{path}: ERROR -- {exc}")
        return

    if isinstance(result, ServiceDefinition):
        print(f"{path}: OK -- {result.to_summary()}")
    else:
        print(f"{path}: FAIL")
        for error in result:
            location = ".".join(str(part) for part in error["loc"])
            print(f"  {location}: {error['msg']}")


if __name__ == "__main__":
    import sys

    _print_result(Path(sys.argv[1]))

load_yaml_dict is the one place that touches the filesystem and the YAML parser -- it turns either failure into a ConfigError with a message you can print directly, instead of a raw traceback. load_service_yaml hands that dict to validate_service, the same function the last module built -- this module never re-implements validation, it only gets a dict to validate_service safely. Note yaml.safe_load, not yaml.load -- the lesson explains why that choice is not optional.

4. Write the tests​

Create tests/test_config.py:

tests/test_config.py
import pytest

from platformops.config import ConfigError, load_service_yaml
from platformops.servicedef import ServiceDefinition


def test_a_good_yaml_file_loads_into_a_validated_model(tmp_path):
    good = tmp_path / "service.yaml"
    good.write_text(
        "name: checkout-api\n"
        "repository: github.com/example/checkout-api\n"
        "environment: prod\n"
        "team_owner: payments-team\n"
        "kubernetes_namespace: checkout\n"
        "deployment_name: checkout-api\n"
        'aws_account: "111122223333"\n'
        "region: us-east-1\n"
        "observability:\n"
        "  dashboard_url: https://grafana.example.com/d/checkout-api\n"
        '  alert_channel: "#checkout-alerts"\n'
    )

    result = load_service_yaml(good)

    assert isinstance(result, ServiceDefinition)
    assert result.name == "checkout-api"


def test_a_missing_file_raises_a_clean_configerror_not_a_traceback(tmp_path):
    missing = tmp_path / "does-not-exist.yaml"

    with pytest.raises(ConfigError, match="not found"):
        load_service_yaml(missing)


def test_invalid_yaml_raises_a_clean_configerror(tmp_path):
    broken = tmp_path / "broken.yaml"
    # Two keys at the same indentation claiming the same line -- not valid
    # YAML, the kind of typo a hand-edit produces.
    broken.write_text("name: checkout-api\n  bad indent: oops\n")

    with pytest.raises(ConfigError, match="invalid YAML"):
        load_service_yaml(broken)


def test_a_file_that_fails_model_validation_surfaces_the_missing_field(tmp_path):
    bad = tmp_path / "service-bad.yaml"
    bad.write_text(
        "name: checkout-api\n"
        "repository: github.com/example/checkout-api\n"
        "environment: prod\n"
        "team_owner: payments-team\n"
        "kubernetes_namespace: checkout\n"
        'aws_account: "111122223333"\n'
        "region: us-east-1\n"
        "observability:\n"
        "  dashboard_url: https://grafana.example.com/d/checkout-api\n"
        '  alert_channel: "#checkout-alerts"\n'
    )

    errors = load_service_yaml(bad)

    assert isinstance(errors, list)
    assert any(
        error["loc"] == ("deployment_name",) and error["type"] == "missing"
        for error in errors
    )

Each test uses pytest's built-in tmp_path fixture -- a fresh, empty folder pytest creates and deletes for every test, so these tests never touch service.yaml or service-bad.yaml on disk and never leave files behind.

Phase B -- delegate the env overrides, JSON output and dry run​

Right now config.py reads exactly what is in the file and nothing else, prints plain text only, and has no way to preview a change without writing it. Those are the three things Phase B adds -- plus writing the resolved result back to disk the safe way the lesson covered.

7. Ask your coding agent to extend the module​

Open your coding agent in the project folder:

claude

Paste this request exactly as written:

I'm working in this uv-managed Python project, in src/platformops/config.py (a
ConfigError exception, load_yaml_dict, load_service_yaml, and a tiny __main__ demo
that print()s an OK/FAIL/ERROR line for one file path). Please extend it into a
proper CLI, without touching load_yaml_dict or load_service_yaml's existing
behavior:

1. Add apply_env_overrides(data: dict, environ: dict | None = None) -> dict that
   layers environment-variable overrides on top of the file's dict, for exactly
   these fields: environment, region, team_owner, kubernetes_namespace. Each
   field's env var is PLATFORMOPS_<FIELD_UPPER> (e.g. PLATFORMOPS_ENVIRONMENT). An
   env var wins over the file value; a field with no matching env var is left
   alone. environ defaults to the real os.environ, but a caller (a test) can pass
   its own dict instead.
2. Add write_resolved_config(data: dict, out_path: Path) -> None that writes data
   as YAML to out_path atomically: write to a temp file in out_path's own
   directory, then os.replace() it into place. Never write straight to out_path.
3. Replace the __main__ block with a real CLI (argparse is fine) that takes a
   required path argument, plus two flags: --json (print machine-readable JSON
   instead of plain text) and --check (validate and resolve only -- print what
   would be written, write nothing).
4. Without --check, on a successful validation, write the resolved config (file
   values with env overrides applied) to <path stem>.resolved.yaml next to the
   input file, using write_resolved_config.
5. Do not add any new third-party dependencies -- pyyaml, argparse and the
   standard library are enough for all of this.
6. Add tests: an env var overriding a file value, a field with no matching env
   var keeping the file value, --check writing nothing, a normal run writing the
   resolved file atomically, an env override flowing into the written file, and
   --json producing output that json.loads() can parse. Every existing test must
   stay green, unchanged.
7. Run `uv run ruff check .` and `uv run pytest -q` yourself before you finish,
   and tell me the result.

This spec names the exact fields the env layer is allowed to touch (not "read some environment variables"), states the write must be atomic and names the mechanism (temp file + os.replace), and asks the agent to verify its own work -- the same discipline as the last two modules' Phase B.

Now read the two functions that matter most in the actual change:

This course's own reference diff for the env-override and atomic-write functions looks like this -- your agent's exact naming may differ, the shape should not:

+def apply_env_overrides(data: dict, environ: dict | None = None) -> dict:
+    """Layer environment-variable overrides on top of file values."""
+    environ = os.environ if environ is None else environ
+    resolved = dict(data)
+    for field in ENV_OVERRIDE_FIELDS:
+        env_name = f"{ENV_PREFIX}{field.upper()}"
+        if env_name in environ:
+            resolved[field] = environ[env_name]
+    return resolved
+
+
+def write_resolved_config(data: dict, out_path: Path) -> None:
+    """Write `data` to `out_path` as YAML -- atomically."""
+    out_path = Path(out_path)
+    fd, tmp_name = tempfile.mkstemp(
+        dir=out_path.parent, prefix=f".{out_path.name}.", suffix=".tmp"
+    )
+    try:
+        with os.fdopen(fd, "w", encoding="utf-8") as tmp_file:
+            yaml.safe_dump(data, tmp_file, sort_keys=False)
+        os.replace(tmp_name, out_path)
+    except BaseException:
+        Path(tmp_name).unlink(missing_ok=True)
+        raise

apply_env_overrides only ever looks at the four field names in ENV_OVERRIDE_FIELDS -- an env var for a field this module was never told to watch cannot silently change anything. write_resolved_config never opens out_path for writing at all -- it writes a complete file next to it, then swaps it in with os.replace, exactly the pattern from the lesson.

Run the checklist this course keeps coming back to:

  • Does apply_env_overrides touch only the four named fields? Not aws_account, not name -- an env var overriding a field nobody asked it to override is a bug, not a feature.
  • Does write_resolved_config ever call out_path.write_text(...) or open(out_path, "w") directly? It should not -- every write goes through the temp file first.
  • Did the agent add a dependency? pyproject.toml should show only the one pyyaml line from step 1 -- argparse, os, tempfile and json are all in the standard library.
  • Is there one test per new behavior -- env override wins, no-match keeps the file value, --check writes nothing, a normal run writes the file, an override reaches the written file, --json is parseable? Six new tests, roughly.

Troubleshooting
  • ModuleNotFoundError: No module named 'yaml' -- either uv add pyyaml was never run, or you ran python directly instead of uv run python (or python -m platformops.config). uv run makes sure you are using the project's own virtual environment.
  • A tab character error from PyYAML, or found character '\t' that cannot start any token -- YAML forbids tab characters for indentation; it only accepts spaces. Most editors show this as a red squiggle -- if yours does not, search the file for a literal tab and replace it with two spaces.
  • UnicodeDecodeError: 'utf-8' codec can't decode byte ... -- the file has bytes that are not valid UTF-8, usually because an older editor saved it in a legacy encoding (Latin-1, Windows-1252) while writing a non-ASCII character (an accented name in team_owner, for example). read_text(encoding="utf-8") refuses to guess -- ask whoever produced the file to re-save it as UTF-8, the encoding every tool in this stack (Python, YAML, git, GitHub) assumes by default.
  • kubernetes_namespace or region rejected after an env override -- apply_env_overrides does not validate anything; it just substitutes a string. validate_service still runs afterward and will reject PLATFORMOPS_REGION=eu-central-1 the same way it rejects a bad value in the file, because eu-central-1 is not in this model's allowed list from the last module.
  • --check still wrote a file -- check your agent's diff for the order of operations; the write must happen only in the branch where args.check is False. This is exactly the kind of scope-creep bug the review checklist in step 8 exists to catch.
  • Your agent's diff touches pyproject.toml a second time (after step 1's uv add pyyaml) -- it added a dependency. Reject that part of the change; argparse, os, tempfile and json are all in Python's standard library.
