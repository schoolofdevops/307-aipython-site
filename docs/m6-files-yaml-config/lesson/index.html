Files, YAML, JSON and Configuration

Module slides​

Walk this short whiteboard deck for the big picture, or open it fullscreen.

▶ M6 — Files, YAML, JSON and ConfigurationOpen fullscreen ↗

A deploy script updates service.yaml to record which image tag is now running. Halfway through writing the file, the process is killed -- a spot instance reclaimed, a laptop lid closed, an out-of-memory kill, it does not matter which. The next command that reads service.yaml gets a file that is neither the old version nor the new one -- just whatever bytes made it to disk before the process died. Every teammate and every script that trusted that file is now working from garbage, and nobody knows it yet.

This module is about the file itself: reading and writing it in a way a crash cannot corrupt, parsing the formats it actually comes in (YAML, JSON, CSV), and deciding where a setting should live -- in the file, in an environment variable, or nowhere at all because it is a secret. Get this right and a config file is boring and reliable. Get it wrong and it is the thing that fails silently, at the worst time, in a way nobody notices until an on-call engineer is staring at a service running the wrong image in the wrong region.

1. A path is an object, not a piece of string​

Most scripts that touch files start by building a path with string concatenation: base_dir + "/" + service_name + "/config.yaml". That works until the script runs on a different OS with a different separator, or base_dir already ends in a slash and now the path has two, or someone forgets the slash and gets one long filename instead of a folder and a file.

Think of the difference between a piece of string you tie into a path by hand, and a proper address written in labeled fields -- street, city, postal code. The labeled address knows what each part means; the string is just characters until you parse it again. Python's pathlib.Path is the labeled version:

from pathlib import Path

config_path = Path("configs") / "checkout-api" / "service.yaml"
print(config_path)
print(config_path.name, config_path.suffix, config_path.parent)
print(config_path.exists())

Expected output

configs/checkout-api/service.yaml
service.yaml .yaml configs/checkout-api
False

The / operator joins path parts correctly for the OS the script runs on, so the same code produces configs\checkout-api\service.yaml on Windows without you writing an if for it. .name, .suffix, and .parent answer questions you would otherwise be slicing strings to get at, and .exists() asks the filesystem directly instead of you guessing.

2. Reading and writing text -- and why write_text is dangerous on its own​

path.read_text(encoding="utf-8") reads a whole file as a string in one call; path.write_text(...) writes one. Both are fine for a one-off script. What write_text does not tell you is that it opens the target file, truncates it to zero bytes immediately, and only then starts writing your new content. If the write is interrupted after the truncate and before it finishes, the old content is already gone and the new content never fully arrived. Section 6 below fixes this properly -- keep it in mind as you read the next few sections.

3. Three formats you will parse constantly​

JSON is what most APIs and lockfiles speak: strict, no comments, easy for machines. json.load(file) parses it into Python dict/list/str/int; json.dump(data, file) writes it back out.

YAML is what most teams hand-edit: comments, no quoting required for plain strings, and nested structure shown with indentation instead of brackets -- which is exactly why service.yaml in this module's lab is YAML, not JSON. Python parses it with the third-party pyyaml package:

import yaml

with open("service.yaml") as f:
    data = yaml.safe_load(f)

Use yaml.safe_load, never the plain yaml.load. YAML has a feature called tags that can tell a loader to construct arbitrary Python objects while parsing -- not just plain data. safe_load only ever builds plain dicts, lists, strings, and numbers; it refuses anything else. Loading a config file with the unsafe yaml.load is loading a file you did not write and trusting it to only ever ask for data, when the format itself allows it to ask for more. The Deep Dive shows exactly what that "more" can look like, safely, without running it.

CSV shows up for tabular exports and reports -- a list of services with one row each. csv.DictReader(file) turns each row into a dict keyed by the header row; csv.DictWriter writes one back out the same way. It is worth knowing mainly because it is the one format here where a stray comma inside a value can silently shift every column after it -- the csv module handles quoting correctly, hand-splitting on , does not.

4. Where a setting's value actually comes from -- the three-layer rule​

A service needs to know which environment it is running in. That value could come from three places: a built-in default in the code, the service.yaml file checked into the repository, or an environment variable set for this one run. All three cannot win -- there has to be an order.

Think of a recipe card pinned to the kitchen wall. It has a base recipe already printed on it (the default). Today's card has been updated in pen for this kitchen's usual batch (the config file). And right now, tasting the pot, the cook calls out "more salt" -- a decision for this one batch only, that overrides everything printed or written on the card (the environment variable). Nobody rewrites the card for a one-time adjustment; the spoken instruction just wins for as long as this batch is cooking.

Each layer overrides everything to its left, and only if it actually sets that value -- an environment variable you did not set leaves the file's value untouched. This module's lab builds exactly this: service.yaml supplies the file layer, and PLATFORMOPS_ENVIRONMENT (and a few sibling variables) supply the environment layer on top of it.

5. A file that might not be there​

Before you read a config file, you do not know it exists -- a teammate renamed it, a fresh clone never had it, a typo in the path is one keystroke away. path.exists() and path.is_file() answer that before you try to open it, so your script can say "config file not found at configs/checkout-api/service.yaml" instead of leaking a raw FileNotFoundError traceback at someone who is not going to know what to do with it. The same applies to permissions -- a file that exists but that the current user cannot read raises PermissionError, a different failure with a different fix, worth catching separately rather than lumping into "something went wrong."

6. Never leave a half-written file on disk -- temp file, then rename​

Back to the opening story: the fix is to never write to the real destination directly. Write the full new content to a temporary file in the same folder, then rename that temp file over the real one in a single step.

Picture how a scoreboard operator updates the total: they do not erase the old number and start writing the new one stroke by stroke while the crowd watches a half-formed digit. They write the complete new number on a fresh card, off to the side, then swap the whole card in one motion. Anyone glancing at the board sees the old total right up until the swap, then the new total -- never a half-drawn number.

os.replace() (or Path.replace()) performs that swap as one atomic operation on the same filesystem -- the operating system guarantees it either completes fully or does not happen at all, with nothing readable in between. If the process is killed before the replace, the original service.yaml is untouched. If it is killed during the write to the temp file, again the original is untouched -- only the temp file (never read by anything) is incomplete. There is no window where a reader can see a half-written service.yaml. This module's lab writes its resolved config exactly this way.

7. A backup is only a backup once you have restored from it​

Before a script overwrites a config that matters, copying the old version aside first (service.yaml.bak, or a timestamped copy) costs almost nothing and buys you an undo button. The habit only pays off if you actually keep more than the last copy and actually rehearse restoring from one before you need it under pressure -- an untested backup is a guess, not a safety net.

8. A config file is not a safe or a vault​

service.yaml gets committed to git, attached to support tickets, copied into backups, and read by anyone with clone access. None of that is a safe place for an API key or a database password -- once a secret is in git history, it is there permanently, even after you delete it in a later commit. Secrets belong in environment variables sourced from a secret manager (or, at minimum, a .env file that is in .gitignore and never committed), not in the config file itself. The convention teams use to keep this straight is a .env.example file: committed to the repo, listing every environment variable a secret should come from -- DATABASE_PASSWORD=, with no value -- so a new teammate knows exactly what to set without a real secret ever touching git.

Common pitfalls
  • Calling plain yaml.load() on a file you did not write yourself. It can construct more than plain data from the file's content. Use yaml.safe_load() for every config file this toolkit reads.
  • Writing straight to the destination file with write_text() or open(path, "w"). Both truncate the file the instant they open it -- a crash mid-write leaves a corrupt or empty file where a good one used to be. Write to a temp file and os.replace() it into place instead.
  • Hand-building paths with string concatenation. It breaks across operating systems and hides bugs a Path object would catch (a double slash, a missing separator). Use pathlib.
  • Assuming a config file exists before reading it. Check path.exists() first, or catch FileNotFoundError and turn it into a message someone can act on.
  • Committing a real .env instead of a .env.example. A secret in git history stays there even after you "remove" it in a later commit -- rotate the credential, do not just delete the line.
