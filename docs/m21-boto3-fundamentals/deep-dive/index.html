Deep Dive — AWS Automation Fundamentals with Boto3

The lab proved cloudinventory.py works. This page goes one level deeper on three things the lab used but did not fully prove: exactly which credential source wins when more than one is available, exactly what makes the pagination test trustworthy rather than a coincidence, and exactly which failures botocore retries for you automatically and which ones it correctly leaves alone.

Where this picks up

This page assumes ~/platformops at v1.6.0, with src/platformops/cloudinventory.py and its inventory-scan CLI command in place from the lab. Nothing here depends on any file being left over from the lab — every script below is created fresh, in a scratch location outside the project.

cd ~/platformops
uv run platformops version

Expected output

platformops 1.6.0

1. The credential chain, traced concretely​

The lesson listed the order boto3 checks: explicit session arguments, then environment variables, then the shared config/credentials files, then an IAM role. "Explicit session arguments" means something specific: passing profile_name=... when you create a boto3.Session() yourself, the way cloudinventory.get_client() does. It is easy to assume environment variables always win, because they are the most commonly used override — but they only win when nothing more specific was requested. Two live runs settle exactly where each source ranks.

Case 1 — no profile requested: environment variables beat the shared credentials file​

cat > /tmp/credchain_demo.py << 'PYEOF'
import os
import tempfile

import boto3

creds_dir = tempfile.mkdtemp()
creds_path = os.path.join(creds_dir, "credentials")
with open(creds_path, "w") as f:
    f.write(
        "[labprofile]\n"
        "aws_access_key_id = AKIAPROFILEKEYFAKE\n"
        "aws_secret_access_key = profile-secret-fake\n"
    )

os.environ["AWS_SHARED_CREDENTIALS_FILE"] = creds_path
os.environ["AWS_CONFIG_FILE"] = "/nonexistent/config"
os.environ["AWS_ACCESS_KEY_ID"] = "AKIAENVKEYFAKE00000"
os.environ["AWS_SECRET_ACCESS_KEY"] = "env-secret-fake"

print("--- Session() with NO profile_name (env vars should win) ---")
session = boto3.Session()
creds = session.get_credentials()
print("access key used:", creds.access_key)

print()
print("--- Session(profile_name='labprofile') (explicit profile) ---")
session2 = boto3.Session(profile_name="labprofile")
creds2 = session2.get_credentials()
print("access key used:", creds2.access_key)
PYEOF
uv run python /tmp/credchain_demo.py

Expected output

--- Session() with NO profile_name (env vars should win) ---
access key used: AKIAENVKEYFAKE00000

--- Session(profile_name='labprofile') (explicit profile) ---
access key used: AKIAPROFILEKEYFAKE
No real secrets anywhere

Every key in this file is a fake string this script wrote to a temporary file it created itself (AKIA...FAKE...). Nothing here is a real AWS credential, and nothing is read from your real ~/.aws/ directory — AWS_SHARED_CREDENTIALS_FILE and AWS_CONFIG_FILE are pointed at the temporary file instead.

Both results are real, and together they trace the full chain from the lesson:

  • Session() with no profile_name — boto3 has nothing more specific to go on than the environment, so AWS_ACCESS_KEY_ID wins over the labprofile credentials sitting in the shared file. This is "environment variables beat the shared credentials file" in the chain order.
  • Session(profile_name="labprofile") — cloudinventory.get_client(profile="labprofile", ...) calls exactly this. Even though the same environment variables are still set, the explicitly requested profile wins. This is "explicit session arguments outrank environment variables" — the highest step in the chain.

The practical takeaway: if platformops inventory-scan --profile some-profile seems to be using the wrong AWS account, check some-profile's section in ~/.aws/credentials first — an explicit --profile always wins over whatever is in your environment, on purpose.

2. Why pagination matters even with a small fixture​

The lab's pagination test creates 5 fake instances and forces PaginationConfig={"PageSize": 2}, then asserts list_instances() still returns all 5. That assertion alone proves the paginator loop works — but seeing the actual pages makes it concrete instead of taking the assertion on faith.

cat > /tmp/pagination_demo.py << 'PYEOF'
import boto3
from moto import mock_aws

from platformops.cloudinventory import list_instances


@mock_aws
def demo():
    client = boto3.client("ec2", region_name="us-east-1")
    for _ in range(5):
        client.run_instances(
            ImageId="ami-12345678", MinCount=1, MaxCount=1, InstanceType="t2.micro"
        )

    paginator = client.get_paginator("describe_instances")
    page_count = 0
    for page in paginator.paginate(PaginationConfig={"PageSize": 2}):
        page_count += 1
        found = sum(len(r["Instances"]) for r in page["Reservations"])
        print(f"page {page_count}: {found} instance(s), NextToken present: {'NextToken' in page}")
    print(f"total pages fetched: {page_count}")

    records = list_instances(client, page_size=2)
    print(f"list_instances() returned {len(records)} record(s) total (walked all {page_count} pages)")


demo()
PYEOF
uv run python /tmp/pagination_demo.py

Expected output

page 1: 2 instance(s), NextToken present: True
page 2: 2 instance(s), NextToken present: True
page 3: 1 instance(s), NextToken present: False
total pages fetched: 3
list_instances() returned 5 record(s) total (walked all 3 pages)

Five instances, page size 2, three real pages — NextToken is present on the first two pages (there is more to fetch) and absent on the third (nothing left). list_instances() returned all 5 only because it kept calling the paginator until NextToken stopped appearing. A version of this function that read paginator.paginate(...) and only used the first page's Reservations — a completely reasonable-looking mistake — would have printed 2, not 5, right here. That is the whole argument for always using a paginator: the bug is invisible until you specifically go looking for it, exactly like this.

This module deliberately does not re-test that botocore's paginator itself correctly requests page 2 after page 1 — that mechanism is botocore's own responsibility, covered by botocore's own test suite. What this proves is narrower and more relevant: list_instances() calls the paginator and consumes every page it yields, instead of stopping early.

3. What botocore's retry config actually retries​

cloudinventory.get_client() sets Config(retries={"max_attempts": 5, "mode": "standard"}). That config does not mean "retry every failure up to 5 times" — botocore only retries failures it considers transient. The exact list lives in botocore's own data, not in this project's code:

uv run python -c "
import json, botocore, os
path = os.path.join(os.path.dirname(botocore.__file__), 'data', '_retry.json')
data = json.load(open(path))
for name, rule in data['definitions'].items():
    print(name, '->', rule['applies_when'])
"

Expected output

throttling -> {'response': {'service_error_code': 'Throttling', 'http_status_code': 400}}
throttling_exception -> {'response': {'service_error_code': 'ThrottlingException', 'http_status_code': 400}}
throttled_exception -> {'response': {'service_error_code': 'ThrottledException', 'http_status_code': 400}}
request_throttled_exception -> {'response': {'service_error_code': 'RequestThrottledException', 'http_status_code': 400}}
too_many_requests -> {'response': {'http_status_code': 429}}
general_socket_errors -> {'socket_errors': ['GENERAL_CONNECTION_ERROR']}
general_server_error -> {'response': {'http_status_code': 500}}
bad_gateway -> {'response': {'http_status_code': 502}}
service_unavailable -> {'response': {'http_status_code': 503}}
gateway_timeout -> {'response': {'http_status_code': 504}}
limit_exceeded -> {'response': {'http_status_code': 509}}
throughput_exceeded -> {'response': {'service_error_code': 'ProvisionedThroughputExceededException', 'http_status_code': 400}}

This is the real, complete list botocore's "standard" retry mode checks a failed response against, straight from the copy of botocore this project's uv.lock pins. Every one of these is a signal that the request was probably fine and the infrastructure had a temporary problem: AWS is asking you to slow down (throttling, 429), or AWS's own servers had a transient failure (500/502/503/504), or the network connection itself dropped. Retrying makes sense for all of them — the same request, sent again a moment later, has a real chance of succeeding.

None of these match InvalidInstanceID.NotFound — the exact ClientError the lab triggered with instance_ids=["i-doesnotexist"]. That error is AWS telling you the request itself is wrong, not that the infrastructure had a hiccup. Retrying it five times would produce the same InvalidInstanceID.NotFound five times, wasting time and API calls for no benefit. botocore does not retry it, and cloudinventory.scan_inventory() should not either — it catches the ClientError once and reports it, the same way it would report any other permanent rejection like UnauthorizedOperation (a missing permission) or InvalidParameterValue (a malformed argument).

The rule this module's error handling is built on: a 4xx-style rejection of the request itself is not retried; a 5xx/429/throttling/connection-level signal is. scan_inventory()'s own except botocore.exceptions.ClientError block runs after botocore has already decided not to retry — by the time your code sees a ClientError at all, botocore has already concluded retrying would not help.

Where you will use this
  • Use it when: a script that takes --profile seems to be hitting the wrong AWS account — check the named profile's section in ~/.aws/credentials first; an explicit --profile always wins over environment variables, even ones you forgot were still exported in your shell.
  • Use it when: you are reviewing someone else's AWS automation code and see a raw describe_* or list_* call with no paginator — on a small test account it will look correct and pass review; on the real account it silently drops results past the first page.
  • Use it when: you are deciding whether to wrap an AWS SDK call in a retry loop of your own — check whether botocore's "standard" retry mode already covers the failure you are worried about (throttling, 5xx, connection errors) before adding a second layer of retries on top of one that already exists.
  • Use it when: an automated job fails on a ClientError and someone suggests "just retry it" — check whether the error is a permanent rejection (bad parameter, missing permission) instead of a transient one; retrying a permanent rejection wastes time and never succeeds.

Teardown​

cd ~/platformops
rm -f /tmp/credchain_demo.py /tmp/pagination_demo.py

No AWS state, real or faked, survives past these scripts' own runs — nothing else to clean up.
