Lab — Build PlatformOps v1.0: the Tested Automation Core

This lab does not add a single new command or a single new source file. Every change in this lab lands inside tests/. First you hand-write four new tests against real gaps in the existing suite — a parametrized rewrite of a repetitive validation test, a fixture that catches an unsafe subprocess call the moment it appears, an idempotency check for the config CLI, and an end-to-end check-security test that calls real grep instead of a mock. Then you hand a coding agent a precise list of the httpclient error paths nobody has tested yet, and review its diff against the same litmus test the lesson just taught you: delete the assert, and see if the test still passes.

You need ~/platformops from the M11 lab, already tagged v0.9, with uv run pytest -q passing.

cd ~/platformops
git log --oneline -1

Expected output

d905179 platformops v0.9 -- Local Operations Adapter

The commit hash will differ, but the message should name v0.9.

1. Replace four repetitive tests with one parametrized test​

Open tests/test_servicedef.py. It already has four tests that follow the exact same shape: take GOOD_EXAMPLE, change one field to a bad value, check that validate_service() rejects it at that field's location. Add import pytest at the top of the file, then delete these four tests -- test_an_aws_account_that_is_not_exactly_12_digits_is_rejected, test_an_environment_outside_dev_staging_prod_is_rejected, test_a_region_outside_the_allowed_list_is_rejected, and test_a_namespace_that_is_not_lowercase_dns_safe_is_rejected -- and replace all four with this one parametrized test:

tests/test_servicedef.py
import pytest

from platformops.servicedef import GOOD_EXAMPLE, ServiceDefinition, validate_service


@pytest.mark.parametrize(
    "field, bad_value",
    [
        ("aws_account", "12345"),
        ("environment", "production"),
        ("region", "ap-northeast-9"),
        ("kubernetes_namespace", "Checkout_API"),
    ],
)
def test_a_bad_field_value_is_rejected(field, bad_value):
    data = {**GOOD_EXAMPLE, field: bad_value}

    errors = validate_service(data)

    assert isinstance(errors, list)
    assert any(error["loc"] == (field,) for error in errors)

uv run pytest tests/test_servicedef.py -v still reports four separate pass/fail lines -- one per field, bad_value pair, each named in the output -- from this one function definition instead of four.

uv run pytest tests/test_servicedef.py -v

2. Catch an unsafe subprocess call with a fixture​

tests/test_local_ops.py already has test_git_status_never_uses_shell_true, a test that captures the exact arguments git_status() passes to subprocess.run() and checks two things: no shell=True, and a timeout is always present. docker_info() and container_list() have no equivalent test -- a regression in either one would slip past the whole suite today. Instead of copying that capture logic three times, write it once as a fixture.

Add import pytest at the top of tests/test_local_ops.py, then add this fixture near the top of the file, right after the _completed() helper:

tests/test_local_ops.py
import pytest


@pytest.fixture
def captured_subprocess_call(monkeypatch):
    """The stage crew: swaps subprocess.run for a spy that records exactly
    what it was called with, then hands back a clean, empty success result."""
    captured = {}

    def fake_run(args, **kwargs):
        captured["args"] = args
        captured["kwargs"] = kwargs
        return _completed(returncode=0, stdout="")

    monkeypatch.setattr("platformops.local_ops.subprocess.run", fake_run)
    return captured

Then add these two tests at the end of the file, after the scan_for_shell_true tests:

tests/test_local_ops.py
def test_docker_info_never_uses_shell_true_and_always_passes_a_timeout(
    captured_subprocess_call,
):
    docker_info()

    assert captured_subprocess_call["kwargs"].get("shell", False) is False
    assert "timeout" in captured_subprocess_call["kwargs"]


def test_container_list_never_uses_shell_true_and_always_passes_a_timeout(
    captured_subprocess_call,
):
    container_list()

    assert captured_subprocess_call["kwargs"].get("shell", False) is False
    assert "timeout" in captured_subprocess_call["kwargs"]

Any test in this file that names captured_subprocess_call as a parameter gets the same spy, ready to use, with no setup code of its own -- the exact division of labor the lesson's stage-crew analogy described.

3. Prove the config CLI is idempotent​

"Idempotent" means running the same operation twice produces the same result as running it once -- a property every operation this course has built so far has claimed informally, but never actually tested. Add this test to tests/test_config.py, near the other main() tests:

tests/test_config.py
def test_running_the_config_cli_twice_produces_the_same_resolved_file(tmp_path):
    service_file = tmp_path / "service.yaml"
    service_file.write_text(GOOD_YAML_TEXT)
    resolved_file = tmp_path / "service.resolved.yaml"

    main([str(service_file)])
    first_write = resolved_file.read_text()

    main([str(service_file)])
    second_write = resolved_file.read_text()

    assert first_write == second_write

This calls main() -- the same function test_cli_without_check_writes_the_resolved_config already calls once -- a second time against the same input, and checks that write_resolved_config's atomic write produces byte-identical output both times. A version of write_resolved_config that accidentally included something that changes between runs (a timestamp, a random ID) would fail this test immediately; the existing single-run tests would never catch it.

4. Test check-security end to end, with no mocking at all​

Every check-security test in tests/test_cli.py so far monkeypatches scan_for_shell_true -- useful for testing the CLI's exit-code and output wiring in isolation, but none of them actually exercise the real grep call underneath. Add these two tests after the existing check-security tests, using tmp_path as a real, disposable directory instead of a mock:

tests/test_cli.py
def test_check_security_end_to_end_against_a_real_directory_with_a_violation(tmp_path):
    bad_file = tmp_path / "bad.py"
    bad_file.write_text('import subprocess\nsubprocess.run("echo hi", shell=True)\n')

    result = runner.invoke(app, ["check-security", "--path", str(tmp_path)])

    assert result.exit_code == 1
    assert "shell=True" in result.stdout


def test_check_security_end_to_end_against_a_real_clean_directory(tmp_path):
    (tmp_path / "clean.py").write_text("print('hello')\n")

    result = runner.invoke(app, ["check-security", "--path", str(tmp_path)])

    assert result.exit_code == 0

Neither test monkeypatches anything -- scan_for_shell_true() runs a real grep against a real, tiny directory tmp_path creates and pytest deletes afterward. This is a deliberate contrast with every other test in this file: mocking is the right call when the real dependency is slow, remote, or unpredictable (a network request, a Docker daemon). grep against two files in a temp directory is none of those things, so calling it for real, inside the test, is both simpler and more honest about what is actually being checked.

Every test so far in this lab was aimed at a gap you already knew about -- a repetitive test, an untested subprocess call, an untested idempotency property. pytest-cov answers a different question: across the whole project, which lines has nothing ever executed at all.

Read the report's Missing column, not just the Cover percentage. Two different kinds of gaps tend to show up in this project, and they do not deserve the same reaction:

  • src/platformops/inventory/report.py -- 94%, two lines missed. The two uncovered lines (24 and 32) are both else: print(" (none)") branches inside print_report(). The function itself runs under test, but those two fallback branches never fire because the test data always has at least one item. This is a low-severity gap -- there is very little for a bug to hide in a bare print() call.
  • src/platformops/inventory/__main__.py -- 0%, three lines missed. This is the if __name__ == "__main__" entry point file. It has zero coverage because tests import the package through its public API, not by running the module as a script. That is normal for a __main__.py and not worth writing a test for.
  • Anything inside servicedef.py, config.py, httpclient.py, or local_ops.py that shows up as missing. These modules hold real decisions -- what counts as a valid region, what happens on a 429, whether shell=True ever sneaks in. A missing line here is exactly the kind of gap this lab exists to close, not to shrug off.

The percentage itself is worth noting once, then set aside -- the lesson's point about coverage holds here too: a high number tells you lines ran, not that the tests checking them would catch a real bug. Do not chase 100%. Use the Missing column to decide whether each specific gap is print_report()-shaped (low stakes) or validate_service()-shaped (worth a test), the same judgment call step 7 asks your coding agent to make explicit for httpclient.py.

7. Extend the suite: hand this to your coding agent​

Three real gaps remain in tests/test_httpclient.py, all in code paths nobody has tested yet:

  • check_health()'s third except branch -- the generic httpx.HTTPError catch, distinct from the already-tested httpx.TimeoutException and httpx.ConnectError branches.
  • check_health_async()'s httpx.TimeoutException branch and its generic httpx.HTTPError branch -- only its ConnectError branch is tested today.
  • The two small private helpers _sleep_backoff(attempt) and _next_page_url(response), both exercised only indirectly today (through the retry and pagination tests), never tested directly against their own specific contract.

Open your coding agent in the project folder:

claude

Paste this request exactly as written:

I'm working in this uv-managed Python project. src/platformops/httpclient.py has
check_health(url, *, timeout=DEFAULT_TIMEOUT, transport=None) -> HealthResult,
check_health_async(url, *, client, timeout=DEFAULT_TIMEOUT) -> HealthResult,
the private helper _sleep_backoff(attempt: int) -> None (delay =
BASE_BACKOFF_SECONDS * (2 ** attempt) + random.uniform(0,
BASE_BACKOFF_SECONDS), then time.sleep(delay)), and the private helper
_next_page_url(response: httpx.Response) -> str | None (parses the "next"
link out of an RFC 5988 Link header, returns None if there is no Link
header at all or no rel="next" entry in it). tests/test_httpclient.py
already covers check_health()'s httpx.TimeoutException and httpx.ConnectError
branches, and check_health_async()'s httpx.ConnectError branch, using
httpx.MockTransport and respx. Please add tests, without changing any
existing function's behavior:

1. A test for check_health()'s third except branch (plain httpx.HTTPError,
   not TimeoutException or ConnectError) -- use httpx.MockTransport with a
   handler that raises httpx.HTTPError("boom") (or a concrete subclass like
   httpx.ProtocolError) directly. Assert the function does not raise, and
   that the returned HealthResult has ok=False, status_code=None, and
   error containing the exception's message.

2. Two equivalent tests for check_health_async(): one for its
   httpx.TimeoutException branch (untested today), one for its generic
   httpx.HTTPError branch (also untested today). Follow the existing async
   test pattern in the file -- a plain sync test function wrapping the
   coroutine in asyncio.run().

3. A direct unit test for _sleep_backoff(attempt): monkeypatch
   platformops.httpclient.time.sleep to capture the duration it was called
   with instead of actually sleeping. Call _sleep_backoff(0) and
   _sleep_backoff(1) and assert two things: neither call actually sleeps
   (the test must run in a small fraction of a second, not several
   seconds), and the captured duration for attempt=1 is greater than
   BASE_BACKOFF_SECONDS * 1 (proving the delay grows with the attempt
   number, not just adds jitter to a flat base).

4. Three direct unit tests for _next_page_url(response), building an
   httpx.Response with a specific "link" header directly (no live request
   needed): one where the Link header is missing entirely (assert returns
   None), one where a Link header is present but contains only
   rel="prev" and rel="last" entries, no rel="next" (assert returns
   None), and one where a rel="next" entry is present among others
   (assert it returns exactly that URL, not the whole header).

5. Once you're done, re-read every test you just wrote and apply this
   rule: if you deleted this test's assert lines, would it still pass? If
   any of your new tests would still pass with its asserts removed, fix
   it before finishing -- do not leave it in. Tell me explicitly whether
   you found and fixed any such test, or whether all of them already
   passed this check.

6. Run `uv run ruff check .` and `uv run pytest -q` yourself before you
   finish, and tell me the result.

This spec names every existing function signature exactly as it is in the project, states the specific untested branch for each function, and asks for the same self-review and self-verification every agent step in this course has asked for.

8. Review what changed -- before you trust it​

git diff --stat v0.9 -- tests/test_httpclient.py

Expected output

 tests/test_httpclient.py | 120 +++++++++++++++++++++++++++++++++++++++

Run the checklist:

  • Does the check_health() test actually hit the third except branch, not one of the already-tested ones? Confirm it raises a plain httpx.HTTPError (or a subclass that is neither TimeoutException nor ConnectError) from the mock transport, not one of those two.
  • Do both new check_health_async() tests assert something specific about the result -- "timed out" in result.error for the timeout case, a non-empty error for the generic case -- or do they only check that the function returned something, without checking what?
  • Does the _sleep_backoff test actually avoid a real sleep? Time the test file: uv run pytest -q tests/test_httpclient.py -k sleep_backoff should finish in a small fraction of a second. If it takes several seconds, time.sleep was not actually mocked.
  • Do the three _next_page_url tests cover three genuinely different cases -- no header at all, a header with no rel="next" entry, and a header that does have one -- or do two of them accidentally test the same thing?
  • Apply the delete-the-assertion litmus test yourself, to at least two of the agent's new tests. Read each one, mentally remove every assert line, and ask: would this test still pass? If yes, it is not a real test yet -- ask the agent to fix it, or fix it yourself.
  • Compare the agent's own answer to step 5 against your own reading of the diff. An agent that reports "I found nothing to fix" should still get the same scrutiny as one that reports a fix -- trust your own read of the assertions over the agent's self-report either way.

The first major version

Every release so far has been v0.x -- a toolkit still finding its shape, module by module. v1.0 is different: it is the first release with a real, disciplined test suite behind it, not tests added informally alongside each feature. Semantic versioning reserves the jump from 0.x to 1.0 for exactly this kind of milestone -- the point where the project is stable and trustworthy enough to make that claim in its own version number.

Eleven rungs of the release ladder now.

Troubleshooting
  • pytest collects 0 tests, or ignores a test you just wrote. Confirm the file name starts with test_ and the function name starts with test_ -- both rules are non-negotiable, and a helper function like _completed() is deliberately invisible to pytest's discovery for exactly this reason.
  • A parametrized test only shows up as one line in pytest -q's summary, not four. Run with -v instead of -q to see each parametrized case listed individually by its actual input values -- -q's summary line only prints a single count, which can look like the parametrize did not take effect even when it did.
  • captured_subprocess_call says "fixture not found" in a test in a different file. A fixture defined inside one test_*.py file is only visible to tests in that same file, unless it is moved into a shared conftest.py -- this lab keeps it local to tests/test_local_ops.py on purpose, since only that file's tests need it.
  • The idempotency test in step 3 fails on the second main() call. Check that nothing in write_resolved_config() embeds something that changes between runs -- a timestamp, a random temp-file name that leaks into the written content instead of just the write mechanism. The atomic-write temp file itself is fine to differ; the content written to out_path must not.
  • The _sleep_backoff test in step 7 actually takes a few seconds to run. The mock target has to be "platformops.httpclient.time.sleep", not "time.sleep" directly -- the same imported-name trap the lesson's Common Pitfalls named for subprocess.run.
  • check-security's end-to-end test in step 4 fails with "grep: command not found" or similar. This lab assumes grep is on PATH, the same assumption check-security itself already makes in production -- it ships on every platform this course's lab environment supports.

Teardown​

This lab never starts a service, a container, or a background process -- every command it runs is a short-lived pytest, ruff, or grep invocation that exits on its own, and every file it touches outside tests/ (pyproject.toml, README.md) is meant to stay changed as part of this release.

cd ~
rm -rf platformops

Run this only if you want to remove the project and rebuild it from the checkpoint. Otherwise, keep ~/platformops; it carries forward into every later module.
