Testing Python Automation

Since M4 you have run uv run pytest -q after almost every change to platformops. Someone else wrote most of those tests for you, in the lab instructions, and you copied them in. This module changes that. From here on, you write the tests yourself, and you learn to read a test the way you already read a git diff — carefully, with a question in mind: does this test actually prove what it claims to prove?

The tools are not new. pytest, monkeypatch, tmp_path and respx have appeared in every lab since M6. What is new is treating testing as a skill in its own right, not something that happens quietly alongside "the real work." By the end of this module you can write a test with a fixture, a mock, and a parametrized set of inputs from scratch, and — just as important — you can look at a test someone else (including a coding agent) wrote and tell whether it is worth keeping.

1. Why test at all​

Picture a mountain road with a guardrail. Nobody thinks about that guardrail on a normal day — cars just drive past it, mile after mile, and it does nothing visible. The one day a driver drifts too close to the edge, the guardrail is the only thing standing between "a bad moment" and "a disaster." A test suite works the same way. On a normal day nobody notices it. The day someone — possibly you, possibly a coding agent — makes a change that quietly breaks something, the test suite is what stands between "a bad moment" and "a disaster nobody notices for a week."

Here is a realistic version of that disaster. Say a teammate edits servicedef.py to allow a new region value, and makes a small typo while doing it. Nothing crashes. ruff check passes — a typo in a string is not a syntax error. The change gets merged. From that day on, validate_service() silently accepts a service.yaml file that should have been rejected — a service pointed at a region nobody actually operates in. Nobody finds out until a deploy fails in production, days or weeks later, and someone has to work backward from a confusing failure to a one-character typo in a file they do not even remember touching. A test that says "an unknown region must be rejected" — one that already exists in tests/test_servicedef.py — would have failed on the teammate's own laptop, in under a second, the moment that change was made. That is the entire value of a test: it turns a mistake that takes a week to notice into a mistake that takes one second to notice.

2. How pytest finds and runs your tests​

pytest follows a small, fixed set of rules to find your tests, and knowing them saves confusion the first time a test you wrote does not run. A file is only searched if its name starts with test_ (or ends with _test.py) — helpers.py sitting next to test_config.py in the same folder is never touched, no matter what is inside it. Inside a file pytest does search, only a function whose name starts with test_ is treated as a test — a helper like _completed() in tests/test_local_ops.py, which every test in that file calls to build a fake CompletedProcess, is invisible to pytest's discovery, which is exactly what you want.

uv run pytest -q

A plain assert is the entire assertion language pytest needs — no self.assertEqual(a, b), no special assertion class to import, just a normal Python boolean expression:

def test_git_status_reports_clean_for_no_changes(monkeypatch):
    result = git_status("/some/repo")
    assert result.clean is True

When an assert fails, pytest does something a plain Python assert cannot do on its own: it shows you both sides of the comparison, not just the word "AssertionError." The Deep Dive covers exactly how pytest does this; for now, the practical result is that a failing test names the actual values involved, not just the fact that something, somewhere, was false.

3. Fixtures: the stage crew for your tests​

Think about a play. Before an actor walks on stage, someone has already placed the furniture, turned on the right lights, and handed the actor any prop they need. The actor's job is only to perform the scene, not to also drag furniture around first. In pytest, a fixture is that stage crew. It is a function, marked with @pytest.fixture, that sets up something a test needs before the test runs, and can clean it up again afterward. Your test function's job stays simple: perform the scene, using whatever the fixture already handed it.

tests/test_cli.py already has a fixture you have used without necessarily noticing it was one:

@pytest.fixture
def good_service_yaml(tmp_path):
    path = tmp_path / "service.yaml"
    path.write_text(GOOD_YAML_TEXT)
    return path


def test_validate_a_good_file_exits_0_and_reports_ok(good_service_yaml):
    result = runner.invoke(app, ["validate", str(good_service_yaml)])
    assert result.exit_code == 0

A test that names good_service_yaml as a parameter gets back whatever that fixture returns — a ready-made file on disk — without writing the setup itself. tmp_path is itself a fixture, one pytest ships for you: it hands your test a fresh, empty directory that exists only for the length of that one test, and pytest deletes it afterward. This is why the lab has never once created a real file inside ~/platformops just to test file-loading code — tmp_path gives every test its own private, disposable folder instead.

monkeypatch is also a fixture — the one you have used the most so far, in test_local_ops.py, test_config.py and test_httpclient.py. It temporarily replaces a function, an attribute, or an environment variable for the length of one test, then puts the original back automatically once the test ends — even if the test fails partway through:

def test_git_status_reports_error_when_git_is_missing(monkeypatch):
    def raise_not_found(*args, **kwargs):
        raise FileNotFoundError("git")

    monkeypatch.setattr("platformops.local_ops.subprocess.run", raise_not_found)

    result = git_status("/some/repo")
    assert "not installed" in result.error

That automatic put-back-afterward step is the whole reason monkeypatch exists instead of you reassigning subprocess.run yourself: a manual reassignment that never gets undone would leak into every test that runs after it in the same file, breaking tests that have nothing to do with the one you were writing.

4. Mocking: replacing the outside world with a scripted answer​

git_status() runs a real git process. check_health() makes a real network request. Neither of those things belongs inside a test. A test that actually ran git would depend on your machine having git installed, having a real repository at that path, and behaving identically every time — three things a test should never have to assume. A test that actually made an HTTP request would depend on a server being up, having a network connection, and not being rate-limited, and it would be slow — it could not test "what happens on a timeout" without an actual ten-second wait, every single time the test suite runs.

Mocking means replacing that outside dependency with a stand-in you fully control, one that returns exactly the answer your test wants to check a specific behavior against, instead of whatever the real world happens to return today. local_ops.py's tests mock subprocess.run itself with monkeypatch:

monkeypatch.setattr(
    "platformops.local_ops.subprocess.run",
    lambda *a, **k: _completed(returncode=128, stderr="fatal: not a git repository"),
)

httpclient.py's tests use two different mocking tools for two different jobs. httpx.MockTransport swaps out the network layer for a single scripted response — the right tool for check_health(), which makes exactly one request. respx intercepts by URL and can script a sequence of responses to the same URL — the right tool for get_repo_info(), whose retry logic needs to see a 429 on the first call and a 200 on the second:

route = respx.get("https://api.github.com/repos/httpx/httpx").mock(
    side_effect=[
        httpx.Response(429, headers={"Retry-After": "1"}),
        httpx.Response(200, json=REPO_PAYLOAD),
    ]
)

The rule that decides which tool to reach for is simple: mock at the boundary your own code actually calls. local_ops.py calls subprocess.run directly, so that is what gets mocked. httpclient.py calls out over the network through httpx, so httpx's own mocking tools get used. Mocking so much that the test no longer exercises your actual code is a common mistake — Section 6 comes back to it.

5. Parametrize: one test, many inputs​

tests/test_servicedef.py already has four tests that are almost identical to each other. Each one takes GOOD_EXAMPLE, changes exactly one field to a bad value, and checks that validate_service() rejects it:

def test_an_environment_outside_dev_staging_prod_is_rejected():
    data = {**GOOD_EXAMPLE, "environment": "production"}
    errors = validate_service(data)
    assert any(error["loc"] == ("environment",) for error in errors)


def test_a_region_outside_the_allowed_list_is_rejected():
    data = {**GOOD_EXAMPLE, "region": "ap-northeast-9"}
    errors = validate_service(data)
    assert any(error["loc"] == ("region",) for error in errors)

@pytest.mark.parametrize exists for exactly this shape: the same test logic, run once per set of inputs, instead of one hand-copied function per input.

@pytest.mark.parametrize(
    "field, bad_value",
    [
        ("environment", "production"),
        ("region", "ap-northeast-9"),
        ("kubernetes_namespace", "Checkout_API"),
        ("aws_account", "12345"),
    ],
)
def test_a_bad_field_value_is_rejected(field, bad_value):
    data = {**GOOD_EXAMPLE, field: bad_value}
    errors = validate_service(data)
    assert any(error["loc"] == (field,) for error in errors)

pytest -q reports each of those four cases as its own pass or fail, with the actual input values named in the output the moment one of them fails — you get the readability of four separate test names without maintaining four nearly-identical function bodies. The lab has you make exactly this change to real code, not a toy example.

parametrize is the right tool when the logic is identical and only the data changes — four different bad values hitting the same validation path, the way the example above does. It is the wrong tool the moment the test bodies genuinely differ in what they check, not just what data they feed in — forcing two different checks into one parametrized test to save a few lines makes the failure output harder to read, not easier, which defeats the entire point.

6. What makes a test meaningful​

A test that runs without crashing proves almost nothing on its own. The only thing that makes a test worth having is an assert that would actually fail if the code it is testing broke. There is a quick, reliable way to check this on any test you did not write yourself — including one a coding agent just handed you: delete the assertion, and see if the test still passes.

# Looks like a test. Proves almost nothing.
def test_check_health_handles_a_timeout():
    result = check_health("https://slow.example.com", transport=timeout_transport)
    # no assert at all, so this test can never fail, no matter what check_health() returns
# The same scenario, actually checked.
def test_check_health_reports_timeout_without_raising():
    result = check_health("https://slow.example.com", transport=timeout_transport)
    assert result.ok is False
    assert "timed out" in result.error

The first version runs, prints green, and counts toward "tests passing," while proving nothing about whether check_health() actually handles a timeout correctly. Delete the assert lines from the second version and it passes trivially too — which is exactly the signal that tells you the assert lines were the only part of the test doing real work. A coverage report can be just as misleading: "100% coverage" means every line of code ran during the test suite — it says nothing about whether any test checked that the line did the right thing. A test that calls a function and asserts nothing about the result can still count as "covering" every line inside that function. The Deep Dive shows this concretely, with a function that reaches 100% line coverage from a test that would not catch an actual bug in it.

Common pitfalls
  • A test with no assert at all, or an assert that can never fail (assert True, assert result is not None on a value that is never None in any real code path). Run the delete-the-assertion check on it: if removing the assert changes nothing about whether the test passes, the assert was not testing anything to begin with.
  • Mocking so much of a function that the test only checks that a mock was called, never what the function actually did with the result. A test for check_health() that only asserts mock_client.get.assert_called_once() never confirms the function correctly turned a 503 into ok=False — the one thing that function actually exists to do.
  • Patching the wrong target. monkeypatch.setattr("subprocess.run", ...) does nothing useful here — local_ops.py already imported subprocess.run into its own namespace, so the patch has to target "platformops.local_ops.subprocess.run" to actually take effect. The M11 lesson named this trap for subprocess specifically; it applies to patching any imported name, in any module.
  • Forcing unrelated cases into one parametrize block to look tidy. If the test body needs an if statement to handle different parameter combinations differently, the cases were not actually testing the same logic — write them as separate tests instead.
  • Chasing a coverage percentage instead of a behavior. A test written purely to make a coverage number go up, with no real assertion behind it, makes the test suite slower and the coverage report less trustworthy at the same time — worse than not writing the test at all.
  • Treating a passing test suite as proof nothing needs a human's judgment. A test suite catches what it was written to catch. A test that nobody wrote for the actual bug in front of you stays green while that bug ships — reading a coding agent's diff, and its tests, is still your job.
