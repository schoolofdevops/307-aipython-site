Deep Dive — What pytest Actually Does

The lab had you write tests using rules stated as fact: a file named test_*.py, a function named test_*, a fixture named as a parameter, a plain assert. This page opens up how pytest actually implements each of those rules -- how it decides which files and functions are tests at all, how it turns a fixture's name in a parameter list into a real function call, why a failing assert can show you the exact values involved instead of just "AssertionError," and what a coverage report is actually measuring underneath the percentage it prints. You will use this the day a test you wrote mysteriously never runs, the day you have to explain to a teammate why "100% coverage" did not catch a real bug, or the day you need to decide whether a fixture belongs in one file or in a shared conftest.py.

Where this picks up

You need ~/platformops at v1.0 from the lab. Every command below runs a short, disposable script or test file in its own scratch folder -- none of them touch your real tests/ folder or your project's git history.

mkdir -p ~/platformops/dd-scratch && cd ~/platformops/dd-scratch

Re-running any command on this page is safe.

1 — Test discovery: how pytest decides what counts as a test​

Think of pytest's collection step as a mail sorting room with one very specific rule painted on the wall: only envelopes with a label matching an exact pattern get opened at all -- every other envelope, no matter what is inside it, stays sealed and goes straight into the "not mail" bin without a second look. pytest's default patterns are test_*.py or *_test.py for files, and Test* (a class, only if it has no __init__ method) or test_* (a function) for what is inside one of those files. Nothing else is ever imported as a test, no matter how it is named otherwise.

dd-scratch/collection_demo.py
def test_this_one_gets_collected():
    assert 1 + 1 == 2


def helper_this_one_does_not():
    assert 1 + 1 == 2  # never runs -- the name does not start with test_


class TestGroupThisGetsCollected:
    def test_inside_a_test_class(self):
        assert True


class HelperClassThisDoesNot:
    def test_inside_a_non_test_class(self):
        assert True  # never runs -- the class name does not start with Test
uv run pytest dd-scratch/collection_demo.py --collect-only -q

Expected output

dd-scratch/collection_demo.py::test_this_one_gets_collected
dd-scratch/collection_demo.py::TestGroupThisGetsCollected::test_inside_a_test_class

2 tests collected in 0.01s

helper_this_one_does_not and everything inside HelperClassThisDoesNot never appear in that list -- pytest's collector never even considers them "tests" to evaluate, the same way the mail room never opens an envelope with the wrong label on it. This is the mechanism behind a bug that trips up almost everyone at least once: a test function that got renamed, or copy-pasted with a typo in the test_ prefix, does not fail -- it silently stops existing as far as pytest -q's pass/fail count is concerned, and a shrinking or unchanged test count is the only clue something is wrong.

2 — Fixture injection: how a parameter name becomes a function call​

A test function that names tmp_path or monkeypatch (or captured_subprocess_call from the lab) as a parameter never imports it. pytest reads your test function's parameter list the way a program reads its own source code -- through introspection, the same technique inspect.signature() gives you directly in plain Python -- and for every parameter name it does not already know how to provide, it searches a registry of every @pytest.fixture-decorated function currently visible: first in the same file, then in any conftest.py in that directory or a parent directory. A name that matches gets called, and its return value becomes the argument your test receives. A name that matches nothing produces the "fixture not found" error you may have already hit in the lab if a fixture defined in one file was referenced from a test in a different one.

A yield-based fixture splits into two halves: everything before yield runs as setup, the yielded value is what the test receives, and everything after yield runs as teardown -- and pytest guarantees the teardown half runs even if the test itself fails.

dd-scratch/fixture_order_demo.py
import pytest


@pytest.fixture
def traced_resource():
    print("\nSETUP: resource created")
    yield "a-resource"
    print("TEARDOWN: resource cleaned up")


def test_that_passes(traced_resource):
    print(f"TEST BODY: using {traced_resource}")
    assert True


def test_that_fails(traced_resource):
    print(f"TEST BODY: using {traced_resource}")
    assert False, "deliberate failure to prove teardown still runs"
uv run pytest dd-scratch/fixture_order_demo.py -s -v

The -s flag disables pytest's own output capturing so the print() lines are visible in order. This is exactly why tmp_path never leaves a stray directory behind even when a test using it fails partway through: the fixture's own teardown step runs regardless of how the test body ended.

3 — Assertion rewriting: how a plain assert gets a detailed failure message​

A plain Python assert expr, message raises AssertionError(message) if message was given, or a bare AssertionError with no detail at all if it was not. Run a failing assert [1, 2, 3] == [1, 2, 4] directly with plain Python, and you get nothing about which index differed:

python3 -c "assert [1, 2, 3] == [1, 2, 4]"

Expected output

Traceback (most recent call last):
  File "<string>", line 1, in <module>
    assert [1, 2, 3] == [1, 2, 4]
           ^^^^^^^^^^^^^^^^^^^^^^
AssertionError

pytest shows you far more detail than that on the exact same expression, because of something called assertion rewriting: before a test file is ever imported, pytest's own import hook parses it into an AST (an Abstract Syntax Tree -- the same tree-shaped representation of your source code Python's own compiler builds internally) and replaces every plain assert statement with an expanded version that evaluates each sub-expression separately and remembers its value, purely so it can build a detailed message if the assertion fails. Your source file on disk never changes -- this rewriting happens only to the copy pytest imports into memory for the run.

dd-scratch/assertion_demo.py
def test_list_equality_with_a_real_difference():
    assert [1, 2, 3] == [1, 2, 4]
echo "-- with rewriting (pytest's default) --"
uv run pytest dd-scratch/assertion_demo.py -v
echo
echo "-- with rewriting disabled --"
uv run pytest dd-scratch/assertion_demo.py -v --assert=plain

With rewriting on, the failure shows exactly which index differs and what each side's value was. With --assert=plain, pytest steps out of the way and lets the bare AssertionError through with no detail -- the same experience as running the assertion in plain Python. --assert=plain exists mainly for debugging pytest itself; every test you have written in this course, in every module, has been relying on rewriting being on by default to make its own failures readable.

4 — Coverage mechanics: what a coverage percentage actually measures​

The lab had you install pytest-cov and run pytest --cov=platformops --cov-report=term-missing against the real project. pytest-cov is not a separate coverage engine of its own -- it is a thin pytest plugin around coverage.py, the same library behind most CI coverage badges. Both work the same way underneath: installing a trace function -- a hook Python's interpreter calls on every line it executes -- for the duration of the test run. Every time execution reaches a line inside a file coverage is watching, that line's file and number get recorded as "executed." When the tests finish, coverage compares the set of lines recorded as executed against the set of lines that exist in the file, and the percentage it reports is exactly that ratio -- nothing more. The two scratch examples below use standalone coverage commands instead of pytest --cov only so each one stays a self-contained, two-line demonstration -- the underlying mechanism is identical to what you already ran against the whole platformops package in the lab.

That last part is the trap. A function with no branching at all reaches 100% coverage the moment a test calls it even once, whether or not the test checks anything about what came back:

dd-scratch/is_healthy.py
def is_healthy(status_code: int) -> bool:
    return status_code < 500
dd-scratch/test_is_healthy.py
from is_healthy import is_healthy


def test_is_healthy_runs_without_crashing():
    is_healthy(200)
    # no assert on the return value at all -- this test proves the function
    # did not crash, and nothing else
uv run --with coverage coverage run -m pytest dd-scratch/test_is_healthy.py -q
uv run --with coverage coverage report -m --include="*is_healthy.py"

Expected output

.                                                                        [100%]
1 passed in 0.01s
Name                            Stmts   Miss  Cover   Missing
-------------------------------------------------------------
dd-scratch/is_healthy.py            2      0   100%
dd-scratch/test_is_healthy.py       3      0   100%
-------------------------------------------------------------
TOTAL                               5      0   100%

The report shows 100% -- both lines in is_healthy.py genuinely executed. But test_is_healthy_runs_without_crashing never asserts what is_healthy(200) actually returned. Apply the lesson's delete-the-assertion litmus test and there is nothing to delete -- this test was never checking a result in the first place. A version of is_healthy that returned True for every input, a genuine bug, would pass this exact test and still show 100% coverage, because "the line ran" and "the line did the right thing" are two different questions, and only a real assertion answers the second one.

A function with branching shows a different, more familiar kind of gap -- one line coverage already catches on its own, no special mode required:

dd-scratch/branchy.py
def classify_latency(latency_ms: float) -> str:
    if latency_ms < 200:
        return "fast"
    else:
        return "slow"  # untested below: this line's execution count will be 0
dd-scratch/test_branchy.py
from branchy import classify_latency


def test_classify_latency_labels_a_fast_response():
    assert classify_latency(50) == "fast"
uv run --with coverage coverage run -m pytest dd-scratch/test_branchy.py -q
uv run --with coverage coverage report -m --include="*branchy.py"

Expected output

.                                                                        [100%]
1 passed in 0.02s
Name                         Stmts   Miss  Cover   Missing
----------------------------------------------------------
dd-scratch/branchy.py            4      1    75%   5
dd-scratch/test_branchy.py       3      0   100%
----------------------------------------------------------
TOTAL                            7      1    86%

This time the report is genuinely below 100%, and the Missing column names the exact line number of return "slow" -- that line's execution count stayed at zero because no test in this run ever called classify_latency with a value of 200 or more. Unlike the is_healthy example, this gap needs no special coverage mode to surface: an entire unexecuted line is exactly what plain line coverage is built to catch.

coverage run --branch (branch coverage, instead of the default line coverage) goes one step further -- it additionally records which direction each if took, not just whether the line containing it executed. This matters most for an if with no else at all, where the "condition was false" path corresponds to no line of its own for plain line coverage to ever mark as missing:

uv run --with coverage coverage run --branch -m pytest dd-scratch/test_branchy.py -q
uv run --with coverage coverage report -m --include="*branchy.py"

Expected output

.                                                                        [100%]
1 passed in 0.01s
Name                         Stmts   Miss Branch BrPart  Cover   Missing
------------------------------------------------------------------------
dd-scratch/branchy.py            4      1      2      1    67%   5
dd-scratch/test_branchy.py       3      0      0      0   100%
------------------------------------------------------------------------
TOTAL                            7      1      2      1    78%

Either mode catches classify_latency's gap here, since it already has a line of its own to miss. Neither mode, in either example, can catch the deeper problem is_healthy demonstrated: a test that runs every line (or takes every branch) but asserts nothing about the result. No coverage tool, of any kind, can measure whether an assertion was correct -- that is a judgment only a human (or, on a first pass, a careful reading of a coding agent's diff) can make.

Teardown​

cd ~/platformops
rm -rf dd-scratch

This removes only the scratch folder this page created. Your real tests/, pyproject.toml and the rest of ~/platformops are untouched.

Where you will use this
  • A test file or function that does not match pytest's naming pattern is silently never run, not flagged as an error. Use it when: a test count looks wrong after a rename or a copy-paste -- run pytest --collect-only -q first, before assuming the code itself is broken.
  • A fixture is resolved by matching a test's parameter name against a registry built from @pytest.fixture functions in the same file and any conftest.py above it. Use it when: a fixture used by tests in more than one file needs to move into a shared conftest.py instead of staying duplicated or local to one file.
  • pytest rewrites the assert statements in your test files at import time to produce detailed failure messages -- your source file on disk never changes. Use it when: a teammate asks why a failing test shows a detailed diff instead of a bare AssertionError, or when debugging a plugin that seems to interact strangely with assertions (--assert=plain is the tool to isolate whether rewriting itself is involved).
  • "100% coverage" means every line ran during the test suite -- it says nothing about whether any assertion checked the right thing, and even branch coverage only proves both paths were reached, not that either one was verified correctly. Use it when: reviewing a coding agent's tests (or your own) that report high coverage -- read the actual assertions before trusting the percentage, the same delete-the-assertion litmus test the lesson introduced.
