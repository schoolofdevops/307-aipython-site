Python as the Deterministic Layer Inside Skills

Module 17 gave service-readiness-review a good shape: a clear trigger, tight steps, an agent-neutral core. But look closely at Step 3 of that skill. It says: run platformops validate <path> --json, then read the errors list in the output and decide what to report. That last part, "read the output and decide," is a model doing the thinking, every single time the skill runs. This module fixes that.

1. The thermometer analogy​

Imagine a kitchen runbook step that says: "check if the oven is hot enough before you put the dish in." Different cooks read that step differently. One opens the door and holds a hand near the heat. Another watches how fast the oven light cycles. A third just guesses based on how long it has been preheating. All three are reasonable ways to answer the same question. And all three can give a different answer on the same oven.

Now put a thermometer in the oven. The step becomes: "check if the thermometer reads 220°C or higher." Every cook who reads that thermometer gets the exact same number. The judgment call is gone. The step is no longer "figure out if it's hot enough." It is "read the number."

A skill step that says "run the validator and read the JSON output" is the first kind of step. The coding agent is the cook, and the JSON is the oven. It has to look at a list of error objects and decide how to phrase what it found. Ask the same agent to review the same file twice, or ask two different agents to review it, and you can get two reports worded differently, or one report that misses a detail the other one caught. A Python script that reads the JSON and prints one fixed report is the thermometer. Same input, same output, every time.

Why this matters at work

Imagine a service-readiness check that runs automatically on every pull request, posted as a comment by a bot. If the report's wording changes slightly every run, even when the underlying file has not changed, nobody trusts the comment. They start re-checking the file by hand anyway, which defeats the point of automating the check. A fixed-format report, worded the same way every time, is what makes an automated check something a team can actually rely on without double-checking it.

2. Deterministic vs non-deterministic steps​

Not every step in a skill needs to become a script. A step like "read the file's name field and mention it in your greeting" is fine left to the agent. There is no single correct wording for a greeting, so there is nothing to make deterministic. The question is not "should I script everything." It is "does this step need one fixed, repeatable answer."

Three signals tell you a step should be scripted:

  1. The step parses structured output. Anything that reads JSON, YAML, or a table and pulls specific fields out of it is a parsing job. A model can do it, but a script does it the same way every time, and does it without spending any reasoning effort.
  2. The step needs exact formatting. If the report must always have the same fields, in the same order, with the same labels, so that something else (a bot, a dashboard, a teammate skimming quickly) can rely on its shape, that is a formatting contract, and a script is the only way to guarantee it holds.
  3. The step makes a pass/fail decision. "Is this ready to ship?" should have one correct answer given the same input. If the rule for deciding that answer can be written down as code, write it as code. Do not leave a yes/no call up to a model's mood on a given run.

If a step shows even one of these three signals, script it. If it shows none of them (it is open-ended, there is no fixed correct answer, judgment is genuinely part of the job), leave it to the agent.

3. The thin-script pattern​

Here is the trap: once you decide to script a step, it is tempting to write the entire validation logic again inside the script, from scratch. Do not do that. Module 5 already built validate_service() in platformops.servicedef, a function with its own tests, already proven correct. A script that reimplements those same rules creates a second copy of the logic, and the two copies will drift apart the first time someone fixes a bug in only one of them.

The thin-script pattern avoids that trap. The script's only job is:

  1. Import the real logic from the tested package (validate_service, load_yaml_dict).
  2. Call it. Do not reimplement it.
  3. Format the result as one fixed-shape JSON report.
  4. Exit with a code that tells the caller, without any parsing, whether it passed.

Think of the script as a translator standing between the tested package and the agent, not as a second brain that reasons about validity on its own. It never repeats a rule that already lives in servicedef.py or config.py. It only calls those rules and writes down the answer in a fixed format.

4. The exit-code contract​

A script that only prints text still leaves the agent guessing. Did it pass or fail? An exit code answers that question without any parsing at all. This module's script uses three:

Exit codeMeaningWhat the skill does next
0The file is ready to shipReport PASS, relay the recommendation: "ready to ship" field
1The file was read, but validation or an observability check failedReport FAIL, relay the problems list
2The file could not even be read (missing, unreadable, not valid YAML)Stop — there is nothing to validate yet

The skill branches on this number, not on scanning the printed text for words like "PASS" or "error." An exit code is a contract a shell, a CI pipeline, or an agent can check in one step, if exit_code == 0, with no risk of a phrase like "not a fail" being misread as a pass.

5. Updating the skill​

Once the script exists, the skill's job changes. Before, Step 3 told the agent to run the validator and Steps 4-6 told it how to read and format what came back. Three steps of judgment. After, one step runs the script, and the rest of the skill tells the agent to relay the script's report instead of re-deriving it. The agent's role shifts from interpreting a raw result to relaying a finished one.

This is a small change in the SKILL.md file, but it removes every place the old skill asked the agent to make a judgment call about wording. The report the skill hands back is now exactly the report the script printed. Nothing added, nothing paraphrased.

Common pitfalls​

  • Writing a fat script that duplicates validation logic. If a script contains its own if not name: fail() checks instead of calling validate_service(), it is a second copy of rules that already exist and are already tested. The two copies will disagree eventually. Script it thin, always import the real check.
  • Printing unstructured text instead of JSON. A script that prints "Looks okay to me" to stdout still leaves the agent guessing at the shape of the answer. Print a fixed JSON object with the same keys every run, so anything reading the output (agent, bot, or another script) can rely on the shape.
  • Forgetting exit codes, or using only 0 and 1. A script that always exits 0 and expects the caller to read stdout to find out what happened defeats the purpose of scripting the step. This module's script uses three distinct codes because "the file is bad" and "the file is missing" are different problems that need different next steps.
  • A script that never imports anything from the package. If scripts/review-service.py does not have an import line pulling from platformops, that is the clearest sign the script has become a second implementation instead of a thin adapter over the first one.
