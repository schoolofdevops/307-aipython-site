Deep Dive — Measuring Determinism Instead of Assuming It

The lab claimed that scripting a step removes wording variance, that an exit code is a cleaner contract than scanning text, that the words a script's Steps section used to carry move into the script itself rather than disappearing, that a fixed assert is a real line between a scripted step and an agent step, and that a thin script stays correct only because it imports the real validation logic. This page turns all five claims into commands you can run and numbers you can read, the same way Module 17's Deep Dive measured a skill instead of guessing about it.

Where this picks up

You need ~/platformops at v1.3.0, with scripts/review-service.py and the updated .claude/skills/service-readiness-review/SKILL.md in place from the lab. Every example on this page runs in its own scratch copy -- nothing here touches your real project:

rm -rf /tmp/m18-dd-scratch
cp -r ~/platformops /tmp/m18-dd-scratch
cd /tmp/m18-dd-scratch
rm -rf .venv
uv sync
cp service-bad.yaml test-service.yaml

The rm -rf .venv && uv sync step is needed because copying a uv-managed virtual environment breaks the internal symlinks that point at your Python install. Removing the copy and rebuilding it takes a few seconds and gives you a working environment. scripts/review-service.py came along with the copy, unchanged -- this page only runs it.

Re-running any command on this page is safe.

1 — Measuring output variance, not assuming it​

The lesson's thermometer claim is that a script gives the same reading every time, where an agent interpreting raw output can give a different one on every run. Test the script's half of that claim first -- it should be boring:

cd /tmp/m18-dd-scratch
uv run python scripts/review-service.py test-service.yaml > /tmp/m18-run1.json
uv run python scripts/review-service.py test-service.yaml > /tmp/m18-run2.json
uv run python scripts/review-service.py test-service.yaml > /tmp/m18-run3.json
cmp /tmp/m18-run1.json /tmp/m18-run2.json
echo "run 1 vs run 2: $?"
cmp /tmp/m18-run2.json /tmp/m18-run3.json
echo "run 2 vs run 3: $?"

Expected output

run 1 vs run 2: 0
run 2 vs run 3: 0

cmp prints nothing when two files match and exits 0 -- a much harder result to misread than scanning for a "no differences" message, and worth using in place of a plain diff if your shell has anything (an alias, a wrapper, a hook) sitting in front of diff you have not personally verified -- a wrapper that summarizes instead of comparing byte for byte can report two different files as identical without you ever finding out. Three separate processes, three separate runs, byte-for-byte the same output both times. Nothing about that should be surprising -- review() has no randomness and no hidden state, so the same file in always produces the same report out.

Now test the other half of the claim: what an agent produces when it is asked to run the validator directly and write its own interpretation of the result, the way Module 17's skill used to work, instead of running this module's script. Run the same prompt against the same file three separate times:

cd /tmp/m18-dd-scratch
for i in 1 2 3; do
  claude -p "Run 'uv run platformops validate test-service.yaml --json' and then write a short readiness report interpreting the errors list for a teammate: state PASS or FAIL, list the problems found, and give a one-line recommendation." --permission-mode bypassPermissions
  echo "--- end of run $i ---"
done

Expected output (three real runs, same prompt, same file)

Run 1
Service Readiness Review — test-service.yaml

- Validation: **FAIL**
- Problems found: `deployment_name` — missing (Field required)
- Recommendation: fix required before shipping. Add `deployment_name` field, re-run validate.
Run 2
Service Readiness Review -- test-service.yaml

- Validation: FAIL
- Problems found: deployment_name: Field required
- Observability: dashboard_url set (yes), alert_channel set (yes)
- Namespace checked: checkout
- Recommendation: fix required before shipping
Run 3
## Readiness Report — checkout-api

**Verdict: FAIL**

**Problems found:**
- `deployment_name` field missing. Required, not present.

**Recommendation:** add `deployment_name` field, re-validate.

Your own three runs will read differently again -- that is the point, not a flaw in the demo. Look at the shape, not the wording: Run 1 uses a "Recommendation" line with an inline fix suggestion the prompt never asked for. Run 2 happens to land close to this module's Output format (it likely picked that shape up from files already in the project). Run 3 drops the - Validation: line format entirely and uses a "Verdict" heading instead. All three correctly identify the missing deployment_name field -- the underlying validation is deterministic, as Section 1's script runs already proved. What varies is only the layer above it: how each run chose to phrase and format a finding that was never in question. That layer is exactly what scripts/review-service.py removes, and Module 17's skill used to require.

2 — The exit-code contract, mapped to real files​

The lesson's table maps three exit codes to three skill-step branches. Prove the mapping holds against three real files -- a good one, one that fails validation, and one that does not exist:

cd /tmp/m18-dd-scratch
for f in service.yaml service-bad.yaml service-does-not-exist.yaml; do
  uv run python scripts/review-service.py "$f" > /dev/null 2>&1
  echo "$f -> exit $?"
done

Expected output

service.yaml -> exit 0
service-bad.yaml -> exit 1
service-does-not-exist.yaml -> exit 2

Every branch in that diagram is one if on a single integer -- no text to scan, no phrase to misread. Compare this to a script that only used exit codes 0 and 1: a caller checking if exit_code != 0 would treat "the file is missing" and "the file has a bad field" as the same problem, when Step 5 of the skill needs to know which one happened before it can decide whether to even look at a problems list that, in the missing-file case, was never produced by a real validation pass.

3 — Where the words went​

The lesson's claim is that scripting a step does not delete the reasoning it used to take -- it moves that reasoning somewhere it only has to be written once. Check the actual word counts before and after Module 17:

cd /tmp/m18-dd-scratch
wc -w .claude/skills/service-readiness-review/SKILL.md

Expected output

     832 .claude/skills/service-readiness-review/SKILL.md

The whole file is about the same length as Module 17's version (833 words) -- the total did not shrink much, because Failure handling grew more explicit about the exit-code contract at the same time Steps got shorter. The more telling number is the Steps section alone, the part that used to tell the agent how to interpret raw output:

cd /tmp/m18-dd-scratch
sed -n '/^## Steps/,/^## Tools/p' .claude/skills/service-readiness-review/SKILL.md | wc -w

Expected output

     192

Module 17's Steps section, over the same range, ran 225 words across seven steps that included reading a raw errors list and deciding how to phrase a report. This module's Steps section covers the same procedure -- confirm the file, run something, branch on the result, report it -- in 192 words across five steps, because three of Module 17's steps (read the raw JSON, decide what it means, write a sentence about it) collapsed into "run the script and relay its fields." Now look at where that judgment actually lives now:

cd /tmp/m18-dd-scratch
wc -w scripts/review-service.py

Expected output

     470 scripts/review-service.py

The script is 470 words, counting the docstring and every line of code. That is not free -- it is the cost of making the deterministic part of the review repeatable. The difference is where those words live: in a file with tests that fail loudly the moment its behavior changes, instead of in a markdown instruction an agent re-reads and re-interprets on every single run.

4 — The testing boundary, checked mechanically​

The lesson's rule for deciding whether a step belongs in a script: could you write assert output == expected for it? Count how many places tests/test_review_service.py actually does exactly that:

cd /tmp/m18-dd-scratch
grep -c "^def test_" tests/test_review_service.py

Expected output

6
cd /tmp/m18-dd-scratch
grep -c "    assert " tests/test_review_service.py

Expected output

21

Six test functions, twenty-one assert statements between them -- one for every field the script's review() function returns, across the pass path, the schema-failure path, the empty-observability path, and the missing-file path. Every one of those assertions has the exact shape the lesson's rule describes: given this input, the output must equal this value, every time.

Now look for the equivalent test file for the skill's own judgment calls -- Step 1 ("confirm the target file matches service*.yaml") and Step 5 ("if the exit code was 2, report the single entry... and stop"):

cd /tmp/m18-dd-scratch
find tests -iname '*skill*'

Expected output

<no output -- no matching file>

Nothing. There is no test_service_readiness_review.py, and there should not be one written the same way test_review_service.py is written. Steps 1 and 5 are not pure functions of an input you could assert against in the same mechanical sense -- "confirm the target file matches service*.yaml" still calls for the agent to read a request and decide whether a file qualifies, not to run a fixed function against a fixed value. That is the boundary the lesson draws, made checkable: one file has an assert for every claim it makes; the other does not, because its claims are not the kind a fixed assertion can cover.

5 — The fat-script anti-pattern, caught in the act​

The lesson warns against a script that reimplements validation instead of importing it. Build one deliberately and watch it disagree with the real validator on a file the real one correctly rejects.

First, a file with one deliberate problem the schema catches -- an invalid Kubernetes namespace (uppercase letters and an underscore, which Kubernetes itself would reject):

cd /tmp/m18-dd-scratch
cat > service-bad-namespace.yaml << 'EOF'
name: checkout-api
repository: github.com/example/checkout-api
environment: prod
team_owner: payments-team
kubernetes_namespace: Checkout_API
deployment_name: checkout-api
aws_account: "111122223333"
region: us-east-1
observability:
  dashboard_url: https://grafana.example.com/d/checkout-api
  alert_channel: "#checkout-alerts"
EOF

Now a small "fat" script that checks required fields are present, but -- like a script written in a hurry, copying the field list instead of the rule that goes with each field -- never reimplements the pattern check validate_service() already runs on kubernetes_namespace:

cd /tmp/m18-dd-scratch
cat > fat-review-service.py << 'EOF'
#!/usr/bin/env python3
"""Anti-pattern demo: a script that reimplements validation instead of importing it.

Do not copy this pattern -- see the Deep Dive for what goes wrong.
"""

import json
import sys
from pathlib import Path

import yaml

REQUIRED_FIELDS = [
    "name",
    "repository",
    "environment",
    "team_owner",
    "kubernetes_namespace",
    "deployment_name",
    "aws_account",
    "region",
]


def review(path: Path) -> tuple[dict, int]:
    data = yaml.safe_load(path.read_text())
    problems = [field for field in REQUIRED_FIELDS if not data.get(field)]
    if problems:
        return {"validation": "FAIL", "problems": problems}, 1
    return {"validation": "PASS", "problems": []}, 0


if __name__ == "__main__":
    report, exit_code = review(Path(sys.argv[1]))
    print(json.dumps(report, indent=2))
    sys.exit(exit_code)
EOF

Run both scripts against the same file:

cd /tmp/m18-dd-scratch
echo "--- real thin script (imports validate_service) ---"
uv run python scripts/review-service.py service-bad-namespace.yaml
echo "exit=$?"
echo
echo "--- fat script (reimplements its own checks) ---"
uv run python fat-review-service.py service-bad-namespace.yaml
echo "exit=$?"

Expected output

--- real thin script (imports validate_service) ---
{
  "file": "service-bad-namespace.yaml",
  "validation": "FAIL",
  "problems": [
    "kubernetes_namespace: String should match pattern '^[a-z0-9]([-a-z0-9]*[a-z0-9])?$'"
  ],
  "observability": {
    "dashboard_url_set": true,
    "alert_channel_set": true
  },
  "namespace": "Checkout_API",
  "recommendation": "fix required before shipping"
}
exit=1

--- fat script (reimplements its own checks) ---
{
  "validation": "PASS",
  "problems": []
}
exit=0

Same file, opposite verdicts. The real script imports validate_service(), which runs kubernetes_namespace's pattern check -- the same check tests/test_servicedef.py has covered since Module 5. The fat script only checks that each required field is present, not that its value is valid, because that rule was never imported -- it would have had to be retyped by hand, and it was not. Checkout_API sails through the fat script's checks and comes back PASS, which is exactly the kind of value Kubernetes itself would reject at deploy time.

This is the drift the lesson warns about, not a hypothetical: the moment a script's checks are retyped instead of imported, the two copies can answer the same question differently, and the test suite that covers validate_service() says nothing about whether the fat script agrees with it -- there is no test for the fat script's own REQUIRED_FIELDS logic, because it was never meant to exist in the first place. scripts/review-service.py's two import lines are what this module actually ships to prevent this.

Teardown​

rm -rf /tmp/m18-dd-scratch /tmp/m18-run1.json /tmp/m18-run2.json /tmp/m18-run3.json

This removes only this page's scratch copy and its temporary output files. Nothing on this page touched ~/platformops -- scripts/review-service.py, the updated .claude/skills/service-readiness-review/SKILL.md, and the v1.3.0 version bump from the lab are the only real additions this module makes to your project, and they are already there before this page starts.

Where you will use this
  • A script's own output is deterministic by construction -- three runs, three identical files -- but that says nothing about what an agent does with raw output it still has to interpret. Use it when: you are deciding whether a skill step already "is" deterministic just because the command it runs is -- run the agent's actual relay through it two or three times before assuming the wording is fixed too.
  • Three exit codes, not two, is what lets a caller tell "the data is bad" apart from "there was no data to check" without reading a single line of text. Use it when: a script you are writing only ever exits 0 or 1 -- ask whether "it ran but failed" and "it could not run at all" are really the same problem for whatever calls it.
  • The fastest way to catch a fat script is to run it next to the real validator on a file you know should fail -- agreement on the easy cases hides disagreement on the case that matters. Use it when: you inherit a script that "does its own validation" and you are not sure whether it imports the tested package or reimplements it -- one bad-namespace file, run through both, answers the question in seconds.
  • Word count moved from a skill's Steps section into a script's tested code is a real, measurable trade, not just a claim -- wc -w a Steps section before and after you script a step. Use it when: you are deciding whether a step is worth turning into a script -- if scripting it barely shortens the Steps section, the step may not have been carrying much judgment to begin with.
  • Counting assert statements in a script's test file, and confirming no equivalent test file exists for the skill's own judgment calls, is a mechanical version of the lesson's scripting rule. Use it when: a teammate argues a step "obviously" belongs in a script (or obviously does not) -- ask them to write the assert for it; if they cannot state one fixed expected output, the step is not a scripting candidate yet.
