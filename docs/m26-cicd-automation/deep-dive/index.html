Deep Dive — Source Control and CI/CD Automation

The lab proved release-check produces a ready verdict against a full-pass fixture set, and a not_ready verdict with a clear per-section breakdown against a partial-failure one. This page goes one level deeper on three claims the lesson made but did not fully prove on their own: that the fetch/aggregate split really has zero verdict logic on one side and zero network calls on the other (not just "we tried to keep them apart"), what a real outage looks like when one evidence source goes down mid-check, and why this specific lab needed deterministic fixtures where Module 9's did not.

Where this picks up

This page assumes ~/platformops at v2.1.0, with src/platformops/releasecheck.py and the release-check CLI command in place from the lab.

cd ~/platformops
uv run platformops version

Expected output

platformops 2.1.0

1. Fetch and aggregate, proven mechanically​

The lesson claimed the six gather_*_evidence() functions never decide pass or fail, and evaluate_release_readiness() never touches the network. "We tried to keep them apart" is not the same claim as "they really are apart" — the same discipline Module 24's Deep Dive used to prove cloudaudit.py's detection was really free of write-mode AWS calls. Grep the six fetch functions for a verdict word:

awk '/^def gather_pr_evidence\(/{p=1} /^class ReleaseReadinessReport:/{exit} p' src/platformops/releasecheck.py | rg -i '"ready"|"pass"|"fail"'; echo "exit=$?"

Expected output

exit=1

rg exits 1 when it finds zero matches. Across all six fetch functions — gather_pr_evidence() through gather_deployment_evidence() — not one of them contains the string "ready", "pass" or "fail" in any form. Each one only ever returns a "fetched" flag plus the raw facts it found.

Now the other half — evaluate_release_readiness(), the function that does all the judging, checked for the two things that would prove it secretly depends on the network:

awk '/^def evaluate_release_readiness\(/{p=1} /^def run_release_check\(/{exit} p' src/platformops/releasecheck.py | rg 'httpx|gather_'; echo "exit=$?"

Expected output

exit=1

Zero matches. evaluate_release_readiness()'s entire body — building the sources_ok/ sources_failed lists, running each _evaluate_* helper, combining five gating sections into one verdict — never mentions httpx and never calls a gather_* function. A stronger check confirms the whole module never even imports the HTTP library at all:

rg '^import httpx|^from httpx' src/platformops/releasecheck.py; echo "exit=$?"

Expected output

exit=1

That third check is the strongest of the three. evaluate_release_readiness() is not merely a function that happens not to call the network today — it is a function that could not call the network even if a future edit tried to add a shortcut, because the module doing the judging never holds a reference to httpx in the first place. Adding a network call there would require adding a new import first, which is a far more visible change in a code review than adding one more line to a function that already has httpx in scope.

2. A real outage, mid-check — what the report actually looks like​

The lesson stated the rule: a source that could not be reached becomes UNKNOWN, never a silent PASS. Here it is with a real simulated outage — the check-runs endpoint refuses every connection attempt, exactly as it would during a GitHub incident or a firewall blocking outbound traffic from a CI runner, while every other endpoint answers normally.

cat > /tmp/m26_degraded_source_demo.py << 'PYEOF'
import json
from pathlib import Path

import httpx
import respx

import platformops.httpclient as httpclient
from platformops.releasecheck import run_release_check

# Skip the real backoff sleeps for this demo -- the retry timing itself is
# already proven in tests/test_httpclient.py; here we only care about what
# the report looks like once every retry is exhausted.
httpclient.time.sleep = lambda _seconds: None

FIXTURES = Path("tests/fixtures/github")


def _fixture(name):
    return json.loads((FIXTURES / name).read_text())


OWNER = "acme-platform"
REPO = "payments"

with respx.mock:
    respx.get(f"https://api.github.com/repos/{OWNER}/{REPO}/pulls/482").mock(
        return_value=httpx.Response(200, json=_fixture("pr_approved.json"))
    )
    respx.get(f"https://api.github.com/repos/{OWNER}/{REPO}/actions/runs").mock(
        return_value=httpx.Response(200, json=_fixture("workflow_success.json"))
    )
    # Simulate an outage: the check-runs endpoint refuses every connection attempt.
    respx.get(f"https://api.github.com/repos/{OWNER}/{REPO}/commits/main/check-runs").mock(
        side_effect=httpx.ConnectError("connection refused")
    )
    respx.get(f"https://api.github.com/repos/{OWNER}/{REPO}/actions/artifacts").mock(
        return_value=httpx.Response(200, json=_fixture("artifacts_present.json"))
    )
    respx.get(f"https://api.github.com/repos/{OWNER}/{REPO}/releases/latest").mock(
        return_value=httpx.Response(200, json=_fixture("release_latest.json"))
    )
    respx.get(f"https://api.github.com/repos/{OWNER}/{REPO}/deployments").mock(
        return_value=httpx.Response(200, json=_fixture("deployment.json"))
    )

    report = run_release_check(owner=OWNER, repo=REPO, branch="main", pr=482, service="payments")

print("verdict:", report.verdict)
print("checks section:", report.checks)
print("sources_ok:", report.sources_ok)
print("sources_failed:", report.sources_failed)
PYEOF
uv run python /tmp/m26_degraded_source_demo.py

Expected output

https://api.github.com/repos/acme-platform/payments/commits/main/check-runs?per_page=100: attempt 1/5 failed (connection refused), retrying
https://api.github.com/repos/acme-platform/payments/commits/main/check-runs?per_page=100: attempt 2/5 failed (connection refused), retrying
https://api.github.com/repos/acme-platform/payments/commits/main/check-runs?per_page=100: attempt 3/5 failed (connection refused), retrying
https://api.github.com/repos/acme-platform/payments/commits/main/check-runs?per_page=100: attempt 4/5 failed (connection refused), retrying
verdict: not_ready
checks section: {'status': 'UNKNOWN', 'detail': 'https://api.github.com/repos/acme-platform/payments/commits/main/check-runs?per_page=100 unreachable after 5 attempt(s): connection refused'}
sources_ok: ['pr', 'ci', 'artifacts', 'release', 'deployment']
sources_failed: ['checks']

Four retries, then _request_with_retry() gives up and raises EndpointUnreachableError — the exact retry-with-backoff mechanism Module 9's Deep Dive already covered, working here on a new endpoint without a single line of change. gather_check_runs_evidence() catches that exception and returns "fetched": False. Nothing crashes. The other five sources still answered normally and are listed in sources_ok. checks alone lands in sources_failed, and the verdict is not_ready — even though every source that did answer would, on its own, have said ready.

This is the same behavior a real CI pipeline calling release-check needs during a real GitHub incident: five green signals and one endpoint down does not mean "probably fine, ship it" — it means "we do not actually know", and the report says exactly that instead of guessing.

3. Why this lab used fixtures, and Module 9's did not​

Think of the difference the way a photograph differs from a live camera feed. Module 9's workflow-runs lab pointed at a live camera feed on purpose — kubernetes-sigs/kind's real, running CI history, changing every day, because the only thing that lab needed to prove was "can this client follow pagination through however many pages a real busy repository happens to have right now." Any answer the feed gives back on any given day proves the same thing.

This lab needed a photograph instead — one exact, unchanging moment: pull request #482, merged, with a specific workflow run, three specific passing check runs, one specific unexpired artifact, and one specific deployment record, all agreeing with each other at once. A live camera feed cannot promise that combination will still be sitting there the next time this lab runs. A real repository gets more commits, more merged PRs, more expired artifacts — the exact multi-source scenario a release-readiness check needs to demonstrate would not be reproducible for grading, or even for you running it a second time next week.

The trade-off is real, not free. respx-mocked fixtures prove release-check's own logic — aggregation, verdict computation, honest degradation — works correctly against a known shape. They cannot prove GitHub's real API still returns exactly that shape today; a live smoke test against octocat/Hello-World (the way Module 9's lab used a real, stable public repository) is still worth running occasionally to catch a genuine upstream API change. Fixtures and a live check answer different questions, and this lab picked the one — reproducibility — that a release-readiness report specifically needs.

Where you will use this
  • A tool that decides can be tested without a network, and a tool that talks to a network can be tested without deciding anything. Use it when: you are reviewing a pull request that adds a new evidence source to a report like this one — check which side of the split the new code landed on before approving it.
  • An unreachable source degrades a report honestly instead of crashing it or passing it silently. Use it when: you are debugging why an automated release gate said "not ready" during an actual GitHub incident — check sources_failed first, before assuming something in your own pull request actually broke.
  • A photograph proves a specific scenario works; a live feed proves a client survives whatever the real system throws at it today. Use it when: you are deciding whether a new test needs a fixture or a live call — ask whether you are proving "this exact multi-part scenario computes correctly" (fixture) or "this client still works against the real, current API" (live, occasional).

Teardown​

cd ~/platformops
rm -f /tmp/m26_degraded_source_demo.py

Nothing else from this page persists — every scenario here ran against respx-mocked fixtures already committed to the project from the lab. There is no real GitHub state, container, or cluster this page touched.
