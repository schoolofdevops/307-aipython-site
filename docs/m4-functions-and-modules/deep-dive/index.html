What Import Actually Does

The lab turned inventory.py into a package, added __main__.py so python -m platformops.inventory kept working, and had your coding agent remove a duplicated loop without creating a circular import between rules.py and summary.py. All three of those moves work because of one mechanism: what Python's import statement actually does when it runs. This page opens that mechanism up — the module cache, why python -m behaves differently from running a file directly, why circular imports happen at all, and how to find exactly which file a function really lives in once it has been re-exported three times. You will reach for this the next time an import fails in a way that makes no sense from reading the code alone, or the next time you have to decide where a shared helper should live to keep two files from depending on each other.

Where this picks up

You need ~/platformops at v0.2 — the package layout from the lab (src/platformops/inventory/ with data.py, rules.py, summary.py, report.py, __init__.py, __main__.py). Every command below reads the project or runs a short, disposable Python one-liner against it; none of them change committed files permanently, and the one that does (section 3) is reverted with git checkout in the same step. Re-running any command on this page is safe.

cd ~/platformops

1 — Import runs the file once, then hands out the same object forever​

The first time anything in your program writes import platformops.inventory.data, Python does real work: it finds the file, runs every line in it top to bottom (which is why INVENTORY = [...] gets built), and then stores the finished module object in a dictionary called sys.modules, keyed by its full dotted name. Every import of that same name afterwards — anywhere else in your program, in a completely different file — is not a second read of the file. It is a dictionary lookup that hands back the exact same object.

Think of sys.modules as a hotel's key-card system rather than a hotel room itself. The first guest to check into room platformops.inventory.data gets the room made up (the file executed) and a key card issued. Every other request for that same room number gets a copy of the same key card — nobody remakes the room. If someone rearranges the furniture (mutates something in that module), everyone holding a key card to that room sees the rearranged room, because there is only one room, not one per guest.

uv run python -c "
import sys
import platformops.inventory.data as d1
import platformops.inventory.data as d2
print(d1 is d2)
print('platformops.inventory.data' in sys.modules)
"

Expected output

True
True

d1 is d2 is True because both names point at the one cached module object — the second import line did not re-run data.py. This is exactly why your __init__.py's re-exports (from .data import INVENTORY) are cheap no matter how many other files also import data.py directly: the file only ever runs once per process, no matter how many places import it.

2 — Why python -m succeeds where python file.py fails​

Running uv run python -m platformops.inventory and running uv run python src/platformops/inventory/report.py look like two ways of doing the same thing. They are not. -m tells Python "resolve this dotted name as a package, starting from somewhere on sys.path, and run it inside that package" — Python knows report.py's parent is platformops.inventory, so a line like from .data import INVENTORY inside it has a package to be relative to. Running the file directly by its filesystem path skips all of that: Python treats the file as a lone script with no package context, and a relative import has nothing to be relative to.

The analogy is how you address a letter. "-m platformops.inventory" is a full postal address — country, city, street, unit number — so the relative instruction "flat 2, this building" (.data, "the file next to me") makes sense. Handing someone the file directly is like handing them a note that only says "flat 2" with no building attached — there is no "this building" for .data to mean anything relative to.

uv run python src/platformops/inventory/report.py

Expected output

Traceback (most recent call last):
  File "<your home>/platformops/src/platformops/inventory/report.py", line 3, in <module>
    from .data import INVENTORY, MIN_PROD_MEMORY_GB
ImportError: attempted relative import with no known parent package

That ImportError: attempted relative import with no known parent package is not a bug in report.py — it is Python telling you the truth: this file was never designed to run standalone. __main__.py exists precisely so there is a supported way to run something inside the package (-m platformops.inventory) instead of reaching around it.

3 — Why circular imports happen, and where the fix actually lives​

A circular import is not "two files importing each other" in the abstract — plenty of packages have files that reference each other and work fine. It is specifically: module A is still in the middle of running, top to bottom, when it reaches an import of module B — and B, also running top to bottom, tries to use a name from A that A has not defined yet, because A paused halfway through to go load B. Python does not deadlock; it raises immediately, because the name genuinely does not exist yet on the partially-built module.

Picture two colleagues who each refuse to finish their half of a status update until they've read the other's — both wait on each other and neither one is done, except Python does not wait: the moment one of them reaches for the other's still-unwritten section, it says so and stops.

Reproduce the exact failure the lab's Troubleshooting section named, then undo it:

python3 -c "
path = 'src/platformops/inventory/rules.py'
text = open(path).read()
text = text.replace(
    'from .data import MIN_PROD_MEMORY_GB\n',
    'from .data import MIN_PROD_MEMORY_GB\nfrom .summary import filter_by_environment  # BROKEN\n',
)
open(path, 'w').write(text)
"
uv run python -c "import platformops.inventory"

Expected output

Traceback (most recent call last):
  File "<string>", line 1, in <module>
  File "<your home>/platformops/src/platformops/inventory/__init__.py", line 11, in <module>
    from .report import print_report
  File "<your home>/platformops/src/platformops/inventory/report.py", line 4, in <module>
    from .rules import count_by_environment, find_low_memory_prod, find_missing_owner
  File "<your home>/platformops/src/platformops/inventory/rules.py", line 4, in <module>
    from .summary import filter_by_environment  # BROKEN
    ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
  File "<your home>/platformops/src/platformops/inventory/summary.py", line 3, in <module>
    from .rules import _servers_in_environment, count_by_environment
ImportError: cannot import name '_servers_in_environment' from partially initialized module 'platformops.inventory.rules' (most likely due to a circular import) (<your home>/platformops/src/platformops/inventory/rules.py)

Read the traceback bottom to top: rules.py started loading, hit the new line importing summary.py, which itself tried to import _servers_in_environment back out of rules.py — but rules.py had not defined it yet, because it paused on the line above to go load summary.py first. Undo the change:

git checkout -- src/platformops/inventory/rules.py
uv run python -c "import platformops.inventory; print('restored')"

Expected output

restored

This is also why the position of an import inside a file matters, not just its existence — if that broken line had come after _servers_in_environment was already defined, the same two-file cycle would not have failed at all, because the name it needed would already exist by the time the cycle closed. That is also why "just move the import" is a real fix, not a workaround: moving a shared name to a file that both sides can depend on one-directionally (as the lab's dedup did, keeping the helper in rules.py and having summary.py depend on it, never the reverse) removes the cycle entirely, permanently, regardless of ordering. The other standard fixes you will meet in larger codebases — importing inside a function body instead of at the top of the file, or merging two modules that keep needing each other — solve the same problem by breaking the same "A isn't finished before B needs it" timing.

4 — Where a function actually lives, after three re-exports​

find_missing_owner is importable as platformops.inventory.find_missing_owner because __init__.py re-exports it. That re-export does not move the function's code anywhere — it just adds another name pointing at the same function object, the same way backup = inventory in the last module's lesson added a second label without copying the list. Python tracks a function's real home in its __module__ attribute, set once, when the function is defined — re-exporting it never changes that.

uv run python -c "
import inspect
from platformops.inventory import find_missing_owner
print(find_missing_owner.__module__)
print(inspect.getsourcefile(find_missing_owner))
"

Expected output

platformops.inventory.rules
<your home>/platformops/src/platformops/inventory/rules.py

__module__ reads platformops.inventory.rules — not platformops.inventory — because that is where the def statement actually ran. inspect.getsourcefile goes one step further and gives you the real file path on disk. This is the same evidence you would reach for while reading a stack trace that names a function you only ever imported from the top-level package: the traceback (and __module__) will point at its real file, not the __init__.py you imported it through.

Where you will use this
  • Two imports of the same module return the exact same cached object, never a fresh copy. Use it when: you are debugging why a config value or in-memory cache "changed everywhere at once" — check whether two parts of the program hold the same cached module object rather than two independent copies.
  • python -m package and python path/to/file.py are genuinely different operations, not two spellings of the same command. Use it when: a script works from one directory but throws a relative-import error from another, or in CI — run it as python -m from the project root instead of by file path.
  • A circular import fails only at the exact moment a not-yet-defined name is needed — not merely because two files reference each other. Use it when: you are deciding where a newly extracted helper function should live during a refactor — put it in the file with fewer outgoing dependencies, so the other file can depend on it one-directionally.
  • __module__ and inspect.getsourcefile() tell you a function's real home, regardless of how many places re-export it. Use it when: a traceback or an IDE "go to definition" lands you somewhere unexpected inside a re-exporting __init__.py — these two tell you exactly which file to actually go fix.

Teardown​

Nothing here to tear down. Section 3 reverts its own change with git checkout --; everything else only reads the project or runs a throwaway python -c one-liner. ~/platformops is left exactly at v0.2, ready for the next module.
