Functions, Modules and Reusable Automation

Module slides​

Walk this short whiteboard deck for the big picture, or open it fullscreen.

▶ M4 — Functions, Modules and Reusable AutomationOpen fullscreen ↗

Your inventory.py from the last module already works. It has three functions and a report. The problem is not that it's broken — the problem is that it's still one file, so if you wanted to reuse find_missing_owner from a different script, or hand only the "rules" part to a teammate to review, you couldn't. This module fixes that: you split one working file into small, well-named pieces, and you learn the rules that make that split safe.

1. A function is one job, done the same way every time​

A function is like a form at a government office: you fill in the blanks (the parameters), the clerk does exactly one task with them, and you get one result back (the return value). You wouldn't want the clerk to also go update three other unrelated files while you wait — a good form does one thing, and so should a good function.

def find_missing_owner(inventory):
    """Return the names of servers that have no `owner` tag."""
    missing = []
    for server in inventory:
        if "owner" not in server["tags"]:
            missing.append(server["name"])
    return missing

Why this matters at work: during an incident, you are often reading code you did not write, under time pressure. A function that does one job, named after that job, tells you what it does before you read a single line inside it. A function that "checks owners, and also updates a counter, and also prints a warning" makes you read the whole thing every time, because you can never be sure which of its three jobs you actually need right now.

return is what hands the result back to whoever called the function. A function with no return statement still runs fine — it just hands back None, Python's way of saying "nothing here." That is a common source of confusion: if you call a function only for its print() output and try to use what it "returns," you get None, not the thing you saw printed on screen.

2. Positional, keyword and default arguments​

Look at this call:

find_low_memory_prod(INVENTORY, 8)

INVENTORY and 8 are matched to the function's parameters purely by position — first argument to first parameter, second to second. That works, but a reader has to go check the function's definition to know what 8 means. Compare:

find_low_memory_prod(INVENTORY, min_memory_gb=8)

Now 8 names itself. Keyword arguments cost nothing extra and remove a whole class of "wait, which argument was that again" mistakes — especially useful once a function takes three or four arguments, which is exactly what happens as automation scripts grow.

A default argument lets a caller skip a value entirely:

def find_low_memory_prod(inventory, min_memory_gb=8):
    ...

find_low_memory_prod(INVENTORY)          # uses 8
find_low_memory_prod(INVENTORY, 16)      # overrides it
The mutable-default trap

Never write a default value that is a list, dict, or set:

def add_finding(name, findings=[]):   # WRONG
    findings.append(name)
    return findings

A default value is created once, the moment Python reads the def line — not fresh on every call. Every call that relies on the default shares the same list, the same mutable object from the last module's lesson. Call add_finding("web-02") twice and the second call sees the first call's leftover data still sitting in findings, because it's the same list both times. The fix is a default of None, checked inside the function:

def add_finding(name, findings=None):
    if findings is None:
        findings = []
    findings.append(name)
    return findings

3. Scope — where a name is visible​

Think of a function body as a private notebook. Anything you write inside it (a local variable) is visible only on that page — close the notebook, and the name is gone. A name defined at the top of a file, outside any function, is a module-level (sometimes called "global") name — visible from every function in that file, like a shared whiteboard in the hallway everyone walks past.

MIN_PROD_MEMORY_GB = 8    # module level -- every function here can read it

def find_low_memory_prod(inventory, min_memory_gb=MIN_PROD_MEMORY_GB):
    ...   # min_memory_gb is local -- it only exists inside this call

Reading a module-level constant from inside a function is fine and common — MIN_PROD_MEMORY_GB above is exactly that. The trap is writing to a module-level name from inside a function without saying so. If a function reassigns a global by accident, every other function reading that name — possibly a CLI command running minutes later, in a different part of the same automation run — now sees a different value, with no return and no argument telling you where it changed. That's the operational cost of globals: a bug that shows up somewhere far from where it was caused. Automation scripts that stay a small handful of pure functions mostly avoid this trap by simply not needing to write to globals at all.

4. Modules and packages — a file, then a folder of files​

A Python module is just a .py file. When you write import platformops.inventory, you are asking Python to run one file and hand you back everything it defined. A package is a folder containing an __init__.py file — that one extra file is what tells Python "treat this folder as a single importable thing," the same way one library needs a front door before strangers can walk in and find the right shelf.

This module's lab turns inventory.py into exactly this shape: a package with one file per job — data, rules, filtering/sorting, and the report — plus __init__.py re-exporting the same public names so every import that worked before still works. __main__.py is a small but important detail: it's the file Python runs when you type python -m platformops.inventory against a package instead of a single file. Without it, that command stops working the moment inventory.py becomes a folder — the lab shows you exactly why, and the Deep Dive after it shows you what import and -m are doing underneath.

5. Separate input, processing and output — the testability argument​

Split any piece of automation into three questions: where does the data come from (input), what do you do with it (processing), and where does the result go (output — a print(), a file write, an API call). find_missing_owner above is pure processing: it takes data in, and returns data out. It never prints, never opens a file, never reaches the network.

That's what makes it a pure function — same input, same output, every time, with no side effects. Pure functions are the easiest thing in this entire course to test: a test just calls the function with sample data and checks the answer, with no server, no file, no mocking required. print_report() is the opposite — it's almost entirely output, and it's also the one function in this module's lab you can't write a simple return-value test for. Keeping the "what to check" functions pure and pushing all the printing into one place is why you can test the logic hard and the report barely at all — you've already tested every piece print_report calls.

6. A function signature and its docstring are a contract​

Before you read a single line inside a function, its signature — the def line, its parameter names, its defaults — plus its docstring already tell you the deal: what goes in, what optional knobs exist, what comes back.

def find_low_memory_prod(inventory, min_memory_gb=MIN_PROD_MEMORY_GB):
    """Return the names of prod servers with less than `min_memory_gb` memory."""

Read that line and you know: it takes a list, it has one tunable threshold with a sensible default, and it hands back a list of names. You did not need to read the loop inside it to decide whether it's the function you want. This is exactly what you read first when reviewing a coding agent's diff — the contract, before the implementation.

7. When not to reach for a class​

This audience — engineers coming from Bash, Ansible, Terraform — tends to over-use classes once they learn Python has them, wrapping a handful of functions in a class that has no state to protect and no behavior that varies by instance. INVENTORY, three check functions, and a report function do not need a class: there is one shared list, and functions that operate on it. A class earns its place when you have data and behavior that must travel together and vary per object — a ServiceDefinition with its own fields and its own validation, which is exactly what a later module introduces. Until you have that, a module full of well-named functions is simpler to read, simpler to test, and simpler for a coding agent to extend without inventing structure nobody asked for.

Common pitfalls
  • A mutable default argument (findings=[]) — it is created once and shared across every call that relies on it. Default to None and build the list inside the function instead.
  • Reassigning a module-level name inside a function without meaning to — the change leaks into every other function reading that name, with no return telling you where it happened. Pass the value in and return the new one instead of writing to the global.
  • Forgetting a function's return — it still runs, but hands back None. If you use its result and get None where you expected data, check for a missing return first.
  • Wrapping a few plain functions in a class "to be organized" — if there's no state to protect and no behavior that varies per instance, a class only adds a layer a reader (or a reviewing coding agent) has to look through. A module of functions does the same job.
  • Forgetting __init__.py when turning a file into a folder — the import that used to work stops resolving cleanly. The lab and Deep Dive both show you the exact error this produces and how to read it.
