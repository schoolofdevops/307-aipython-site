Lab — Build PlatformOps v0.2: the Modular Inventory Engine

This lab has two phases, the same shape as the last module. In Phase A you split the working inventory.py file from v0.1 into a small package, by hand, so you know exactly where every function lives and why. In Phase B you hand a short, written request to a coding agent to remove a piece of duplicated logic that Phase A leaves behind, then you review its diff before accepting it.

You need the ~/platformops project from the M3 lab, already tagged v0.1, with uv run pytest -q passing and git log showing that tag.

cd ~/platformops

Phase A — split inventory.py into a package by hand​

1. Turn the file into a folder​

Right now, src/platformops/inventory.py is one file. You are about to turn it into a package: a folder with the same name, containing several small files instead of one big one. Delete the old file first, then create the folder:

rm src/platformops/inventory.py
mkdir -p src/platformops/inventory

2. Write the data file​

Create src/platformops/inventory/data.py — the inventory data, and nothing else:

"""Infrastructure inventory reporter — PlatformOps v0.2.

The raw inventory data lives here and nowhere else. Every other file in
this package imports `INVENTORY` from this module instead of holding its
own copy of it -- one source of truth for what a "server" record looks
like.
"""

MIN_PROD_MEMORY_GB = 8

This is byte-for-byte the same data you already have in v0.1 — you are only moving it, not changing it.

3. Write the rule checks​

Create src/platformops/inventory/rules.py — the three functions M3 called "the checks a platform team runs by hand":

"""The three rule checks a platform team runs on the inventory by hand today."""

from .data import MIN_PROD_MEMORY_GB


def find_missing_owner(inventory):
    """Return the names of servers that have no `owner` tag."""
    missing = []
    for server in inventory:
        if "owner" not in server["tags"]:
            missing.append(server["name"])
    return missing


def find_low_memory_prod(inventory, min_memory_gb=MIN_PROD_MEMORY_GB):
    """Return the names of prod servers with less than `min_memory_gb` memory."""
    flagged = []
    for server in inventory:
        if server["env"] == "prod" and server["memory_gb"] < min_memory_gb:
            flagged.append(server["name"])
    return flagged


def count_by_environment(inventory):
    """Return a dict mapping each environment name to its server count."""
    counts = {}
    for server in inventory:
        env = server["env"]
        counts[env] = counts.get(env, 0) + 1
    return counts

from .data import MIN_PROD_MEMORY_GB is a relative import — the leading dot means "from the file next to me, inside this same package," not "search the whole project for a module named data." That is why the folder needs to be a proper package, which brings you to the next step.

4. Write the filter/sort/summary trio​

Create src/platformops/inventory/summary.py — the three functions the coding agent added in the M3 lab's Phase B:

"""Filter, sort and summarize the inventory -- the Phase B extension from M3."""

from .rules import count_by_environment


def filter_by_environment(inventory, env):
    """Return only the servers whose `env` matches the one given."""
    return [server for server in inventory if server["env"] == env]


def sort_by_name(inventory):
    """Return a new list of servers sorted by name."""
    return sorted(inventory, key=lambda server: server["name"])


def build_summary(inventory):
    """Return counts and totals across the whole inventory."""
    return {
        "total_servers": len(inventory),
        "total_cpu": sum(server["cpu"] for server in inventory),
        "total_memory_gb": sum(server["memory_gb"] for server in inventory),
        "by_environment": count_by_environment(inventory),
    }

Notice summary.py imports count_by_environment from rules.py — one file in this package reusing a function from another. That is exactly what a package buys you: rules.py and summary.py can each stay focused on one job, while still calling into each other where it genuinely makes sense.

5. Write the report​

Create src/platformops/inventory/report.py:

"""Print the plain-text inventory report -- the only file that talks to the terminal."""

from .data import INVENTORY, MIN_PROD_MEMORY_GB
from .rules import count_by_environment, find_low_memory_prod, find_missing_owner
from .summary import build_summary, filter_by_environment, sort_by_name


def print_report():
    """Print a plain-text infrastructure inventory report."""
    print("PlatformOps Inventory Report")
    print("=============================")
    print(f"Total servers: {len(INVENTORY)}")

    print("\nServers by environment:")
    for env, count in count_by_environment(INVENTORY).items():
        print(f"  {env}: {count}")

    print("\nMissing owner tag:")
    missing = find_missing_owner(INVENTORY)
    if missing:
        for name in missing:
            print(f"  - {name}")
    else:
        print("  (none)")

    print(f"\nProd servers with low memory (< {MIN_PROD_MEMORY_GB}GB):")
    low_memory = find_low_memory_prod(INVENTORY)
    if low_memory:
        for name in low_memory:
            print(f"  - {name}")
    else:
        print("  (none)")

    print("\nSummary:")
    summary = build_summary(INVENTORY)
    print(f"  Total CPU (cores): {summary['total_cpu']}")
    print(f"  Total memory (GB): {summary['total_memory_gb']}")
    for env, count in summary["by_environment"].items():
        print(f"  {env}: {count} server(s)")

    print("\nProd servers (filtered):")
    for server in filter_by_environment(INVENTORY, "prod"):
        print(f"  - {server['name']}")

    print("\nAll servers, sorted by name:")
    for server in sort_by_name(INVENTORY):
        print(f"  - {server['name']} ({server['env']})")

6. Write the public surface — __init__.py​

This is the file that turns the inventory folder into an importable package, and the one that keeps every existing import working unchanged:

"""Infrastructure inventory reporter — PlatformOps v0.2.

This used to be one file, `inventory.py`. It is now a package: a folder with
its own `__init__.py`. The public surface stays exactly the same on purpose
-- everything this package exposed as `platformops.inventory.<name>` before
the split is re-exported here, so no import anywhere else in the project
(or in your tests) has to change.
"""

from .data import INVENTORY, MIN_PROD_MEMORY_GB
from .report import print_report
from .rules import count_by_environment, find_low_memory_prod, find_missing_owner
from .summary import build_summary, filter_by_environment, sort_by_name

__all__ = [
    "INVENTORY",
    "MIN_PROD_MEMORY_GB",
    "count_by_environment",
    "find_low_memory_prod",
    "find_missing_owner",
    "filter_by_environment",
    "sort_by_name",
    "build_summary",
    "print_report",
]

__all__ is optional, but it is worth writing: it states, in one place, exactly which names this package promises to keep stable for anyone importing it. tests/test_inventory.py still does from platformops.inventory import (INVENTORY, find_missing_owner, ...) — and that line does not change at all, because __init__.py now hands out exactly those same names from a package instead of a single file.

7. Write the entry point — __main__.py​

"""Lets `uv run python -m platformops.inventory` keep working now that
`inventory` is a package instead of a single file.

A plain module (`inventory.py`) runs itself when you name it with `-m`
because there is only one file to run. A package has no single file to
run -- Python needs to be told which file inside the package is the entry
point when it is invoked with `-m`. That file must be named exactly
`__main__.py`.
"""

from .report import print_report

if __name__ == "__main__":
    print_report()

Your src/platformops/inventory/ folder now holds six files: data.py, rules.py, summary.py, report.py, __init__.py, __main__.py.

Phase B — delegate the duplication cleanup​

Look at rules.py and summary.py again. find_low_memory_prod (in rules.py) filters the inventory down to env == "prod" before checking memory. filter_by_environment (in summary.py) filters the inventory down to any env you name. Those two functions loop over the inventory checking server["env"] == <something> — the same idea, written twice, in two different files. That repetition is exactly what Phase B asks your coding agent to find and remove.

10. Ask your coding agent to deduplicate the environment filter​

Open your coding agent in the project folder:

claude

Paste this request exactly as written:

I'm working in this uv-managed Python project, inside src/platformops/inventory/
(a package: data.py, rules.py, summary.py, report.py, __init__.py, __main__.py).

Please find and remove the duplicated environment-filtering logic between
rules.py and summary.py:

1. find_low_memory_prod (in rules.py) and filter_by_environment (in
   summary.py) both loop over the inventory checking server["env"] == X.
   Extract that shared check into one small private helper function and
   have both call it instead of repeating the loop.
2. Do not add any classes -- a small helper function is enough.
3. Do not add any new third-party dependencies.
4. Do not change the observable behavior of any function -- every function's
   inputs, outputs and the printed report must stay exactly the same.
5. All existing tests in tests/test_inventory.py must stay green, unchanged.
6. Run `uv run ruff check .` and `uv run pytest -q` yourself before you
   finish, and tell me the result.

This spec names the exact duplication (not "clean up the code" in general), states the constraints (no classes, no new dependencies, no behavior change), and asks the agent to verify its own work before handing it back — the same discipline as the M3 lab's Phase B.

Why does the spec say "no classes"?

Nothing about deduplicating a repeated loop needs a class. A private helper function does the job in three lines. If your agent comes back having wrapped rules.py and summary.py in an InventoryRules class "for organization," that is unnecessary structure this spec explicitly ruled out — reject that part of the diff and ask for the plain-function version instead. This audience tends to reach for classes out of habit brought over from other languages; this lesson's rule of thumb still applies: no shared state to protect, no behavior that varies per object, no class needed.

Let the agent work. It will report back once it has made the change and run the checks itself.

Troubleshooting
  • ModuleNotFoundError: No module named 'platformops.inventory' — check that the folder is named inventory (matching the old file's name) and sits directly inside src/platformops/, and that it has an __init__.py file. A folder with Python files but no __init__.py is a namespace package — Python may still find the folder, but none of the names your __init__.py was supposed to re-export will resolve, since there is no __init__.py to do the re-exporting.
  • ImportError: cannot import name 'INVENTORY' from 'platformops.inventory' (unknown location) — this is exactly the error above, one level further in: the folder exists and Python found it, but with no __init__.py, there is nothing re-exporting INVENTORY from it. Add the file back.
  • ImportError: cannot import name '...' from partially initialized module '...' (most likely due to a circular import) — two of your package's files import from each other in both directions (for example, rules.py importing something from summary.py while summary.py also imports from rules.py). Keep the shared helper in the file that has no reason to import from the other, and have the other file import from it — one direction only. The Deep Dive walks through exactly why this happens.
  • ImportError: attempted relative import with no known parent package — you (or your agent) ran a file directly, like python src/platformops/inventory/report.py, instead of uv run python -m platformops.inventory. A file that uses from .data import ... needs Python to know which package it belongs to, and that only happens when you run it as part of the package with -m, not as a standalone file.
  • uv run python -m platformops.inventory prints nothing, or errors with "No module named platformops.inventory.main" — the package is missing __main__.py, or it is misspelled (it must be exactly __main__.py, two leading and two trailing underscores).
  • Your agent's diff touches pyproject.toml — it added a dependency you did not ask for. Reject that part of the change; nothing in this refactor needs anything beyond the standard library.
