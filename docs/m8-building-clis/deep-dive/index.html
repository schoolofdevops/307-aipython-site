What Happens When You Type platformops

The lab wired an entry point and moved on. This page opens up what that one line in pyproject.toml actually does, how Typer turns a typed function into a full command with no parser code of your own, why splitting stdout from stderr is not a style choice but the thing a CI pipeline's exit code depends on, and why a CLI's own test suite calls the app directly instead of shelling out to it. You will reach for this the next time command not found shows up after a fresh install, you are deciding whether a new internal tool is worth a Typer dependency, you are debugging a CI job that reported success on a run that actually failed, or you are wondering why your CLI's test suite runs in milliseconds instead of seconds.

Where this picks up

You need ~/platformops at v0.6 from the lab. Every command below runs a short, disposable script in its own scratch folder -- none of them touch cli.py, pyproject.toml or your project's git history. Re-running any command on this page is safe.

mkdir -p ~/platformops/dd-scratch && cd ~/platformops/dd-scratch

1 -- What actually runs when you type platformops​

Think of uv sync as hiring a receptionist: it reads pyproject.toml's [project.scripts] line once, and in exchange it writes one small file that will always know exactly which department to forward you to, so nobody who calls in later needs to know your internal extension. That file is .venv/bin/platformops -- look at it directly:

cat ../.venv/bin/platformops

Expected output

You will see one of two shim styles, depending on your platform and uv version:

#!/<path-to-your>/.venv/bin/python3
# -*- coding: utf-8 -*-
import sys
from platformops.cli import app
if __name__ == "__main__":
    sys.exit(app())

Or, on some older setups, a sh-polyglot wrapper:

#!/bin/sh
'''exec' '<your home>/platformops/.venv/bin/python3' "$0" "$@"
' '''
# -*- coding: utf-8 -*-
import sys
from platformops.cli import app
if __name__ == "__main__":
    sys.exit(app())

Either way, the important part is the same: it is a plain Python file that does exactly two things -- import app from platformops.cli, and call sys.exit(app()). Every word after platformops = in [project.scripts] -- platformops.cli:app -- maps directly onto that import ... ; sys.exit(app()) pair. uv sync did not invent this file from nothing; it read your project's installed metadata for the exact mapping:

cat > entry_point_lookup.py << 'EOF'
from importlib.metadata import entry_points

eps = entry_points(group="console_scripts")
for ep in eps:
    if ep.name == "platformops":
        print(ep)
EOF
uv run python3 entry_point_lookup.py

Expected output

EntryPoint(name='platformops', value='platformops.cli:app', group='console_scripts')

That EntryPoint object is the same information [project.scripts] declared, now readable at runtime by any tool that cares -- uv, pip, and the shim-generation step itself all read this same metadata. When you typed platformops --help in the lab, this is the full chain: your shell's PATH found .venv/bin/platformops (because uv run put .venv/bin at the front of PATH for that command); the shim execed the project's own python3; that python3 imported platformops.cli, which built the app object at import time; sys.exit(app()) called it, Typer parsed sys.argv, and dispatched to the validate/inspect/version function you wrote.

command not found: platformops almost always means step two failed -- either .venv/bin was never on PATH (you ran platformops instead of uv run platformops outside an activated venv), or the shim was never (re)generated because uv sync never ran after [project.scripts] changed.

2 -- How Typer builds a command from a typed function​

Typer's job is to turn def validate(path: Annotated[Path, typer.Argument(...)]) -> None into a fully working command -- without you writing a parser. It does this by inspecting the function's own signature at import time, the same introspection any Python program can do:

cat > signature_demo.py << 'EOF'
import inspect

from platformops.cli import validate

print(inspect.signature(validate))
EOF
uv run python3 signature_demo.py

Expected output

(ctx: 'typer.Context', path: "Annotated[Path, typer.Argument(help='path to a service definition YAML file')]", as_json: "Annotated[bool, typer.Option('--json', help='print machine-readable JSON instead of plain text')]" = False) -> 'None'

Everything Typer needs is right there in that signature object: path's type (Path, so convert the raw string argument into a Path), that it is required (no default), its help text (inside the Annotated[...]), and that as_json is a --json flag defaulting to False. @app.command() reads exactly this at import time and builds a click.Command from it -- the same mechanism --help's formatting, argument validation, and error messages all come from.

Write the same single command with argparse instead, to see what that inspection step buys you:

cat > validate_argparse_style.py << 'EOF'
"""The same one command, hand-built with argparse -- the parser-building
code Typer writes for you from a type-hinted function."""

import argparse
import sys
from pathlib import Path


def build_parser() -> argparse.ArgumentParser:
    parser = argparse.ArgumentParser(
        prog="validate_argparse_style.py",
        description="Validate a service definition file.",
    )
    parser.add_argument("path", type=Path, help="path to a service definition YAML file")
    return parser


def main(argv=None) -> int:
    args = build_parser().parse_args(argv)
    print(f"would validate {args.path}")
    return 0


if __name__ == "__main__":
    sys.exit(main())
EOF
wc -l validate_argparse_style.py

Expected output

25 validate_argparse_style.py

For one command, 25 hand-written lines against roughly the same for the Typer version -- not a dramatic difference yet. The real gap opens once there is more than one command. cli.py has three @app.command()-decorated functions and nothing else for dispatch:

grep -c "@app.command()" ../src/platformops/cli.py

Expected output

3

The equivalent argparse routing -- before a single line of validation, JSON, or logging logic -- needs subparsers and a manual dispatch chain:

cat > three_commands_argparse_chassis.py << 'EOF'
"""The subcommand-routing skeleton three commands need under argparse --
no validation logic yet, just the wiring Typer's three @app.command()
decorators replace entirely."""

import argparse
import sys
from pathlib import Path


def build_parser() -> argparse.ArgumentParser:
    parser = argparse.ArgumentParser(prog="platformops")
    subparsers = parser.add_subparsers(dest="command", required=True)

    validate_parser = subparsers.add_parser("validate", help="Validate a service definition file.")
    validate_parser.add_argument("path", type=Path)

    subparsers.add_parser("inspect", help="Print the infrastructure inventory report.")
    subparsers.add_parser("version", help="Print the installed platformops version.")

    return parser


def main(argv=None) -> int:
    args = build_parser().parse_args(argv)
    if args.command == "validate":
        print(f"would validate {args.path}")
    elif args.command == "inspect":
        print("would inspect")
    elif args.command == "version":
        print("would print version")
    return 0


if __name__ == "__main__":
    sys.exit(main())
EOF
wc -l three_commands_argparse_chassis.py

Expected output

35 three_commands_argparse_chassis.py

Thirty-five lines of pure routing -- no JSON, no logging, no error handling -- against three decorator lines. This is where "Typer saves you code" actually lives: not inside any one command's body, but in the subcommand dispatch chain and the per-command parser wiring you never have to write or keep in sync as commands are added.

3 -- Exit codes and stdout/stderr are a pipeline's only API​

An analogy: a shipping label and the box's contents are two separate channels on purpose -- a forklift operator routes the box by reading only the label, never by opening it. stdout and stderr work the same way for a script reading your command's output: exit code and stdout are the label (route on these, always); stderr is the box's packing slip (useful detail, never routed on). platformops writes its report to stdout and its log lines to stderr -- verify both independently:

uv run platformops validate ../service-bad.yaml 2>/dev/null

Expected output

../service-bad.yaml: FAIL
  deployment_name: Field required
uv run platformops validate ../service-bad.yaml 1>/dev/null

Expected output

WARNING platformops.cli: ../service-bad.yaml failed validation: 1 field(s)

Redirect either stream away and the other is untouched -- exactly what lets a CI job keep the FAIL report in its log while dropping routine warning noise, or the reverse. Now the gotcha most practitioners never test for: a shell pipeline's exit code is the last command's, not the first's, unless you say otherwise.

uv run platformops validate ../service-bad.yaml | wc -l
echo "pipeline exit code: $?"

Expected output

WARNING platformops.cli: ../service-bad.yaml failed validation: 1 field(s)
       2
pipeline exit code: 0

validate exited 1 -- the file really did fail -- but the pipeline reports 0, because $? belongs to wc, which succeeded at counting lines. A CI step written as platformops validate service.yaml | tee validate.log would silently report success on every failing file. The fix is one shell option:

bash -c 'set -o pipefail; uv run platformops validate ../service-bad.yaml | wc -l; echo "pipeline exit code: $?"'

Expected output

WARNING platformops.cli: ../service-bad.yaml failed validation: 1 field(s)
       2
pipeline exit code: 1

With pipefail set, the pipeline's exit code is the worst of every stage's, so platformops failing is no longer hidden behind wc succeeding. This is not specific to platformops -- it is true of any command in any pipeline -- but it only bites the day a validation step is piped into something else in a CI script, which is exactly the shape teams reach for once a CLI exists.

4 -- CliRunner: testing without a subprocess​

The lab's tests call runner.invoke(app, [...]), not subprocess.run(["uv", "run", "platformops", ...]). CliRunner calls your app object directly, in the same Python process the test is running in -- no new interpreter starts, no uv run resolution happens, stdout and stderr are captured with a simple redirect instead of a pipe to another process. Measure the difference:

cat > clirunner_speed.py << 'EOF'
import time

from typer.testing import CliRunner

from platformops.cli import app

runner = CliRunner()
n = 100
start = time.perf_counter()
for _ in range(n):
    runner.invoke(app, ["version"])
elapsed = time.perf_counter() - start
print(f"{n} in-process CliRunner calls: {elapsed:.3f}s total, {elapsed / n * 1000:.2f}ms each")
EOF
uv run python3 clirunner_speed.py

Expected output

100 in-process CliRunner calls: 0.097s total, 0.97ms each
time (for i in 1 2 3; do uv run platformops version > /dev/null; done)

Expected output

( for i in 1 2 3; do; uv run platformops version > /dev/null; done; )  0.13s user 0.05s system 9% cpu 1.820 total

(zsh's builtin time prints one summary line like this -- if your shell is bash instead, you get three separate lines, real/user/sys; either way the exact numbers depend on your machine, the shape does not.) A hundred in-process calls finish in under a tenth of a second; three real subprocess calls take close to two seconds combined -- each real subprocess pays for a fresh interpreter start and uv's own environment resolution, a cost CliRunner skips entirely because there is no second process. This is why a CLI test suite with dozens of command-and-flag combinations still runs in a fraction of a second, and why CliRunner -- not subprocess-based end-to-end tests -- is the right default for unit-testing a Typer app's logic. A slower, subprocess-based test still has a place: proving the installed platformops command on PATH actually works after uv sync, which is a different question than "does validate's logic behave correctly."

Where you will use this
  • The console-script shim is a plain, readable file, not magic. Use it when: command not found shows up after a fresh install -- check PATH, then check whether uv sync ran after [project.scripts] last changed, before assuming something deeper is broken.
  • Typer's real savings is in dispatch and parser wiring, not in any one command's body. Use it when: deciding whether a new internal tool with a single flat command needs Typer at all -- argparse is still the leaner choice until a second command shows up.
  • A shell pipeline's exit code belongs to its last stage unless pipefail is set. Use it when: writing or reviewing a CI script that pipes a validation or check command into anything else (| tee, | jq, | wc) -- without set -o pipefail, a real failure can be silently reported as success.
  • stdout carries the report, stderr carries the noise, and a script should only ever route on stdout plus the exit code. Use it when: designing a new command's output -- decide up front which stream each line belongs on, before any of it ships.
  • CliRunner calls your app in-process; a real subprocess call proves the installed command actually works. Use it when: choosing what to unit-test with CliRunner versus what to leave to a slower, real end-to-end check of the installed platformops command.

Teardown​

cd ~/platformops
rm -rf dd-scratch

This removes only the scratch folder this page created. Your real service.yaml, cli.py and the rest of ~/platformops are untouched.
