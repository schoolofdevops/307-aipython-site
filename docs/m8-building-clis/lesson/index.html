Building Command-Line Tools

Module slides​

Walk this short whiteboard deck for the big picture, or open it fullscreen.

▶ M8 — Building Command-Line ToolsOpen fullscreen ↗

In M1's solution ladder you learned that a CLI is "a script with an interface" -- flags, help text and exit codes -- and that it earns its place the moment someone other than you runs your code: a teammate, or CI. Every module since M2 has grown a script rung: diagnostics.py you run with python -m, a report you get by importing a function. This module climbs to the CLI rung for real. By the end, platformops is one command with sub-commands under it -- validate, inspect, version -- the shape it keeps for the rest of the course.

1. Why a script needs an interface​

Think about a vending machine versus a friend who hands you a snack. Your friend understands "the blue one, please." A vending machine cannot -- it only understands a fixed set of button presses and coin slots, and in exchange it gives every stranger the exact same behaviour, every time, with no explanation needed beyond the label on each button.

A Python script you run with uv run python -m platformops.diagnostics service.yaml is the friend: it works, but only for someone who already knows the module path, the argument order, and what sys.argv[1] means. A CLI is the vending machine: platformops validate service.yaml is a fixed, labelled interface anyone on the team -- or a CI job that has never seen your source code -- can operate correctly on the first try.

2. Typer: a command is a typed function​

Typer turns a plain Python function into a command with one decorator:

@app.command()
def validate(path: Path) -> None:
    """Validate a service definition file."""
    ...

Typer reads the function's type hints and docstring to build the command: path: Path becomes a required argument, the docstring becomes the --help text. You already write type-hinted functions with docstrings from M4 onward -- Typer's whole idea is that this is already enough information to build a CLI from, so you do not write it twice.

Why Typer over argparse here? argparse is in the standard library and is a completely reasonable choice for one flat command with a handful of flags -- platformops.config and platformops.diagnostics already use it, and that code is not going away. Typer earns its place the moment you have more than one command: it turns each typed function into a sub-command automatically, builds the COMMAND [ARGS] dispatch for you, and formats --help consistently across every command without you writing that formatting once per command. The trade-off is one more dependency. For a three-command tool that will keep growing, that trade is worth it; for a single throwaway script, plain argparse is still the right call.

3. Arguments, options and flags​

  • Argument -- a value the command cannot run without, given by position: platformops validate service.yaml (service.yaml is the argument).
  • Option -- named and usually optional; it can take a value, though in this module every option happens to be a flag.
  • Flag -- an option that only turns something on or off, no value after it: --verbose, --quiet, --json.

The rule of thumb: if the command is meaningless without it, make it an argument. If it changes how the command reports, not what it operates on, make it an option.

4. --help is documentation your users actually read​

Nobody reads a wiki page before running a command; they run platformops --help first. That means --help is not a courtesy -- it is the contract for what your command does, and it has to stay true the moment behaviour changes, because it is the only documentation most users will ever open.

Typer builds this exact tree from your @app.command() functions and prints it for platformops --help; platformops validate --help drills into one command's own arguments and options the same way.

5. Exit codes: the contract a script cannot see, but a CI job lives by​

M7 taught you that diagnose() returns 0 for a clean file and 1 for a problem, and that a silent 0 on a bad file is the single most dangerous bug a validation tool can ship, because nothing downstream reads the printed text -- only the number. A CLI keeps that exact contract and adds one more code: 2 for a usage error -- the caller invoked the command wrong (a missing argument, two flags that contradict each other), a different kind of failure from "the file you gave me is invalid." Typer raises this automatically for a missing required argument; you raise it yourself, deliberately, for a contradiction like --verbose together with --quiet.

6. Output has two audiences​

A human reading a terminal wants a short, formatted line: service.yaml: OK -- checkout-api [prod/us-east-1]. A script piping your output into jq or a test wants one parseable object. Trying to serve both with one format either clutters the human's screen with brackets and quotes, or gives the script text it has to scrape with regular expressions -- fragile either way. The fix is not clever text formatting; it is two output modes, chosen explicitly: plain text by default, machine-readable JSON behind --json, so nothing has to guess which one it is looking at.

--quiet and --verbose are a second, separate axis: they change how much a human sees -- --quiet silences the routine "all is well" line so a CI log stays short, --verbose adds the debug detail from M7's logging -- but neither ever changes what --json prints, because a script that asked for --json should get the same object whether a human also happens to be watching.

7. Confirmation prompts, and --yes for the script that cannot type "y"​

A command that deletes something, or changes a live system, should ask "are you sure?" before a human runs it by hand. But a CI job cannot type "y" back at a prompt; a script that hangs waiting for input just times out. The fix is a --yes (or --force) flag that skips the prompt on purpose, so the same command works both ways: interactive by default, non-interactive when a script asks for it explicitly. You will build this once the toolkit reaches a command that can actually change something (the cloud remediation modules later in this course); for now, know the shape, because you will recognise it the moment you need it.

8. Dry-run: showing the plan without touching anything​

platformops.config already has this pattern -- its --check flag validates and resolves a config and reports what it would write, without writing anything. That is a dry run: run the real logic, stop one step before the side effect, and print exactly what would have happened. It pairs with --yes: dry-run for "show me first," --yes for "skip asking, I already know." Both exist for the same reason -- a command that changes something real needs to be safe in a human's hands and predictable in a script's.

9. Designing for a human and a script, with the same command​

Put the last few sections together and one discipline falls out: never build two separate tools for "a person runs this" and "CI runs this." Build one command whose defaults suit a human (a readable line, a confirmation prompt) and whose flags suit a script (--json, --quiet, --yes), so the exact same binary, the exact same tested code path, serves both. That is what platformops validate and platformops inspect do starting this module, and what every later command in this toolkit keeps doing.

Common pitfalls
  • Treating --help text as an afterthought. It is the only documentation most users open -- write it like someone will read it cold, because they will.
  • Making --json output change based on --verbose. A script asking for JSON should get the same object regardless of how chatty the human-facing side is; keep the two axes independent.
  • Using exit code 1 for both "bad input" and "you called this wrong." Reserve 2 for usage errors, the way Typer already does for a missing argument -- a script branching on the exit code needs to tell the two apart.
  • Adding a confirmation prompt with no way to skip it in CI. Every prompt needs a --yes escape hatch, or the command cannot run unattended, ever.
  • Forgetting that --quiet must never hide a real failure. Quiet means "no chatter on success," not "no news is good news" -- a failure must still be visible even under --quiet.
