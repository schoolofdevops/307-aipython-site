Testing, Securing and Distributing Agent Skills

Module 17 through Module 19 built three real skills, one at a time. Each one was checked by hand: count the words in the frontmatter, count the steps, grep for an agent's name, grep for a stray git commit. That was fine for one skill. It does not scale to ten, and it will not scale to the skill library this toolkit is going to grow into. This module turns those by-hand checks into one reusable tool, adds a third real skill on top of it, and makes the whole library something a team can actually govern — checked the same way every time, versioned, and safe to hand to a new team member without a walkthrough.

1. The library that checks every book before it lends it out​

Imagine a small public library. Anyone can donate a book, and for a while the librarian reads every donation cover to cover before deciding whether to shelve it. That works when there are five books. Once there are fifty, nobody has time to read every one in full — so the librarian builds a checklist instead: does it have a title page, a table of contents, a legible print run, no torn pages. The checklist does not judge whether the book is good. It catches the books that are not even fit to hand to a reader — a missing title page, pages bound in the wrong order — before a patron ever checks one out.

A growing library of agent skills needs the same kind of checklist. scripts/skill_lint.py does not judge whether a skill's advice is good — that still takes a human reading it. It catches the things Module 17 and Module 19 already learned matter mechanically: is the frontmatter short relative to the body, is there a clear trigger phrase, does the Steps section have a sane number of steps, are the required sections all there, does the skill stay usable by any coding agent (not just one), and does a skill that claims to be read-only actually avoid describing a write. Every skill this project ships from here on runs through the same checklist — the same way every book a library shelves gets the same catalog check, no matter what it is about.

Why this matters at work

A checklist that only exists in one senior engineer's head does not scale past that person. The moment a checklist becomes a script anyone can run, a new team member — or a new module in this course — can add a skill and know immediately whether it meets the bar, without asking anyone. That is the actual value of turning M17's and M19's by-hand checks into skill_lint.py.

2. What the checklist actually checks​

skill_lint.py takes the path to one SKILL.md file and prints one JSON report: six checks, each with its own pass/fail, plus one overall verdict.

CheckWhat it catches
Frontmatter ratioA description so long it crowds out the body — under 20% of the file's total words
Trigger phraseNo clear "use this when" (or equivalent) sentence telling an agent when to reach for this skill
Step countA Steps section with too few steps to be a real procedure, or too many to stay a short one (4-8)
Required headingsA skill missing one of the eight sections the working skills already use
Agent-neutral coreAn agent's name (like "Claude") mentioned before the "Optional extensions" section, which would make the skill only work for one coding agent
Read-onlyA skill that claims to be read-only, but describes writing a file or running git commit/git push anyway

None of these six checks reads the skill for meaning. A skill can pass every check and still give bad advice — the checklist is the library's catalog check, not a book review. The lab runs this tool against all three real skills in this project and shows you the real result.

3. A third real skill, built the same way as the first two​

This module also adds incident-context-collector, the third real skill in this project. It follows the exact discipline service-readiness-review and platformops-service-readiness already proved: a thin script, scripts/incident_context.py, imports three functions this course already built and tested — git_status() and docker_info() from Module 11, check_health() from Module 9 — and combines their answers into one report. The skill itself only runs that script and relays what it printed. Nothing about git status, Docker, or an HTTP health check is reimplemented; every answer comes from code that already has its own tests.

This is deliberately the third skill built on the same shape, not a new shape. A library that adds a new cataloging rule for every new book stops being a library and starts being chaos. A skill library holds together the same way: one script-plus-skill pattern, reused every time, is what makes skill_lint.py's checklist meaningful in the first place — it can only check for a consistent shape because every skill actually follows one.

4. What a cross-agent smoke test proves — and what it does not​

Module 17, 18 and 19 each proved a skill worked the same way in both Claude Code and Codex: run claude -p "...", run codex exec "..." with an equivalent prompt, and read both transcripts to see if they matched. scripts/smoke_test_skill.sh formalizes exactly that comparison. Give it a skill name and a short task description, and it runs both agents non-interactively, then checks each agent's output for the field labels the skill's own ## Output section promises (Git:, Docker:, Health:, and so on).

Be precise about what that proves. It proves both agents produced a report shaped the way the skill says it should be shaped — the right fields showed up. It does not prove either agent's judgment inside those fields was correct, and it does not replace the unit tests that already cover scripts/incident_context.py's actual logic. A structural check answers "did the report have the right shape." A unit test answers "is the logic behind that shape correct." A human (or a more careful review) still answers "is this specific report's content right." The Deep Dive shows this gap concretely.

5. Version pinning: a skill's freshness, checkable on its own​

Every skill's frontmatter now carries its own version field, separate from platformops's own version in pyproject.toml. This matters because a skill and the project's Python code do not always change together. A skill can need updating — a new required section, a clearer trigger phrase — with zero lines of Python touched. A Python module can gain a new function with no skill needing a single word changed. Pinning them separately means a skill's own freshness is a fact you can check by reading one line of its frontmatter, not something you have to infer from the project's changelog.

Think back to the library: a book's edition number and the library's own catalog software version are two completely different facts. The library can upgrade its catalog system without reprinting a single book, and a publisher can release a new edition of one book without the library changing anything else. skills/CATALOGUE.md now tracks both — which skill, which version, which release it shipped in — the same way a library's own catalog records each book's edition alongside the catalog system's own version.

Common pitfalls​

  • Treating skill_lint.py failing a check as proof the skill is bad. It is proof the skill's shape has a problem worth looking at — a missing heading, too few steps. Read the detail field before assuming the skill's actual advice is wrong.
  • Assuming a passing smoke test means the skill's judgment is trustworthy. It only means both agents produced a report with the right fields. Passing structure and passing correctness are two different claims — see the Deep Dive.
  • Bumping the skill's version without checking what actually changed. A version bump is a signal to anyone reading skills/CATALOGUE.md that something changed. Bump it when the skill's own content changes, not automatically every time the project's own version changes.
  • Writing a new skill that reimplements what an existing, tested function already does. incident-context-collector only works because it imports git_status(), docker_info() and check_health() instead of shelling out to git and docker itself. A skill that duplicates tested logic loses every test that logic already has.
