Deep Dive — Testing, Securing and Distributing Agent Skills

The lab proved skill_lint.py, incident_context.py, and smoke_test_skill.sh all work — the tests pass, all three real skills lint clean, and both coding agents produced a matching report shape. This page proves three things a careful reviewer would actually check before trusting any of that: that a clean lint pass is evidence the tool works, not evidence the tool always says yes; exactly what a structural smoke test does and does not prove; and why pinning a skill's version separately from the project's version is not just bookkeeping.

Where this picks up

This page assumes ~/platformops at v1.5.0, with scripts/skill_lint.py, scripts/incident_context.py, scripts/smoke_test_skill.sh, and .claude/skills/incident-context-collector/SKILL.md in place from the lab. Nothing here depends on any file being left over from the lab — the broken skill fixture below is created fresh, in a scratch directory outside the project.

cd ~/platformops
uv run platformops version

Expected output

platformops 1.5.0

1 — Proving the lint tool actually catches problems​

All three real skills in this project pass every check skill_lint.py runs. That is a good sign, but a clean pass on its own does not distinguish a working checklist from one that always prints "passed": true regardless of input. The way to tell the difference is to run it against something that should fail, and confirm it actually does.

Build a deliberately broken SKILL.md in a scratch directory — short frontmatter description missing the trigger phrase, only two steps, three missing required headings, and a write-mode open() call sitting right in its Steps:

mkdir -p /tmp/m20-broken-skill
cat > /tmp/m20-broken-skill/SKILL.md << 'EOF'
---
name: broken-example
description: >
  A deliberately broken skill file, built only to prove skill_lint.py
  actually catches real problems instead of always saying yes.
---

# Broken Example

## When to use this

This is handy for demonstrating a lint failure.

## Preconditions

- None.

## Steps

1. Do the thing.
2. Save the result with open(report_path, 'w') as f.

## Tools this skill may use

- A command.

## Output

A report.
EOF
uv run python scripts/skill_lint.py /tmp/m20-broken-skill/SKILL.md
echo "exit=$?"

Expected output

{
  "file": "/tmp/m20-broken-skill/SKILL.md",
  "passed": false,
  "checks": [
    { "name": "frontmatter_ratio", "passed": false, "detail": "32.4% of 71 total words are frontmatter (must be under 20%)" },
    { "name": "trigger_phrase", "passed": false, "detail": "no 'use this when' (or equivalent) trigger phrase found" },
    { "name": "step_count", "passed": false, "detail": "2 step(s) (must be 4-8)" },
    { "name": "required_headings", "passed": false, "detail": "missing: When NOT to use this, Failure handling, Optional extensions" },
    { "name": "agent_neutral_core", "passed": true, "detail": "no agent name before Optional extensions" },
    { "name": "read_only", "passed": false, "detail": "found: open(report_path, 'w" }
  ]
}
exit=1

Five of the six checks correctly failed — the frontmatter ratio, the missing trigger phrase, the short Steps section, the three missing headings, and the write-mode open() call. Only agent_neutral_core passed, because this fixture genuinely never mentions an agent by name — a correct pass, not a missed failure. This is the proof a clean report on the three real skills means something: the same tool that passes them cleanly fails a broken one specifically, and for the right reasons, not randomly.

lint() is also a pure function of the file's contents: same file, same report, every time. Run it twice against the same skill and compare with cmp, not diff — a shell alias or a misconfigured hook can make plain diff report two different files as identical without you noticing:

cd ~/platformops
uv run python scripts/skill_lint.py .claude/skills/incident-context-collector/SKILL.md > /tmp/m20-dd-check1.json
uv run python scripts/skill_lint.py .claude/skills/incident-context-collector/SKILL.md > /tmp/m20-dd-check2.json
cmp /tmp/m20-dd-check1.json /tmp/m20-dd-check2.json && echo identical || echo differs
rm -f /tmp/m20-dd-check1.json /tmp/m20-dd-check2.json

Expected output

identical

2 — What a structural smoke test proves, and the gap it leaves open​

smoke_test_skill.sh checks one thing: did each agent's output contain every field label the skill's ## Output section promises. That is a real, useful check — a skill whose Output shape silently changed, or an agent that ignored the skill entirely and improvised its own report format, would fail it immediately. But it is worth being precise about the boundary.

Consider what the script's check_output() function actually does — it searches for each label string (Git, Docker, Health, Overall) anywhere in the agent's output, case-insensitively:

cd ~/platformops
grep -c 'grep -qi -- "\$label"' scripts/smoke_test_skill.sh

Expected output

1

That single grep -qi call is the entire correctness bar this script enforces. An agent's output would pass this check even if it reported - Git: DIRTY when the tree was actually clean — the string Git appeared, which is all the script verifies. It would also pass if the agent invented a plausible-sounding but wrong container count, since containers_running's value is never inspected, only the presence of the Docker label around it.

This is not a flaw in the script — it is a deliberate, honestly-scoped boundary, the same discipline this project has kept since Module 19's cloud/kubernetes sections: say exactly what you checked, and no more. Three different layers of this project catch three different kinds of mistake, and none of them substitute for another:

LayerWhat it catchesWhat it cannot catch
tests/test_incident_context.pyWrong logic inside gather_report() — e.g. has_concern computed incorrectlyWhether an agent follows the skill's Steps correctly at all
skill_lint.pyA skill's mechanical shape — missing sections, no trigger phrase, a write-mode callWhether the skill's instructions are actually good advice
smoke_test_skill.shAn agent producing a report with the wrong shape, or ignoring the skill's Output format entirelyWhether the values inside a correctly-shaped report are accurate

A report that gets every field label right and every value inside those fields wrong would pass smoke_test_skill.sh and fail nothing else in this project's test suite either, because no existing check inspects a live agent run's field values — the unit tests check the script's logic directly, not an agent's transcript. Closing that specific gap would need either a human reading the transcript, or a second model scoring the first one's output against ground truth — both real techniques, and both out of scope for a lightweight, repeatable smoke test that runs in seconds.

3 — Why a skill's version is not the project's version​

skills/CATALOGUE.md's "Shipped skills" table pins each skill to the release where its content last changed — not the release where platformops itself is currently at. Prove this is not just a coincidence of timing by checking each skill's own frontmatter against the CHANGELOG entry for the release it names:

cd ~/platformops
grep 'version:' .claude/skills/service-readiness-review/SKILL.md
grep -A1 '## \[1.3.0\]' CHANGELOG.md | head -2

Expected output

version: 1.3.0
## [1.3.0] - Script-Backed Agent Skill Foundation
### Added

service-readiness-review's pinned version (1.3.0) matches the release whose CHANGELOG entry describes a change to that exact skill ("Step 2 now runs scripts/review-service.py..."), not 1.2.1, the release where the skill file was first created. The skill's version tracks its own content history, deliberately independent of pyproject.toml's version, which by v1.3.0 had already moved past several unrelated changes to src/platformops/ that this skill's file never touched.

This independence runs in both directions. A future module could add a ninth required section to every skill's shape — that would bump every skill's version, with pyproject.toml's version possibly unchanged if no Python code needed to change alongside it. Equally, this course's Module 21 will add an AWS adapter to src/platformops/ and bump the project version — with none of this module's three skills needing a version bump at all, because nothing about their content changes. A skill's freshness and the project's freshness are two different facts, and pinning them separately is what makes each one checkable on its own, the same way a book's printed edition number tells you nothing about which version of the library's cataloging software recorded it.

Teardown​

rm -rf /tmp/m20-broken-skill

Expected output

Nothing else needs cleanup — every command on this page either read an existing file or wrote to a scratch path under /tmp.

Where you will use this
  • Use it when: a growing set of internal tools, prompts, or agent skills needs the same mechanical bar checked consistently — build one lint tool once, run it in CI, instead of re-reviewing each new addition by hand.
  • Use it when: you are asked whether an automated check "proves" something works — this page is the habit of asking "proves what, exactly" before accepting a green checkmark at face value.
  • Use it when: you are deciding whether a passing integration or smoke test is enough evidence to ship — know which layer (unit test, structural check, human review) actually covers correctness versus shape before you trust a passing run.
  • Use it when: two artifacts in the same repository change on different schedules (a prompt and the code that calls it, a config schema and the service that reads it) — version them separately so each one's freshness is a fact you can check in one place.
