Deep Dive — Safe Kubernetes Operations

The lab proved the plan → refuse → approve → audit → cooldown → timeout flow works end to end: a dry-run plan, a refused execute without --approve, a real restart that fixed a transient failure, a refused rapid second restart, and an honest timed_out on a permanent one. This page goes past "it worked once" into three places an on-call engineer — or an agent reading this module's source before trusting it — actually needs proof, not narration: that the dry run really is validated by Kubernetes itself and not a client-side guess, that the cooldown loop-guard survives across separate process invocations and genuinely expires, and why monitor_rollout() checks updated_replicas instead of trusting rollout_state() == "healthy" alone.

Where this picks up

This page builds its own small kind cluster and its own single Deployment — it does not depend on anything the lab left behind, and it is safe to run whether the lab's Teardown already ran or not.

uv run platformops version

Expected output

platformops 2.4.0

1 — The dry run is a real API server guarantee, not client-side code​

The lesson claims build_restart_plan() never mutates anything, even though it calls the exact same API method (patch_namespaced_deployment) execute_restart() uses for a real restart. Prove it mechanically first, then live.

The grep proof​

grep -c '.patch_namespaced_deployment(' src/platformops/kubernetes_restart.py

Expected output

1

Exactly one literal call site exists in the whole module:

grep -n '.patch_namespaced_deployment(' src/platformops/kubernetes_restart.py

Expected output

284:    apps_client.patch_namespaced_deployment(

That line is inside build_restart_plan(), and it always carries dry_run="All". The real mutation in execute_restart() is reached through getattr(apps_client, action.api_call)(**action.args) — action.api_call is the string "patch_namespaced_deployment", read from data at runtime, so it never appears in the source as a literal .patch_namespaced_deployment( call at all. An automated scan for dangerous write calls — the same kind of check M24 and M28 already prove their modules pass — finds exactly one hit here, and it is the safe one.

The live proof​

Build a small, self-contained scenario:

kind create cluster --name platformops-m29-dd
kubectl create namespace demo
cat <<'EOF' | kubectl apply -f -
apiVersion: apps/v1
kind: Deployment
metadata:
  name: widget
  namespace: demo
  labels:
    app: widget
spec:
  replicas: 2
  selector:
    matchLabels:
      app: widget
  template:
    metadata:
      labels:
        app: widget
    spec:
      containers:
        - name: widget
          image: busybox:1.36
          command: ["sh", "-c", "sleep 3600"]
          resources:
            requests:
              cpu: 50m
              memory: 32Mi
            limits:
              cpu: 100m
              memory: 64Mi
          readinessProbe:
            exec:
              command: ["sh", "-c", "true"]
            initialDelaySeconds: 2
            periodSeconds: 5
EOF
sleep 20
kubectl -n demo get pods

Expected output (excerpt)

NAME                      READY   STATUS    RESTARTS   AGE
widget-7f9588bd4f-8cd8g   1/1     Running   0          33s
widget-7f9588bd4f-wpzt6   1/1     Running   0          33s

Write a small ops config allowing demo:

cat > /tmp/k8s-ops-dd.yaml << 'EOF'
namespace_allowlist:
  - demo
cooldown_seconds: 10
rollout_timeout_seconds: 30
rollout_poll_interval_seconds: 2
audit_log_path: /tmp/k8s-ops-dd-audit.jsonl
EOF

Now compare resourceVersion — a number Kubernetes bumps on every real change — before and after a restart-plan call:

kubectl -n demo get deployment widget -o jsonpath='{.metadata.resourceVersion}'; echo
uv run platformops restart-plan widget -n demo --ops-config /tmp/k8s-ops-dd.yaml
kubectl -n demo get deployment widget -o jsonpath='{.metadata.resourceVersion}'; echo

Expected output

504
demo/widget -- plannable
  before: healthy
  would call: patch_namespaced_deployment (dry_run=All, validated)
504

504 before, 504 after. The API server validated the exact patch this restart would apply and reported it would be accepted — and persisted nothing. This is not a convention this module chose to follow; dry_run="All" is a real Kubernetes API feature, verified here against a real API server, not assumed from documentation.

2 — The cooldown survives across process boundaries, and genuinely expires​

last_restart_at() reads audit_log_path from disk on every call. Prove that matters: two completely separate platformops process invocations, seconds apart, both have to see the same history for the loop guard to mean anything.

The audit log is append-only — start from a clean file, so the count below is exact and not a mix of this run and any earlier one:

rm -f /tmp/k8s-ops-dd-audit.jsonl
uv run platformops restart-execute widget -n demo --approve --ops-config /tmp/k8s-ops-dd.yaml

Expected output

demo/widget -- restarted
  rollout: rolled_out (before=healthy after=healthy, 0.0s of 30s timeout)
  restart triggered -- rollout completed within timeout

Run the exact same command again, immediately — a brand-new Python process, with no memory of the first invocation except what is on disk:

uv run platformops restart-execute widget -n demo --approve --ops-config /tmp/k8s-ops-dd.yaml

Expected output

Error: 'demo/widget' was restarted less than 9s ago -- refusing to restart again this soon (this is the runaway-restart-loop guard, not a bug)

Refused — and no Kubernetes API call was made to get that answer; last_restart_at() only read a file. Now wait past the 10-second cooldown this config set, and try again:

sleep 11
uv run platformops restart-execute widget -n demo --approve --ops-config /tmp/k8s-ops-dd.yaml
cat /tmp/k8s-ops-dd-audit.jsonl

Expected output

demo/widget -- restarted
  rollout: rolled_out (before=healthy after=healthy, 0.0s of 30s timeout)
  restart triggered -- rollout completed within timeout
{"timestamp": "2026-08-05T21:48:36.340838+00:00", "namespace": "demo", "name": "widget", "status": "restarted", "rollout_outcome": "rolled_out", "before_rollout_state": "healthy", "after_rollout_state": "healthy", "timeout_seconds": 30, "elapsed_seconds": 0.0, "approved_by": "gshah"}
{"timestamp": "2026-08-05T21:48:49.610237+00:00", "namespace": "demo", "name": "widget", "status": "restarted", "rollout_outcome": "rolled_out", "before_rollout_state": "healthy", "after_rollout_state": "healthy", "timeout_seconds": 30, "elapsed_seconds": 0.0, "approved_by": "gshah"}

Two real, successful restarts thirteen seconds apart, with the middle attempt refused — the cooldown is genuinely time-bound, not a permanent lockout, and it is genuinely durable across process restarts, not an in-memory flag that would have reset the instant the first platformops process exited.

Why this is the loop guard an agent needs

An AI agent calling this CLI as a tool does not share memory between calls the way a long-running program would — each invocation is its own process, exactly like the two restart-execute calls above. If the cooldown lived in memory, an agent retrying a failed or unclear result would restart the same Deployment every single time, with nothing stopping it. Because the guard lives in the audit log instead, it holds no matter what is calling it, or how many separate times.

3 — Why updated_replicas, not rollout_state() alone​

monitor_rollout() does not return rolled_out the moment rollout_state(status) == "healthy". Read the exact condition:

grep -n 'updated_replicas == status.desired_replicas' src/platformops/kubernetes_restart.py

Expected output

325:        if final_state == "healthy" and status.updated_replicas == status.desired_replicas:

Both halves have to be true together. Here is why that second half is not decoration. A Deployment mid-rollout can have every replica ready while some of those ready replicas are still Pods from the previous ReplicaSet — Kubernetes tears down old Pods gradually, not all at once, so a Deployment can sit at ready=2/2, available=2/2 (which rollout_state() alone reports as "healthy") for a moment where zero of those two Pods are actually new. updated_replicas counts only Pods matching the Deployment's current pod-template hash — it is the one field that tells "the replicas that are up" and "the replicas this restart actually created" apart.

The lab's own captured evidence already backs this: every rolled_out entry in k8s-ops-audit.jsonl recorded after_rollout_state: "healthy" — but monitor_rollout() only stopped polling and returned that outcome once updated_replicas matched desired_replicas too, on each real run. A version of this check that dropped the updated_replicas condition would have reported rolled_out on some runs several polls earlier than it did — sooner, but wrongly, on a Deployment whose new Pods were not actually up yet.

Common pitfalls​

  • Assuming any server-side dry_run parameter behaves the same for every API and every write verb. It does here, for patch_namespaced_deployment — always verify a dry run really leaves resourceVersion unchanged for the specific call you rely on, the way this page just did, instead of assuming the parameter name alone is proof.
  • Testing the cooldown by calling the function twice in the same Python process. That proves nothing about the real failure mode — an in-memory guard would also "work" inside one process. The proof that matters is two separate CLI invocations, which is what this page ran.
  • Reading only ready_replicas/available_replicas when checking whether a rollout finished. Both can already equal desired_replicas from Pods the previous rollout left behind — always cross-check updated_replicas too, whether you are writing your own rollout-watcher or reading this module's.
  • Shortening rollout_timeout_seconds to make demos faster, then leaving it that low in a real ops config. A short timeout that suits a lab recording will report timed_out on real workloads that would have recovered given a realistic amount of time — tune it back up for anything but a demo.
Where you will use this
  • Comparing resourceVersion before and after a dry-run call. Use it when: you are adding a new write-capable tool anywhere in your platform and want a five-second, mechanical check that a claimed "safe preview" mode is not secretly mutating the object it previews.
  • A disk-backed rate limit instead of an in-memory one. Use it when: you are building any guardrail meant to stop a script, cron job, or AI agent from repeating an action too fast — if the caller can start a new process between attempts, an in-memory guard protects nothing.
  • Checking updated_replicas, not just replica readiness, before declaring a rollout done. Use it when: you write your own rollout-watching logic, a readiness gate in a CI/CD pipeline, or any code that has to know whether a Deployment's new Pods, not just some Pods, are up.
  • Running the exact CLI command twice from two separate shells to test a loop guard. Use it when: reviewing a pull request that adds any approval or rate-limiting logic — a same-process unit test alone cannot prove a guard survives the way a real caller will actually use it.
