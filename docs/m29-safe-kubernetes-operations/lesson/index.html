Safe Kubernetes Operations

Module 28 built workload-inspect — a tool that reads a Deployment's real health and never once writes to the cluster. It told you plainly it was leaving the acting part for later: "the governed, approval-gated version that IS allowed to act on a cluster is Module 29's Safe Kubernetes Operations, not this one." This is that module.

The one action this module is allowed to take is a restart — the same thing kubectl rollout restart deployment/<name> does. It is a small, well-understood action: Kubernetes replaces every Pod with a fresh one, using the same Deployment spec. But "small" is not the same as "safe by default." A restart command with no guardrails can run against a namespace nobody approved, be triggered without anyone signing off, or fire over and over in a tight loop — the last one is a real risk once an automated agent, not a person, is the thing calling this tool. Every guardrail in this module exists because "small action" is not the same promise as "safe action."

Why this matters at work

An on-call engineer restarts things constantly — a stuck Pod, a service that needs to pick up a config change, a workload that has been acting strange since a dependency blipped. Doing this by hand with kubectl is fine for one person, once. The moment you want an agent, a runbook, or a scheduled job to do it instead, "just restart it" stops being a small ask. Who is allowed to trigger a restart, and where? Did anyone actually approve this one, or did a script assume it was fine? What happens if the same trigger fires five times in ten seconds because of a bug in the caller, not the cluster? This module builds the tool that answers all three questions before it ever touches a real Deployment — and is honest, every time, about whether the restart it just performed actually fixed anything.

1. A power-cycle needs a work order, not just a hand on the switch​

Picture a data center technician standing in front of a rack. A server is misbehaving, and power-cycling it — turning it off, then on again — often clears whatever state it is stuck in. But no technician worth trusting just walks up and hits the power switch because it seems like a good idea. There is a work order first, naming the exact machine and why. A second person signs off before power is actually cut. Every power-cycle gets logged — which machine, when, who approved it. And there is a hard rule everyone follows: you do not power-cycle the same machine again five minutes later just because it is still acting up. Doing that usually means something else is wrong, and cycling it again will not fix a problem a restart cannot fix — it just hides how bad the underlying issue actually is.

kubernetes_restart.py works the same way for a Kubernetes Deployment. The plan (restart-plan) is the work order — it names the exact Deployment and checks whether this kind of action is even allowed here, before anyone signs off on anything. Approval (--approve) is the second person's sign-off — nothing happens without it. The audit log is the maintenance log — every real restart is written down with what the rollout looked like before and after. And the cooldown is the "not five minutes later" rule — the same target cannot be restarted again until enough time has passed, whether the second attempt comes from a person, a script, or an AI agent retrying too eagerly.

2. Three gates, not two​

Module 25's cloudremediate.py used two independent gates — an allowlist and --approve — because a tag-and-encrypt fix, once applied, does nothing more if you run it again: the second attempt just finds nothing left to do. A restart is different. Restarting a Deployment twice is not "safe to repeat," it is two real rollouts, two sets of Pods torn down and rebuilt. That is why this module needs a third, independent gate the AWS module never did.

The namespace allowlist is the first gate, in k8s-ops.example.yaml. Only a namespace on this list is ever a valid restart target — checked before this module even tries to read the Deployment, so a namespace that is not allowed is refused the same way whether the workload inside it is healthy or badly broken. --approve is the second gate — run restart-execute without it, and the command refuses, prints the plan again, and exits non-zero; it never quietly does nothing and reports success. The cooldown is the third — even with an allowed namespace and --approve, the exact same namespace/Deployment cannot be restarted again until cooldown_seconds has passed since its last real restart. This is what a data center's "not five minutes later" rule protects against here: an agent stuck in a retry loop, a runbook step that fires twice by accident, a person who reruns a command because they were not sure the first one worked.

3. A real dry run, not a guess written in Python​

Kubernetes' own API server can validate a change without applying it — pass dry_run="All" on a write call, and the server checks the object is well-formed and would be accepted, then throws the result away instead of saving it. This module's restart-plan uses exactly that, on the exact same patch restart-execute would send for real. It does not write its own client-side guess at what "the change would work" means — it asks the one system that actually knows.

This is provable, not just claimed. Before running restart-plan on a real Deployment, its resourceVersion (a number Kubernetes bumps every time an object actually changes) reads 467. After restart-plan runs, it still reads 467 — nothing changed, even though the exact same API call that restarts the Deployment for real was made, just with dry_run="All" attached.

The same method name, two very different outcomes

build_restart_plan() and the real mutation inside execute_restart() both call patch_namespaced_deployment — but only one of them ever appears as a literal call in this module's source. execute_restart() reaches the write method through getattr(apps_client, action.api_call)(...), dispatched from data, never spelled out by name. Grep the file for .patch_namespaced_deployment( and exactly one match comes back — the dry-run one inside build_restart_plan(). The Deep Dive proves this live.

4. Restart-plan is safe to run any number of times — execute rebuilds it fresh anyway​

Like remediate-plan in Module 25, restart-plan only reads. Run it ten times back to back and nothing changes, because the dry run never persists. But execute_restart() does not simply trust a plan handed to it — it rebuilds the plan from scratch, with a fresh dry run against current live state, immediately before the real patch. That is what makes the namespace allowlist apply at execute time too, not only when a caller happened to call restart-plan first — and it is what catches a Deployment that was deleted, or a namespace that was removed from the allowlist, in the gap between planning and approving.

5. The cooldown reads its memory from the audit log, not from RAM​

An in-memory "don't restart this again for five minutes" flag only works if the same process stays running. A script, an agent, or a CI job calling platformops restart-execute starts a brand-new process every single time — so the loop guard has to remember across process boundaries, or it remembers nothing at all.

last_restart_at() answers "when was this exact namespace/Deployment last really restarted?" by reading the audit log file itself, every time, from disk. Two completely separate invocations of restart-execute --approve, seconds apart, both see the same history — because they are reading the same file, not two different copies of a variable that reset when the first process exited. The Deep Dive proves this with two real, separate command runs: the second is refused, and after the cooldown window genuinely passes, a third run on the same target succeeds again.

6. Watching the rollout, honestly, up to a timeout​

A restart does not finish the instant the patch call returns — Kubernetes still has to tear down old Pods and bring up new ones. execute_restart() polls the Deployment after patching it, the same way Module 28's rollout_state() already knows how to summarize a Deployment's health, and stops as soon as every replica is both ready and freshly rolled out — checking updated_replicas, not just ready_replicas, because a Deployment mid-rollout can still show old, already-ready Pods from the previous rollout long enough to look "healthy" by replica count alone, even though the new Pods are not up yet.

If the rollout has not finished by rollout_timeout_seconds, execute_restart() gives up and reports timed_out — not an error, a plain fact. The restart still happened; it just did not fix the problem in time, or at all.

7. What a restart can fix, and what it never will​

This is the part a governed tool has to be honest about, the same way Module 25 was honest that approved-regions and max-age-days can never be auto-remediated. A restart forces Kubernetes to try starting a Deployment's containers again, from the same spec. That genuinely recovers a Deployment stuck on a transient condition — a ConfigMap that did not exist yet when the Pods first tried to start, a dependency that was briefly unreachable — because trying again, right now, with the world in its current (now-fixed) state, is exactly what was missing.

It does nothing for a permanent condition. A container image tag that does not exist will still not exist after the restart — Kubernetes will dutifully create new Pods, and those new Pods will fail to pull the same missing image, forever. This module's lab restarts a Deployment in exactly that state on purpose: the restart really happens, a fresh rollout really starts, and execute_restart() still, correctly, reports timed_out — because that is the truth. A tool that quietly reported success here would be worse than useless; it would teach an operator, or an agent reading its output, to stop looking for the real cause.

Common pitfalls​

  • Treating a restarted status as "fixed." status: restarted only means the patch was applied and a new rollout began — check rollout_outcome (rolled_out vs timed_out) to know whether it actually worked.
  • Assuming rollout_state() == "healthy" alone proves the rollout finished. Old Pods from the previous rollout can still be ready while new ones are not up yet — always check updated_replicas == desired_replicas too, the same check monitor_rollout() makes. Never mistake a stale-but-ready read for a completed restart.
  • Expecting the cooldown to reset when you re-run the CLI. It will not — last_restart_at() reads the audit log on disk, so restarting the process does not reset anything. The cooldown is tied to the target and the clock, not to a running program.
  • Adding a namespace to the allowlist for one urgent restart, then forgetting to remove it. The allowlist is a standing decision, not a one-time favor — treat every namespace on it as "restarts here are approved as an ongoing policy," not "approved just this once."
  • Restarting a Deployment with a permanently bad image or config and expecting the timeout to be a bug. A timed_out result on a workload that cannot recover is the tool working correctly, not failing — the fix in that case is to correct the image or config, not to restart again.
