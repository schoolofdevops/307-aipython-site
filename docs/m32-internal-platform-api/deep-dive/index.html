Deep Dive — Building Internal Platform Capabilities

The lab proved every route in platformops.api produces the same answer the matching CLI command does, and that POST /remediations/plan never mutated a real Floci bucket. This page goes one level deeper on two claims the lesson made but did not fully prove on their own: that this module really has no way to call an adapter directly or execute a remediation -- not just that it happens not to today -- and what actually happens, in what order, when a request arrives with both a bad X-API-Key and a malformed body. That second question turns out to matter for a reason the lesson only mentioned in passing: what an unauthenticated caller is allowed to learn about a request that was never going to succeed anyway.

Where this picks up

This page assumes ~/platformops at v2.7.0, with src/platformops/api.py and the api-serve CLI command in place from the lab.

cd ~/platformops
uv run platformops version

Expected output

platformops 2.7.0

1. The reuse contract, proven by grep -- not just "it happens to call the right function today"​

The lesson's central claim is that every route in api.py is a thin wrapper: it calls a function this project already built, and never talks to an adapter directly. The strongest version of that claim is not "no route currently makes a raw AWS/GitHub/Kubernetes call" -- it is "this module could not, because it never imports the library that call would need."

grep -E '^import (boto3|httpx)$|^from (boto3|httpx|kubernetes)' src/platformops/api.py
echo "exit=$?"

Expected output

exit=1

Zero matches -- api.py imports no adapter library directly, only already-tested platformops functions:

grep '^from platformops' src/platformops/api.py

Expected output

from platformops import __version__
from platformops.awsclient import get_aws_client
from platformops.cloudremediate import (
from platformops.config import ConfigError, ConfigNotFoundError, load_yaml_dict
from platformops.incidentcontext import collect_incident_context
from platformops.releasecheck import run_release_check
from platformops.servicedef import ServiceDefinition, validate_service

Every one of those seven imports is a function or a small set of exceptions this course already built and already tested in an earlier module -- awsclient.get_aws_client() (Module 21), cloudremediate (Module 25), config (Module 6), incidentcontext.collect_incident_context() (Module 31), releasecheck.run_release_check() (Module 26), servicedef (Module 5). This is the same "no import, no path to add it quietly" argument Module 31's Deep Dive already made for its own read-only guarantee, applied here to the reuse guarantee instead: adding a raw boto3.client() call inside a route handler would require adding a new top-level import first, a far more visible change in code review than adding one more line inside a function that already has the library in scope.

The cloudremediate import is the one worth reading in full, because it is also the plan-only proof:

grep -A 8 '^from platformops.cloudremediate import' src/platformops/api.py

Expected output

from platformops.cloudremediate import (
    FindingNotFoundError,
    append_audit_log,
    build_remediation_plan,
    find_finding,
    load_remediation_config,
    plan_to_dict,
)
from platformops.config import ConfigError, ConfigNotFoundError, load_yaml_dict

Six names, and build_remediation_plan() -- the read-only planner -- is the only one of them that touches a finding. execute_remediation_plan() and execute_remediation_batch(), the two functions in this project actually allowed to call a write-mode AWS API, are not in that list. A direct check confirms neither name appears anywhere in this file as an importable symbol:

grep -E '^\s*(execute_remediation_plan|execute_remediation_batch),?\s*$' src/platformops/api.py
echo "exit=$?"

Expected output

exit=1

The only two places those two names appear anywhere in api.py at all are inside the module's own docstring, explaining in prose exactly why they are never imported -- not inside an import statement, and not inside a function body:

grep -n 'execute_remediation' src/platformops/api.py

Expected output

29:imports `cloudremediate.execute_remediation_plan()` or
30:`execute_remediation_batch()` -- there is no `/remediations/execute` route,
412:        `cloudremediate.execute_remediation_plan()` at all.

Lines 29-30 and 412 are prose inside triple-quoted docstrings, not code. There is no code path in platformops.api -- today, or reachable by adding one more line to an existing function -- that could call either execute function, because the module doing the calling never holds a reference to them at all.

2. Auth is checked before the body is even parsed -- and that is a deliberate, useful ordering​

require_api_key() reads the X-API-Key header; services_validate()'s other parameter, payload, is the request body validated against ServiceValidateRequest. It would be reasonable to assume these two checks are independent, and that whichever one fails first is arbitrary. Live evidence says otherwise.

First, a request with a valid key but a body missing the required path field:

uv run platformops api-serve --port 8092 --audit-log /tmp/dd-audit.jsonl &
sleep 2
curl -s -w "\nHTTP %{http_code}\n" -X POST http://localhost:8092/services/validate \
  -H "X-API-Key: dev-ci-bot-key-local-only" -H "Content-Type: application/json" -d '{}'

Expected output

{"detail":[{"type":"missing","loc":["body","path"],"msg":"Field required","input":{}}]}
HTTP 422

A 422 -- FastAPI's own Pydantic validation error, since require_api_key() accepted the key. Now the same malformed body, with a wrong key instead:

curl -s -w "\nHTTP %{http_code}\n" -X POST http://localhost:8092/services/validate \
  -H "X-API-Key: totally-wrong" -H "Content-Type: application/json" -d '{}'

Expected output

{"detail":"missing or invalid X-API-Key"}
HTTP 401

401, not 422 -- even though the body is equally broken in both requests. require_api_key() runs and raises before FastAPI ever attempts to validate payload against ServiceValidateRequest. This is not an accident of this one route; it holds because caller: RequireApiKey -- a header-based dependency -- resolves independently of, and ahead of, the body model FastAPI has to actually read and parse off the wire.

This ordering is not just a curiosity -- it is the reason an unauthenticated or wrongly-authenticated caller learns nothing about what a valid request would even need to contain. A caller presenting no key, or the wrong one, always gets the same 401 missing or invalid X-API-Key -- never a 422 revealing that this particular endpoint expects a JSON body shaped {"path": "..."}. Reversing that order (validating the body first, checking identity second) would leak the endpoint's request schema to a caller who was never going to be let through in the first place -- a small but real piece of information a hostile caller should not get for free.

3. The audit trail is unconditional -- including a request that fails validation​

_audit_middleware() wraps call_next(request) and writes one record after it returns, whatever that response turned out to be. FastAPI turns both a validation failure and an HTTPException into an ordinary Response object internally -- neither one is an unhandled exception that would skip the middleware -- so the audit log captures both outcomes as ordinary entries, not as gaps.

cat /tmp/dd-audit.jsonl

Expected output

{"timestamp": "2026-08-06T03:29:32.678360+00:00", "event": "api-server-started", "version": "2.7.0"}
{"timestamp": "2026-08-06T03:30:04.201359+00:00", "method": "POST", "path": "/services/validate", "caller": "ci-bot", "status_code": 422, "duration_ms": 25.3}
{"timestamp": "2026-08-06T03:30:34.777133+00:00", "method": "POST", "path": "/services/validate", "caller": "anonymous", "status_code": 401, "duration_ms": 4.7}

Two entries, matching the two requests from Section 2 exactly. The first shows caller: "ci-bot" with status_code: 422 -- proof that require_api_key() really did run and resolve an identity before the body validation failed, exactly as Section 2 argued from the HTTP status codes alone. The second shows caller: "anonymous" with status_code: 401 -- the key was never valid, so request.state.caller was never set, and _audit_middleware()'s getattr(request.state, "caller", ANONYMOUS_CALLER) falls back to the same default GET /health uses. One audit log, one honest record of every request this server received, regardless of which of its two gates -- authentication or body validation -- a request failed, or passed both.

kill %1
rm -f /tmp/dd-audit.jsonl
Where you will use this
  • "No import" is a stronger reuse/safety guarantee than "no call found today." Use it when: you are reviewing a pull request that adds a new route to an internal API like this one -- check the import list first, not just whether the new route's body looks safe today. An import is the one thing that has to change before a dangerous call could ever be added.
  • Dependency resolution order (auth before body) is a real security property, not an implementation detail. Use it when: you are designing any authenticated API -- put identity checks on request parts (headers, path) that resolve independently of the body, so a rejected caller never learns anything about the shape of a request they were never going to be allowed to send.
  • An audit log that only fires on success is not an audit log. Use it when: you are adding logging or auditing to any HTTP service -- wrap the whole request/response cycle (middleware, not a line inside each handler) so a 401, a 422 and a 200 all leave the same kind of record, the same way this module's audit log treats every outcome as worth writing down.

Teardown​

Nothing from this page persists beyond the two temporary server instances (Section 2's, killed at the end of Section 3) and /tmp/dd-audit.jsonl, already removed above. No Floci resource, real GitHub call, or file inside ~/platformops was touched by this page.
