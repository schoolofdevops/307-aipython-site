Building Internal Platform Capabilities

Every command this course has built so far runs one way: someone types platformops <command> in a terminal that has this project installed. That is fine for the person who built it. It is not fine for the twenty other engineers in the org who also need a release-readiness verdict, or an incident report, or a quick check on whether a service definition is valid -- and who should not have to clone this repository, install uv, and learn Typer's option names just to ask a question this project already knows how to answer. This module turns five of those answers into a small, self-service HTTP API anyone on the team can call.

Why this matters at work

A teammate on a different team pings you: "can you check if payments is ready to release?" You run platformops release-check, paste the output into Slack, and move on. Multiply that by every team, every day, and you become a human API -- a bottleneck standing between a question this project can already answer and the person asking it. An internal API removes you from that loop. Anyone with a key can call GET /release-readiness themselves, from a CI job, a Slack bot, or a dashboard -- while you keep building the one place that answer actually comes from.

1. A recipe you cook, and a dish anyone can order​

Picture a home cook who has perfected a recipe. It is genuinely good -- but only the cook can make it, because only the cook has the recipe, the exact technique, and the specific pans in their own kitchen. If someone else wants that dish, they need to learn to cook it themselves, in their own kitchen, the cook's way.

A restaurant turns that same recipe into a menu item. The kitchen still cooks it exactly the same way -- nothing about the recipe changes -- but now anyone can order it without knowing how to cook at all. They read a short menu description (the recipe's "contract": what you get, what it costs, how long it takes), they place an order, and the kitchen -- not the customer -- does the work.

platformops up to this module is the recipe: powerful, but only usable by someone who has this project installed and knows its commands. This module's POST /services/validate, GET /health, GET /release-readiness, GET /incident-context and POST /remediations/plan are the menu. Three ideas make that difference real, not just a metaphor:

  • Self-service -- a caller does not need platformops installed, does not need to know Python, and does not need to ask you to run a command on their behalf. They send one HTTP request.
  • A golden path -- one well-lit, supported way to get this answer, instead of everyone writing their own script that half-reimplements release-check slightly differently.
  • A stable contract -- the request shape and response shape are declared up front (a Pydantic model), the same way a menu states exactly what a dish contains before you order it. The kitchen can change how it cooks the dish; the menu item's description does not change underneath a customer who already knows what to expect.

2. Every route is a thin wrapper -- never a second recipe​

The one mistake that would ruin this idea: writing the release-readiness logic a second time, slightly differently, inside the API. Two recipes for the same dish drift apart -- one kitchen seasons the sauce differently, and now the same menu item tastes different depending on which kitchen made it. This project already has exactly one implementation of each answer this API serves, and this module is not allowed to add a second:

  • POST /services/validate calls config.load_yaml_dict() + servicedef.validate_service() -- the same two calls the CLI's validate command already makes (Module 5/6).
  • GET /release-readiness calls releasecheck.run_release_check() -- the same function the CLI's release-check command already calls (Module 26).
  • GET /incident-context calls incidentcontext.collect_incident_context() -- the same function the CLI's incident-collect command already calls (Module 31), itself composing six adapters from six earlier modules.
  • POST /remediations/plan calls cloudremediate.build_remediation_plan() -- the same function the CLI's remediate-plan command already calls (Module 25).

Every route handler's job is small and mechanical: turn the HTTP request into the same keyword arguments the matching CLI command already builds, call the one function that already exists, and shape its return value into a response. No route re-decides what "ready" means, re-gathers evidence a different way, or re-implements a validation rule. The lab proves this two ways: for POST /services/validate and POST /remediations/plan, by running the CLI and the API against the exact same input -- a local file, a real Floci bucket -- and diffing the output live; for GET /release-readiness and GET /incident-context, whose evidence comes from GitHub, Kubernetes and observability backends this laptop lab does not stand up identically on every run, by a test that monkeypatches the underlying function and asserts the route calls it with the right arguments and shapes its return value correctly -- the same "prove the wiring, not the already-tested logic underneath it" discipline this project's other test suites already use. Either way, api.py itself is also grepped for anything that looks like domain logic, and finds none.

3. Who can call this, and why -- API keys, and what a bigger system would add​

A script only you can run has an implicit access control: whoever can log into your laptop. The moment that same capability is reachable over the network, "who is calling this, and why" stops being implicit and has to become a real decision. This lab builds one real, working answer, appropriately scoped for a local, internal tool, and is honest about what a larger production system would add on top:

  • What this lab actually builds: every route except GET /health requires a request header, X-API-Key, checked against a small YAML file mapping keys to caller names (api-keys.example.yaml). A request with a missing or wrong key gets a real 401 Unauthorized -- there is no route that quietly proceeds without one. GET /health is the one deliberate exception: a liveness probe an orchestrator calls needs to succeed before it can prove it even knows who it is.

  • What a production version would add, and why this lab does not build it: a shared static key in a file is a real access control, but it is a blunt one -- everyone with the key looks identical, keys rarely rotate, and a leaked key works forever until someone notices. Three ideas a production internal-platform API layers on top:

    • OAuth2 client-credentials -- a caller (a CI job, a service) exchanges its own identity for a short-lived token from an identity provider, instead of holding a long-lived secret directly.
    • mTLS (mutual TLS) -- both sides present a certificate; the caller's certificate itself is the identity, which is much harder to leak by accident than a string in a header.
    • Per-caller scopes -- "this caller may call /release-readiness but not /remediations/plan" is a decision an API-key-only design like this lab's cannot express without another layer on top.

    This project is a course about DevOps and platform Python, not a full identity platform -- these three ideas are real and worth knowing, but this lab's code does not implement them. Naming that boundary honestly matters more than pretending a shared key is something it is not.

4. An audit trail -- who called what, when, with what result​

Every governed mutation this course has built already writes an audit log: Module 25's cloud remediation and Module 29's governed Kubernetes restarts each append one JSON line per real change, because "it worked" is not enough during an incident review -- you need to know who acted, when, and what happened. An HTTP API reachable by more people than just you needs that same discipline applied more broadly: not only to mutations (this API has none beyond a dry-run plan), but to every request, because "someone tried to call /remediations/plan with the wrong key three times in a row" is exactly the kind of signal an audit trail exists to surface.

This module reuses that same audit-log function -- cloudremediate.append_audit_log() -- rather than inventing a second one. Every request this server receives, whatever happens to it, becomes one JSON line: the method and path, the caller's identity (or "anonymous", for a request an invalid key was rejected from, or GET /health, which needs none), the HTTP status code, and how long it took.

5. A protocol status and a business verdict are two different things​

GET /release-readiness and GET /incident-context almost always answer 200 OK -- even when the release is not ready, or the incident report is only partial. That is a deliberate design choice, not an oversight. An HTTP status code answers one question: did the server do its job and produce a response? A 200 means yes. Whether that response is good news -- ready versus not_ready, ok versus partial -- is business data carried inside the response body, in a verdict or status field, the same way the CLI's own --json output already carries it in a field, not in its exit code's sign. A caller branches on that field, exactly the way a script branches on the CLI's exit code -- not on the HTTP status code alone. Collapsing "the server worked" and "the news was good" onto the same status code is a common API design mistake this lab avoids on purpose.

6. Plan, never execute -- the same safety line Module 25 already drew​

POST /remediations/plan is deliberately plan-only. It calls build_remediation_plan() -- which only ever reads live state -- and never execute_remediation_plan(), which is the one function in this project that is allowed to call a write-mode AWS API. There is no /remediations/execute route in this module, and platformops.api does not even import the execute-side function -- so there is no code path anywhere in this file that could mutate a cloud resource.

Module 25 already worked out what executing a remediation safely needs: an explicit --approve, a rule on an allowlist, and an audit-log record of exactly what changed. Exposing that same power over an open HTTP endpoint on localhost:8080 would need an equivalent of every one of those gates -- and, on top of them, a much stronger notion of who is allowed to approve a real mutation than one shared API key can express. Building that endpoint without solving that problem first would be a real safety regression, not a convenience -- so this module does not build it. If your team later decides an execute endpoint is worth the engineering it needs, the checklist is exactly the gap between this section and Module 25's --approve/allowlist/audit-log design: per-caller identity strong enough to attribute an approval to a real person, a scope that limits which caller may approve which rule, and the same allowlist and audit trail Module 25 already built, now enforced server-side instead of trusted from a CLI flag.

Common pitfalls​

  • Reading a 200 response as "everything is fine." GET /release-readiness and GET /incident-context return 200 whenever they successfully produced a report -- check the body's verdict/status field for the actual news, the same way you would check the CLI's printed report, not just its exit code's sign.
  • Assuming /health needs a key, because every other route does. It is the one deliberate exception -- a liveness probe has to succeed before it can prove it knows who is calling. Everything else always requires X-API-Key.
  • Treating the shared API key as equivalent to a full identity system. It answers "does this caller have a valid key," not "should this specific caller be allowed to approve a mutation." Do not reach for this pattern to gate anything more consequential than the read-only and plan-only routes this lab actually builds.
  • Expecting a /remediations/execute route. There is not one, on purpose -- see Section 6.
  • Reimplementing a route's logic instead of calling the existing function. If a route handler in api.py ever grows an if/else that decides business logic (what counts as "ready", how to gather cloud evidence), that is a sign the reuse discipline broke -- the fix is always to call the existing function, never to duplicate what it already does.

Next: the lab builds platformops.api test-first, one route at a time, wires api-serve into the CLI, starts the server for real, and proves -- with real curl calls compared against the real CLI -- that both produce the same answer from the same input. It ships as v2.7.0, the PlatformOps Internal API.
