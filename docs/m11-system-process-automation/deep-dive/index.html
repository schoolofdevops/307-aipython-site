Deep Dive — What subprocess Actually Does to a Child Process

The lab built local_ops.py on three rules stated as fact: pass arguments as a list, always pass a timeout, never raise on a normal failure. This page opens up why those rules exist at the level of the operating system underneath subprocess -- what a shell actually does with a string before your command ever runs, why subprocess replaced os.system and os.popen instead of sitting alongside them, why reading a command's output the naive way can hang your script even though nothing is actually broken, and what a timeout really does to a process that will not finish. You will use this the day you are asked to review a PR that builds a shell command from a variable, when a script that streams a large build log mysteriously freezes, or when you have to decide whether killing a stuck subprocess outright is safe for the thing it was running.

Where this picks up

You need ~/platformops at v0.9 from the lab, with local_ops.py's git_status(), git_log(), docker_info() and container_list() in place. Every command below runs a short, disposable script in its own scratch folder -- none of them touch local_ops.py, cli.py or your project's git history.

mkdir -p ~/platformops/dd-scratch && cd ~/platformops/dd-scratch

Re-running any command on this page is safe.

1 — Shell injection: what shell=True actually lets through​

The lesson already told you not to use shell=True with an interpolated string. This section proves what "reinterpreted" means concretely, with a marker file standing in for real damage -- never an actual destructive command.

dd-scratch/injection_demo.py
import subprocess
from pathlib import Path

MARKER = Path("pwned_marker.txt")
MARKER.unlink(missing_ok=True)

# Stands in for a value this code does not control -- imagine it arrived
# through a --path option, a webhook payload, or a filename another team
# supplied.
attacker_controlled_path = "; touch pwned_marker.txt #"

print("-- unsafe: shell=True with an interpolated string --")
subprocess.run(f"git log {attacker_controlled_path}", shell=True)
print(f"marker file created by an injected command: {MARKER.exists()}")
MARKER.unlink(missing_ok=True)

print()
print("-- safe: argument list, no shell involved --")
result = subprocess.run(
    ["git", "log", attacker_controlled_path], capture_output=True, text=True
)
print(f"git's own exit code: {result.returncode} (git treated the whole string as one path and rejected it)")
print(f"marker file created: {MARKER.exists()}")
uv run python3 dd-scratch/injection_demo.py

Expected output

-- unsafe: shell=True with an interpolated string --
commit 85e2603 (HEAD -> main, tag: v0.9)
Author: Test User <test@example.com>
Date:   Tue Aug 4 13:12:32 2026 +0530

    fix check-security false positives on own docstrings

... (git log output from this repository -- yours will differ) ...
marker file created by an injected command: True

-- safe: argument list, no shell involved --
git's own exit code: 128 (git treated the whole string as one path and rejected it)
marker file created: False

The shell=True line hands the string git log ; touch pwned_marker.txt # to /bin/sh before any of it becomes a program call. The shell reads that string exactly the way it would read a line you typed at a prompt: git log is one command, ; ends it and starts a new one, touch pwned_marker.txt is a second, completely unrelated command, and # comments out anything after it. git never even sees the injected part -- the shell already split it into two commands before either one ran. The argument-list version never involves a shell at all: the entire string, semicolon and all, arrives at git as a single argument. git log fails cleanly, because ; touch pwned_marker.txt # is not a valid path -- which is exactly the correct, boring outcome for an untrusted value that happens to contain punctuation.

2 — subprocess vs os.system vs os.popen: why one API won​

Before subprocess existed as the recommended tool, Python code reached for os.system() or os.popen(). Both still work today; both are missing something subprocess.run() gives you for free.

dd-scratch/api_comparison.py
import os
import subprocess

print("-- os.system --")
status = os.system("echo hello-from-os-system")
print(f"raw return value: {status} (not a clean exit code)")
print(f"decoded exit code: {os.WEXITSTATUS(status)}")

print()
print("-- os.popen --")
with os.popen("echo hello-from-os-popen") as pipe:
    output = pipe.read()
print(f"captured stdout: {output!r}")
print("(getting a clean exit code back from os.popen takes an extra pipe.close() dance)")

print()
print("-- subprocess.run --")
result = subprocess.run(
    ["echo", "hello-from-subprocess"], capture_output=True, text=True, timeout=5
)
print(f"stdout: {result.stdout!r}, returncode: {result.returncode}")
uv run python3 dd-scratch/api_comparison.py

Expected output

hello-from-os-system
-- os.system --
raw return value: 0 (not a clean exit code)
decoded exit code: 0

-- os.popen --
captured stdout: 'hello-from-os-popen\n'
(getting a clean exit code back from os.popen takes an extra pipe.close() dance)

-- subprocess.run --
stdout: 'hello-from-subprocess\n', returncode: 0

os.system() always routes the string through a shell -- there is no argument-list form at all, so every os.system() call is a shell=True call by construction. What it hands back is not the program's exit code directly; on POSIX it is a 16-bit encoded wait status that needs os.WEXITSTATUS() to decode into the number you actually want, an easy detail to miss. os.popen() gives you the command's stdout as a readable file object -- convenient for a quick script -- but it is implemented on top of subprocess.Popen() with a shell underneath it, and getting a trustworthy exit code back out requires reading the return value of pipe.close() correctly, which most code that reaches for os.popen() skips entirely. subprocess.run() is the one API that gives you stdout, stderr, and a clean return code together, defaults to no shell at all, and accepts an explicit timeout -- which is the whole reason it replaced both older functions as this course's (and the standard library documentation's own) recommended tool.

3 — PIPE deadlocks: why manual Popen plumbing can hang on real output​

An operating system pipe connecting a child process's stdout to your Python process has a fixed, small capacity -- commonly 64KB on Linux. Think of it as a conveyor belt of fixed length between two workstations: if the belt fills up and nobody at the receiving end is taking items off it, the worker adding items has nowhere to put the next one and simply stops. Popen(stdout=subprocess.PIPE) followed by .wait() before ever reading that pipe recreates exactly this stall: the child process blocks the moment its own write() call fills the pipe buffer, and your Python process is blocked inside .wait(), which will not return until the child exits -- and the child cannot exit until someone reads the pipe it is blocked writing to. Neither side can move.

dd-scratch/pipe_deadlock_demo.py
import subprocess
import time

# Enough output to fill a typical 64KB pipe buffer before the child exits.
BIG_OUTPUT_CMD = ["python3", "-c", "print('x' * 200_000)"]

print("-- safe: subprocess.run(capture_output=True) reads both streams concurrently --")
start = time.perf_counter()
result = subprocess.run(BIG_OUTPUT_CMD, capture_output=True, text=True, timeout=5)
print(f"finished in {time.perf_counter() - start:.2f}s, captured {len(result.stdout)} bytes")

print()
print("-- risky pattern: Popen + wait() before reading stdout --")
print("(bounded with a short timeout here so this demo cannot actually hang forever)")
proc = subprocess.Popen(BIG_OUTPUT_CMD, stdout=subprocess.PIPE, text=True)
try:
    proc.wait(timeout=2)
    print("wait() returned -- this run's output fit inside the pipe buffer")
except subprocess.TimeoutExpired:
    print("wait() timed out -- the child is blocked writing to a full pipe, and we were blocked waiting for it to exit instead of reading")
    proc.kill()
    proc.wait()
uv run python3 dd-scratch/pipe_deadlock_demo.py

Expected output

-- safe: subprocess.run(capture_output=True) reads both streams concurrently --
finished in 0.02s, captured 200001 bytes

-- risky pattern: Popen + wait() before reading stdout --
(bounded with a short timeout here so this demo cannot actually hang forever)
wait() timed out -- the child is blocked writing to a full pipe, and we were blocked waiting for it to exit instead of reading

subprocess.run(capture_output=True) never hits this failure mode, because internally it reads stdout and stderr concurrently with the child running, instead of waiting for the child to finish first. Whether the exact output size in this demo happens to trigger a visible stall on your machine depends on the OS pipe buffer size and how fast Python fills it -- the important fact is the mechanism, not this one run's timing: any code that calls .wait() (or reads .stdout and .stderr sequentially instead of concurrently) on a Popen before draining its pipes is exposed to this deadlock the moment the child's output is large enough, which in production usually means a verbose build log or a command with an unexpectedly large result set, not a toy example.

4 — Signal handling: what a timeout actually does to a stuck process​

Popen.terminate() and Popen.kill() are not two names for the same thing. terminate() sends SIGTERM -- a request the target process can catch, and clean up before it actually exits. kill() sends SIGKILL -- unconditional and immediate, a signal the process cannot catch, block, or ignore, and cannot run any of its own shutdown code in response to. When subprocess.run(..., timeout=N)'s deadline fires, it kills the process -- not terminates it -- before re-raising TimeoutExpired. A process wrapped in subprocess.run()'s timeout never gets a chance to flush a buffer, close a file cleanly, or run any cleanup code of its own; it is simply gone.

dd-scratch/timeout_kill_demo.py
import subprocess
import time

CHILD_SCRIPT = (
    "import signal, sys, time\n"
    "def handler(signum, frame):\n"
    "    print('got SIGTERM, exiting cleanly', flush=True)\n"
    "    sys.exit(0)\n"
    "signal.signal(signal.SIGTERM, handler)\n"
    "time.sleep(10)\n"
)

print("-- subprocess.run(timeout=...) on expiry --")
try:
    subprocess.run(["python3", "-c", CHILD_SCRIPT], timeout=1, capture_output=True, text=True)
except subprocess.TimeoutExpired as exc:
    print(f"TimeoutExpired raised; stdout captured before the kill: {exc.stdout!r}")
    print("note: the child's SIGTERM handler above never ran -- run() kills, it does not terminate")

print()
print("-- Popen.terminate() gives the child a chance to catch SIGTERM --")
proc = subprocess.Popen(["python3", "-c", CHILD_SCRIPT], stdout=subprocess.PIPE, text=True)
time.sleep(0.3)
proc.terminate()
try:
    stdout, _ = proc.communicate(timeout=2)
    print(f"child's own stdout: {stdout!r}")
except subprocess.TimeoutExpired:
    proc.kill()
    print("child ignored SIGTERM within the grace window -- had to kill() as a fallback")
uv run python3 dd-scratch/timeout_kill_demo.py

Expected output

-- subprocess.run(timeout=...) on expiry --
TimeoutExpired raised; stdout captured before the kill: None
note: the child's SIGTERM handler above never ran -- run() kills, it does not terminate

-- Popen.terminate() gives the child a chance to catch SIGTERM --
child's own stdout: 'got SIGTERM, exiting cleanly\n'

The first block never prints got SIGTERM, exiting cleanly -- subprocess.run()'s timeout path kills the process outright, so the child's own signal handler never gets a chance to run. The second block does print it, because terminate() sends the catchable SIGTERM and the demo gives the child time to respond before falling back to kill(). This is the practical decision this section exists to support: subprocess.run(..., timeout=N) is the right, simple choice for a short command like git status or docker info that has nothing to clean up. A long-running process that manages its own state -- a database migration, a build with temp files it wants to remove on the way out -- deserves the Popen + terminate() + a bounded grace period + kill() fallback pattern instead, so it gets a real chance to shut down before being forced.

Teardown​

cd ~/platformops
rm -rf dd-scratch

This removes only the scratch folder this page created. Your real local_ops.py, cli.py and the rest of ~/platformops are untouched.

Where you will use this
  • Shell metacharacters in an interpolated shell=True string execute as separate commands, not as literal text. Use it when: reviewing any PR that builds a command string from user input, a webhook payload, or another team's data before running it -- reject shell=True with interpolation on sight, and insist on the argument-list form instead.
  • os.system() and os.popen() both route through a shell and hand back a weaker contract than subprocess.run() -- a raw wait-status integer, or stdout with no clean return code. Use it when: you inherit an old script that still uses os.system() or os.popen() and need to add real error handling -- migrating the call to subprocess.run() is usually the actual fix, not patching around the old API's gaps.
  • A Popen pipe fills and both sides block if a child produces enough output while you call .wait() before reading it. Use it when: wrapping any command that can produce large or unbounded output -- a verbose build log, a docker ps against a host running hundreds of containers -- use capture_output=True (or read both streams concurrently yourself), never Popen + .wait() + read.
  • subprocess.run(timeout=N) kills a stuck process outright; it never gives it a chance to shut down gracefully. Use it when: wrapping a process that manages its own state -- an in-progress migration, a build writing temp files -- where an abrupt kill could leave things half-done. Reach for Popen with terminate() and a bounded grace period instead of subprocess.run()'s timeout in that specific case.
