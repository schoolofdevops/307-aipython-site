System and Process Automation

M10 gave platformops a way to check the health of a fleet of HTTP endpoints — all of them reachable over the network. A lot of real operational work never leaves your own machine at all: is this repository clean before you deploy from it, what did the last few commits actually change, is the Docker daemon even running before you try to build an image. Those answers already exist — they live in the output of git status, git log, docker info, tools you already run by hand every day. This module adds local_ops.py, a small layer that runs those exact command-line tools from Python and turns their output into structured data your CLI can report. The mechanism behind it, subprocess, is also one of the sharpest ways to make Python automation genuinely unsafe if you are careless with it. This lesson spends real time on why, because the lab and the Deep Dive both build directly on getting this right.

1. Running a program and reading its answer​

Think of subprocess.run() as sending a request through an intercom to someone in the next room: you ask them to do one specific job, you wait until they say they are done, and then you find out two things — what they wrote down, and whether they finished successfully or gave up partway. subprocess.run() does exactly that with an external program: it starts the program as a separate process, waits for it to finish, and hands you back everything you need to know about what happened.

result = subprocess.run(
    ["git", "status", "--porcelain"],
    capture_output=True,
    text=True,
    timeout=10,
    cwd=repo_path,
)

capture_output=True is what makes the intercom two-way. Without it, the external program's output goes straight to your terminal the same way it would if you had typed the command yourself — your Python code gets nothing back to work with. text=True decodes that output from raw bytes into a normal Python string, so result.stdout.splitlines() and .strip() behave the way you expect instead of handing you a bytes object every string method quietly rejects.

What comes back is a CompletedProcess object with three fields that matter almost every time: result.stdout, result.stderr, and result.returncode. A returncode of 0 means success by convention — the same convention you already rely on from a shell script's exit code — and anything else means the program is telling you something went wrong, even if it printed nothing alarming to stdout.

2. Never let the shell reinterpret what you meant to say​

Picture handing someone a shopping list, one item per line, versus reading them the same list out loud over a noisy phone line and trusting them to split it correctly. If one "item" on that spoken list happens to contain a pause that sounds like "and one more thing," the listener might treat it as a brand new instruction instead of part of the item's name. shell=True in subprocess is the spoken version: the string you build gets handed to a shell (/bin/sh or similar) to interpret before it becomes a program call, and that shell treats characters like ;, |, && and backticks as instructions, not as plain text — even if you only meant them as part of a filename or a path.

# Unsafe -- a shell reinterprets anything the caller controls
subprocess.run(f"git log {repo_path}", shell=True)

# Safe -- git receives repo_path as exactly one argument, no shell involved
subprocess.run(["git", "log", repo_path])

The difference is not cosmetic. In the first line, if repo_path ever comes from outside your own code — a CLI option, a webhook payload, a filename another team controls — anything hiding a semicolon or a pipe inside it runs as a second command. In the second line, there is no shell parsing step at all: the operating system starts git directly and hands it repo_path as a single argument, whatever characters it contains, including ones that would have meant something different to a shell. The rule this module follows without exception: build a list of arguments, never a string, and never pass shell=True. The Deep Dive works through a concrete, non-destructive demonstration of what an attacker-controlled path can actually do to the unsafe version.

3. Deciding: wrap a CLI, call an SDK, or step back from Python entirely​

M9 already made one side of this decision for you — GitHub has a documented, typed HTTP API, so platformops used httpx and stayed inside Python's own retry and error-handling logic instead of shelling out to curl or the gh CLI. git and docker are a different case: there is no comparable, always-installed Python SDK that understands your local .git directory or your running Docker daemon socket better than the tools that already do. Wrapping the CLI is the right call when the CLI is the real interface to something local — a .git working tree, a Docker daemon — and no typed API exists at that layer to replace it. A well-documented HTTP or SDK contract beats scraping a CLI's text output whenever both are genuinely available; the CLI wins when it is the only interface that actually exists.

There is a third option this module also draws a line around: not writing Python at all. A while True: run_check(); time.sleep(300) loop looks tempting the first time you want a repeated check, but it quietly reinvents a job you already have a mature tool for. It will not restart itself if it crashes, it will not survive a reboot unless you build that separately, it gives you no log rotation, and it leaves you with no easy way to answer "did last night's run even happen" without your own bookkeeping. cron and systemd timers already solve exactly this — restart policy, logging, and scheduling reliability come free — and Python's job in that picture is the one-shot script the scheduler invokes on its own timeline, not the scheduler itself.

4. A deadline for every external command​

A support line with no cap on hold time can leave you waiting forever if the person on the other end gets distracted. timeout= on subprocess.run() is exactly that cap for an external command: if the process has not finished within that many seconds, subprocess.run() raises subprocess.TimeoutExpired instead of hanging your script indefinitely. A CLI wrapper with no timeout is not any safer than a network call with no timeout — the failure mode is identical, a caller stuck waiting on something that may never answer. This course has insisted on an explicit timeout for every network call since M9's check_health(); the rule extends unchanged to every external command a script starts.

5. git and docker, from Python​

git status --porcelain gives one line per changed file in a stable, script-friendly format — no headers to skip, no colours to strip, exactly what a program wants instead of what a human wants to read on a terminal. git log --oneline -n 5 gives you the last five commits, one line each, short SHA and subject. docker info --format json turns the usual human-formatted docker info output into a single JSON document a program can parse directly, instead of scraping columns of text. Every one of these follows the same shape you just learned: build the argument list, pass a timeout, capture the output, and turn the CompletedProcess into something the rest of platformops can use — the same job check_health() did for an HTTP response in M9, done here for a local process instead of a network reply.

Common pitfalls
  • Building a shell string with untrusted input and shell=True. A repository path, a filename, or a branch name is not always something you control — treat every one of them as untrusted the moment it can come from outside your own code.
  • Missing timeout. A hung git status against a repository on a broken network mount, or a Docker daemon that never answers, blocks the whole script with no way to recover.
  • Forgetting capture_output=True and text=True together. Forgetting capture_output leaves output printed straight to the terminal instead of returned to you; forgetting text=True hands you bytes when you expected str, breaking every .strip() or .splitlines() call downstream.
  • Assuming git or docker is always installed. A missing binary raises FileNotFoundError — catch it and report it as data, the same way a timeout or a non-zero exit code is reported, instead of letting the whole command crash.
  • Checking stdout without checking returncode. A command can print something and still fail; the exit code is the actual signal a caller should branch on first.
  • Silently treating a non-zero exit as if it were success. If your code never inspects result.returncode, a failed git or docker call looks identical to a successful one until something downstream breaks in a confusing way.
