Deep Dive — The Allowlist Gate, Idempotency and Rollback Evidence

The lab proved the plan → approve → execute flow works: a dry-run plan, a refused execute without --approve, a real mutation with --approve, and one honest not_supported answer. This page goes past "it worked once" into three places an on-call engineer actually needs proof, not narration: that the allowlist really is a second gate the code cannot route around, that running the same fix twice back-to-back is genuinely safe (not just "probably fine"), and why a write call returning without an error is not, by itself, evidence a change is real.

Where this picks up

This page seeds and deletes its own two demo buckets — it does not depend on anything the lab left behind, and it is safe to run whether the lab's Teardown already ran or not. It only needs Floci reachable at http://localhost:4566:

curl -s http://localhost:4566/_floci/health | head -c 80

If a bucket name below already exists from an earlier run of this page, delete it first (see the Teardown at the end) and re-run.

1 — The allowlist gate, proven mechanically​

The lesson states that the allowlist is checked before cloudremediate.py even looks up whether a planner function exists. Read the actual order in the source, not the description of it:

awk '/^def build_remediation_plan\(/{p=1} p{print} /^def append_audit_log\(/{exit}' \
  src/platformops/cloudremediate.py | grep -n 'rule_id not in allowlist\|PLANNERS.get'

Expected output

20:    if rule_id not in allowlist:
33:    planner = PLANNERS.get(rule_id)

Line 20 is the allowlist check. Line 33 — thirteen lines later — is where a planner function is even looked up. A rule fails the allowlist check and returns not_supported before the code ever asks "do I know how to fix this." Being in PLANNERS is necessary, but the grep proves it is not sufficient, and it is not sufficient first.

That is a mechanical fact about the code, not yet proof about behavior. Prove behavior next, against a real running Floci: seed a real violation, get a real remediable plan, then take that exact rule off the allowlist and try --approve again.

uv run python -c "
from platformops.awsclient import get_aws_client
c = get_aws_client('s3', region='us-east-1', endpoint_url='http://localhost:4566')
c.create_bucket(Bucket='platformops-deepdive-allowlist-demo')
print('seeded')
"
uv run platformops cloud-audit --policy policy.example.yaml --region us-east-1 \
  --endpoint-url http://localhost:4566 --output /tmp/m25dd_report1.json | grep "allowlist-demo"

Expected output

seeded
  [HIGH] platformops-deepdive-allowlist-demo (required-tags): missing tags: team_owner, environment
  [HIGH] platformops-deepdive-allowlist-demo (require-encryption): encryption: not using a customer-managed KMS key (AWS-managed SSE-S3 default only)

With the normal remediation.example.yaml, this finding is remediable:

uv run platformops remediate-plan /tmp/m25dd_report1.json \
  platformops-deepdive-allowlist-demo:required-tags \
  --region us-east-1 --endpoint-url http://localhost:4566

Expected output

platformops-deepdive-allowlist-demo:required-tags (required-tags) -- remediable
  would call: put_bucket_tagging
  args: {"Bucket": "platformops-deepdive-allowlist-demo", "Tagging": {"TagSet": [{"Key": "environment", "Value": "unassigned"}, {"Key": "team_owner", "Value": "platform-unassigned"}]}}
  before: {"tags": {}}

Now make a scratch copy of the config with required-tags removed from allowlist — everything else stays the same:

cat > /tmp/m25dd_remediation_no_tags.yaml << 'EOF'
allowlist:
  - require-encryption
  - no-public-exposure

policies:
  required-tags:
    defaults:
      team_owner: platform-unassigned
      environment: unassigned
  require-encryption:
    kms_key_id: alias/platformops-remediation-demo

audit_log_path: remediation-audit.jsonl

batch:
  default_cap: 5
EOF

Plan and execute the exact same finding — same bucket, same rule, --approve this time — against this edited config:

uv run platformops remediate-plan /tmp/m25dd_report1.json \
  platformops-deepdive-allowlist-demo:required-tags \
  --region us-east-1 --endpoint-url http://localhost:4566 \
  --remediation-config /tmp/m25dd_remediation_no_tags.yaml

uv run platformops remediate-execute /tmp/m25dd_report1.json \
  platformops-deepdive-allowlist-demo:required-tags \
  --region us-east-1 --endpoint-url http://localhost:4566 \
  --remediation-config /tmp/m25dd_remediation_no_tags.yaml --approve

Expected output

platformops-deepdive-allowlist-demo:required-tags (required-tags) -- not_supported
  reason: rule 'required-tags' is not on the remediation allowlist -- remediation is refused regardless of whether code exists for it
platformops-deepdive-allowlist-demo:required-tags (required-tags) -- not_supported
  rule 'required-tags' is not on the remediation allowlist -- remediation is refused regardless of whether code exists for it

Exit code 1, from the second command, even with --approve on the command line. Nothing about the finding changed between the first remediate-plan (remediable) and this one (not_supported) except the config file — the same resource, the same rule, the same real live check for missing tags. Confirm directly that the bucket really has no tags:

uv run python -c "
from platformops.awsclient import get_aws_client
import botocore.exceptions
c = get_aws_client('s3', region='us-east-1', endpoint_url='http://localhost:4566')
try:
    print(c.get_bucket_tagging(Bucket='platformops-deepdive-allowlist-demo'))
except botocore.exceptions.ClientError as e:
    print('no tags yet:', e.response['Error']['Code'])
"

Expected output

{'ResponseMetadata': {...}, 'TagSet': []}

An empty TagSet. The allowlist gate did not just print a different message — it genuinely stopped the write from happening, with a valid plan and --approve both present.

2 — Idempotency, proven with two real consecutive runs​

The lesson describes the guarantee: an approved execute re-checks live state right before mutating, so a second run on an already-fixed finding reports already_fixed instead of re-applying the change. Here it is with two real, back-to-back command runs.

uv run python -c "
from platformops.awsclient import get_aws_client
c = get_aws_client('s3', region='us-east-1', endpoint_url='http://localhost:4566')
c.create_bucket(Bucket='platformops-deepdive-idempotency-demo')
print('seeded')
"
uv run platformops cloud-audit --policy policy.example.yaml --region us-east-1 \
  --endpoint-url http://localhost:4566 --output /tmp/m25dd_report2.json | grep "idempotency-demo"

Expected output

seeded
  [HIGH] platformops-deepdive-idempotency-demo (required-tags): missing tags: team_owner, environment
  [HIGH] platformops-deepdive-idempotency-demo (require-encryption): encryption: not using a customer-managed KMS key (AWS-managed SSE-S3 default only)

First run — a real mutation:

uv run platformops remediate-execute /tmp/m25dd_report2.json \
  platformops-deepdive-idempotency-demo:required-tags \
  --region us-east-1 --endpoint-url http://localhost:4566 --approve
wc -l remediation-audit.jsonl

Expected output

platformops-deepdive-idempotency-demo:required-tags (required-tags) -- executed
  action: put_bucket_tagging
  before: {"tags": {}}
  after:  {"tags": {"environment": "unassigned", "team_owner": "platform-unassigned"}}
  verified: True
  remediation applied
       1 remediation-audit.jsonl

Second run — immediately after, same finding id, same report, same --audit-log file:

uv run platformops remediate-execute /tmp/m25dd_report2.json \
  platformops-deepdive-idempotency-demo:required-tags \
  --region us-east-1 --endpoint-url http://localhost:4566 --approve
wc -l remediation-audit.jsonl

Expected output

platformops-deepdive-idempotency-demo:required-tags (required-tags) -- already_fixed
  before: {"tags": {"environment": "unassigned", "team_owner": "platform-unassigned"}}
  after:  {"tags": {"environment": "unassigned", "team_owner": "platform-unassigned"}}
  all configured default tags are already present
       1 remediation-audit.jsonl

Still one line. The second, real, consecutive run did not skip the write because it remembered running before — there is no such memory anywhere in this module. It re-read the bucket's live tags, saw both defaults already present, and reported already_fixed on that evidence alone. Run this a hundred times in a row and the log stays at one line every time, because the live check, not a cache or a flag, is what decides.

3 — The audit log as rollback evidence, and why "no exception" is not proof​

Read the actual line the first run above wrote:

cat remediation-audit.jsonl

Expected output

{"timestamp": "2026-08-05T06:27:13.141887+00:00", "finding_id": "platformops-deepdive-idempotency-demo:required-tags", "resource_id": "platformops-deepdive-idempotency-demo", "rule_id": "required-tags", "action": "put_bucket_tagging", "before_state": {"tags": {}}, "after_state": {"tags": {"environment": "unassigned", "team_owner": "platform-unassigned"}}, "approved_by": "gshah"}

Put before_state and after_state side by side:

tags
before_state{}
after_state{"environment": "unassigned", "team_owner": "platform-unassigned"}

That is the entire rollback plan for this change, in one line: to undo it by hand, call put_bucket_tagging again with before_state's tags. No other record in this system could tell you that — not the CLI's stdout (which scrolls away), not the resource itself (a bucket's tags do not carry their own history; the old value is simply gone the moment the new one is written). before_state had to be captured before the API call, because there is no way to ask AWS "what were this bucket's tags a moment ago" after the fact. Capture it late, or not at all, and the log records that a change happened without recording what it changed from — evidence of an event, not evidence you can reverse.

Now look again at verified: True in the plain-text output from Section 2's first run. It would be reasonable to assume that field is redundant — put_bucket_tagging did not raise an exception, so of course the tags are set. That assumption is exactly the gap execute_remediation_plan() refuses to rely on.

A courier's scan is not a signature

A courier's handheld scanner beeping "delivered" at a doorstep is not the same evidence as a signature on the door. The scan can succeed — no error, no exception — while the parcel is still in the courier's hand, misrouted, or left at the wrong address. A dispatcher who only checks "did the scan raise an error" cannot tell a real delivery from a failed one that merely didn't error. The signature — going back and confirming the parcel is actually where it should be — is the only thing that closes the loop.

An AWS write call returning 200 OK is the scan, not the signature. Most AWS write calls are synchronous and this course's Floci matches that, so in this lab the read-back almost always agrees with the write immediately — but "almost always" is exactly the gap that matters. A retry behind the scenes, a proxy acknowledging before a write is durably applied, a service with eventually-consistent reads: any of these can make a write call return cleanly while a fresh read still shows the old state for a moment, or shows something unexpected. execute_remediation_plan() never treats the absence of an exception as the finish line. Immediately after the write call, it calls _after_state_for() — the exact same live-state reader build_remediation_plan() uses to build before_state — and compares the two. verified is True only when that fresh read actually shows the resource changed. A remediation that returns without error but leaves verified: False is a real, distinguishable outcome this module can report — not something a design that only checks for a raised exception could ever see.

Teardown​

Delete this page's two demo buckets and its local audit log:

uv run python -c "
from platformops.awsclient import get_aws_client
c = get_aws_client('s3', region='us-east-1', endpoint_url='http://localhost:4566')
for name in ['platformops-deepdive-allowlist-demo', 'platformops-deepdive-idempotency-demo']:
    c.delete_bucket(Bucket=name)
    print('deleted', name)
print('remaining:', [b['Name'] for b in c.list_buckets()['Buckets']])
"
rm -f remediation-audit.jsonl /tmp/m25dd_report1.json /tmp/m25dd_report2.json /tmp/m25dd_remediation_no_tags.yaml

Expected output

deleted platformops-deepdive-allowlist-demo
deleted platformops-deepdive-idempotency-demo
remaining: []

This teardown does not run floci stop — leave the container running.

Where you will use this
  • The allowlist gate is checked before a planner is even looked up, and re-checked at execute time from the same config, not just remembered from the plan. Use it when: a compliance review asks "can you prove a rule change to the remediation config takes effect immediately, for every path, without a code deploy" — point at the grep and the live test above, not a description of the design.
  • Idempotency here comes from re-reading live state on every run, not from tracking what has already been done. Use it when: a remediation job gets retried after a timeout, or someone reruns it by hand because they were not sure the first run went through — you need to know re-running is safe by design, not "probably fine because nothing broke last time."
  • A write call returning without an exception is not proof a resource changed — verified is a fresh read-back comparison, taken after the call, against state captured before it. Use it when: writing your own remediation or automation code against any cloud API — always capture pre-change state before the write, and always read the resource again afterward instead of trusting a clean return value alone.
