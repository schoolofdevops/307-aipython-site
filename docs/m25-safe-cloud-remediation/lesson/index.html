Safe Cloud Remediation

Module 24 built cloudaudit.py — a tool that checks real AWS resources against a written policy and reports what breaks it. It never fixes anything. It only looks and writes down what it sees, the same way a building inspector hands over a citation report and leaves the repairs to someone else.

This module is that "someone else." cloudremediate.py reads the findings cloudaudit.py produces and actually fixes some of them — for real, against a real running Floci container. This is the first module in the whole course where a write call to a cloud resource is the right thing to do, not a mistake to avoid. That is a real change in how careful you have to be, not a chance to relax. Every module before this one earned your trust by never touching anything. This module has to earn trust a different way: every change it makes has to be planned, allowed, approved, written down, and checked — every single time.

Why this matters at work

An audit report that nobody acts on is just a list nobody reads. At some point, someone has to fix the untagged bucket, turn on the right encryption, or lock down a bucket that is open to the public. In a small team, an engineer does this by hand, one aws s3api command at a time, hoping they remember which buckets were already checked. In a team running hundreds of buckets across many accounts, that does not scale, and "I think I fixed it" is not something you can show an auditor. This module builds the tool that fixes what it is told to fix, refuses to guess, and leaves a paper trail of exactly what changed and when — the same evidence a security review or a post-incident write-up will ask for.

1. A doctor's order, not a hallway fix​

Picture a hospital ward. A patient needs a new medication. The doctor does not walk up and give it to the patient on the spot. The doctor writes an order — the drug, the dose, the reason. A nurse reads the order, checks it against the patient's chart, and only then gives the medication. Some orders — a strong drug, a change to dosage — need a second doctor's sign-off before anyone administers them. And every dose given gets written on the chart: what was given, how much, when, and by whom. If something goes wrong, that chart is how the care team knows what to undo or counteract.

Nobody in a hospital treats "the doctor said so once, informally" as enough to give a drug. The order has to be written down, checked, and only then acted on — and the record of what was actually done has to exist afterward, or there is no way to safely reverse a mistake.

cloudremediate.py works the same way. The plan (remediate-plan) is the doctor's written order — it says exactly what would change, and it changes nothing by itself. Approval (--approve) is the nurse's check before acting — nothing is applied without it. The audit log is the chart — every real change is written down with what the resource looked like before and after, so there is a record to work from if the change needs to be undone by hand later. Keep this picture in your head through the rest of this lesson: a plan is not a change, and a change without a record is a change nobody can safely walk back.

2. Two gates, not one​

A doctor's order and a nurse's check are two separate people making two separate decisions. Losing either one is dangerous — an order with no check might get carried out on the wrong patient; a check with no order has nothing to check against. cloudremediate.py has two separate gates in the same spirit, and both must open before anything changes.

The first gate is --approve on the command line. Run remediate-execute without it, and the command refuses — it prints the plan again and exits with a non-zero status. It never quietly does nothing and reports success; a script checking the exit code always knows whether a change really happened.

The second gate is the remediation allowlist, a list of rule IDs in remediation.example.yaml. Only a rule on this list is ever remediated — even if the code to fix it exists, and even with --approve on the command line. Take required-tags off the allowlist, and every finding for that rule comes back not_supported, no matter what else you pass. This gate does not care whether you meant to approve the change; it only cares whether that kind of change is allowed at all right now. Removing a rule from the allowlist is enough to stop this tool from ever touching that kind of finding again — nobody has to change a line of Python.

These two gates check different things, and both are needed. --approve says "yes, apply the one plan in front of you, right now." The allowlist says "this whole category of change is something we have decided, in advance, is safe to automate." A doctor's sign-off approves one order for one patient; a hospital's own drug formulary decides, ahead of time and independent of any one doctor, which drugs are ever given at all. Losing either gate would defeat the purpose of having both.

3. Not every finding should be fixed by a machine​

The most important design decision in this module is which findings get an automatic fix at all. Three of cloudaudit.py's five checks are remediable here:

  • required-tags — add the missing tag(s) with a placeholder value (put_bucket_tagging).
  • require-encryption — turn on SSE-KMS with a configured key (put_bucket_encryption).
  • no-public-exposure — make the bucket private again (put_bucket_acl).

Two are not, and never will be, no matter what you put in the allowlist:

  • approved-regions — an S3 bucket cannot move region. Fixing this means creating a new bucket in the right region and migrating every object into it — a decision with real cost and real risk that a human has to make on purpose.
  • max-age-days — "this resource is old" is not the same as "this resource is safe to delete." Only a person who knows what the resource actually holds can make that call.

This is not a gap in the code that a future module will close. It is the point. A remediation plan for one of these two rules always comes back status: not_supported, with a plain-English reason — the same as if the rule were simply missing from the allowlist. The tool is honest about the limits of automation instead of pretending everything can be fixed by a script.

4. Plan first — and it costs nothing to run twice​

remediate-plan never writes anything. It reads the resource's current state — the real tags on the bucket right now, not the tags from an old audit report — and reports what a fix would look like. Run it as many times as you want, on the same finding, back to back. Nothing changes, because nothing is supposed to.

This matters because an audit report can go stale. A finding from an hour ago might already be fixed by someone else, or might have gotten worse. build_remediation_plan() always reads live state before deciding what to say — that is what makes the plan trustworthy right up to the moment you decide to approve it.

5. Re-checking before you act — the idempotency guarantee​

Running the same fix twice should never be dangerous. If a finding is already fixed, applying the fix again should do nothing, not error out and not apply the change a second time. This matters at work because remediation scripts get re-run — after a retry, after a flaky network call, after someone reruns a job by hand because they were not sure the first run worked.

execute_remediation_plan() guarantees this by re-checking the finding's live state a second time, immediately before it would mutate anything — even if you already have a plan in hand. If that fresh check shows the finding no longer applies, the function reports already_fixed and stops there. No second write call ever happens. This re-check is not optional and cannot be skipped by the caller — it runs on every approved execution, every time.

The idempotency test is the "run it twice" test

The Deep Dive proves this with two real, consecutive runs against Floci: the first mutates and logs a change; the second, on the same now-fixed finding, reports already_fixed with no second entry in the audit log. That is what "proven," not just "assumed," idempotency looks like.

6. The chart: why the audit log is the rollback plan​

This module does not build a one-click "undo" button. Full automatic rollback is out of scope. What it does build is the information a person needs to undo a change by hand — and that information is only useful if it was captured before the change was made.

Every executed remediation appends one line to a JSON-lines audit log: a timestamp, the finding ID, the resource, the rule, the exact API call made, the resource's state before the call, its state after, and who approved it. That "before" state is the whole reason this log exists. If someone only records "the call succeeded," there is nothing to go back to — you know the change happened, but not what it changed from. The chart in a hospital works the same way: it is only useful for reversing a bad dose because someone wrote down the patient's condition before it was given, not just that it was given.

7. Bounding the blast radius​

A single bad remediation touches one resource. A batch remediation with no limit can touch hundreds, on one command, in one moment — and if the remediation config was wrong, so can the damage. remediate-execute-batch refuses, outright, to run more than a small default number of findings (five) in one invocation, unless you explicitly raise that number with --max-batch. It does not quietly remediate the first five and drop the rest — an operator who asked for ten and got five with no warning would walk away thinking all ten were handled.

Common pitfalls​

  • Running remediate-execute --approve without reading remediate-plan first. The plan is there so a human reviews the exact change before it happens. Skipping straight to --approve throws away the one step that catches a bad plan before it becomes a real change.
  • A batch remediation with no cap in mind. Even with the built-in default cap, raising --max-batch without thinking about how many resources that really touches turns one command into a much bigger action than anyone reviewed.
  • Forcing an automated fix on approved-regions or max-age-days. These come back not_supported on purpose. Adding a rule like this to the allowlist does nothing — there is no planner for it — and trying to force it defeats the whole reason these two are excluded: some changes need a person to decide, not a script.
  • Treating "the API call did not raise an error" as proof the fix worked. A write call succeeding is not the same as the resource actually changing. This module always reads the resource's state again after the call, and the Deep Dive shows a real case where that second read is what actually proves the fix took effect — not the absence of an error.
