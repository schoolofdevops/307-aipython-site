Deep Dive — How the Quality Gates Actually Work

The lab had you wire mypy, ruff, and uv's lockfile into platformops on trust: run the command, read the pass/fail, move on. This page opens up what each tool is actually doing underneath that pass/fail line -- how uv decides a set of package versions is impossible before it ever downloads one of them, why ruff catches a real bug a plain text search cannot, how mypy narrows a broad type down to a specific one branch by branch, and what a lockfile's guarantee actually covers. You will use this the day a dependency upgrade fails with a wall of resolver text, the day you have to explain to a teammate why grep is not a substitute for a linter, and the day someone asks whether a locked, pinned dependency is automatically a safe one.

Where this picks up

You need ~/platformops at v1.1 from the lab. Every command below runs inside its own scratch project or scratch file, entirely separate from your real src/ and tests/ -- none of them touch your project's own dependencies or git history.

mkdir -p ~/platformops/dd-scratch && cd ~/platformops/dd-scratch

Re-running any command on this page is safe.

1 — Dependency resolution: why a conflict fails before anything downloads​

uv add fastapi flask on a large project can print a wall of red text about versions that "cannot be used together" before a single package is installed. This looks like magic the first time you see it, but it is closer to solving a sudoku puzzle: every dependency and every version constraint is one more filled-in cell, and the solver's whole job is figuring out whether a consistent grid exists at all -- and if it does not, which cells actually contradict each other. uv's resolver (built on the same family of algorithm as Rust's Cargo and Dart's pub, called PubGrub) treats every requirement in your project as a constraint, and searches for one assignment of exact versions that satisfies every constraint at once. When no such assignment exists, it does not just say "failed" -- it walks back through which specific requirements are mutually incompatible and reports that chain, the same way you would explain a sudoku has no solution by pointing at the two cells that force a contradiction.

Look at the real graph uv already solved for platformops -- this command only reads the existing lock, it changes nothing:

cd ~/platformops && uv tree

Every line in that tree is a constraint the resolver satisfied simultaneously -- httpx, typer, pydantic, pyyaml, and everything each of them in turn depends on, all pinned to versions that agree with every other constraint in the graph at once. Now force an actual contradiction, in a disposable scratch project that never touches platformops's own lock:

cd ~/platformops/dd-scratch
uv init --no-readme --no-workspace conflict-demo
cd conflict-demo
uv add "sphinx==7.0.0" "jinja2==2.11.3"

Expected output

  × No solution found when resolving dependencies:
  ╰─▶ Because sphinx==7.0.0 depends on jinja2>=3.0 and your project depends
      on jinja2==2.11.3, we can conclude that your project and sphinx==7.0.0
      are incompatible.
      And because your project depends on sphinx==7.0.0, we can conclude that
      your project's requirements are unsatisfiable.

Pinning sphinx==7.0.0 alongside jinja2==2.11.3 looks reasonable at first glance -- they are two different packages, not two pins of the same one. But sphinx 7.0.0 depends on jinja2>=3.0 internally. That means the resolver has to find a version of jinja2 that is simultaneously ==2.11.3 (because you asked for it) and >=3.0 (because sphinx requires it) -- and no such version exists. The resolver reports the two requirements that contradict each other directly, following the same chain it would use for a far more tangled multi-package conflict.

2 — Why ruff catches what a grep-based check cannot​

check-security, from earlier in this course, is a grep-based scanner: it searches source text for the literal string shell=True. That works well for one specific, fixed string -- but a linter like ruff has to catch a much broader family of mistakes, including ones that depend on how a name is actually used, not just whether it appears. ruff does this by parsing your file into an AST (Abstract Syntax Tree) -- the same tree-shaped structure Python's own compiler builds internally, where every name, assignment, and function call is a distinct node with a known role, not just a run of characters. A grep-based check reads text; ruff reads structure -- the difference between a proofreader who understands grammar and one who is only matching words on a page.

Here is a case a text search genuinely cannot resolve on its own: a variable assigned but never read again, where a second, similarly-named variable is used.

dd-scratch/unused_demo.py
def summarize(service_name):
    servicename = service_name.strip()  # assigned, never read again
    return f"service: {service_name}"

servicename (no underscore) is dead -- nothing after it ever reads that name. A grep for servicename still finds one match in this file (its own assignment line), and finds nothing wrong because grep has no concept of "read" versus "write." Confirming this one is genuinely unused requires tracking which specific name gets referenced later in that same scope -- exactly what an AST lets ruff do reliably:

uv run ruff check dd-scratch/unused_demo.py

Expected output

F841 Local variable `servicename` is assigned to but never used
 --> dd-scratch/unused_demo.py:2:5
  |
1 | def summarize(service_name):
2 |     servicename = service_name.strip()  # assigned, never read again
  |     ^^^^^^^^^^^
3 |     return f"service: {service_name}"
  |
help: Remove assignment to unused variable `servicename`

Found 1 error.

That finding is rule F841, "local variable assigned but never used." Ask ruff to explain any rule it reports, by code, without re-running the check:

uv run ruff rule F841

Expected output

# unused-variable (F841)

Derived from the **Pyflakes** linter.

Fix is sometimes available.

## What it does
Checks for the presence of unused variables in function scopes.

## Why is this bad?
A variable that is defined but not used is likely a mistake, and should
be removed to avoid confusion.

If a variable is intentionally defined-but-not-used, it should be
prefixed with an underscore, or some other value that adheres to the
[`lint.dummy-variable-rgx`] pattern.

The check-security scanner earlier in this course is not a weaker version of this -- it is solving a narrower, deliberately fixed problem (one exact literal string) where grep is fast, honest and sufficient. The moment the question becomes "is this name actually used," text matching runs out of ways to answer correctly, and something that understands the code's structure has to take over.

3 — Type narrowing: how mypy follows a branch to a specific type​

config.py's load_service_yaml() returns ServiceDefinition | list[dict[str, Any]] -- a union type, meaning "one of these two shapes, and the caller has to find out which." Think of mypy reading your function the way a detective narrows a suspect list: at the start, either shape is possible, so only what both shapes have in common is safe to use. The moment your code checks isinstance(result, ServiceDefinition), that check is a clue -- and inside the branch where it was true, mypy narrows its own understanding of result's type down to exactly ServiceDefinition, for the rest of that branch only. This is not a runtime behavior; Python itself does nothing special here. It is mypy tracking, statically, which possibilities each if branch has ruled out.

reveal_type() is a special name mypy recognizes at check time only -- it is not a real function, and calling it in code that actually runs would raise NameError. It exists purely so you can ask "what does the type checker currently believe this name's type is, right here":

dd-scratch/narrowing_demo.py
from pathlib import Path

from platformops.config import load_service_yaml
from platformops.servicedef import ServiceDefinition


def report(path: Path) -> str:
    result = load_service_yaml(path)
    reveal_type(result)  # the full union -- nothing narrowed yet

    if isinstance(result, ServiceDefinition):
        reveal_type(result)  # narrowed to ServiceDefinition in this branch
        return result.to_summary()

    reveal_type(result)  # narrowed to list[dict[str, Any]] in this branch
    return f"{len(result)} error(s)"
cd ~/platformops
uv run mypy dd-scratch/narrowing_demo.py

Expected output

dd-scratch/narrowing_demo.py:9: note: Revealed type is "platformops.servicedef.ServiceDefinition | list[dict[str, Any]]"
dd-scratch/narrowing_demo.py:12: note: Revealed type is "platformops.servicedef.ServiceDefinition"
dd-scratch/narrowing_demo.py:15: note: Revealed type is "list[dict[str, Any]]"
Success: no issues found in 1 source file

Three Revealed type notes come back, one per reveal_type() call -- the first names the full union, the second and third each name exactly one member of it, matching the branch that call sits inside. This is the same mechanism that makes result.to_summary() type-check cleanly inside the isinstance branch at all: to_summary() only exists on ServiceDefinition, not on list[dict[str, Any]], and mypy only allows the call because it has already ruled out the other possibility by that point in the code.

4 — What a lockfile actually guarantees (and what it does not)​

A sealed jar of pickles guarantees the contents have not changed since the jar was sealed -- same brine, same batch, opened a year from now and it is still exactly what it was. It does not guarantee those pickles are the freshest option available, or that a recall was never issued against that batch after it shipped. uv.lock makes exactly the sealed-jar guarantee, and nothing more: every dependency is pinned to one exact version, with a cryptographic hash of the exact file that gets installed.

cd ~/platformops
grep -A 12 'name = "httpx"' uv.lock | head -13

Expected output

name = "httpx"
version = "0.28.1"
source = { registry = "https://pypi.org/simple" }
dependencies = [
    { name = "anyio" },
    { name = "certifi" },
    { name = "httpcore" },
    { name = "idna" },
]
sdist = { url = "https://files.pythonhosted.org/...", hash = "sha256:75e98c5f16b0f35b567856f597f06ff2270a374470a5c2392242528e3e3e42fc", size = 141406 }
wheels = [
    { url = "https://files.pythonhosted.org/...", hash = "sha256:d909fcccc110f8c7faf814ca82a9a4d816bc5a6dbfea25d6591d6985b8ba59ad", size = 73517 },
]

That hash is the actual guarantee: if the file downloaded ever differs from what was locked -- a compromised package registry serving a different artifact under the same version number, for instance -- uv refuses to install it, rather than silently accepting whatever it received. uv sync --locked goes one step further, and is the flag worth using in CI: it fails immediately if pyproject.toml and uv.lock have drifted apart at all, instead of silently re-resolving and installing something the lockfile never actually recorded.

uv sync --locked

Expected output

Resolved 34 packages in 3ms
Audited 33 packages in 2ms

What the lock does not cover is time. The hash proves the file is unchanged since the day it was locked -- it says nothing about whether that exact, unchanged version is still considered safe today. A CVE disclosed against a version you locked six months ago does not un-pin itself; the lockfile keeps reproducing that exact vulnerable version, byte for byte, forever, until you explicitly re-resolve. This is precisely why the lab's dependency-audit gate is a separate step from uv sync itself, and why it needs to run repeatedly rather than once: reproducibility and safety are two different questions, and only one of them is a fact that stops changing the moment you lock it.

Teardown​

cd ~/platformops
rm -rf dd-scratch

This removes only the scratch folder this page created. Your real src/, pyproject.toml, uv.lock and the rest of ~/platformops are untouched.

Where you will use this
  • uv's resolver reports a conflict by naming the exact requirements that contradict each other, the same way for two or two hundred packages. Use it when: a dependency upgrade fails with a wall of resolver text -- read the first and last requirement it names instead of the whole wall; that pair is usually the actual contradiction.
  • A grep-based check reads text; ruff reads the parsed structure of your code, so it can tell a read from a write and a real match from a lookalike string. Use it when: deciding whether a new check belongs in a fixed, fast grep-based script (one exact pattern, like shell=True) or needs a real linter rule (anything that depends on how a name is actually used).
  • mypy narrows a union type branch by branch, following isinstance and similar checks the same way your own reading of the code would. Use it when: mypy reports an error only inside one specific if branch -- the fix is almost always a missing or wrong narrowing check right above that line, not a problem with the function's overall type.
  • A lockfile's hash guarantees reproducibility -- the exact same file, forever -- and says nothing about whether that exact file is still considered safe. Use it when: reviewing whether "our dependencies are pinned" is enough of a security answer on its own -- it is the reproducibility half of the story; a recurring dependency audit is the safety half.
