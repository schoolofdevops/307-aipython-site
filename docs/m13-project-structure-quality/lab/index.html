Lab — Build PlatformOps v1.1: the Maintainable PlatformOps Foundation

This lab does not add a single new command. Every change in this lab is a guardrail: a CHANGELOG.md that records every release so far, a pyproject.toml that turns the checks you already run by hand into project-level configuration, a type checker wired against real bugs in config.py, a secret-scan script built the same safe way check-security was in M11, and one script that runs every gate in the right order. You write the first version of each by hand, then hand a coding agent the harder, wider version of the same job: extending type annotations across the rest of the package and adding a dependency audit.

You need ~/platformops from the M12 lab, already tagged v1.0, with uv run pytest -q passing.

cd ~/platformops
git log --oneline -1

Expected output

a3f9c21 platformops v1.0 -- Tested Automation Core

The commit hash will differ, but the message should name v1.0.

Starting fresh from the checkpoint?

If you skipped M12 or lost your project, copy the frozen checkpoint and set up git:

cp -r ~/307-aipython-labs/labs/checkpoints/v1.0 ~/platformops
cd ~/platformops
git init && git add -A && git commit -m "platformops v1.0 -- Tested Automation Core"
git tag v1.0
uv sync

Then re-run git log --oneline -1 to confirm you see the v1.0 message.

1. Write CHANGELOG.md​

platformops has eleven releases behind it, from v0.0 to v1.0, and nothing anywhere lists what each one added in one place. Create CHANGELOG.md in the project root, using the same "Keep a Changelog" shape most real projects use: newest release first, a short heading per version, a bulleted list of what changed under it.

CHANGELOG.md
# Changelog

All notable changes to this project are documented in this file. Format follows
[Keep a Changelog](https://keepachangelog.com/), and versions follow
[Semantic Versioning](https://semver.org/).

## [1.0.0] - Tested Automation Core

- Added a full `pytest` suite covering service validation, inventory filtering, API error
  handling and CLI exit codes.
- Added `pytest-cov` and a coverage report for the whole package.

## [0.9.0] - Local Operations Adapter

- Added `docker-info` and `container-list`, backed by safe `subprocess` calls (no `shell=True`,
  always a timeout).
- Added `check-security`, a `grep`-based scan for unsafe shell usage in `src/`.

## [0.8.0] - Concurrent Health Checker

- Added concurrent health checks across many service endpoints, with a concurrency limit,
  per-request timeouts and partial-failure reporting.

## [0.7.0] - Repository and API Inspector

- Added repository and workflow lookups against a source-control API, with pagination, retries
  and response validation.

## [0.6.0] - PlatformOps CLI

- Added the `platformops` CLI: `validate`, `inspect`, `version`, shell completion and Markdown
  output.

## [0.5.0] - Reliable Validation and Diagnostics

- Repaired six failure scenarios in the validation tool: invalid YAML, missing file, missing
  field, wrong type, permission failure, unexpected value.

## [0.4.0] - Service Configuration Validator

- Added `service.yaml` loading and validation, environment-variable overrides, JSON output and a
  `--check` dry-run mode.

## [0.3.0] - Service Definition Model

- Added the typed `ServiceDefinition` model: name, repo, environment, owner, namespace,
  deployment, AWS account, region, observability references.

## [0.2.0] - Modular Inventory Engine

- Refactored the inventory script into reusable functions and modules, with no change in
  behavior.

## [0.1.0] - Infrastructure Inventory Reporter

- Added the first inventory reporter: reads infrastructure inventory, flags rule violations,
  with filtering, sorting and summary extensions.

## [0.0.0] - Project Foundation

- Bootstrapped the project with `uv`, `ruff`, `pytest` and Git.
Write the entry when you make the change, not at release time

You wrote this changelog after the fact, from the release names in this course -- a real project does the opposite. The right time to write a changelog entry is the same session you make the change, while the detail is still fresh. From this release onward, add your [Unreleased] entry as you work, not the day you tag.

2. Configure ruff and pytest in pyproject.toml​

ruff format and ruff check already pass against this project -- but only because they are falling back to their built-in defaults. Nothing in pyproject.toml says what this project's own rules actually are, so a teammate's editor, a CI job, and your own terminal are all one config change away from silently disagreeing. Add these two sections to pyproject.toml:

pyproject.toml
[tool.ruff]
target-version = "py312"

[tool.ruff.lint]
select = ["E", "F", "I", "UP"]
ignore = ["E501"]

[tool.pytest.ini_options]
testpaths = ["tests"]

select names four rule groups: E (style), F (real bugs like unused imports), I (import order), UP (outdated syntax a newer Python version no longer needs). ignore = ["E501"] tells ruff to skip "line too long" checks — the formatter (ruff format) already handles line length, so checking it twice would cause false alarms on lines the formatter intentionally left long. testpaths tells pytest exactly where to look, instead of walking the whole project directory on every run.

uv run ruff check .
uv run ruff format --check .
uv run pytest -q

Expected output

All checks passed!
22 files already formatted
138 passed in 1.31s
If ruff check now reports import-order findings

Adding the I rule group can surface import ordering nobody enforced before. Run uv run ruff check --fix . once to let ruff reorder the imports itself, then re-run uv run ruff format . and uv run pytest -q to confirm nothing broke.

3. Add mypy, scoped to one module first​

uv add --dev mypy

Expected output

Resolved 31 packages in 198ms
Prepared 1 package in 512ms
Installed 1 package in 4ms
 + mypy==2.3.0

Configure mypy with a practical, not maximal, starting point. Add this section to pyproject.toml:

pyproject.toml
[tool.mypy]
python_version = "3.12"
files = ["src/platformops/config.py"]
disallow_untyped_defs = true
warn_return_any = true
warn_unused_ignores = true
warn_redundant_casts = true

[[tool.mypy.overrides]]
module = "yaml"
ignore_missing_imports = true

files is what keeps this narrow: mypy only looks at exactly the one module you are about to clean up, config.py, not the whole src/ tree. disallow_untyped_defs (every function needs a type-annotated signature) applies to that one module for now. The override tells mypy that yaml (the PyYAML package) ships no type information of its own, so it should stop reporting that as an error and trust the calls instead.

uv run mypy

Expected output

src/platformops/config.py:65: error: Missing type parameters for generic type "dict"  [type-arg]
src/platformops/config.py:114: error: Missing type parameters for generic type "dict"  [type-arg]
src/platformops/config.py:114: error: Missing type parameters for generic type "dict"  [type-arg]
src/platformops/config.py:133: error: Missing type parameters for generic type "dict"  [type-arg]
src/platformops/config.py:157: error: Missing type parameters for generic type "dict"  [type-arg]
Found 5 errors in 1 file (checked 1 source file)

Only config.py is checked at all. Every other module in src/platformops has no type-checking demanded of it yet -- that is deliberate, and step 7 is where you widen the net.

4. Tighten config.py's types​

A bare dict return type is a promise with no detail: it says "you get a dict back," not what is inside it. Open src/platformops/config.py and add Any to the imports at the top:

src/platformops/config.py
from collections.abc import Mapping
from typing import Any

Then tighten these four signatures, in order, top to bottom:

src/platformops/config.py
def load_yaml_dict(path: Path) -> dict[str, Any]:
src/platformops/config.py
def load_service_yaml(path: Path) -> ServiceDefinition | list[dict[str, Any]]:
src/platformops/config.py
def apply_env_overrides(
    data: dict[str, Any], environ: Mapping[str, str] | None = None
) -> dict[str, Any]:
src/platformops/config.py
def write_resolved_config(data: dict[str, Any], out_path: Path) -> None:

One more: _report's result parameter carries the same list[dict] shape as load_service_yaml's return value. Tighten it the same way:

src/platformops/config.py
def _report(
    path: Path, result: ServiceDefinition | list[dict[str, Any]], as_json: bool
) -> None:

dict[str, Any] says something real: the keys are always strings (a YAML mapping's keys, once parsed), but the values could be anything -- a string, a number, a nested mapping. That is an honest description of what a service definition looks like before validate_service() gets to it, not a promise this module cannot keep.

uv run mypy

Expected output

Success: no issues found in 1 source file

Mark the package itself as carrying type information, for any future consumer -- another module, or a coding agent's own type checker -- that imports it:

touch src/platformops/py.typed

An empty py.typed file is a real, standard signal (defined by PEP 561) that this package's type hints are meant to be trusted, not just internal notes.

uv run pytest -q

Expected output

138 passed in 1.29s

5. Write the secret-scan script​

check-security (from M11) already proves the pattern: use grep safely -- an argument list, no shell=True, an explicit timeout -- to catch one specific category of problem before it reaches a shared repository. A secret scanner is the same pattern aimed at a different target: instead of shell=True, it looks for text shaped like a real credential.

Create scripts/check-secrets.sh:

mkdir -p scripts
scripts/check-secrets.sh
#!/usr/bin/env bash
set -euo pipefail

# Patterns tuned to one specific credential shape each -- an AWS access key
# ID, a private key file header, a GitHub personal access token. Deliberately
# narrow, not a general "looks suspicious" heuristic. Scans the given
# directory (defaults to the whole project) so it can be pointed at a
# throwaway scratch folder too, not just the real source tree.
TARGET="${1:-.}"

PATTERNS=(
  'AKIA[0-9A-Z]{16}'
  'BEGIN (RSA|OPENSSH|EC|DSA) PRIVATE KEY'
  'gh[pousr]_[A-Za-z0-9]{36}'
)

found=0
for pattern in "${PATTERNS[@]}"; do
  if grep -rnE --include='*.py' --include='*.yaml' --include='*.yml' \
      --exclude-dir='.venv' --exclude-dir='.git' \
      -e "$pattern" "$TARGET" 2>/dev/null; then
    found=1
  fi
done

if [ "$found" -eq 1 ]; then
  echo "check-secrets: FAIL -- possible credential found above"
  exit 1
fi

echo "check-secrets: clean -- no credential patterns found in $TARGET"
exit 0
chmod +x scripts/check-secrets.sh
./scripts/check-secrets.sh

Expected output

check-secrets: clean -- no credential patterns found in .

Prove it actually catches something, using a throwaway file outside the project so you never have to plant (and remember to remove) a fake credential inside your real source tree:

mkdir -p /tmp/m13-secret-demo
echo 'AWS_KEY = "AKIAABCDEFGHIJKLMNOP"' > /tmp/m13-secret-demo/leaky.py
./scripts/check-secrets.sh /tmp/m13-secret-demo

Expected output

/tmp/m13-secret-demo/leaky.py:1:AWS_KEY = "AKIAABCDEFGHIJKLMNOP"
check-secrets: FAIL -- possible credential found above

The command exits non-zero here -- confirm it with echo $? if you want to see the exit code directly. Clean up the demo file:

rm -rf /tmp/m13-secret-demo
This is a pattern scanner, not proof

It only catches text shaped like the three patterns above, checked against the current working tree. A secret already committed to git history is still there even after this script goes clean on the working copy -- the Deep Dive covers exactly what that gap means and what closing it for real requires.

6. Wire every gate into one script​

Six checks now exist: two you already had (ruff format, ruff check), one from M12 (pytest), and three new to this module (mypy, the secret scan, and the dependency audit you add in step 7). Wire the first five into one script -- the sixth, pip-audit, is what you hand to your coding agent next.

scripts/check-gates.sh
#!/usr/bin/env bash
set -euo pipefail

echo "== ruff format --check =="
uv run ruff format --check .

echo "== ruff check =="
uv run ruff check .

echo "== mypy =="
uv run mypy

echo "== pytest =="
uv run pytest -q

echo "== secret scan =="
./scripts/check-secrets.sh

echo "All quality gates passed."
chmod +x scripts/check-gates.sh
./scripts/check-gates.sh

Expected output

== ruff format --check ==
22 files already formatted
== ruff check ==
All checks passed!
== mypy ==
Success: no issues found in 1 source file
== pytest ==
138 passed in 1.31s
== secret scan ==
check-secrets: clean -- no credential patterns found in .
All quality gates passed.

set -euo pipefail at the top is what makes this a real gate and not just a report: the first command that fails stops the script immediately, with a non-zero exit code -- the same signal a CI job checks to decide whether a change is allowed through.

7. Extend the rollout: hand this to your coding agent​

Two things remain, both wider or riskier than a single-module change is comfortable doing by hand: widening mypy's files setting from just config.py to the whole src/ tree (which means adding real type annotations to every function mypy newly complains about), and adding a dependency audit as this project's sixth and final gate.

Open your coding agent in the project folder:

claude

Paste this request exactly as written:

I'm working in this uv-managed Python project, platformops. It already has
mypy configured in pyproject.toml with files = ["src/platformops/config.py"]
and disallow_untyped_defs = true, plus an override that sets
ignore_missing_imports = true for the yaml module.
src/platformops/config.py is already fully annotated and passes mypy
cleanly. Every other module under src/platformops (cli.py, diagnostics.py,
httpclient.py, local_ops.py, servicedef.py, and everything under
inventory/) is not checked by mypy yet, because files only names config.py.
Please do the following, without changing any function's runtime behavior:

1. Widen the mypy files list to files = ["src"], so every module under
   src/platformops (cli.py, diagnostics.py, httpclient.py, local_ops.py,
   servicedef.py, and everything under inventory/) is checked, not just
   config.py. disallow_untyped_defs = true already applies to the whole
   [tool.mypy] section, so widening files is what puts every other module
   under that same requirement.

2. Add complete type annotations (parameters and return types) to every
   function and method in src/platformops/cli.py, diagnostics.py,
   httpclient.py, local_ops.py, servicedef.py, and every file under
   inventory/, so that each one passes mypy under the same strictness
   config.py already uses. Prefer precise types over Any wherever the
   actual value is known -- dict[str, Any] is fine for a genuinely
   open-ended mapping (like a parsed YAML value), but a function that
   always returns a str or a specific dataclass should say so. If a
   specific third-party import has no type information available (the
   same situation yaml was already in), add a scoped
   [[tool.mypy.overrides]] entry for that module instead of silencing the
   finding with a blanket # type: ignore.

3. Run `uv run mypy` yourself and fix anything it still reports before
   moving on.

4. Add scripts/check-deps.sh, a small script that runs a dependency security
   audit with `uvx pip-audit` against this project (do not add pip-audit as
   a permanent project dependency -- run it through uvx so it stays a
   throwaway tool invocation, never installed into the project itself).
   Make it executable, and have it exit non-zero if pip-audit reports a
   vulnerability. Then add a "== dependency audit ==" step to the end of
   scripts/check-gates.sh, after the existing secret-scan step, that calls
   scripts/check-deps.sh.

5. Run `uv run pytest -q` and `uv run ruff check .` yourself and confirm
   both still pass -- you changed type annotations only, not behavior, so
   the test count and every existing test result should be unchanged.

6. Run the full ./scripts/check-gates.sh yourself and tell me the result, including
   whether pip-audit reported any findings against this project's current
   dependencies.

This spec draws a hard line around what changes (type annotations, the mypy files scope, one new script and one new gate step) and what does not (any function's actual behavior, the test suite, the existing dependency list).

Run the checklist:

  • Does uv run mypy actually report success, project-wide, not just for config.py? Run it yourself; do not take the agent's word for it.
  • Does pyproject.toml now read files = ["src"], not files = ["src/platformops/config.py"] any more? A files list that never actually changed means the widening never happened, even if the agent reports success -- mypy would still only be checking one file.
  • Is the yaml override still exactly ignore_missing_imports = true, untouched? And did any new third-party-import findings get a scoped override of their own, instead of a blanket # type: ignore sprinkled through the code?
  • Are the new annotations honest, not a shortcut? Skim a handful of the changed function signatures. A parameter or return type that is Any everywhere, even where the function clearly always returns (say) a str, defeats the entire point of this step -- mypy would report success without actually checking anything meaningful at those call sites.
  • Does pytest -q report the exact same test count and result as before this step? Type annotations are not supposed to change runtime behavior at all -- if the count moved, something besides annotations changed.
  • Is pip-audit a permanent dependency in pyproject.toml, or does scripts/check-deps.sh call it through uvx? It should be the latter -- a security scanner does not need to be installed into the project just to be run.
  • Does scripts/check-deps.sh actually exit non-zero if pip-audit finds something? Read it; confirm it does not swallow a non-zero exit code the way a stray || true would, and that scripts/check-gates.sh calls it as its final step.
  • What did pip-audit actually report against this project's current dependencies? A clean result today does not mean this gate is done -- it means today's run found nothing. The Common Pitfalls section in the lesson already named why this gate needs to run repeatedly, not once.

A MINOR bump, on purpose

Troubleshooting
  • mypy reports errors in files you have not touched, like .venv/ or a scratch script. Confirm pyproject.toml's [tool.mypy] section still has a files list scoping the check -- running a bare mypy . with no files config instead walks the whole project directory, including your virtual environment.
  • The files = ["src/platformops/config.py"] setting in step 3 seems to have no effect -- uv run mypy reports nothing at all. Confirm the path is exact and relative to the project root (not platformops/config.py or an absolute path) -- mypy's files list is a literal path match, not a fuzzy one.
  • scripts/check-secrets.sh: Permission denied when you run it directly. You ran ./scripts/check-secrets.sh before chmod +x scripts/check-secrets.sh -- add the execute bit, or run it as bash scripts/check-secrets.sh instead.
  • scripts/check-gates.sh keeps running even after one step fails. Confirm the first line is exactly set -euo pipefail -- a script missing set -e keeps going after a failing command, defeating the whole point of a gate.
  • uvx pip-audit in step 7 fails with a network error. pip-audit checks a public vulnerability database over the network -- if this machine has no internet access right now, that step cannot run; note it and come back to it later rather than treating it as a bug in the script.
  • Type annotations the agent added in step 7 use Any almost everywhere. This is exactly what the review checklist's third item asks you to catch -- mypy reporting success is not the same as the annotations being honest. Ask the agent to replace Any with the real, specific type anywhere the function's actual return value is known.

Teardown​

This lab never starts a service, a container, or a background process -- every command it runs is a short-lived ruff, mypy, pytest, grep, or pip-audit invocation that exits on its own, and every file it touches (CHANGELOG.md, pyproject.toml, README.md, scripts/, src/platformops/) is meant to stay changed as part of this release.

cd ~
rm -rf platformops

Run this only if you want to remove the project and rebuild it from the checkpoint. Otherwise, keep ~/platformops; it carries forward into every later module.
