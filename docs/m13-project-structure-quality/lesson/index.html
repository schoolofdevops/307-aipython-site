Structuring and Maintaining Python Projects

platformops now has real logic in it: a service model, a config loader, a CLI, an HTTP client, local operations helpers, and over a hundred tests. That is exactly the point where a project stops being "a script you wrote" and becomes "a thing other people depend on": a teammate installs it, a CI job runs it, a coding agent edits it. This module is about the parts of a project that make that handoff safe: a clear history of what changed and when, a version number people can trust, and a fixed set of checks every change has to pass before it is considered done. It does not matter whether a human wrote that change or an agent did.

None of this is about writing new features. check-security, check-health, and every other command you built already work. This module adds the guardrails around them.

1. A changelog is the project's incident timeline​

Picture an incident: a service starts failing intermittently at 11 AM, and the first question anyone asks is "what changed?" If the answer lives only in individual people's memory, or in a long git log nobody wants to read line by line, that question takes an hour to answer instead of a minute. A changelog is a short, human-readable file, CHANGELOG.md, that answers "what changed, in this release" in one glance, release by release. It is not a replacement for git log; it is a summary written for a person who needs the answer fast, not one who is willing to dig.

platformops already has ten releases behind it, from v0.0 to v1.0. In this module you write a CHANGELOG.md that lists what each one added, the same way a "Keep a Changelog"-style file does at any real company: one section per version, newest first, a short bulleted list of what changed.

2. A version number is a promise, not just a label​

A version number like 1.0.0 looks like three numbers separated by dots, but each number means something specific under semantic versioning (semver): MAJOR.MINOR.PATCH. A PATCH bump means "nothing about how you call this changed, just a fix inside it." A MINOR bump means "something new was added, but everything that worked before still works." A MAJOR bump means "something that used to work may no longer work the same way. Read the changelog before you upgrade." This is the same promise you rely on every time you pin a library version in pyproject.toml: you trust that httpx>=0.28.1,<1.0 will not suddenly break your code, because the library's own maintainers made that same promise about their own MAJOR number.

platformops is currently at 1.0.0. This module's release, v1.1.0, is a MINOR bump: it adds new guardrails (type checking, secret scanning, a dependency audit) without changing anything about how the existing commands behave.

3. Quality gates: one fixed order, every single time​

Think about an assembly line. Each station checks one specific thing, in a fixed order, and a part that fails a station never reaches the next one. Quality gates work the same way for code: a short, ordered sequence of automated checks that a change has to pass before it is considered ready. platformops already has two: ruff format (does the code look consistent?) and ruff check (does it follow the project's lint rules?), plus pytest (does it behave correctly?). This module adds three more stations to that same line: a type checker (does every function get the kind of value it expects?), a secret scanner (did a credential slip into a file that should never hold one?), and a dependency check (does anything this project depends on have a known security problem?).

The order matters for a practical reason: formatting and linting are near-instant, so they run first and fail fast, before you wait on the slower type checker and test suite. This is the same reasoning behind putting a cheap sanity check before an expensive one in any pipeline, CI or otherwise. You wire all six into one script in this module's lab, so running the whole line is one command, not six you have to remember in order.

4. Type checking: catching a mismatch before it runs​

A function signature like def load_yaml_dict(path: Path) -> dict: is a promise about the kind of value that goes in and the kind that comes out. But Python itself never checks that promise. It only checks types the moment code actually runs, and only for the exact path that execution happens to take that time. A type checker like mypy reads your whole codebase without running any of it, and checks every function call against every function's declared types. That is the same way a second reviewer reads a document for a factual error before it gets published, instead of waiting to find out the fact was wrong after readers already saw it.

Here is a realistic case this catches: a teammate (or a coding agent) changes a function that used to return a plain dict so it now sometimes returns None on an edge case, but forgets to update every place downstream that calls .get() on the result without checking for None first. pytest only catches this if a test happens to exercise that exact edge case. mypy catches it on every single call site, every time, without running a single line, because the mismatch is visible from the function's declared type alone, not from any one specific input.

5. Secret scanning: one detector, one specific thing​

Airport security has a scanner tuned to find one specific category of item, checked on every single bag, regardless of how trustworthy the traveler looks. A secret scanner does the same job for a codebase: it checks every file for text that matches the shape of a real credential (an AWS access key, a private key header, a GitHub token) and flags it before it reaches a shared repository. This is one of the most common real incidents in software teams: someone hardcodes a key while debugging locally, forgets to remove it, and commits it. Once a secret is in git history, rotating it (issuing a new one and revoking the old one) is the only real fix. Deleting the line in a later commit does not remove it from history. A gate that catches it before the commit is far cheaper than a rotation after the fact.

6. Dependency security: your supply chain, not just your code​

ruff and mypy check the code you wrote. Neither one looks at the dozens of packages your project depends on, and a real vulnerability disclosed in one of them (a known CVE in a specific version of a library you pinned) is invisible to both. A dependency audit checks your locked dependency versions against a public vulnerability database and reports anything with a known, disclosed problem. This matters because a lockfile (uv.lock) only guarantees that everyone installs the exact same versions. It says nothing about whether those versions are still considered safe today. The Deep Dive goes further into exactly what a lockfile does and does not guarantee.

Common pitfalls
  • Writing a changelog entry after the fact, from memory, instead of as you make the change. The detail fades fast. Write the entry in the same session you make the change, not at release time.
  • Bumping the wrong version number. Adding a new command is a MINOR bump; fixing a bug in an existing one is a PATCH bump. Get this wrong and downstream users cannot trust your version number to warn them about a real behavior change.
  • Adding mypy and trying to fix every warning at once. A codebase that has never been type-checked before will report dozens of findings on the first run. Start with one module, get it clean, and only then widen the scope. That is exactly what this module's lab does with config.py.
  • Treating a passing secret scan as proof no secret ever existed. A scanner only catches patterns it knows to look for, run against the current working tree. A credential already committed to git history is still there even after the working file is fixed. Rotation, not deletion, is the fix.
  • Running the dependency audit once and considering the job done. A version that is safe today can have a CVE disclosed against it next month. This gate needs to run repeatedly, not once at release time. Most teams schedule it in CI on a recurring basis, not only on every commit.

Ten releases in, platformops has real users depending on it, even if today that "user" is a teammate, a CI job, or your own coding agent picking up where you left off. This module is what makes it safe to keep growing.
