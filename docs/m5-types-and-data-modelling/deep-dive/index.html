What Validation Actually Costs and Catches

The lab built a ServiceDefinition model, added three field constraints, and proved with tests that good data passes and bad data does not. This page opens up the mechanism behind that: what a type annotation actually is before Pydantic touches it, when Pydantic builds the code that checks your data (and how often it rebuilds it), exactly what shape a validation failure takes as data, when Pydantic converts a value for you instead of rejecting it -- and when that convenience becomes a real risk -- and how to turn a validated model back into a plain dict or JSON to write it somewhere else. You will reach for this the next time you are deciding whether a slow validation path is Pydantic's fault, building an API that needs to report exactly which field failed, or arguing with a teammate about whether a field should accept "close enough" input.

Where this picks up

You need ~/platformops at v0.3 -- the ServiceDefinition model with its three field constraints and to_summary() method, from the lab. Every command below reads the project or runs a short, disposable Python one-liner against it; none of them change committed files. Re-running any command on this page is safe.

cd ~/platformops

1 -- A type hint is a label, until something reads it​

The lesson's total_cpu("3", 2) example showed a type hint being ignored. Here is the same fact from a different angle: Python stores a function's annotations in a plain dictionary and never consults it while the function runs.

uv run python -c "
def f(x: int) -> str:
    return x

print(f.__annotations__)
result = f(123)
print(result, type(result))
"

Expected output

{'x': <class 'int'>, 'return': <class 'str'>}
123 <class 'int'>

f is annotated to take an int and return a str. It was called with an int and handed back an int -- violating its own declared return type -- and Python did not so much as warn. Think of an annotation as a shipping label glued to a box: "Fragile," "This side up," "Contents: electronics." The label is genuinely useful information, but the box does not enforce it. Nothing about gluing a label to a box makes the forklift driver read it, or stops them from stacking it upside down. Someone -- or something -- has to actively read the label and act on it. For a type hint, that "something" is either a separate tool you run (a type checker like mypy, reading your code without running it) or, at runtime, a library that was written to walk your annotations on purpose. Pydantic is exactly that library.

2 -- Pydantic reads your annotations once, not on every call​

When Python executes class ServiceDefinition(BaseModel):, Pydantic's base class machinery walks every annotated field on the spot and compiles a validator for the whole model -- a SchemaValidator object, implemented in Rust by pydantic-core, attached to the class as __pydantic_validator__. That compilation happens exactly once, when the class is defined (effectively, when the module is imported). Every later call to ServiceDefinition(...) or ServiceDefinition.model_validate(...) reuses that same compiled object; it does not re-read your annotations or rebuild anything.

This is the same idea as a printing press: cutting the metal plate is the slow, one-time setup -- reading every letter of the design and engraving it. Printing the thousandth page reuses the same plate; it does not re-cut it. Confirm it directly: validate two different dicts and check whether the class's compiled validator is literally the same object both times.

uv run python -c "
from platformops.servicedef import ServiceDefinition, GOOD_EXAMPLE

v1 = ServiceDefinition.__pydantic_validator__
print(type(v1))
inst1 = ServiceDefinition.model_validate(GOOD_EXAMPLE)
inst2 = ServiceDefinition.model_validate(GOOD_EXAMPLE)
v2 = ServiceDefinition.__pydantic_validator__
print(v1 is v2)
"

Expected output

<class 'pydantic_core._pydantic_core.SchemaValidator'>
True

This is exactly why "Pydantic is slow" is rarely the right diagnosis when a validation-heavy service is slow. The expensive part -- reading your class definition and compiling a checker for it -- happens once, at import time, for the whole process's lifetime. What runs on every request is the compiled Rust validator doing its actual job on that one payload. If a validation path is slow in production, look at the shape of the data (deeply nested models, huge lists) or what happens after validation succeeds, not at the existence of validation itself.

3 -- ValidationError.errors(): structured data, not a string to parse​

validate_service in the lab already returns exc.errors() instead of the raw exception. Feed it two failures at once and look at exactly what comes back:

uv run python -c "
from platformops.servicedef import validate_service, GOOD_EXAMPLE

bad = {**GOOD_EXAMPLE, 'environment': 'production', 'aws_account': 111122223333}
for error in validate_service(bad):
    print(error)
"

Expected output

{'type': 'literal_error', 'loc': ('environment',), 'msg': "Input should be 'dev', 'staging' or 'prod'", 'input': 'production', 'ctx': {'expected': "'dev', 'staging' or 'prod'"}, 'url': 'https://errors.pydantic.dev/2.13/v/literal_error'}
{'type': 'string_type', 'loc': ('aws_account',), 'msg': 'Input should be a valid string', 'input': 111122223333, 'url': 'https://errors.pydantic.dev/2.13/v/string_type'}

Every error is a plain dict with the same five keys: type (a stable, machine-matchable error code -- literal_error, string_type, missing, and so on, not free text you would have to pattern-match), loc (which field, as a tuple -- for a nested model this would read something like ('observability', 'alert_channel')), msg (the human-readable reason), input (exactly what was received), and url (a link to Pydantic's docs for that error type). This is what turns a validation failure into something a program can act on: an API endpoint can loop over these dicts and return a 422 response naming every bad field at once; a CLI can turn each one into a line of its own instead of dumping a Python traceback at a user who never wrote any Python.

4 -- Coercion vs. strict: the same input, two different verdicts​

By default, Pydantic is "lax": it accepts some values that are not exactly the annotated type, if converting them is unambiguous. A string that reads as a whole number becomes an int. Turn that off with strict=True and the same input is rejected outright:

uv run python -c "
from pydantic import BaseModel, ConfigDict, ValidationError

class Deployment(BaseModel):
    replicas: int

class StrictDeployment(BaseModel):
    model_config = ConfigDict(strict=True)
    replicas: int

d = Deployment(replicas='3')
print('lax:', d.replicas, type(d.replicas))

try:
    StrictDeployment(replicas='3')
except ValidationError as exc:
    print('strict rejects it:')
    for error in exc.errors():
        print(' ', error['type'], '-', error['msg'])
"

Expected output

lax: 3 <class 'int'>
strict rejects it:
  int_type - Input should be a valid integer

Lax mode is genuinely useful where the source of the data is always text -- an environment variable, a CLI flag, a value typed into a form -- and "3" plainly means the number 3. It becomes a liability when the coercion hides a real mistake: an int field will happily accept True as 1, because Python's bool is technically a subtype of int -- fine for a retry_count, alarming for a field where a stray boolean should never have been anywhere near it in the first place. ServiceDefinition sidesteps this question for aws_account by typing it str, not int -- there is no numeric coercion to worry about, because the field was never declared as a number Pydantic might try to be helpful about. Choosing a field's type is also a choice about how much benefit-of-the-doubt you are giving the data that arrives in it; reach for strict=True (globally with ConfigDict(strict=True), or per field with Field(strict=True)) when that benefit of the doubt is the wrong call for a specific value.

5 -- model_dump() and model_dump_json(): getting validated data back out​

Validation is not one-directional. Once you have a ServiceDefinition, you often need to hand it back out -- write it to a YAML file after a script edits one field, or send it as an API request body:

uv run python -c "
from platformops.servicedef import validate_service, ServiceDefinition, GOOD_EXAMPLE

svc = validate_service(GOOD_EXAMPLE)
print(svc.model_dump())
print()
print(svc.model_dump_json())
print()
round_tripped = ServiceDefinition.model_validate(svc.model_dump())
print(round_tripped == svc)
"

Expected output

{'name': 'checkout-api', 'repository': 'github.com/example/checkout-api', 'environment': 'prod', 'team_owner': 'payments-team', 'kubernetes_namespace': 'checkout', 'deployment_name': 'checkout-api', 'aws_account': '111122223333', 'region': 'us-east-1', 'observability': {'dashboard_url': 'https://grafana.example.com/d/checkout-api', 'alert_channel': '#checkout-alerts'}}

{"name":"checkout-api","repository":"github.com/example/checkout-api","environment":"prod","team_owner":"payments-team","kubernetes_namespace":"checkout","deployment_name":"checkout-api","aws_account":"111122223333","region":"us-east-1","observability":{"dashboard_url":"https://grafana.example.com/d/checkout-api","alert_channel":"#checkout-alerts"}}

True

model_dump() walks back down through the nested ObservabilityRefs model automatically, handing you a plain nested dict -- the same shape you would write to YAML. model_dump_json() does the same but returns a JSON string directly, without a separate json.dumps() call. round_tripped == svc being True confirms the whole trip is lossless: dump a validated model out, validate the dump back in, and you get an equal object. That is what makes it safe for a coding agent (or a script) to load a ServiceDefinition, change one field in memory, dump it, and write the result back to disk -- the fields it did not touch survive the round trip exactly.

Where you will use this
  • A compiled validator is built once, at class-definition time, and reused for every later call. Use it when: you are profiling a validation-heavy service and tempted to blame Pydantic for latency -- check the shape of the data and what runs after validation first; the schema itself was not rebuilt on this request.
  • ValidationError.errors() is a list of plain dicts with a stable type, loc, msg and input, not a string you would have to parse. Use it when: you are building an API endpoint, CLI, or webhook handler that needs to report exactly which fields failed and why, instead of surfacing a raw traceback to whoever (or whatever) sent the bad data.
  • Lax mode coerces unambiguous values (a numeric string to int, True to 1); strict mode rejects anything that is not already the exact declared type. Use it when: you are deciding how to type a field sourced from an environment variable or CLI flag (let lax coercion help) versus a field where an unexpected conversion could hide a real mistake (turn on strict=True, or pick a type -- like str for an account ID -- that leaves nothing to coerce).
  • model_dump()/model_dump_json() losslessly round-trip a validated model back to a plain dict or JSON, nested models included. Use it when: an agent or script needs to modify one field of a validated definition and write the whole thing back out to a YAML file or an API call, without hand-reconstructing the dict itself.
