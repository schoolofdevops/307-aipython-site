Lab — Build PlatformOps v0.3: the Service Definition Model

This lab has two phases. In Phase A you add Pydantic to the project and hand-build a ServiceDefinition model yourself, so you know exactly what it checks and why. In Phase B you hand a short, written request to a coding agent to add field-level constraints and a summary method on top of that model, then you review its diff before accepting it -- the same review habit from the last two modules.

You need the ~/platformops project from the M4 lab, already tagged v0.2, with uv run pytest -q passing and git log showing that tag.

cd ~/platformops

Phase A -- add Pydantic and hand-build the model​

1. Add Pydantic -- the toolkit's first real dependency​

Every module so far has used only Python's standard library. This one adds the toolkit's first third-party package:

Your exact version numbers may resolve slightly newer -- Pydantic ships often. uv add did two things at once: it wrote pydantic into pyproject.toml's dependencies list, and it resolved, downloaded and locked five packages into uv.lock -- pydantic itself plus four packages it depends on (pydantic-core is the compiled validation engine written in Rust; annotated-types and typing-extensions/typing-inspection are small typing-support libraries). Look at what changed:

git diff pyproject.toml

Expected output

-dependencies = []
+dependencies = [
+    "pydantic>=2.13.4",

uv.lock also changed -- by well over a hundred lines -- but you never hand-edit that file. It pins the exact resolved version of every package (direct and transitive) so that uv sync reproduces the identical dependency set on any machine, including a teammate's laptop or CI. That is the whole point of a lockfile: pyproject.toml says "pydantic 2.13 or newer," uv.lock says "pydantic 2.13.4, pydantic-core 2.46.4, and nothing else will be silently substituted."

2. Create the service definition module​

The toolkit's inventory package earned its own folder in the last module because it grew to six files with distinct jobs -- data, rules, filtering, reporting. This module's work is one cohesive idea: one Pydantic model, one nested model, one validation function, and one demo entry point. That fits comfortably in a single file, the same size inventory.py was in v0.1 before it needed splitting. Create src/platformops/servicedef.py:

"""Service definition model -- PlatformOps v0.3.

A service definition is the small record every team is supposed to keep up to
date about their own service: what it is called, where its code lives, which
environment and namespace it runs in, who owns it, and where to look when it
misbehaves. Today that record usually lives in a YAML file a team edits by
hand -- which means it is exactly as trustworthy as the last person who
edited it.

`ServiceDefinition` turns a raw dict (loaded from that YAML, or from an API
call, or typed in by a user) into a validated, typed object. `validate_service`
is the one function anything in this toolkit calls to make that conversion --
nothing downstream should ever read a raw service dict again.
"""

from pydantic import BaseModel, ValidationError


class ObservabilityRefs(BaseModel):
    """Where an on-call engineer looks when this service misbehaves."""

    dashboard_url: str
    alert_channel: str


class ServiceDefinition(BaseModel):
    """One service's operational identity."""

    name: str
    repository: str
    environment: str
    team_owner: str
    kubernetes_namespace: str
    deployment_name: str
    aws_account: str
    region: str
    observability: ObservabilityRefs


def validate_service(data: dict) -> ServiceDefinition | list[dict]:
    """Validate a raw dict against `ServiceDefinition`.

    Returns the validated model on success. On failure, returns
    `ValidationError.errors()` -- a plain list of dicts -- instead of raising,
    so a caller can log, report or reject bad input without wrapping every
    call site in its own try/except.
    """
    try:
        return ServiceDefinition.model_validate(data)
    except ValidationError as exc:
        return exc.errors()


GOOD_EXAMPLE = {
    "name": "checkout-api",
    "repository": "github.com/example/checkout-api",
    "environment": "prod",
    "team_owner": "payments-team",
    "kubernetes_namespace": "checkout",
    "deployment_name": "checkout-api",
    "aws_account": "111122223333",
    "region": "us-east-1",
    "observability": {
        "dashboard_url": "https://grafana.example.com/d/checkout-api",
        "alert_channel": "#checkout-alerts",
    },
}

BAD_EXAMPLE = {
    "name": "checkout-api",
    "repository": "github.com/example/checkout-api",
    "environment": "prod",
    "team_owner": "payments-team",
    "kubernetes_namespace": "checkout",
    "aws_account": "111122223333",
    "region": "us-east-1",
    "observability": {
        "dashboard_url": "https://grafana.example.com/d/checkout-api",
        "alert_channel": "#checkout-alerts",
    },
}


def _print_result(label: str, data: dict) -> None:
    result = validate_service(data)
    print(f"{label}:")
    if isinstance(result, ServiceDefinition):
        print(
            f"  OK -- {result.name} ({result.environment}/{result.kubernetes_namespace})"
        )
    else:
        for error in result:
            location = ".".join(str(part) for part in error["loc"])
            print(f"  FAIL -- {location}: {error['msg']}")


if __name__ == "__main__":
    _print_result("Good service definition", GOOD_EXAMPLE)
    print()
    _print_result("Bad service definition (missing deployment_name)", BAD_EXAMPLE)

Notice BAD_EXAMPLE is GOOD_EXAMPLE with deployment_name removed entirely -- a required field left out, the same kind of mistake as a teammate forgetting a line in a YAML file. observability is a nested model: Pydantic validates dashboard_url and alert_channel inside it exactly the same way it validates the outer model's own fields. The if __name__ == "__main__": block at the bottom is your demo entry point -- it runs only when this file is executed directly (or with -m), never when something else imports validate_service from it.

3. Write the tests​

Create tests/test_servicedef.py:

from platformops.servicedef import GOOD_EXAMPLE, ServiceDefinition, validate_service


def test_a_complete_valid_definition_validates_successfully():
    result = validate_service(GOOD_EXAMPLE)
    assert isinstance(result, ServiceDefinition)
    assert result.name == "checkout-api"
    assert result.observability.alert_channel == "#checkout-alerts"


def test_a_missing_required_field_fails_with_the_field_required_error():
    data = {
        key: value for key, value in GOOD_EXAMPLE.items() if key != "deployment_name"
    }
    errors = validate_service(data)
    assert isinstance(errors, list)
    assert any(
        error["loc"] == ("deployment_name",) and error["type"] == "missing"
        for error in errors
    )


def test_a_wrong_type_value_fails_instead_of_being_silently_accepted():
    data = {**GOOD_EXAMPLE, "aws_account": 111122223333}  # int, not str
    errors = validate_service(data)
    assert isinstance(errors, list)
    assert any(
        error["loc"] == ("aws_account",) and error["type"] == "string_type"
        for error in errors
    )

The third test is the one worth reading twice: aws_account is 111122223333 as an int, not a string. Pydantic does not quietly stringify it -- it rejects the whole definition with a string_type error, because silently converting a number to a string can hide a mistake (was that AWS account ID typed as a number by accident, dropping a leading zero?). The next module's Deep Dive digs into exactly which type conversions Pydantic performs automatically and which it refuses.

Phase B -- delegate the field constraints​

Right now ServiceDefinition checks that every field is present and has the right basic type, but it does not check that environment is a real environment, that region is a region this company actually operates in, or that kubernetes_namespace is a name Kubernetes will accept. Those are the checks Phase B adds.

5. Ask your coding agent to add the constraints​

Open your coding agent in the project folder:

claude

Paste this request exactly as written:

I'm working in this uv-managed Python project, in src/platformops/servicedef.py
(a Pydantic v2 ServiceDefinition model, its ObservabilityRefs nested model, and a
validate_service function). Please add the following, without touching anything else
in the file:

1. Restrict `environment` to exactly "dev", "staging" or "prod" -- any other value
   must fail validation.
2. Restrict `region` to a small, fixed allowed list of AWS regions (pick 3-4
   realistic ones, e.g. us-east-1, us-west-2, eu-west-1, ap-south-1) -- any other
   value must fail validation.
3. Restrict `kubernetes_namespace` to a lowercase, DNS-safe name: lowercase letters,
   digits and hyphens only, must not start or end with a hyphen -- reject anything
   else.
4. Add a `to_summary()` method on ServiceDefinition that returns one line an
   on-call engineer could read in a paging alert (name, environment, region,
   namespace, owner, alert channel -- your call on the exact wording).
5. Do not add any new third-party dependencies -- pydantic's own field types and
   constraints are enough for all four of the above.
6. Add a test for each of the three new constraints (a value that should now be
   rejected) plus one test for to_summary(). Every existing test must stay green,
   unchanged.
7. Run `uv run ruff check .` and `uv run pytest -q` yourself before you finish,
   and tell me the result.

This spec names the exact constraints (not "add some validation"), states the boundary (no new dependencies -- Pydantic's own Literal types and Field(pattern=...) cover all four asks), and asks the agent to verify its own work, the same discipline as the last two modules' Phase B.

Now read the actual change to the model:

git diff --cached -- src/platformops/servicedef.py

This course's own reference diff for the four asks looks like this -- your agent's exact naming may differ, the shape should not:

-from pydantic import BaseModel, ValidationError
+from typing import Literal
+
+from pydantic import BaseModel, Field, ValidationError
+
+Environment = Literal["dev", "staging", "prod"]
+Region = Literal["us-east-1", "us-west-2", "eu-west-1", "ap-south-1"]
+
+# RFC 1123 DNS label: lowercase letters, digits, hyphens; must not start or end
+# with a hyphen. Kubernetes rejects anything else for a namespace name, so
+# rejecting it here is catching the same mistake before it reaches a cluster.
+_NAMESPACE_PATTERN = r"^[a-z0-9]([-a-z0-9]*[a-z0-9])?$"


 class ObservabilityRefs(BaseModel):
@@ class ServiceDefinition(BaseModel):

     name: str
     repository: str
-    environment: str
+    environment: Environment
     team_owner: str
-    kubernetes_namespace: str
+    kubernetes_namespace: str = Field(pattern=_NAMESPACE_PATTERN)
     deployment_name: str
     aws_account: str
-    region: str
+    region: Region
     observability: ObservabilityRefs

+    def to_summary(self) -> str:
+        """One line an on-call engineer can scan in a paging alert."""
+        return (
+            f"{self.name} [{self.environment}/{self.region}] "
+            f"ns={self.kubernetes_namespace} owner={self.team_owner} "
+            f"alerts={self.observability.alert_channel}"
+        )

environment and region became Literal types -- a fixed, closed set of allowed strings, checked the same way any other type is. kubernetes_namespace kept its str type but gained a Field(pattern=...) constraint -- a regular expression Pydantic runs against the value. Neither change required a new import beyond what Pydantic already ships (Field, and Literal from Python's own typing module).

Run the checklist this course keeps coming back to:

  • Does each constraint match the spec exactly? Three rejections (environment, region, kubernetes_namespace), not two, not four.
  • Did the agent add a dependency? Check pyproject.toml a second time -- it should still show only pydantic. Literal and Field(pattern=...) are enough.
  • Is there one test per new constraint, plus one for to_summary()? Count them.
  • Did the three original Phase A tests change at all? They should not have -- if your agent "improved" a test you did not ask it to touch, that is scope creep, not a fix.

Troubleshooting
  • ModuleNotFoundError: No module named 'pydantic' -- either uv add pydantic was never run, or you ran python directly instead of uv run python (or python -m platformops.servicedef). uv run is what makes sure you are using the project's own virtual environment, the one uv add installed pydantic into.
  • uv add pydantic hangs or fails with a network error -- uv add needs to resolve and download packages the first time. If you are genuinely offline and pydantic is already cached from a previous run (yours or a teammate's, on the same machine), uv add pydantic --offline will use the cache instead of reaching the network; otherwise, check your connection and retry.
  • Confusing Pydantic v1 and v2 method names -- this course uses Pydantic v2 throughout: model_validate() (not parse_obj()), model_dump() (not .dict()), ValidationError.errors() (unchanged between versions). Run uv run python -c "import pydantic; print(pydantic.VERSION)" -- it should print 2.x. uv add pydantic with no version pin always resolves the latest v2 release.
  • A field you expected to be required is silently optional, or the other way around -- in Pydantic, a field with no = <default> after its type is required; a field with one (aws_account: str = "unknown") is optional. Read the field line, not just the type.
  • Your agent's diff touches pyproject.toml a second time (after step 1's uv add) -- it added a dependency. Reject that part of the change; Literal and Field(pattern=...) are built into Pydantic and Python's own typing module.
  • string_pattern_mismatch on a namespace you were sure was valid -- check for an uppercase letter or an underscore. Kubernetes namespaces (and this model's pattern) only accept lowercase letters, digits and hyphens.
