Type Hints and Data Modelling

Module slides​

Walk this short whiteboard deck for the big picture, or open it fullscreen.

▶ M5 — Type Hints and Data ModellingOpen fullscreen ↗

Picture a scaling script. It reads replicas and cpu_per_replica from a config file a teammate hand-edited, then works out how much CPU the change needs:

def total_cpu(replicas: int, cpu_per_replica: int) -> int:
    return replicas * cpu_per_replica

print(total_cpu("3", 2))

Expected output

33

Not 6. The teammate's YAML had replicas: "3" in quotes instead of replicas: 3, so Python received a string, not a number. "3" * 2 is not multiplication -- it is Python's rule for "repeat this string twice," and it hands back "33". There is no crash, no traceback, nothing that stops the script. It just quietly computes the wrong capacity, and whoever reads that number believes it. This is the wrong-type incident this module is built around: the annotation replicas: int is written right there in the function, and Python ignored it completely. A type hint, on its own, is a label -- not a check. This module is about closing that gap: how to annotate your code so both humans and tools can read the intent, and how to make sure data that crosses into your program actually gets checked before anything trusts it.

1. Annotations on functions -- documentation a tool can read​

You already write docstrings that describe what a function expects. A type annotation says the same thing in a form your editor, a linter, and (later in this lesson) Pydantic can all read and act on:

def find_low_memory_prod(inventory: list[dict], min_memory_gb: int = 8) -> list[str]:
    ...

inventory: list[dict] says "a list of dicts in," min_memory_gb: int = 8 says "an integer, defaulting to 8," and -> list[str] says "you get a list of strings back." None of this changes how the function runs -- Python still lets you call it with the wrong types, the same way it let total_cpu above accept a string. What it buys you is a second pair of eyes: your editor underlines a mismatched call before you run it, and a teammate (or a coding agent) reading the signature knows the contract without opening the function body.

2. Typed containers, Optional, and unions​

Real automation data is rarely one plain type. A list of tag dictionaries is list[dict[str, str]]; a lookup by service name that might come up empty is written with Optional or, in modern Python, a union with None:

def find_service(name: str, services: list[dict]) -> dict | None:
    for service in services:
        if service["name"] == name:
            return service
    return None

dict | None (the same as Optional[dict] in older code) tells a reader "this can come back empty -- check before you use it." Skip that annotation and the function still behaves identically, but nothing warns the next person that result["name"] can blow up with an AttributeError on None. A union more generally (int | str, str | list[str]) says "one of these shapes, and the caller must handle either."

3. Dataclasses -- a typed record, still on the honor system​

Before you reach for a full validation library, Python's own dataclasses module gives you a typed record with almost no boilerplate:

from dataclasses import dataclass

@dataclass
class ServerRecord:
    name: str
    env: str
    memory_gb: int = 8

One decorator gets you a generated __init__, a readable __repr__, and equality comparison for free -- a big step up from a plain dict where a typo in a key ("envrionment") fails silently. But a dataclass does not check types at construction. ServerRecord(name="db-01", env="prod", memory_gb="lots") builds without complaint; the field is still annotated int, and Python still is not enforcing it. A dataclass is the right tool once you already trust the data -- it is a container for values you have already checked, not a checkpoint.

4. Pydantic -- a model that actually checks​

pydantic.BaseModel looks like a dataclass but enforces its annotations the moment you build one:

from pydantic import BaseModel

class ServerRecord(BaseModel):
    name: str
    env: str
    memory_gb: int = 8

ServerRecord(name="db-01", env="prod", memory_gb="lots")

Expected output

pydantic_core._pydantic_core.ValidationError: 1 validation error for ServerRecord
memory_gb
  Input should be a valid integer, unable to parse string as an integer [type=int_parsing, input_value='lots', input_type=str]
    For further information visit https://errors.pydantic.dev/2.13/v/int_parsing

Leave a field out entirely and Pydantic tells you it is required; give a field a default (memory_gb: int = 8, same syntax as a dataclass) and it becomes optional. A field can also be another BaseModel -- a nested model -- which is exactly how this module's lab structures a service's observability references inside its service definition. The most useful part is that a failed validation is not a bare exception you have to parse by hand: ValidationError.errors() hands back a plain list of dicts, each naming which field failed, why, and what was received -- data you can log, display to a user, or return from an API, not a wall of stack trace text. The Deep Dive after this lab opens that error shape up in detail.

Two more Pydantic facts you will use immediately. First, by default Pydantic is lenient: if a value is the wrong type but clearly convertible, it quietly converts it — the text "8080" becomes the number 8080. You can switch that off with model_config = ConfigDict(strict=True), which rejects anything that is not already the exact right type. Lenient is friendly for config files typed by humans; strict is safer for machine-to-machine data. (Try both moods in the simulator below.) Second, a model can turn itself back into plain data: model_dump() gives you a normal dict and model_dump_json() a JSON string — so validated data can round-trip out to a file or an API response and come back in again through the same validation gate.

5. The boundary rule -- validate at the edge, trust inside​

Put these together and you get a simple, durable habit: validate once, at the point data enters your program, then let the rest of your code trust it completely.

Everything left of the boundary -- a YAML file a teammate hand-edited, a request body from an API, an argument a coding agent's tool call passed in -- is data you did not write and cannot fully trust. Everything right of the boundary is a ServiceDefinition object: if you are holding one, its fields are guaranteed to be the right shape, because Pydantic would have raised before you ever got it. That guarantee is what lets the rest of your code stop defensively checking if "environment" in data on every function call -- the checking already happened, once, in one place.

6. dict vs. dataclass vs. Pydantic -- picking the right one​

Reach for...When...
dictThrowaway or fully internal data -- a one-off script, JSON you're only passing through unread.
dataclassData you already trust, built inside your own code, and you want typed attributes plus a free __init__/__repr__/__eq__ -- no runtime validation needed.
Pydantic BaseModelData crossing a boundary you do not control -- user input, an API request, a YAML file a teammate hand-edited, arguments an agent passed to a tool call.
Common pitfalls
  • Trusting an annotation like it is a runtime check. total_cpu("3", 2) above proves it is not -- a type hint is a label for humans and tools until something (Pydantic, at construction) actually enforces it.
  • Forgetting | None on a field that can genuinely be missing. The function still runs; the crash just shows up later, further from the cause, as an AttributeError on None.
  • Reaching for a dataclass on data you have not validated yet. A dataclass is a container for already-trusted values, not a checkpoint -- it will happily hold a memory_gb that is a string.
  • A mutable default on a dataclass field, written the same way a plain function default is written. tags: list = [] raises ValueError: mutable default ... is not allowed the moment Python reads the class -- a stricter, earlier version of the mutable-default trap from the last module. Use field(default_factory=list) instead.
  • Catching a ValidationError and only logging its string form. You lose the structure -- .errors() gives you the field, the reason, and the bad value as data, which is what lets you report a validation failure back to a caller instead of just a stack trace.
