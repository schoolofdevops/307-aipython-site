Deep Dive — AI Service Release Readiness

The lab proved ai-release-check reports READY for a matching, resourced, healthy release, and NOT_READY for three different reasons -- a stale version label, missing resource requests, and a low evaluation score. This page goes one level deeper on two claims the lesson made but did not fully prove on their own: that this module genuinely never mutates anything (Kubernetes or MLflow), and that model_quality_verdict and infrastructure_verdict are mechanically incapable of leaking into each other, not just conventionally kept apart by careful naming.

Where this picks up

This page assumes ~/platformops at v2.9.0, with src/platformops/ai_release_readiness.py and the DeploymentResourceProfile/get_deployment_resource_profile() addition to kubernetes_inspect.py in place from the lab.

cd ~/platformops
uv run platformops version

Expected output

platformops 2.9.0

1 — Read-only, proven mechanically, across both files this module touches​

This module extends two files: kubernetes_inspect.py (a new read) and the new ai_release_readiness.py. "We only added a GET-shaped function" is not the same claim as "there is no write call anywhere" -- the same discipline every Deep Dive in this course applies. Start with kubernetes_inspect.py, unchanged since Module 28's own proof, re-run after this module's addition:

rg -c '\.(create|patch|delete|replace)_' src/platformops/kubernetes_inspect.py; echo "exit=$?"

Expected output

exit=1

rg -c prints nothing and exits 1 when it finds zero matches. Adding get_deployment_resource_profile() -- a second call to the same read_namespaced_deployment() this module already used -- did not introduce a single write-mode verb.

Now ai_release_readiness.py itself, checked for every write-mode function name a model-registry or Kubernetes mutation would use:

rg -c 'create_model_version\(|transition_model_version_stage\(|update_registered_model\(|execute_restart\(|build_restart_plan\(|\.(create|patch|delete|replace)_namespaced' src/platformops/ai_release_readiness.py; echo "exit=$?"

Expected output

exit=1

Zero matches. The fetch/aggregate split still holds too -- gather_evaluation_evidence() is checked for a verdict word the way every gather_* function in this course already is:

awk '/^def gather_evaluation_evidence\(/{p=1} /^def gather_kubernetes_evidence\(/{exit} p' src/platformops/ai_release_readiness.py | rg -i '"pass"|"fail"|"unknown"|"not_applicable"'; echo "exit=$?"

Expected output

exit=1

And the aggregation half, evaluate_ai_release_readiness(), checked for anything that would prove it secretly depends on the network:

awk '/^def evaluate_ai_release_readiness\(/{p=1} /^def check_ai_release_readiness\(/{exit} p' src/platformops/ai_release_readiness.py | rg 'gather_|get_kubernetes_clients|get_run\(|httpx\.(get|post|put|delete)'; echo "exit=$?"

Expected output

exit=1

Zero matches again. evaluate_ai_release_readiness()'s entire body -- five _evaluate_* helpers, two verdict roll-ups, one combined verdict -- never mentions a fetch function, a Kubernetes client call, or an httpx verb. This is not "it happens not to reach the network today" -- it is "it cannot, without a future edit adding a new import."

2 — The two verdicts, proven mechanically incapable of cross-contamination​

The lesson's central claim is that a model-quality problem and an infrastructure problem never get confused. The lab's live scenarios already showed this behaviorally -- quality=not_ready infra=ready for a bad evaluation score, quality=ready infra=not_ready for a stale version label or missing resource requests. This section proves why that always holds, by reading evaluate_ai_release_readiness()'s own verdict logic directly, then confirming it with hand-built evidence -- no live cluster required for this proof.

the verdict logic itself, from ai_release_readiness.py
model_quality_verdict = _verdict([model_section, evaluation_section])

infra_sections = [deployment_section, version_match_section]
if endpoint_section["status"] != "NOT_APPLICABLE":
    infra_sections.append(endpoint_section)
infrastructure_verdict = _verdict(infra_sections)

model_quality_verdict is computed from a list containing exactly model_section and evaluation_section -- nothing else. infrastructure_verdict is computed from deployment_section, version_match_section, and conditionally endpoint_section -- and model_section/ evaluation_section never appear in that list. There is no shared mutable state between the two _verdict() calls, and no code path where a FAIL in one list's sections can influence the other list's roll-up. This script constructs one hand-built evidence set with a failing evaluation score and healthy infrastructure, and a second with a passing evaluation score and a degraded rollout, and prints both reports side by side:

cat > /tmp/m34_dd_contrast.py << 'PYEOF'
from platformops.ai_release_readiness import evaluate_ai_release_readiness

_MODEL_READY = {
    "fetched": True,
    "status": "READY",
    "current_stage": "Production",
    "run_id": "a1b2c3d4e5f647a8b9c0d1e2f3a4b5c6",
}
_EVAL_PASSING = {
    "fetched": True,
    "status": "FINISHED",
    "metric_key": "accuracy",
    "metric_value": 0.94,
}
_EVAL_BELOW_THRESHOLD = {
    "fetched": True,
    "status": "FINISHED",
    "metric_key": "accuracy",
    "metric_value": 0.5,
}
_ENDPOINT_HEALTHY = {
    "checked": True,
    "ok": True,
    "status_code": 200,
    "latency_ms": 42.0,
    "error": None,
}
_K8S_HEALTHY_MATCHING = {
    "fetched": True,
    "found": True,
    "rollout_state": "healthy",
    "desired_replicas": 2,
    "ready_replicas": 2,
    "labels": {"model-version": "4"},
    "resource_requests": {"support-assistant": {"nvidia.com/gpu": "1"}},
}
_K8S_DEGRADED = {**_K8S_HEALTHY_MATCHING, "rollout_state": "degraded"}

quality_problem = evaluate_ai_release_readiness(
    service="support-assistant",
    model_version="4",
    eval_threshold=0.9,
    model_evidence=_MODEL_READY,
    evaluation_evidence=_EVAL_BELOW_THRESHOLD,
    endpoint_evidence=_ENDPOINT_HEALTHY,
    kubernetes_evidence=_K8S_HEALTHY_MATCHING,
)
infra_problem = evaluate_ai_release_readiness(
    service="support-assistant",
    model_version="4",
    eval_threshold=0.9,
    model_evidence=_MODEL_READY,
    evaluation_evidence=_EVAL_PASSING,
    endpoint_evidence=_ENDPOINT_HEALTHY,
    kubernetes_evidence=_K8S_DEGRADED,
)

print("Scenario A -- low evaluation score, healthy infra:")
print(
    f"  model_quality_verdict={quality_problem.model_quality_verdict} "
    f"infrastructure_verdict={quality_problem.infrastructure_verdict}"
)
print(f"  deployment section status: {quality_problem.deployment['status']} (unaffected)")

print("Scenario B -- passing evaluation, degraded rollout:")
print(
    f"  model_quality_verdict={infra_problem.model_quality_verdict} "
    f"infrastructure_verdict={infra_problem.infrastructure_verdict}"
)
print(f"  evaluation section status: {infra_problem.evaluation['status']} (unaffected)")
PYEOF
uv run python /tmp/m34_dd_contrast.py

Expected output

Scenario A -- low evaluation score, healthy infra:
  model_quality_verdict=not_ready infrastructure_verdict=ready
  deployment section status: PASS (unaffected)
Scenario B -- passing evaluation, degraded rollout:
  model_quality_verdict=ready infrastructure_verdict=not_ready
  evaluation section status: PASS (unaffected)

In Scenario A, the deployment section stays PASS even though the overall model quality failed -- degrading the rollout evidence never happened, and nothing in _evaluate_deployment() reads evaluation_evidence. In Scenario B, the reverse: evaluation stays PASS while the rollout fails. Each _evaluate_* helper takes exactly one evidence dict and returns one section -- there is no function anywhere in this module that reads more than one evidence source at once, which is what makes the separation structural rather than a matter of careful bookkeeping.

3 — Why labels and resource requests needed a second read, not new fields​

DeploymentStatus (Module 28) exists for one purpose -- rollout_state() needs exactly these fields and nothing else:

awk '/^class DeploymentStatus/{p=1} /^def get_deployment_status/{exit} p' src/platformops/kubernetes_inspect.py | rg '^    [a-z_]+:'

Expected output

    name: str
    namespace: str
    desired_replicas: int
    ready_replicas: int | None
    available_replicas: int | None
    updated_replicas: int | None
    unavailable_replicas: int | None
    conditions: list[dict[str, str | None]]
    selector: dict[str, str]

DeploymentResourceProfile (this module) carries name and namespace -- the same identifying pair DeploymentStatus already has, needed here only to label which Deployment this profile came from -- plus exactly two genuinely new fields, labels and container_resource_requests, neither of which appears anywhere in DeploymentStatus's rollout-focused field list above:

awk '/^class DeploymentResourceProfile/{p=1} /^def get_deployment_resource_profile/{exit} p' src/platformops/kubernetes_inspect.py | rg '^    [a-z_]+:'

Expected output

    name: str
    namespace: str
    labels: dict[str, str]
    container_resource_requests: dict[str, dict[str, str]]

workload-inspect (Module 28's own CLI command) calls get_deployment_status() and has never once needed a label or a resource request -- adding those fields to DeploymentStatus would mean every existing caller of that function starts reading (and every existing test starts hand-building) two fields it never asked for. get_deployment_resource_profile() issues its own, second read_namespaced_deployment() call -- the cost of one extra API call against a Deployment object Kubernetes already has cached, in exchange for keeping DeploymentStatus exactly as focused as Module 28 left it.

The lab's own live evidence already showed why the model-version label specifically matters: relabeling a running, healthy Deployment from model-version: "4" to model-version: "3" changed nothing about its rollout state -- kubectl rollout status still reported success, and get_deployment_status() still reports rollout_state: "healthy" for it. Only version_match, reading DeploymentResourceProfile.labels specifically, caught the drift. That is the mechanical reason this data needed its own read: it lives in a part of the Kubernetes object (metadata.labels) that rollout_state()'s entire calculation never touches.

Where you will use this
  • Reading model_quality_verdict and infrastructure_verdict before a single detail string, to know in one glance whether a not_ready release needs the ML team or the platform team. Use it when: you are on call for a model-serving service and a release-readiness check just failed.
  • Extending a Deployment-reading module of your own with a second concern (labels, annotations, a different resource type) as a second, separate read function and dataclass, instead of growing the first one's fields past what its original caller ever needed. Use it when: you catch yourself about to add an unrelated field to a dataclass that already has a well-defined, narrow purpose.
  • Trusting a rollout-health check (kubectl rollout status, workload-inspect) to answer "is the Deployment up," and a separate, explicit label read to answer "is it running the version I think it is." Use it when: a Deployment can be redeployed, rolled back, or hand-edited without a human remembering to keep a version-identifying label in sync.

Teardown​

cd ~/platformops
rm -f /tmp/m34_dd_contrast.py

No cluster or container state was created by this page -- the proof script above only calls evaluate_ai_release_readiness() with hand-built evidence, the same pure, no-network function the lab's unit tests already exercise.
