Lab — Choose the Right Tool, Walk the Architecture

This lab is the kind of triage a platform team does every sprint: eight real requirements land in your backlog. For each one, you pick the smallest tool class that solves it well and defend your choice. You also decide, for each requirement, what you would hand to a coding agent and what you would keep in your own hands. Your deliverable is a completed decision worksheet, the first artifact (piece of finished work) of this course, plus a marked-up copy of the PlatformOps architecture map you will build against from Module 2 onward.

No Python, no uv, no containers yet. All you need is git and a shell.

1. Get the lab​

You already cloned the labs repository on the Prerequisites page and are sitting at its root. Move into this module's folder:

cd labs/m1

No output means it worked. Your prompt now ends in labs/m1.

Skipped setup, or starting on a fresh machine?

Clone the repo first, from your home directory, then come back to this step:

git clone https://github.com/schoolofdevops/307-aipython-labs.git
cd 307-aipython-labs

Expected output

Cloning into '307-aipython-labs'...

The clone needs no credentials. Your terminal will also print transfer numbers (object counts, sizes) that change from run to run. If git says destination path '307-aipython-labs' already exists, you already have a clone. Just cd 307-aipython-labs and continue.

List what you received:

ls -1

Expected output

architecture-map.md
check.sh
checks.json
decision-worksheet.md
deep-dive.checks.json
scenarios.md
solutions.md

Seven files, one deal: scenarios.md holds the requirements, decision-worksheet.md is where your answers go, check.sh checks that you filled every cell, and solutions.md is the instructor's reasoning, which you open last. The two *.checks.json files are machine-readable files used by the course tooling behind the scenes. You can ignore them.

2. Read the scenarios​

Open scenarios.md in your editor and read all eight requirements before you answer any of them. They are mixed on purpose: some belong in Bash, some in Python, and at least two should not be code you write at all. The top of the file lists the eight tool classes you can choose from. It is the same ladder as the lesson, plus "existing tool + config" for the cases where writing a bit of configuration beats building something new.

3. Study the worked example​

Scenario 1 (the weekly stale-AMI report) is already answered in decision-worksheet.md. Notice the shape of a good answer, because the checker only checks that a cell is filled. Only you can check whether it is a good answer:

  • Tool class names a class, not just a language: Python script (scheduled).
  • Why this tool explains why the smaller options next to it will not do: too much structure for Bash, and no declarative state (nothing you can just describe and let a tool build), so IaC (infrastructure-as-code tools like Terraform) does not apply.
  • Delegate to an agent? splits the work: the agent drafts the API calls and the formatting; the engineer writes the spec and reviews the account loops and tag handling.

That three-part pattern, tool class, why the smaller options fall short, and how you split the work, is what you repeat seven more times.

4. Run the checker before you start​

Run the self-check now, before filling anything, so you know what it measures:

bash check.sh

Expected output

PASS  scenario 1
FAIL  scenario 2: missing tool class, why, delegate
FAIL  scenario 3: missing tool class, why, delegate
FAIL  scenario 4: missing tool class, why, delegate
FAIL  scenario 5: missing tool class, why, delegate
FAIL  scenario 6: missing tool class, why, delegate
FAIL  scenario 7: missing tool class, why, delegate
FAIL  scenario 8: missing tool class, why, delegate
-----
1/8 scenarios complete
RESULT: FAIL — fill the missing cells and re-run

A failing result showing 1/8 is correct at this point, because only the worked example is filled in. The script exits with a non-zero code on FAIL. This is exactly how a CI system (or, later in this course, a coding agent) would read the result.

5. Fill the worksheet​

Work through scenarios 2 to 8 in decision-worksheet.md. For each one, ask the three ladder questions from the lesson:

  1. What is the smallest class that solves this well?
  2. What concrete fact would force you one step up, and is that fact actually in the requirement?
  3. Does an existing tool already do this job as configuration?

Two practical notes: keep each cell on one line, and do not type the | character inside a cell, because it splits the table and the checker will report the row as broken. Expect this to take 10 to 15 minutes. The thinking is the real lab work here.

6. Verify your worksheet​

bash check.sh

Expected output

PASS  scenario 1
PASS  scenario 2
PASS  scenario 3
PASS  scenario 4
PASS  scenario 5
PASS  scenario 6
PASS  scenario 7
PASS  scenario 8
-----
8/8 scenarios complete
RESULT: PASS — now compare your reasoning with solutions.md

The output above is from a completed worksheet. Yours must show 8/8 and RESULT: PASS (exit code 0) before you move on.

7. Compare against the reference answers​

Now open solutions.md. Do not grade yourself on matching the tool class word-for-word. Grade yourself on whether your reasoning still holds up against the challenge questions under the table. Two answers deserve special attention:

  • Scenario 4: if you designed a custom admission webhook (a small service that checks and approves changes before Kubernetes accepts them), you found the right mechanism, but you missed that policy engines already offer this as a ready-made product.
  • Scenario 7: if you designed a boto3 tool to compare and report differences, you rebuilt what terraform plan already does. When IaC (infrastructure-as-code) is the source of truth, let the IaC detect the drift itself.

You are allowed to disagree with the reference answer. Disagreeing with a good reason is the real skill.

8. Annotate the architecture map​

Open architecture-map.md. It shows the PlatformOps v3.0 end state: three interfaces over one core, with adapters to every external system, plus the 37-release ladder mapped to modules. Answer the three questions at the bottom of the file, right there inline. Keep this file. It is your reference for the whole course, and the release table tells you at any point where you stand on the ladder.

Troubleshooting
  • FAIL scenario N: row not found: the table row was reformatted, or a leading | got deleted. Each answer must stay a single table row starting with | N |.
  • A row you filled still reports missing: you likely typed a | inside a cell, which splits it. Rewrite the cell without any pipe characters (use "/" or "," instead).
  • FAIL: worksheet not found: you are not inside 307-aipython-labs/labs/m1. From the repo root, run cd labs/m1 and try again, or run the checker with the full path from the repo root: bash labs/m1/check.sh labs/m1/decision-worksheet.md.
  • git clone fails: check your network connection and the URL https://github.com/schoolofdevops/307-aipython-labs.git. No credentials are needed for this public repository.

Teardown​

This module started nothing: no containers, no clusters, no cloud emulator. So there is nothing to stop. The cloned 307-aipython-labs folder is reused throughout the course, so the practical move is to keep it. If you still want a clean machine, save your two finished files and remove the clone:

cd ../..
cp labs/m1/decision-worksheet.md labs/m1/architecture-map.md ~
cd .. && rm -rf 307-aipython-labs

The first cd returns you to the repo root. The cp saves your two filled files to your home directory before the clone gets removed.

Cloning again later is always safe. The repository is public, and your graded work lives in the two files you already copied out.
