Deep Dive — How a Coding Agent Works on Your Repository

The lab trained your judgment: which tool class, why, and what to hand off. Part 2 opens up the machine you will be handing work to. From Module 3 onward you will give real work to a coding agent. And every review decision you make (how big a change to ask for, why the agent missed a file, why it invented a function that does not exist) traces back to how the agent actually works with a repository. This page builds that mental picture using nothing but your shell and the files you already have.

Where this picks up

You need the Module 1 lab files, whether or not you just finished the lab, and whether or not you ran its teardown. Run this from the folder that contains your clone. That is your home directory, if you followed the setup pages. If you are still inside labs/m1 from the lab, you are already where you need to be. Skip this block entirely.

cd ~
[ -d 307-aipython-labs ] || git clone https://github.com/schoolofdevops/307-aipython-labs.git
cd 307-aipython-labs/labs/m1

Run this from that parent folder. It is safe to run more than once: an existing clone is reused, never cloned again inside itself. If you keep the clone somewhere other than your home directory, cd there instead of ~. Your worksheet can be filled in or empty. This page works either way.

1 — The context window: the agent's working memory​

Imagine a whiteboard used on an incident call. Everything the responders are currently thinking about is written on that board. When it fills up, someone wipes the oldest corner to make room. Any fact that gets wiped is gone from the discussion, unless someone writes it back on. A coding agent's context window is that whiteboard. It is a fixed budget of text (measured in tokens, and one token is roughly three-quarters of a word) that holds the instructions, the conversation, every file it has read, and every command output it has seen. Nothing else exists for the model.

Let's measure what your small lab folder would cost against that budget:

wc -w *.md

Expected output

     485 architecture-map.md
     374 decision-worksheet.md
     596 scenarios.md
    1078 solutions.md
    2533 total

Your numbers will differ a little (a filled-in worksheet weighs more than an empty one), but the shape stays the same: a few thousand words for four small markdown files. A real operational repository can run into hundreds of thousands of words. Even a large context window cannot hold your whole codebase along with the conversation, and models get less reliable when something important is buried in the middle of a very long context. This one limit explains most of the agent behavior you will see in this course: the agent must choose what to look at, and it can quietly lose whatever scrolled off the board.

2 — Exploration: search first, read little​

A new on-call engineer does not read the whole team wiki before their first shift. They search the runbook index for the one page that matters, read that page, and get moving. A coding agent explores your repository the same way, through tools: list the files, search for a piece of text, read one file, run one command. Each tool result gets pasted onto the whiteboard and uses up some of the budget. So a good agent searches narrowly instead of reading broadly.

Do exactly what an agent would do to find the worksheet rules, without reading every file:

grep -rn "Tool class" *.md | head -5

Expected output

decision-worksheet.md:8:- **Tool class**: pick from the list at the top of `scenarios.md`. Name a real tool if it
decision-worksheet.md:20:| # | Requirement (short) | Tool class | Why this tool | Delegate to an agent? |
scenarios.md:7:Tool classes to choose from:
solutions.md:11:| # | Requirement (short) | Tool class | Why this tool | Delegate to an agent? |

Three files, exact line numbers, a few hundred bytes spent, instead of reading four whole files end to end. This is why agents work far better on a well-organized repository than on a messy one: clear file names and a structure you can search are not just nice to have, they are the agent's map. It is also why an agent sometimes misses something that feels obvious to you. If a fact is not somewhere a search would find it, it never reaches the whiteboard.

3 — The loop: propose, verify, repeat​

Your change-management process does not trust anyone's confidence. It trusts the verification step: no change is done until the check passes. An effective coding agent follows the same discipline, as a loop: gather context, suggest an edit, run a verification command, read the result, and either finish or go around again.

How good this loop is depends on what the verification step actually returns. Run this module's own checker the way an agent would, and read the result as a plain machine signal, not as a sentence to interpret:

bash check.sh; echo "exit code: $?"

Expected output (from a completed worksheet)

PASS  scenario 1
PASS  scenario 2
PASS  scenario 3
PASS  scenario 4
PASS  scenario 5
PASS  scenario 6
PASS  scenario 7
PASS  scenario 8
-----
8/8 scenarios complete
RESULT: PASS — now compare your reasoning with solutions.md
exit code: 0

Depending on whether your worksheet is filled in, you will see a passing or a failing summary. Either way, the point is the same: a command that always gives the same result for the same input, that names which scenario is incomplete, and that sets a non-zero exit code on failure, gives the loop something solid to work toward. An agent with a real check can correct itself. An agent without one can declare victory on code that was never even run. That is why every module in this course ships machine-readable checks, and why in M15 you will build verification scripts right into your agent harness (the set of instructions and guardrails that shape how an agent works inside your repo).

4 — Instruction files: standing orders for every session​

Every on-call rotation has standing orders pinned at the top of the channel: escalation rules, forbidden actions, house style. Each new shift reads these before touching anything. Instruction files (AGENTS.md or CLAUDE.md, depending on the agent) are the standing orders for a repository. They get loaded into the context window at the start of every session, before any of your prompts. A typical one for an operations repo looks like this:

# AGENTS.md
- Run `bash check.sh` after every change; do not finish with it failing.
- Never touch deletion paths or credential handling without asking first.
- Use uv for all Python commands; never pip install globally.
- Keep diffs small: one scenario, one change, one review.

Because these lines sit permanently on the whiteboard, they steer the agent's behavior more reliably than anything you type in a single request. And they are versioned, reviewed team policy, not just one engineer's personal habits. In M15 you will grow this idea into a full harness: instructions, approved commands, safety rules, and a clear definition of done.

5 — Failure modes you will actually meet​

Three behaviors follow directly from everything above. Knowing why each one happens tells you which defense actually works:

  • Made-up APIs (what people call "hallucination"). The model writes the code that would be plausible next, and a method that "should exist" on a client library looks plausible. So client.get_stale_amis() shows up, cleanly formatted, and it does not actually exist. Defense: the verification loop (code that runs cannot call a function that does not exist), plus your own review for anything the tests do not catch.
  • Lost context. Long sessions wipe the oldest corner of the whiteboard. The rule you stated forty minutes ago is gone, and the agent confidently breaks it without realizing. Defense: put lasting rules in the instruction file, not just in the conversation, and start a fresh session for each new task instead of running one endless one.
  • Over-eager edits. Asked to fix one function, the agent "improves" five files, because nothing in its loop makes a small change cheaper than a big one. Only your instructions do that. Defense: standing orders that demand small changes, requests scoped to one change at a time, and refusing to review a mixed-up diff as if it were one thing.

None of this is a reason to avoid agents. It is exactly why the delegation split from the lesson looks the way it does, and why the review habits you build from Module 3 onward really matter. They are not just for show.

Where you will use this
  • The context window is a fixed budget. Agents search, they do not already "know" your repo. Use it when: an agent misses an obvious file or invents something that is not there. Check whether the fact was actually findable by search, and fix the repo layout or point the agent at the path, instead of blaming the model.
  • The loop only converges when there is a machine-readable check. Use it when: handing off any task. Give the agent the check command (bash check.sh, pytest, terraform plan) in the same breath as the task, and do not trust any "done" that arrives without a passing run.
  • Instruction files outlive the conversation; chat does not. Use it when: you catch yourself repeating the same rule to an agent for the third time. Move it into AGENTS.md or CLAUDE.md, where every future session loads it automatically.
  • Failure modes are mechanical, so the defenses are too. Use it when: reviewing a generated diff. Scan first for the three warning signs: an API you do not recognize, a forgotten rule, and changes outside what you actually asked for.
