Python in the AI and Agent Era

Where this course ends​

Before any theory, let's look at where you are headed. By the final module, you will have built the PlatformOps Toolkit v3.0. It is a Python operational toolkit with a CLI, an internal API, a library of agent skills, and an MCP server, and you will use it the way it is used below.

The transcript below is a preview of that end state. You cannot run it today. It shows what your terminal will look like in Module 39, when the payments service starts failing in your local lab:

$ platformops incident collect payments

  Incident context: payments
  ── Ownership      team: payments-core   on-call: you
  ── Recent change  deploy 2h ago — payments v1.14.2 (PR #212, config change)
  ── Kubernetes     2/5 pods CrashLoopBackOff, restarts climbing
  ── Cloud          queue depth rising on payments-events
  ── Report         written to incidents/payments-2026-08-03.md

The responder, or a coding agent connected to the same toolkit through MCP, reads that context and suggests a fix. Then it hits a wall you built on purpose: nothing changes anything without a human saying yes first. The agent suggests a plan. PlatformOps checks that plan against policy. You approve it. A limited tool then carries it out. The toolkit checks the result, and every step is written to an audit log (a record of who did what, and when). You will build this whole loop, guardrails included, release by release: 37 tagged versions, from v0.0 to v3.0.

This module ships no code. Its job is to make sure that when you start building in Module 2, you already know why each piece exists, and when you would actually reach for it at work.

1. Why learn Python when agents write Python?​

Think of a commercial pilot. Autopilot flies most of every flight, and it flies smoothly. But airlines still need pilots who can fly the plane by hand. Not because autopilot is useless. It is because the pilot's real job is to notice when the automation is wrong and take over before anyone gets hurt. You cannot do that job if you never learned to fly.

Coding agents put you in the same seat. An agent can happily write a boto3 (the AWS SDK for Python) cleanup script in thirty seconds. But if you cannot read Python, you cannot see that it deletes untagged volumes instead of temp-tagged ones, or that it loops over every region when you only asked for one. In a code review, on an incident call, or when a "harmless" generated change takes down a service, the engineer who can read, direct and check Python is the one who stays in control.

So this course aims at one clear target: enough Python to write the important automation by hand, and enough judgment to direct, review and manage agents that write the rest. You are not training to become a software developer. You are training to be the pilot.

2. Python against the rest of your toolbox​

Think of the tools you already use as vehicles. You would not drive a truck to the corner shop, and you would not move house on a bicycle. Every language in your operations toolbox has a job it is built for:

ToolBuilt forReach for it whenWrong when
BashGlue and textOne-off pipelines, wrapping CLIs, < ~30 linesStructured data, error handling, anything you must test
PythonStructured automationAPI calls, data shaping, tools with tests and interfacesA one-liner would do, or the state is declarative
GoDistributable binariesYou ship a static binary, or extend the k8s ecosystemTeam fluency is Python and speed of change matters more
Terraform / PulumiDesired-state infraProvisioning with plan/review/apply and drift detectionImperative, event-driven, or data-heavy logic
AnsibleConfig on existing machinesFleet configuration, ordered playbooks, agentless pushYou are building a product-like tool, not applying state

In plain words: Bash is like walking across the street. It is the fastest way for a small trip, but risky if you are carrying a lot of luggage (a lot of logic). Python is the van you use every day. It carries structure (lists, dictionaries, typed models), it can talk to any API, and it is the language that every AWS SDK, Kubernetes client and AI or agent framework speaks. Go is the freight truck. It is great when you ship one binary to a thousand machines, but it takes longer to build in the first place. Terraform is not really a vehicle at all. Think of it as the city's permit office: you describe the building you want, and it makes reality match your description. That is exactly why you should not rebuild this logic yourself in boto3. Ansible is the moving crew with a checklist: it pushes configuration onto machines that already exist.

This course puts Python first because your job is mostly about APIs and data. But Modules M21 to M31 will keep sending you back to this table. Sometimes the right answer will be "not Python".

3. The solution ladder — pick the smallest thing that works​

Think about how a company adds structure over time: first a note taped to the wall, then a laminated checklist, then a staffed help desk, and finally a full department. A company adds more structure only once the smaller version stops working. Automation follows the same ladder. Every step up costs more to build, and it costs even more to run forever, which is the part most estimates miss:

  • Script: you run it, it does its job, and it stops. This is fine while you are the only one using it.
  • CLI: a script with an interface, meaning flags, help text and exit codes. The moment someone else runs it (a teammate, or CI), it deserves this step.
  • Service: it keeps running so other systems can call it over HTTP.
  • Worker: it runs on a schedule, or picks up work from a queue. Nobody starts it by hand.
  • Controller: it watches the current state all the time and fixes it when needed. This is the most expensive step, because now it can break things even when you are not there.
  • Agent tool: a capability you expose to an AI agent, with clear rules, limits and a human approval step.

The rule for picking one is simple: choose the lowest step that meets the requirement, and know exactly what fact would force you up one step. A drift report (drift is when the live setup no longer matches what your code says it should be) is a worker. Drift correction, actually fixing it, might justify a controller. "Block bad Pods at admission time" is usually not code you write at all. It is an existing policy engine plus some configuration. Climbing the ladder just to look impressive is how teams end up running a Kubernetes operator to do the job of a simple cron job.

4. What you write, what you delegate​

When you hire a fast contractor, you do not stop inspecting the work. You inspect more, because the work appears faster than you can watch it happen. The contractor pours the concrete. You check the load-bearing walls, and only then do you sign off.

With coding agents, the split looks like this:

  • You write it, or check it line by line: the spec (what the tool should do), the acceptance tests, and any safety-critical path, meaning anything that deletes data, changes data, logs in somewhere, or spends money.
  • You hand it off (delegate it): boilerplate code, API-call plumbing, formatting, cleanup of existing code, extending a pattern you already built, and rough test drafts that you then tighten up.
  • Everything an agent writes gets reviewed and tested before it touches anything real. Agents produce code that looks right, and "looks right" is exactly the dangerous kind: it reads well while calling a method that does not exist, or while handling only the easy case. Review and tests are not paperwork here. They are what makes handing off work safe.

From Module 3 onward, you will practice exactly this split: write the core part yourself, hand off the extension, review the diff (the change), and run the tests.

5. The PlatformOps Toolkit — the one project you build through this course​

One core, many doors in. The main logic lives in one place: a tested Python library. The CLI, the internal API and the agent tools are just thin layers sitting on top of the same functions. Adapters (small pieces of code that each talk to one outside system) keep every external system separate, so local stand-ins like Floci for AWS and kind for Kubernetes can swap in for the real thing without touching the core at all:

You grow it through 37 tagged releases. Versions v0.0 to v0.10 build the foundation (Modules 2 to 12). The v1.x releases add quality checks, a coding-agent harness (a safe way to work with AI agents), agent skills, and cloud auditing (Modules 13 to 24). The v2.x releases bring governed operations: fixes that need approval first, containers, Kubernetes, incident handling, the internal API, and the MCP server (Modules 25 to 38). And v3.0 is the final version that brings it all together. A small, shippable release every module. The same discipline you would expect from a real production service.

Common pitfalls
  • Reaching for Python out of habit. Rewriting a working Bash one-liner in Python, or rebuilding what Terraform already does in boto3. How to fix it: ask the ladder question first, what is the smallest tool class that solves this well?, and let the comparison table rule Python out when it does not fit.
  • Trusting generated code just because it looks clean. Clean formatting says nothing about whether the code is correct. How to fix it: never merge a generated change you have not read yourself, and never run one against real systems without tests, especially for anything that deletes or changes data.
  • Building more than the step needs. A framework, a service and a database for what a scheduled script could do. How to fix it: name the exact, concrete event that would force you up one step. If you cannot name one, stay where you are.
  • Building less than the step needs. A personal script quietly becomes something the whole team depends on, with no flags, no exit codes, and no dry-run mode. How to fix it: the moment a second person or a scheduler runs it, turn it into a proper CLI.
