Deep Dive — What a Coding-Agent Harness Actually Controls

The lab had you write CLAUDE.md, rename an existing script into scripts/verify.sh, and watch an agent follow both while implementing a small feature. This page goes one level under that: how much of a harness an agent actually reads before it starts skimming, what happens when a global rule on your machine disagrees with a project rule in this repo, how you would catch a harness that produces different results from the same spec, what genuinely has to change to make the same harness work with a different agent, and the one bug in a verify script that makes the entire harness worthless without anyone noticing. You will use this the next time you write a harness for a new project, the next time a teammate asks "why did the agent do that, CLAUDE.md says not to," and the next time you catch yourself trusting a green checkmark you never actually looked at.

Where this picks up

You need ~/platformops at v1.2, with CLAUDE.md and scripts/verify.sh in place from the lab. Sections 1, 2 and 4 read (and, in Section 4, extend) that real project directly — nothing in them is destructive. Section 5 works in its own scratch copy, so it is safe to run even if you already tore down a previous attempt:

rm -rf /tmp/m15-dd-scratch
cp -r ~/platformops /tmp/m15-dd-scratch
cd /tmp/m15-dd-scratch
rm -rf .venv
uv sync

The rm -rf .venv && uv sync step is needed because copying a uv-managed virtual environment breaks the internal symlinks that point at your Python install. Removing the copy and rebuilding it takes a few seconds and gives you a working environment.

Re-running any command on this page is safe.

1 — What actually fits, and what gets skimmed​

"The agent has a limited context window" is easy to say. Put a number on the harness you just wrote instead:

cd ~/platformops
wc -w CLAUDE.md

Expected output

     325 CLAUDE.md

A harness this size is small next to an agent's working context — it costs almost nothing to read in full. The risk is not that it gets truncated. It is the same risk a long security briefing has on a guard at the start of a shift: a one-page briefing gets read end to end, every time; a forty-page one gets skimmed, and the rule on page thirty-one is the one that gets missed first. An agent reading a bloated CLAUDE.md full of restated project history, apologies for past mistakes, and paragraphs of prose around every rule behaves the same way — it still "reads" all of it, but the five sections that actually matter (project context, approved commands, safety rules, the verify script, the definition of done) compete for attention with everything else you wrote around them. A harness earns its effectiveness from what it leaves out as much as from what it includes.

2 — When rules disagree: the override order​

You almost certainly have more than one instruction file that could apply to a task in ~/platformops: a personal, global one that applies to every project on your machine, and this project's own CLAUDE.md. Check whether you have a global one:

test -f ~/.claude/CLAUDE.md && echo "global CLAUDE.md present" || echo "no global CLAUDE.md set"

Expected output

global CLAUDE.md present

If you see no global CLAUDE.md set instead, that is fine — it means you have not created a personal, machine-wide instruction file yet. The override order explained below still applies; you simply have one fewer layer active.

Think of a global instruction file the way you would think of a company-wide handbook, and a project's own CLAUDE.md as a department's addendum to it. The company handbook applies everywhere. The department addendum applies only inside that department — and where the two disagree, the addendum wins for anyone actually working there, because it is written for the specific work being done, not the general case. A global rule like "always explain your reasoning before making a change" and a project rule like "use the Approved commands list, no explanation needed for routine gate runs" are both reasonable on their own; when a task runs inside ~/platformops, the project's own CLAUDE.md is the one written for this work, and it takes precedence on anything it explicitly states.

A tool's settings.json (for Claude Code, .claude/settings.json at the project root) is a different axis entirely — it does not restate rules, it controls what the agent is allowed to do at all: which commands can run without asking, which directories are off limits. A harness rule and a permission setting can point at the same command from two different angles — CLAUDE.md says "use uv run pytest," settings.json decides whether the agent may run it without asking you first each time. Neither replaces the other.

3 — Testing the harness, not just the code it produces​

You already re-run a test suite to catch a regression. Apply the same discipline to the harness itself: run the identical spec through your agent twice, and diff what comes back. If one run adds a dependency the harness's Safety rules explicitly forbid, and the other does not, that is not the agent being random — a harness that produces two different scope decisions from the same input is under-specified somewhere, the same way a flaky test points at a real bug in the test's setup, not bad luck.

The part worth checking before you even compare two runs: did the harness itself change between them?

cd ~/platformops
shasum -a 256 CLAUDE.md scripts/verify.sh

Expected output

b0779262fb895acdb426f56e435dd7eafd8cc6f9e7da3b13788edbb1de895208  CLAUDE.md
9cea6c9e780413658dd407d118d3aae90ad8055494132600d2410eab702ffe39  scripts/verify.sh

Record this pair of hashes next to any two runs you compare. If they match across both runs, any difference in what the agent produced came from the agent (or from a genuinely under-specified harness rule) — not from someone editing CLAUDE.md between the two attempts and confusing the comparison.

4 — What actually changes between agents, and what does not​

The lesson already told you the content is portable; here is the mechanical version of that claim. Claude Code looks for CLAUDE.md at the repo root. Codex CLI, and a growing number of other coding-agent tools, look for AGENTS.md instead — the filename is the only thing most of them disagree on. The actual rules — the project description, the approved commands, the safety rules, the definition of done — do not need to be written twice.

The simplest way to guarantee that is to stop maintaining two copies:

cd ~/platformops
ln -s CLAUDE.md AGENTS.md
ls -la CLAUDE.md AGENTS.md

Expected output

lrwxr-xr-x  1 you  staff     9 Aug  4 18:38 AGENTS.md -> CLAUDE.md
-rw-r--r--  1 you  staff  2029 Aug  4 18:28 CLAUDE.md

Your username, timestamp, and byte size will differ — the important detail is the -> arrow on the AGENTS.md line, which shows it is a symlink pointing at CLAUDE.md.

AGENTS.md is now the same file as CLAUDE.md, addressed by a second name. Edit CLAUDE.md once, and a Codex-style agent reading AGENTS.md sees the update immediately — there is no second file to remember to keep in sync, and no risk of the two silently drifting apart the way two independently maintained copies eventually do.

What genuinely does not carry over between agents is anything specific to how one particular tool is configured to run — a permissions file like .claude/settings.json, or an agent's own tool-specific frontmatter for auto-loading behavior. Those live outside the shared file and stay tool-specific on purpose; the project rules inside CLAUDE.md do not.

5 — The bug that makes a verify script lie​

Module 14 taught you not to trust an agent's claim of "tests pass" without evidence. The same distrust applies to the tool you just built to generate that evidence. scripts/verify.sh opens with set -euo pipefail — -e stops the script the instant any command in it exits non-zero; pipefail makes a failure inside a piped command count, instead of only the last command in the pipe. Drop either one, and the script can print a real failure in the middle of its output and still report success at the end.

See it happen, in a scratch copy:

cd /tmp/m15-dd-scratch
printf '\n\ndef test_deliberately_broken():\n    assert False\n' >> tests/test_cli.py
./scripts/verify.sh; echo "exit code: $?"

Expected output

==> ruff format --check
25 files already formatted
==> ruff check
All checks passed!
==> mypy
Success: no issues found in 13 source files
==> pytest
FAILED tests/test_cli.py::test_deliberately_broken - assert False
1 failed, 139 passed in 2.50s
exit code: 1

With set -euo pipefail intact, the broken test stops the script at the pytest step, with a non-zero exit code — exactly what you want. Now simulate the bug: strip the flags that make that stop happen, keeping the broken test in place.

cd /tmp/m15-dd-scratch
sed -i.bak 's/^set -euo pipefail$/set -u/' scripts/verify.sh
./scripts/verify.sh; echo "exit code: $?"

Expected output

==> ruff format --check
25 files already formatted
==> ruff check
All checks passed!
==> mypy
Success: no issues found in 13 source files
==> pytest
FAILED tests/test_cli.py::test_deliberately_broken - assert False
1 failed, 139 passed in 1.76s
==> secret scan
check-secrets: OK -- no known secret patterns found in .
==> dependency audit
==> dependency audit (pip-audit via uvx)
No known vulnerabilities found
check-deps: OK
ALL GATES PASSED
exit code: 0

Watch the middle of the output, not just the last line: the pytest step still prints its failure for the broken test, but the script keeps going through the remaining gates and finishes with its own "all clear" message and a 0 exit code. Nothing about the underlying test failure changed — only whether the script that was supposed to report it kept its promise. This is the same verification gap from Module 14, one level lower: a claim of "verify passed" is no more trustworthy than a claim of "tests pass" if you never confirm the tool making that claim actually fails when it should. The fix, if you ever inherit a verify script and are not sure: deliberately break something small in a scratch copy, run the script, and confirm it stops. A verify script you have not watched fail is a verify script you are trusting on faith.

Teardown​

rm -rf /tmp/m15-dd-scratch

This removes only this page's scratch copy. AGENTS.md from Section 4 is a real, permanent addition to ~/platformops — leave it in place; later modules can rely on it existing.

Where you will use this
  • A harness only protects you on the sections an agent actually reads carefully — length works against you, not for you. Use it when: you are writing or reviewing a CLAUDE.md for a new project — keep it to the rules that change behavior, and cut the parts that only restate history or explain the obvious.
  • A project's own CLAUDE.md wins over a personal, global one for work done in that project; a settings.json permissions file is a separate axis from either. Use it when: a teammate asks why an agent ignored a rule from their personal setup while working in a shared repo — check which file actually governs that repo first, before assuming the agent is at fault.
  • Running the same spec twice and diffing the results tells you whether a harness is under-specified, the same way a flaky test points at a real gap in test setup. Use it when: an agent's behavior on the same kind of task varies run to run — treat the harness as the thing to fix, not the agent's judgment.
  • A symlinked AGENTS.md keeps a harness identical across Claude Code and Codex-style tools with zero duplication. Use it when: your team standardizes on more than one coding agent — link the file once instead of maintaining two copies that will eventually disagree.
  • A verify script you have never watched fail is a verify script you are trusting on faith, not evidence. Use it when: you inherit an existing quality-gate script (renamed into a harness's verify script or otherwise) — break something small in a scratch copy first and confirm it actually stops, before you rely on its "all clear."
