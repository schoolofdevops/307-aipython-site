Lab — Building a Coding-Agent Harness

This lab has two phases, and both happen inside ~/platformops, the project you have been building since Module 2. In Phase 1, you hand-write a harness for it: a CLAUDE.md file, a verify script, and the version bump that ships this module's release, v1.2. In Phase 2, you write a short spec (the same shape you used in Module 14) for a small, real feature, hand it to your coding agent, and check whether the agent actually followed the harness you just wrote.

Before you start

You need ~/platformops at v1.1 (Module 14 was a process module and did not change it), and the labs repo cloned at ~/307-aipython-labs.

cd ~/platformops
git log --oneline -1

Expected output

1cc923e sync platformops to v1.1, align M14 quiz with actual patch

Your commit hash will differ; the message should reference v1.1.

Phase 1 — Hand-write the harness​

Step 1 — Confirm where you are starting from​

cd ~/platformops
cat pyproject.toml | grep 'version ='

Expected output

version = "1.1.0"

You should see version = "1.1.0". If you see anything else, check the recovery box at the bottom of this page before you continue.

Step 2 — Write CLAUDE.md​

This is the harness itself: project context, the exact commands to use, what the agent must never do, and the checklist that decides a task is complete.

cat > CLAUDE.md << 'HARNESS'
# CLAUDE.md — PlatformOps Toolkit

## Project

PlatformOps Toolkit is a command-line tool that inspects, validates and
troubleshoots services across source control, CI/CD, cloud and Kubernetes.
It is a real, working Python project, not a demo — every command in it is
tested and used the way it is documented here.

- **Language / tooling:** Python 3.12, managed with `uv`. No plain `pip`.
- **CLI framework:** Typer (`src/platformops/cli.py` is the entry point).
- **HTTP client:** `httpx`. Never add `requests` — this project standardized
  on `httpx` and does not use two HTTP libraries for the same job.
- **Data validation:** Pydantic.
- **Config files:** PyYAML.

### Repository structure

- `src/platformops/` — the package itself; `cli.py` is the CLI, everything
  else is an importable, independently tested module.
- `tests/` — one test file per source module, run with `pytest`.
- `scripts/` — shell scripts that wrap the project's quality gates
  (`verify.sh`, `check-secrets.sh`, `check-deps.sh`).

## Approved commands

- `uv run pytest` — run the test suite
- `uv run pytest -q` — quiet mode
- `uv run ruff check src/ tests/` — lint
- `uv run ruff format src/ tests/` — format
- `uv run mypy src/` — type check
- `uv run platformops --help` — test the CLI

Do not invoke `pytest`, `ruff`, or `mypy` directly. Always run them through
`uv run` so they use the project's managed environment, not whatever is on
the system `PATH`.

## Safety rules

- Never delete `uv.lock` — it pins exact dependency versions.
- Never run `rm -rf` on project directories.
- Never add dependencies without explicit approval.
- Never modify the version in `pyproject.toml` without following the
  release checklist.
- Always run the verify script before declaring a task done.

## Definition of done

1. All tests pass: `uv run pytest`
2. Linter clean: `uv run ruff check src/ tests/`
3. Types check: `uv run mypy src/`
4. No new ruff warnings introduced
5. `CHANGELOG.md` updated with an `[Unreleased]` entry
HARNESS

Step 3 — Verify the three required sections are present​

grep -c -E '^## (Approved commands|Safety rules|Definition of done)$' CLAUDE.md

Expected output

3

You should see 3. If you see fewer, one of the section headings did not paste exactly — check for a typo or a missing ##.

Step 4 — Name the verify script you already have​

Look at what is already sitting in scripts/:

ls scripts/
cat scripts/check-gates.sh

Expected output

check-deps.sh
check-gates.sh
check-secrets.sh
#!/usr/bin/env bash
set -euo pipefail

echo "==> ruff format --check"
uv run ruff format --check .

echo "==> ruff check"
uv run ruff check .

echo "==> mypy"
uv run mypy

echo "==> pytest"
uv run pytest -q

echo "==> secret scan"
./scripts/check-secrets.sh

echo "==> dependency audit"
./scripts/check-deps.sh

echo "ALL GATES PASSED"

check-gates.sh, from Module 13, already runs ruff check, ruff format --check, mypy, pytest, a secret scan, and a dependency audit — in one command, stopping at the first failure. That is exactly the job a harness's verify script is supposed to do: one command, run before a task is reported done, that proves the work instead of taking someone's word for it. There is no reason to write a second script that does the same thing under a different name. Rename it, so CLAUDE.md — and any agent reading it — has one, obvious, canonical command to run:

git mv scripts/check-gates.sh scripts/verify.sh

The contents do not change — only the name. verify.sh now runs a superset of the harness's Definition of done: everything that checklist requires (tests, lint, types), plus the secret scan and dependency audit this project already had wired in. Running more checks than the minimum is safe; running fewer is the thing to watch for.

Step 5 — Confirm it still runs, under its new name​

./scripts/verify.sh

Expected output

==> ruff format --check
25 files already formatted
==> ruff check
All checks passed!
==> mypy
Success: no issues found in 13 source files
==> pytest
139 passed in 2.07s
==> secret scan
check-secrets: OK -- no known secret patterns found in .
==> dependency audit
==> dependency audit (pip-audit via uvx)
No known vulnerabilities found
check-deps: OK
ALL GATES PASSED

You should see ALL GATES PASSED at the end — the same message check-gates.sh always printed, now under its new name. If any step fails here, on the unmodified project, stop and fix that first — the rest of this lab assumes verify.sh is trustworthy before you hand it to an agent.

Step 6 — Bump the version and record the release​

Add an entry to the top of CHANGELOG.md:

CHANGELOG.md
## [1.2.0] - AI-Assisted Engineering Harness
### Added
- `CLAUDE.md` — the project's coding-agent harness: project context,
  approved commands, safety rules and a definition of done.
- `scripts/verify.sh` — the one command a coding agent (or you) runs to
  check a change against the harness's Definition of done.

Open pyproject.toml and change the version line:

version = "1.2.0"
uv sync
uv run platformops version

Expected output

platformops 1.2.0

You should see platformops 1.2.0.

git add -A
git commit -m "platformops v1.2 -- AI-Assisted Engineering Harness"
git tag v1.2

CLAUDE.md, scripts/verify.sh, and the version bump are now a permanent part of your project — every task from here on, agent-delegated or not, can be checked against them.

Phase 2 — Use the harness with your coding agent​

Step 7 — Write a spec for a small feature​

Use the same seven-section shape from Module 14: Goal, Functional requirements, Allowed files, Approved dependencies, Non-goals, Required tests, Acceptance criteria. This spec adds one small thing: it tells the agent, explicitly, to follow the harness you just wrote.

mkdir -p specs
cat > specs/version-json.md << 'SPEC'
# Feature: platformops version --json

Follow CLAUDE.md for every rule in this spec: use only the approved
commands, follow the safety rules, and run scripts/verify.sh before
reporting this task done.

## Goal

Add a `--json` flag to the existing `platformops version` command, so a
script or a CI job can read the version and the Python runtime as
structured data instead of parsing text.

## Functional requirements

- `platformops version` (no flag) keeps its current behavior: prints
  `platformops <version>` as plain text.
- `platformops version --json` prints ONE JSON object to stdout and
  nothing else: `{"version": "1.2.0", "python": "3.12.x"}`, where
  `"python"` is the running interpreter's version string.
- Exit code 0 in both cases — this command cannot fail.

## Allowed files

- `src/platformops/cli.py` — extend the existing `version` command only
- `CHANGELOG.md` — add an `[Unreleased]` entry

Nothing else changes. Not `pyproject.toml`, not any other command, not any
existing test file's assertions (new tests may be added).

## Approved dependencies

None. The Python version string comes from the standard library
(`platform.python_version()` or equivalent) — no new package.

## Non-goals

- No new persistent dependency of any kind
- No change to plain-text `version` output
- No change to any other command

## Required tests

- A test asserting `version --json` produces output that `json.loads()`
  accepts, with `"version"` and `"python"` keys present.
- A test asserting plain `version` (no flag) is unchanged.
- Existing tests are untouched and still pass.

## Acceptance criteria

- [ ] `platformops version` behaves exactly as before
- [ ] `platformops version --json` outputs one valid JSON object with
      `version` and `python` keys
- [ ] `./scripts/verify.sh` passes
- [ ] `CHANGELOG.md` has a new `[Unreleased]` entry
SPEC

Step 8 — Delegate the spec to your coding agent​

Hand specs/version-json.md to Claude Code (or the coding agent you have been using) and ask it to implement the feature. The instruction can be as short as: "Implement the attached spec. Follow CLAUDE.md."

Watch what the agent does before it reports back. A harness-following agent reads CLAUDE.md first, uses only the commands listed under Approved commands, never touches uv.lock or pyproject.toml, and runs ./scripts/verify.sh — not some other combination of commands it invented — before telling you the task is done.

Step 9 — Review the diff against the harness, not just the spec​

Module 14 taught you to check a diff against the spec's Allowed files and the six common flaws. Now add one more check: did the agent follow the harness itself?

git diff --stat

Expected output

 CHANGELOG.md                    | 3 +++
 src/platformops/cli.py          | 9 ++++++++-
 tests/test_cli.py               | 8 ++++++++
 3 files changed, 19 insertions(+), 1 deletion(-)

Your exact numbers may differ — what matters is which files appear. Check the diff against this short list:

  • Scope: only src/platformops/cli.py and CHANGELOG.md changed — the same discipline from Module 14, now checked against a spec that also names a harness.
  • Approved commands: the agent's own summary (or the commands it ran, if your agent shows them) should name only commands from CLAUDE.md's Approved commands list.
  • Safety rules: uv.lock is untouched, no new dependency was added, pyproject.toml's version line is unchanged.
  • Verification: the agent ran ./scripts/verify.sh — or told you it did — before reporting done, not just "I added the feature."
  • Definition of done: CHANGELOG.md has a new [Unreleased] entry documenting the change.

Step 10 — Confirm it independently​

Do not take the agent's word for the verification step. Run it yourself.

./scripts/verify.sh

Expected output

==> ruff format --check
25 files already formatted
==> ruff check
All checks passed!
==> mypy
Success: no issues found in 13 source files
==> pytest
139 passed in 2.07s
==> secret scan
check-secrets: OK -- no known secret patterns found in .
==> dependency audit
==> dependency audit (pip-audit via uvx)
No known vulnerabilities found
check-deps: OK
ALL GATES PASSED
uv run platformops version --json

Expected output

{"version": "1.2.0", "python": "3.12.9"}

Your Python patch version (the last number after 3.12.) may differ — that is normal. You should see one JSON object with a "version" and a "python" key. If verify.sh fails, or the JSON does not look right, the harness told the agent the rules — it does not force the agent to follow them. That gap is exactly what your own review, independent of the agent's claim, exists to close.

Troubleshooting
  • ./scripts/verify.sh fails on a step you did not expect. Run the failing command from CLAUDE.md's Approved commands list on its own (for example uv run mypy src/) to see the full error, rather than reading only the last line verify.sh printed.
  • The agent modified pyproject.toml or uv.lock. That is a safety-rule violation — reject the change and point the agent back at the Safety rules section of CLAUDE.md, the same way you would reject any diff that touches a file outside the spec's Allowed files list.
  • grep -c in Step 3 reports fewer than 3. Open CLAUDE.md and confirm each of the three headings reads exactly ## Approved commands, ## Safety rules, and ## Definition of done — a missing # or extra space breaks the match.
  • uv run platformops version --json fails or is not valid JSON. Read the agent's diff to cli.py directly and compare it against the existing check-security --json pattern already in that file — the spec pointed at that same shape.

Teardown​

The harness files are a permanent part of your project now, not temporary lab setup — there is nothing to remove. If you want to clean up only the practice spec:

cd ~/platformops
rm -rf specs

CLAUDE.md, scripts/verify.sh, the v1.2 tag, and the version --json flag all stay. Every lab from here on can assume they exist.

If you get stuck

If your ~/platformops diverges from what this lab expects and you cannot recover it, compare against the frozen checkpoint for this module in your labs clone: ~/307-aipython-labs/labs/checkpoints/v1.2/.... Do not compare against labs/platformops inside that clone — that copy keeps moving as later modules add to it, and it will not match a past module's expected state.
