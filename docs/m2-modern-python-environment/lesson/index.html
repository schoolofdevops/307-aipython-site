Setting Up a Modern Python Environment

Module slides​

Walk this short whiteboard deck for the big picture, or open it fullscreen.

1. Why a managed environment matters​

Picture a shared jump host that five different teams use during an incident. You run pip install requests to get a script working, and it fails — another team's script on the same machine needs an old version of a library, and your fix needs a new one. Nobody can touch that machine without breaking someone else's tool. This is what people mean when they say "it works on my machine": every project on that box is dumping its tools onto the same shared shelf, and the shelf cannot hold two different versions of the same tool at once.

Think of system Python as a shared toolbox in a communal garage. Anyone can walk in, add a tool, remove one, or use the wrong wrench on the wrong job — and everyone else's work feels the change immediately. A project-managed environment, the kind uv gives you, is closer to a site foreman who keeps one clearly labelled toolbox and one stock of materials for one project only. Nothing from another job gets mixed in, and nothing you do here affects a different site.

That difference is the reason this module exists. Before you write a single line of the PlatformOps toolkit, you give it its own space: its own Python version, its own installed packages, and a way for any teammate — or a CI server — to rebuild that exact space from a couple of small text files. This is also why a code review goes faster: when the reviewer runs the same two commands you did, they get the same environment, not "well, it worked when I tried it."

2. Pin the Python version, every time​

A recipe that says "add some flour" gives every cook a different cake. A recipe that says "350 grams of flour" gives everyone the same cake. Python versions work the same way: "Python 3" is not one version, it is a whole family, and small differences between 3.11, 3.12 and 3.13 are exactly the kind of thing that breaks a script two months later, on a different machine, in a way that takes an hour to explain in a review.

Pinning means writing down the exact version your project needs, in a file, so nobody has to guess. With uv, this is one command:

uv python pin 3.12

This writes a small .python-version file next to your project. From now on, every uv command run inside that folder uses exactly that version — even if your laptop also has 3.11, 3.13 and 3.14 installed for other projects. You never again ask "which Python does this run with?" The file already answers it.

3. What uv replaces​

Before tools like uv existed, keeping one Python version and one clean set of packages per project meant running three separate tools by hand: pyenv to manage Python versions, venv to create an isolated folder for packages, and pip to install into it — each with its own commands, and each an easy place to forget a step. uv folds all three jobs into one fast tool, so you almost never think about the parts underneath.

You will use five uv commands constantly in this course:

CommandWhat it does
uv python pin 3.12Writes down the exact Python version this project needs
uv initCreates a new project folder with a starting pyproject.toml
uv add <package>Adds a package as a dependency and updates the lockfile
uv run <command>Runs a command inside this project's environment — no manual activation
uv syncRebuilds the environment so it matches the lockfile exactly

The habit to build now: you never type plain python or pip install again in this course. You type uv run python and uv add. That one habit is what keeps this project's tools separate from every other project — and every other Python — on your machine.

4. pyproject.toml and uv.lock — the recipe and the receipt​

pyproject.toml is the recipe: the project's name, the Python version it needs, and the short list of packages you asked for (ruff, pytest, and later requests, boto3, and more). You write this file, or uv writes the first draft for you, and you keep editing it by hand as the project grows.

uv.lock is the receipt: every package your recipe needs, direct and indirect, pinned to an exact version with an exact checksum. You never edit this file by hand — uv writes it whenever you add, remove or update a dependency. A small pyproject.toml with two direct dependencies can easily produce a uv.lock with a dozen entries, because your two dependencies bring in dependencies of their own.

The payoff is uv sync: read the receipt, build the exact same set of packages, every time, on every machine.

Three different machines, one lockfile, three identical environments. This is what makes "it works on my machine" stop being an excuse: if the environment is wrong, uv sync against the same lockfile reproduces the problem exactly, instead of everyone guessing at package versions over chat.

5. Quality gates before you write any code​

An assembly line has an inspection point right after the very first part is fitted — not only at the end. Catching a defect early is cheap; catching it after five more stations have built on top of it is expensive. Your project gets the same idea from day one, before a single feature exists: Ruff checks your code's formatting and flags common mistakes, and pytest runs your tests and tells you, with a result a machine can read, whether the project still works.

uv run ruff format .   # rewrites files to one consistent style
uv run ruff check .    # flags likely bugs and style problems
uv run pytest -q       # runs your tests, quiet output

You are setting these up before writing any real feature because later in this course a coding agent will make changes to this same project — and the way you and the agent both prove a change is safe is by running these same three commands and reading the result, not by re-reading every line by eye.

6. The v0.0 project layout​

Your lab builds the first version of the PlatformOps toolkit with this shape:

platformops/
├── pyproject.toml        # the recipe
├── uv.lock                # the receipt
├── .python-version        # the pinned Python version
├── src/
│   └── platformops/
│       └── __init__.py    # the toolkit code — grows every module
└── tests/
    └── test_foundation.py

Putting your code under src/platformops/ instead of loose in the project's top folder is called a src layout. The small benefit you feel right away: your tests import platformops as a real installed package, the same way a user of your toolkit later would — instead of quietly importing a stray file that happens to sit next to the tests. It is one small habit that avoids a confusing class of "why does this pass on my machine but fail somewhere else" problems.

Common pitfalls
  • Installing into system Python. Running plain pip install outside a project mixes packages across every project on your machine. Recovery: always use uv add inside the project, or uv run pip install if you truly need raw pip for one command.
  • Committing the .venv folder to Git. It is large, machine-specific, and rebuilt from uv.lock in seconds. Recovery: keep .venv listed in .gitignore and never git add it.
  • Ignoring the lockfile. Editing pyproject.toml and skipping uv sync leaves your installed packages out of step with what you asked for. Recovery: run uv sync right after any change to pyproject.toml.
  • Running plain python instead of uv run python. Plain python may quietly use the wrong interpreter — a different version, or one with no packages installed at all. Recovery: make uv run a reflex for every command inside a uv project.
