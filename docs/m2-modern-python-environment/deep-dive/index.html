Deep Dive — What uv Actually Does Under the Hood

The lab had you type five or six uv commands and trust that they worked, because the three gates turned green. This page opens up what those commands actually built: how uv decides exact versions, what .venv really is, where the Python interpreter itself lives on disk, and why a broken lockfile fails loudly in CI instead of quietly installing something different. You will use this model the first time a teammate says "it installs different versions on my machine" or a CI job fails on uv sync with no code change in sight.

Where this picks up

You need your ~/platformops project from the lab, with its .venv present. If you ran the lab's teardown, rebuild it in under a minute:

cd ~
[ -d platformops ] || (uv init --package --vcs none --python 3.12 platformops && cd platformops && uv python pin 3.12 && uv add --dev ruff pytest)
cd ~/platformops
uv sync

Every command below is read-only — it inspects files uv already created. Nothing here changes your project's state, so re-running any command on this page is always safe.

1 — The resolver and the lockfile​

When you ran uv add --dev ruff pytest, uv did not just download two packages. It ran a resolver: a step that reads every version constraint (yours and each package's own requirements) and computes one exact, consistent set of versions that satisfies all of them at once — then writes that set into uv.lock.

Look at the shape of what got written:

wc -l pyproject.toml uv.lock

Expected output

      20 pyproject.toml
     108 uv.lock
     128 total

Your pyproject.toml lists two direct dev dependencies in a handful of lines. uv.lock runs to over a hundred — because Ruff and pytest each pull in smaller packages of their own (packaging, pluggy, iniconfig, pygments), and the resolver pins every one of them, not just the two you typed. The exact line counts will drift a little as Ruff and pytest ship new releases; the shape (uv.lock several times longer than pyproject.toml) stays the same.

Now look at one full entry:

grep -A12 '^name = "pytest"$' uv.lock

Expected output

name = "pytest"
version = "9.1.1"
source = { registry = "https://pypi.org/simple" }
dependencies = [
    { name = "colorama", marker = "sys_platform == 'win32'" },
    { name = "iniconfig" },
    { name = "packaging" },
    { name = "pluggy" },
    { name = "pygments" },
]
sdist = { url = "https://files.pythonhosted.org/packages/e4/47/b9efed96c114afcfa3c9d3fe98a76a1d14c74a9e266d397cf6eb64be5e01/pytest-9.1.1.tar.gz", hash = "sha256:1088fbde8f2b49d95a549a195707afa7a76a3ce9bcadc26b6d71f0ffda5fe313", size = 1636369 }
wheels = [
    { url = "https://files.pythonhosted.org/packages/24/25/1de2678b631f5a49215c6c96fff41ba892b0a34df68d6d80292b1b48aa7f/pytest-9.1.1-py3-none-any.whl", hash = "sha256:37a86b45efb9a47a61a36449063e8e18d0cab3161329fc099eb21783169c4f0c", size = 386536 },

The exact version, hashes and file sizes will differ once pytest ships a new release — the shape (a source, an sdist hash and one or more wheels hashes) stays the same. The ^ and $ in the command anchor the match to the package's own entry, so it does not also match the shorter mentions of "pytest" earlier in the file (in the dev dependency list). Notice the source, the sdist hash and the per-file wheel hashes. This is what makes the lock trustworthy: uv sync will refuse to install a file that does not match its recorded hash. A lockfile is not a suggestion — it is a signed receipt.

A cross-platform detail worth knowing: this same uv.lock file works whether your teammate runs uv sync on macOS, Linux or Windows. Think of it as a shipping manifest that lists the correct package for each destination, not one single box — the lock records which wheel applies to which platform, so uv sync picks the right one automatically and everyone still ends up with matching, compatible versions.

2 — Anatomy of .venv​

A hotel does not install a private washing machine in every room — it plumbs each room to one shared laundry down the hall. .venv/bin/python works the same way: it is not a private copy of the Python interpreter, it is a pointer to one interpreter that lives outside your project and is shared across every project on your machine that needs the same version.

cat .venv/pyvenv.cfg

Expected output

home = /opt/homebrew/opt/python@3.12/bin
implementation = CPython
uv = 0.6.12
version_info = 3.12.3
include-system-site-packages = false
prompt = platformops

The home line names the real interpreter this environment points at. Yours may show a different path — see the note below. Confirm it is a link, not a copy:

readlink .venv/bin/python

Expected output

/opt/homebrew/opt/python@3.12/bin/python3.12

That path is not inside your project at all — which is exactly why .venv can be deleted and rebuilt from uv.lock in seconds: the only thing unique to your project is a handful of small links and installed packages, not a multi-hundred-megabyte Python install.

Your path will likely be different, and that is fine

The exact target of this link depends on what was already on your machine. If uv had to download Python 3.12 itself, the path lives under uv's own managed store — on macOS and Linux that is ~/.local/share/uv/python/...; you would see uv/python somewhere in the path. If your machine already had a compatible Python 3.12 installed — through Homebrew, pyenv, or your OS — uv reuses that one instead of downloading a second copy, and the path points there instead (a Homebrew, pyenv, or system directory, as in the capture above). Either way the point stands: .venv/bin/python is a pointer to an interpreter that lives outside, and is shared by, your project — never a private copy inside it.

The installed console script is built the same way, with a small twist for portability:

head -3 .venv/bin/pytest

Expected output

#!/bin/sh
'''exec' '<your home>/platformops/.venv/bin/python' "$0" "$@"
' '''

That #!/bin/sh line followed by a '''exec' ... trick is a script that is valid shell and valid Python at the same time — it exists because shebang lines have a length limit on some systems, and a deeply nested project path can exceed it. uv run pytest does not need this trick — it resolves the environment directly — but the installed script on disk does, so it still works if you ever call it without uv run.

3 — Where uv keeps its Python interpreters​

uv keeps its own managed store of Python interpreters, separate from any project, so it can download a version once and reuse it for every uv project on your machine that asks for it — the same shared laundry room the last section pointed to. But it does not always download: when you ask for a version, uv first checks whether one is already usable — its own managed store, then a matching interpreter already on your machine — and only downloads its own copy if neither has a match. This is the exact case you saw in the previous section: this machine already had a Homebrew Python 3.12, so uv reused it instead of downloading one.

Look at uv's own managed store directly:

ls ~/.local/share/uv/python/ 2>/dev/null || echo "(empty or not created yet — uv has not had to download its own interpreter on this machine)"

Expected output

(empty or not created yet — uv has not had to download its own interpreter on this machine)

This ran on a machine where a compatible Python 3.12 was already installed, so this lab never needed uv to download one — the store above is empty. On a machine with no matching Python already installed, this same command would instead list one or more cpython-<version>-... folders — one per version uv has downloaded and now manages for every project that asks for it. Either way, the version you pinned in the lab is never downloaded twice: uv downloads a version into this shared store (or finds it already on your machine) once, and every project that pins the same version reuses it instantly after that.

4 — The reproducibility chain, and what changes in CI​

Put the last three sections together and you get a chain with three links: pyproject.toml states a loose constraint ("pytest, something recent"), uv.lock freezes that into one exact, hashed pin, and uv sync turns that pin into a byte-for-byte matching .venv on any machine that runs it. Each link only trusts the one before it — which is exactly what a CI pipeline needs.

Run the check a CI job would run before installing anything:

uv sync --locked

Expected output

Resolved 8 packages in 2ms
Audited 7 packages in 3ms

--locked tells uv to fail instead of silently updating the lockfile if pyproject.toml and uv.lock have drifted apart — for example, if someone added a dependency and forgot to run uv sync before committing. Here is what that failure looks like, captured from a deliberately mismatched project (not something you need to reproduce yourself):

error: The lockfile at `uv.lock` needs to be updated, but `--locked` was provided. To update the lockfile, run `uv lock`.

That is the entire value of the reproducibility chain in one error message: instead of CI quietly installing a different set of packages than what you tested locally, it stops and tells you exactly what to run. A typical CI job for this project does three things in order: uv sync --locked (fail fast on drift), then the same ruff format --check, ruff check and pytest you already run locally — no separate "CI version" of the checks, the same commands, the same gate.

Where you will use this
  • A lockfile is a signed receipt, not a suggestion. Use it when: a teammate reports "it installs a different version for me" — compare uv.lock hashes before suspecting anything else; a matching lock means a matching install, by construction.
  • .venv is disposable; uv.lock is not. Use it when: an environment looks corrupted or half-installed — delete .venv and run uv sync instead of debugging it, since it rebuilds from the lock in seconds.
  • uv keeps one shared pool of interpreters per machine. Use it when: you are deciding whether to worry about disk space or download time for a new Python version pin across many projects — the download happens once, not once per project.
  • uv sync --locked is the CI drift check. Use it when: you are writing or reviewing a CI pipeline for a uv project — put this before the install step so a forgotten uv lock fails the build immediately, instead of shipping an untested set of versions.

Teardown​

This page only read files your lab already created — nothing to stop or remove. Keep ~/platformops for the next module, exactly as the lab's teardown already told you to.
