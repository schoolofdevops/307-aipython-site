Lab — Bootstrap PlatformOps v0.0

In this lab you build your own copy of the PlatformOps toolkit, from nothing, using uv. By the end you will have a working Python project with a pinned Python version, two quality tools wired in, one tested function, and your first Git tag: v0.0. Every later module in this course adds to this same project — it never gets rebuilt from scratch again.

You need uv and git, both already verified green on the Environment page. No Docker, no Kubernetes, no cloud tools for this one.

1. Create the project​

From your home directory, create the project with uv:

cd ~
uv init --package --vcs none --python 3.12 platformops

Expected output

Initialized project `platformops` at `<your home>/platformops`

uv prints the full path where it created the project — yours will show your own home directory, for example /Users/alex/platformops or /home/alex/platformops.

The --package flag is what gives you the src layout from the lesson (src/platformops/ with an __init__.py), instead of one loose file. --vcs none skips Git for now — you will initialize it yourself later in this lab, as a deliberate step. --python 3.12 tells uv which Python version to write into the project's requires-python setting — without it, uv picks the newest Python it can already find on your machine, which on a machine with Python 3.13 or newer already installed would make the pin in the next step fail.

Move into the project for the rest of this lab:

cd platformops

List what uv created:

ls -1

Expected output

pyproject.toml
README.md
src

(.python-version is already there too — ls -1 hides dotfiles by default; ls -1a would show it.)

2. Pin the Python version​

uv python pin 3.12

Expected output

Pinned `.python-version` to `3.12`

If uv does not already have Python 3.12 available, it downloads it the first time — that is normal and only happens once per machine.

3. Add the quality gates​

Add Ruff (formatter and linter) and pytest (test runner) as dev dependencies — tools your project needs to develop with, but that a user of the finished toolkit does not need to install:

uv add --dev ruff pytest

Expected output

Using CPython 3.12.3 interpreter at: /opt/homebrew/opt/python@3.12/bin/python3.12
Creating virtual environment at: .venv
Resolved 8 packages in 391ms
   Building platformops @ file://<your home>/platformops
Downloading pygments (1.2MiB)
Downloading ruff (10.1MiB)
 Downloaded pygments
      Built platformops @ file://<your home>/platformops
 Downloaded ruff
Prepared 7 packages in 2.66s
Installed 7 packages in 10ms
 + iniconfig==2.3.0
 + packaging==26.2
 + platformops==0.1.0 (from file://<your home>/platformops)
 + pluggy==1.6.0
 + pygments==2.20.0
 + pytest==9.1.1
 + ruff==0.16.1

This is the moment uv creates .venv and writes uv.lock for the first time. The exact download time, patch versions and package list will drift a little as Ruff and pytest ship new releases, and as a function of what Python and packages are already on your machine — the shape (a resolved set, an installed count, one line per package) stays the same. The first line also varies: it names the exact Python uv used and, if uv found one already on your machine instead of downloading its own, shows the path to it too. Notice platformops==0.1.0 — that is uv's default starting version; you fix that in the next step.

4. Write the toolkit's first function​

Open pyproject.toml and change exactly two lines: set version to match the release you are about to tag, and give description a real sentence in place of uv's placeholder text. Leave every other line in the file exactly as it is — the sections further down (like [build-system]) are what make the project installable. After your edit, the top of the file reads:

[project]
name = "platformops"
version = "0.0.0"
description = "PlatformOps Toolkit — inspect, validate and troubleshoot your services from one command line"

Now open src/platformops/__init__.py and replace its contents:

"""PlatformOps Toolkit — a Python operational toolkit for DevOps, platform
engineering and SRE work. This module grows release by release through the
course, from this v0.0 foundation to the v3.0 capstone.
"""

__version__ = "0.0.0"


def about() -> str:
    """Return the toolkit's one-line tagline."""
    return f"PlatformOps Toolkit v{__version__} — inspect, validate and troubleshoot your services"


def main() -> None:
    print(about())

This is deliberately small: one version string and one function you can import, call and test. Every later module adds real capability next to it — the shape stays the same.

5. Write the first test​

Create the tests folder first (it does not exist yet), then the file tests/test_foundation.py:

mkdir -p tests
from platformops import __version__, about


def test_version_is_pinned_to_v0_0():
    assert __version__ == "0.0.0"


def test_about_returns_the_toolkit_tagline():
    message = about()
    assert "PlatformOps Toolkit" in message
    assert __version__ in message

6. Update the README​

Open README.md and replace its (empty) contents:

# PlatformOps Toolkit

A Python operational toolkit for DevOps, platform engineering and SRE work. You are
building it module by module in *AI-Powered Python for DevOps, Platform Engineering & SRE*.

Current release: **v0.0 — Project Foundation**.

## Quick start

\`\`\`bash
uv sync
uv run pytest -q
\`\`\`

## Quality gates

\`\`\`bash
uv run ruff format .
uv run ruff check .
uv run pytest -q
\`\`\`

7. Sync the environment​

You changed pyproject.toml and added a new test file. Bring the environment back in step with what you asked for:

uv sync

Expected output

Resolved 8 packages in 35ms
   Building platformops @ file://<your home>/platformops
      Built platformops @ file://<your home>/platformops
Prepared 1 package in 393ms
Uninstalled 1 package in 1ms
Installed 1 package in 2ms
 - platformops==0.1.0 (from file://<your home>/platformops)
 + platformops==0.0.0 (from file://<your home>/platformops)

uv reads uv.lock, checks it against pyproject.toml, and confirms your third-party dependencies (Ruff, pytest and the packages they need) already match — none of those get reinstalled. But platformops itself is also a package in this environment (that is what --package in Step 1 set up), and you just changed its own version number in pyproject.toml. uv rebuilds and reinstalls that one small local package to keep it in step with what you asked for, shown as one - (old version) and one + (new version) line. This is normal and fast — it is your own code, not a download.

8. Run the three quality gates​

uv run ruff format .

Expected output

3 files left unchanged
uv run ruff check .

Expected output

All checks passed!
uv run pytest -q

Expected output

..                                                                       [100%]
2 passed in 0.01s

Three green results: your code is formatted, it passes lint, and both tests pass. This is the same three-command check you will run after every change for the rest of the course — by you, and later, by a coding agent working in this same project.

9. Initialize Git and tag your first release​

git init

Expected output

Initialized empty Git repository in <your home>/platformops/.git/

If this is the first time you have ever run git init on this machine, Git may also print a hint about the default branch name (master vs main) — that is safe to ignore either way, the rest of this lab works the same under both names.

Before you commit, add a .gitignore so the .venv folder — large, machine-specific, and rebuildable in seconds from uv.lock — never gets committed. Save this as .gitignore in the project root:

# Python-generated files
__pycache__/
*.py[oc]
build/
dist/
wheels/
*.egg-info

# Virtual environments
.venv

Stage and commit everything:

git add -A
git commit -m "platformops v0.0 -- project foundation"

Expected output

[main (root-commit) 5422c8a] platformops v0.0 -- project foundation
 7 files changed, 194 insertions(+)
 create mode 100644 .gitignore
 create mode 100644 .python-version
 create mode 100644 README.md
 create mode 100644 pyproject.toml
 create mode 100644 src/platformops/__init__.py
 create mode 100644 tests/test_foundation.py
 create mode 100644 uv.lock

Your own commit hash (5422c8a here) will be different — Git generates a new one from your commit's exact content and timestamp. The branch name in brackets may read master instead of main, depending on your machine's Git setup — both are fine. Seven files is the number that matters: everything needed to rebuild this project on any machine, and nothing that should not be there (no .venv, no __pycache__).

If you have never run a git commit on this machine before, Git may also print a longer notice saying it guessed your name and email from your username and computer name, with instructions to set them explicitly. That is normal for a first-ever commit and does not stop this lab — follow its instructions later if you want your commits attributed to your real name.

Now tag this commit as your first release:

git tag v0.0
git tag

Expected output

v0.0

That is the first rung of the release ladder from Module 1: v0.0 — Project Foundation. Every module from here adds a small, working change to this same project and closes with the next tag.

Lost your progress? Compare against the checkpoint

The instructor's own copy of this exact end state ships in the labs repository at 307-aipython-labs/labs/checkpoints/v0.0/. Use this frozen folder, not 307-aipython-labs/labs/platformops — that one always holds the latest release, so once a later module ships, it will no longer show the v0.0 state you need here. If your project stops passing the gates and you cannot find why, clone or pull the labs repository and compare labs/checkpoints/v0.0/ against yours file by file — do not delete your own project and start over, and there is no need to look at anything outside the labs repository.

Troubleshooting
  • uv: command not found — uv is not on your PATH. Close and reopen your terminal after installing it, or re-run the install command from the Prerequisites page and follow its PATH instructions.
  • uv python pin 3.12 fails with an error about requires-python — you ran Step 1's uv init without the --python 3.12 flag, and your machine's newest already-installed Python is 3.13 or newer, so uv wrote a requires-python that Python 3.12 does not satisfy. Open pyproject.toml and change requires-python to ">=3.12", then re-run uv python pin 3.12.
  • uv run python --version shows the wrong version — you likely ran uv python pin from a different folder. Confirm cat .python-version shows 3.12 while your prompt is inside platformops, then re-run uv sync.
  • ruff: command not found or pytest: command not found — you typed ruff or pytest directly instead of uv run ruff / uv run pytest. These tools live inside .venv, not on your system PATH; uv run is what finds them.
  • uv add seems to hang the first time — it is downloading Python 3.12 and the packages. This only happens once per machine; every later uv sync reuses what is already cached.

Teardown​

Nothing in this lab starts a service, a container or a cluster, so there is nothing to stop. Keep ~/platformops — it is the one project you grow for the rest of this course, module after module. If you want to remove it anyway and rebuild later from the checkpoint:

cd ~
rm -rf platformops

Re-running this lab from Step 1 is always safe and takes under a minute.

See where you are​

This course is really one long build: 37 small releases of the PlatformOps project, from v0.0 (what you just tagged) all the way to v3.0 at the end. There is a small tool that shows your real progress on that path.

Run it from your labs folder (the 307-aipython-labs repository you cloned during setup):

cd ~/307-aipython-labs
python3 labs/tools/release-ladder/serve.py

Then open http://127.0.0.1:8307/ in your browser.

You will see the full release ladder, and your own v0.0 tag lit up as the release you have reached. It reads this straight from git tag in your ~/platformops folder. It is not a demo — it is your real project. Click the Project Foundation tab to see more facts about your project: the version in pyproject.toml, whether .venv exists, and which files are in place.

Keep this tool open (or reopen it any time) as you move through the course. A new tab is added after later modules, always showing the real state of the same project you are building. Stop it any time with Ctrl+C.
