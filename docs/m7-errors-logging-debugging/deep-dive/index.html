What a Traceback Actually Is

The lab taught you to read a traceback bottom-up and to catch only what you can handle. This page opens up the machinery behind both habits. A traceback is not a block of text Python formats for you as an afterthought -- it is a live chain of frame objects you can walk in code, the same objects a debugger or an error-reporting tool inspects. Exception chaining, the "During handling of the above exception" line you have already seen and half-ignored, has a precise rule behind it, and you can choose to turn it on, off, or point it somewhere else. And the thing that decides whether an uncaught exception prints a raw traceback or a clean one-liner is a single function you can replace. You will reach for this the next time you are building an error reporter that needs to know which module actually raised, reviewing a diff that reraises inside an except block, or explaining to a reviewer why a --verbose flag "does nothing."

Where this picks up

You need ~/platformops at v0.5 from the lab. Every command below runs a short, disposable Python script in its own scratch folder -- none of them touch diagnostics.py, config.py or your project's git history. Re-running any command on this page is safe.

mkdir -p ~/platformops/dd-scratch && cd ~/platformops/dd-scratch

1 -- The call stack, made into data you can walk​

Think of a traceback as a security log, not a photograph. Each frame in it is a logged entry -- which function was running, which line it was on -- recorded in order as the call moved deeper. Python does not throw that log away once it prints it; exc.__traceback__ is a linked chain of frame objects, and the traceback module can turn it into a plain list you can loop over, filter, or search.

cat > walk_frames.py << 'EOF'
import traceback


def load_config(path):
    return parse_yaml(path)


def parse_yaml(path):
    return int(path)  # deliberate bug -- path is a string, not a number


try:
    load_config("service.yaml")
except Exception as exc:
    frames = traceback.extract_tb(exc.__traceback__)
    print(f"{len(frames)} frames on the stack when {type(exc).__name__} was raised:")
    for depth, frame in enumerate(frames):
        print(f"  frame {depth}: {frame.name}() at line {frame.lineno} -- {frame.line}")
EOF
uv run python3 walk_frames.py

Expected output

3 frames on the stack when ValueError was raised:
  frame 0: <module>() at line 13 -- load_config("service.yaml")
  frame 1: load_config() at line 5 -- return parse_yaml(path)
  frame 2: parse_yaml() at line 9 -- return int(path)  # deliberate bug -- path is a string, not a number

Frame 0 is the outermost call, frame 2 is where the error actually happened -- the same bottom-up order the lesson already told you to read, except now you have it as a list of FrameSummary objects with a .filename, a .name and a .lineno each. This is exactly what an error-tracking tool (Sentry, Rollbar, or a homegrown incident bot) does with every exception your service raises: it does not scrape the printed text, it walks exc.__traceback__ the same way, to decide which frame is "yours" (inside your package) versus a library's, and to group incidents by that frame instead of by the exception's message string, which changes every time a value in the message changes.

2 -- Exception chaining: three ways to raise inside an except block​

You already saw raise ConfigParseError(...) from exc in config.py. Here is why the from matters, by comparing all three ways of raising a new exception while already handling one.

cat > chaining.py << 'EOF'
import sys
import traceback


def implicit_chain():
    try:
        1 / 0
    except ZeroDivisionError:
        raise ValueError("could not compute the resolved value")


def explicit_chain():
    try:
        1 / 0
    except ZeroDivisionError as exc:
        raise ValueError("could not compute the resolved value") from exc


def suppressed_chain():
    try:
        1 / 0
    except ZeroDivisionError:
        raise ValueError("could not compute the resolved value") from None


for label, fn in [
    ("1. implicit (no `from`)", implicit_chain),
    ("2. explicit (`from exc`)", explicit_chain),
    ("3. suppressed (`from None`)", suppressed_chain),
]:
    print(f"--- {label} ---")
    try:
        fn()
    except ValueError:
        traceback.print_exc(file=sys.stdout)
    print()
EOF
uv run python3 chaining.py

Expected output

--- 1. implicit (no `from`) ---
Traceback (most recent call last):
  File ".../chaining.py", line 7, in implicit_chain
    1 / 0
    ~~^~~
ZeroDivisionError: division by zero

During handling of the above exception, another exception occurred:

Traceback (most recent call last):
  File ".../chaining.py", line 33, in <module>
    fn()
  File ".../chaining.py", line 9, in implicit_chain
    raise ValueError("could not compute the resolved value")
ValueError: could not compute the resolved value

--- 2. explicit (`from exc`) ---
Traceback (most recent call last):
  File ".../chaining.py", line 14, in explicit_chain
    1 / 0
    ~~^~~
ZeroDivisionError: division by zero

The above exception was the direct cause of the following exception:

Traceback (most recent call last):
  File ".../chaining.py", line 33, in <module>
    fn()
  File ".../chaining.py", line 16, in explicit_chain
    raise ValueError("could not compute the resolved value") from exc
ValueError: could not compute the resolved value

--- 3. suppressed (`from None`) ---
Traceback (most recent call last):
  File ".../chaining.py", line 33, in <module>
    fn()
  File ".../chaining.py", line 23, in suppressed_chain
    raise ValueError("could not compute the resolved value") from None
ValueError: could not compute the resolved value

Case 1 is what happens if you do nothing special -- Python chains automatically the moment you raise a different exception while one is already being handled, and labels it "During handling of the above exception" because it does not know if the two are related on purpose. Case 2 is config.py's own pattern: from exc tells Python (and the next reader) this new exception is a direct, deliberate consequence of that one, and the wording changes to "the direct cause." Case 3 throws the original away entirely -- use it only when the original truly adds no information (a retry loop's tenth identical timeout, say), because it deletes evidence a debugger cannot get back. When you review a diff with a bare raise SomeError(...) inside an except block, this is the question to ask: was the chaining to the original exception deliberate, or is Case 1 just happening by accident because nobody thought about it?

3 -- What actually prints the traceback: sys.excepthook​

An analogy first: every uncaught exception in a Python process ends up at one front desk before the process exits. sys.excepthook is that front desk -- a single function Python calls with the exception type, value and traceback, whose job is deciding what the terminal sees. Swap out the person at the desk and the same uncaught exception gets announced differently, with no change to the code that raised it.

cat > excepthook_demo.py << 'EOF'
import sys

from platformops.config import ConfigError, ConfigNotFoundError

print("default sys.excepthook:", sys.excepthook.__module__ + "." + sys.excepthook.__name__)


def friendly_hook(exc_type, exc_value, exc_tb):
    if issubclass(exc_type, ConfigError):
        print(f"error: {exc_value}", file=sys.stderr)
        sys.exit(1)
    sys.__excepthook__(exc_type, exc_value, exc_tb)


sys.excepthook = friendly_hook
raise ConfigNotFoundError("config file not found: service.yaml")
EOF
uv run python3 excepthook_demo.py; echo "exit: $?"

Expected output

default sys.excepthook: sys.excepthook
error: config file not found: service.yaml
exit: 1

sys.__excepthook__ (double underscore) is Python's original hook, kept around so a custom hook can fall back to it for anything it does not want to handle specially -- friendly_hook above only intercepts the toolkit's own ConfigError family and lets every other, genuinely unexpected, exception print its full traceback exactly as before. This is one of two ways a real CLI avoids showing users a raw traceback for an expected failure -- the other is the top-level try/except in main() that diagnostics.py and config.py already use, which is more common in practice because it keeps the handling next to the code that can fail, instead of a global hook nobody remembers exists. Frameworks like click and most argument parsers install their own hook (or an equivalent top-level catch) for exactly this reason -- so a missing file does not end a user's first run of the tool with fifteen lines of frame data.

4 -- Logging has two gates, not one​

The lesson told you --verbose switches a log level. Here is the actual pipeline: a log call has to clear two separate gates before it reaches the terminal -- the logger's own level, and then the level of whichever handler is about to emit it. Think of it like a mailroom: a letter first has to clear the department's overall mail policy (the logger's level), and only then does it reach a specific desk, which can have its own, stricter, inbox rule (the handler's level) that throws it out even though the department already let it through.

cat > logging_pipeline.py << 'EOF'
import logging
import sys

logger = logging.getLogger("platformops.diagnostics.demo")
logger.setLevel(logging.DEBUG)  # gate 1: the logger's own level

quiet_handler = logging.StreamHandler(sys.stdout)
quiet_handler.setLevel(logging.WARNING)  # gate 2a: stricter, on this one handler
quiet_handler.setFormatter(logging.Formatter("QUIET  %(levelname)s: %(message)s"))

verbose_handler = logging.StreamHandler(sys.stdout)
verbose_handler.setLevel(logging.DEBUG)  # gate 2b: matches the logger's own level
verbose_handler.setFormatter(logging.Formatter("VERBOSE %(levelname)s: %(message)s"))

logger.addHandler(quiet_handler)
logger.addHandler(verbose_handler)

logger.debug("loading service.yaml")
logger.warning("service.yaml failed validation: 1 field(s)")
EOF
uv run python3 logging_pipeline.py

Expected output

VERBOSE DEBUG: loading service.yaml
QUIET  WARNING: service.yaml failed validation: 1 field(s)
VERBOSE WARNING: service.yaml failed validation: 1 field(s)

The DEBUG call cleared the logger's gate (set to DEBUG) but was stopped at quiet_handler's own gate (WARNING) -- it never reached that handler's formatter at all, so it only shows up once, from verbose_handler. The WARNING call cleared both handlers' gates, so it shows up twice, once per handler, each with its own formatting. logging.basicConfig(level=...), what platformops.diagnostics and platformops.config both call in main(), is a shortcut that sets up exactly one handler and gives it the same level you pass as the logger's -- which is why, in this toolkit, --verbose looks like it controls one thing, when it is actually setting both gates at once through a single call. The next time a --verbose flag "does nothing" in code you are debugging, check both: the logger's setLevel() and every handler attached to it -- either one alone can silently swallow a message the other would have let through.

5 -- The honest cost of raising an exception​

Every so often a reviewer objects to using an exception for an expected failure (a missing file, a bad value) on performance grounds. Measure it instead of arguing about it:

cat > cost_of_exceptions.py << 'EOF'
import timeit


def validate_with_exception(value):
    if value < 0:
        raise ValueError("negative")
    return value


def validate_with_return_code(value):
    if value < 0:
        return None, "negative"
    return value, None


def run_exception_path(n):
    caught = 0
    for _ in range(n):
        try:
            validate_with_exception(-1)
        except ValueError:
            caught += 1
    return caught


def run_return_code_path(n):
    caught = 0
    for _ in range(n):
        _, err = validate_with_return_code(-1)
        if err:
            caught += 1
    return caught


N = 200_000
exc_time = timeit.timeit(lambda: run_exception_path(N), number=1)
ret_time = timeit.timeit(lambda: run_return_code_path(N), number=1)

print(f"{N:,} calls, raising every time:      {exc_time:.4f}s total, {exc_time / N * 1e6:.2f} microseconds/call")
print(f"{N:,} calls, returning an error code:  {ret_time:.4f}s total, {ret_time / N * 1e6:.2f} microseconds/call")
print(f"exception path is {exc_time / ret_time:.1f}x the return-code path -- per call, both are microseconds")
print(f"diagnose() raises at most once per process run, not once per {N:,} -- the difference above never matters here")
EOF
uv run python3 cost_of_exceptions.py

Expected output

200,000 calls, raising every time:      0.0336s total, 0.17 microseconds/call
200,000 calls, returning an error code:  0.0107s total, 0.05 microseconds/call
exception path is 3.1x the return-code path -- per call, both are microseconds
diagnose() raises at most once per process run, not once per 200,000 -- the difference above never matters here

Your own numbers will differ from these -- the point is the shape, not the exact figures: raising is a small constant-factor slower than returning a code, both measured in fractions of a microsecond. That factor matters if you are validating a hundred million records in a hot loop and choose exceptions as your inner-loop control flow -- it does not matter for platformops.diagnostics, which raises at most once per process invocation, run once per file, once per CI job. The real cost of a badly designed exception is never CPU time; it is a bare except Exception that swallows a bug, or a chain that hides the real cause. Spend your review attention there, not on whether raise is "slow."

Where you will use this
  • exc.__traceback__ is walkable data, not just printable text. Use it when: you are building or debugging an error-reporting integration that needs to group incidents by which frame actually raised, not by the exception's message text, which changes every time a value in it changes.
  • raise ... from exc versus a bare raise inside an except block changes what a reader is told about why the second exception happened. Use it when: reviewing a diff that reraises inside an except block -- if there is no from, ask whether the chaining to the original was deliberate or just what Python does by default when nobody thought about it.
  • sys.excepthook (or a top-level try/except in main()) is the one place that decides whether an uncaught exception shows a user a raw traceback or a clean message. Use it when: a CLI you own still dumps a full traceback for an expected, common failure -- wrap main()'s call site, catching only the exception types you already know how to explain.
  • A log call has to clear the logger's level and the handler's level -- either can silently drop it. Use it when: a --verbose flag "does nothing" -- check both gates before you assume the flag itself is wired wrong.
  • Raising costs a few hundred nanoseconds more than returning a code -- irrelevant for a CLI, relevant only in a hot inner loop processing millions of items. Use it when: a reviewer objects to an exception on performance grounds for code that runs once per request or once per process -- measure it, and spend the review's attention on the catch scope instead.
