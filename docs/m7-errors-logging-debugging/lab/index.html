Lab -- Repair PlatformOps v0.5: Reliable Validation and Diagnostics

This lab is a repair job, not a build-from-nothing job. You are handed diagnostics.py -- a tool someone wrote in a hurry to answer one question fast: "is this service.yaml OK to deploy?" It works on a good file. On a bad one, it either crashes with a confusing traceback or, worse, prints OK when the file is not OK at all. You fix it, one failure scenario at a time. labs/m7/scenarios.md in your labs clone describes exactly what "fixed" looks like for each of the six -- keep it open while you work.

You need ~/platformops from the M6 lab, already tagged v0.4, with uv run pytest -q passing.

cd ~/platformops
git log --oneline -1

Expected output

platformops v0.4 -- service configuration validator

Open src/platformops/diagnostics.py and read it once before running anything. It is short -- one function, diagnose(), and a main() that calls it. Notice two things: a print("DEBUG: ...") left in from whoever wrote it, and a try/except Exception: pass around the file-loading line that swallows whatever goes wrong there without a word.

Read that traceback the way the lesson taught you: bottom-up. The last line says UnboundLocalError: ... 'data' ... -- but service-badyaml.yaml is broken YAML, not a variable scoping bug. 3. Fix scenarios 1-4 by hand​

One root cause explains scenarios 1, 2, 3 and 4: diagnose() opens and parses the file itself with a bare except Exception: pass, instead of using the loader platformops.config already built -- load_yaml_dict(), which already turns a missing file or bad YAML into a clean ConfigError (from the M6 lab). And when validation does run, the tool never looks at what it returns -- it just prints a generic line and returns 0 regardless. Rewrite src/platformops/diagnostics.py:

src/platformops/diagnostics.py
"""platformops.diagnostics -- quick health check for a service definition file.

This answers one question fast: "is this service.yaml OK to deploy?" It
reuses `platformops.config`'s already-safe loader instead of opening the file
itself, so a missing file or broken YAML never reaches this module as a raw
exception -- it arrives as a `ConfigError`, a type this module knows how to
handle and report cleanly.
"""

import sys
from pathlib import Path

from platformops.config import ConfigError, load_yaml_dict
from platformops.servicedef import ServiceDefinition, validate_service


def diagnose(path: Path) -> int:
    """Run the health check on one service definition file.

    Returns the exit code this run should use: 0 if the file is a valid
    service definition, 1 for a file problem (missing, invalid YAML) or a
    data problem (missing field, wrong type, a value the schema does not
    allow).
    """
    try:
        data = load_yaml_dict(path)
    except ConfigError as exc:
        print(f"{path}: ERROR -- {exc}")
        return 1

    result = validate_service(data)

    if isinstance(result, ServiceDefinition):
        print(f"{path}: OK -- {result.to_summary()}")
        return 0

    print(f"{path}: FAIL")
    for error in result:
        field = ".".join(str(part) for part in error["loc"])
        print(f"  {field}: {error['msg']}")
    return 1


def main() -> None:
    path = Path(sys.argv[1])
    sys.exit(diagnose(path))


if __name__ == "__main__":
    main()

Two changes carry all four fixes: reusing load_yaml_dict means a file problem always arrives as a ConfigError this module already knows how to turn into a clean message, instead of a raw exception; and actually looping over validate_service's returned errors -- instead of ignoring them -- means a data problem gets reported by field name, with exit code 1, instead of a generic sentence and a lying 0.

4. Scenarios 5 and 6: hand this to your coding agent​

Two problems remain, and neither is a diagnostics.py bug this time:

  • Permission denied still crashes, because load_yaml_dict() in config.py never learned to catch PermissionError -- it only handles a missing file and bad YAML. This is a gap in the shared loader, not in the tool you just fixed.
  • The bad AWS account number still passes, because nothing in ServiceDefinition checks the shape of aws_account -- only that it is a string. Every field being the right Python type is not the same as every field holding an allowed value.

Both fixes belong in the shared modules underneath diagnostics.py, plus this is a natural point to add the logging the lesson covered: a --verbose flag on both CLIs, and the discipline of never logging a field's actual value.

Run the checklist:

  • Are ConfigNotFoundError, ConfigPermissionError and ConfigParseError all subclasses of ConfigError? Every existing except ConfigError elsewhere in the codebase must keep catching all three -- check test_config.py's existing tests still pass unchanged.
  • Does ConfigPermissionError chain from the original PermissionError with from exc? Losing the chain loses evidence a debugger cannot get back, per the lesson.
  • Is the aws_account check a Field(pattern=...), matching the existing style for kubernetes_namespace? Not a new hand-written validator function duplicating a pattern Pydantic already supports directly.
  • Does any log call include a field's actual value (a name, a URL, an account number)? It should not -- only the file path and, for a validation failure, the field name.
  • Did the agent add a dependency? pyproject.toml should show no new line under dependencies -- argparse and logging are both standard library.

Troubleshooting
  • UnboundLocalError: cannot access local variable 'data' appears from your own code after step 3 -- you have not fully replaced diagnose() yet; the old bare except Exception: pass is still there somewhere, most likely because the file was edited instead of replaced.
  • A test for scenario 5 (permission) fails or errors out oddly on CI or in a container -- if the test runs as root, permission bits do not block reads at all; this is why the test in this lab is skipped in that case (@pytest.mark.skipif(... os.geteuid() == 0 ...)).
  • service-noperm.yaml is still chmod 000 after a step failed partway through -- chmod 644 service-noperm.yaml before touching it again with any editor or git add, or git status and most editors will refuse to read it.
  • The --verbose flag "does nothing" -- check both gates the deep dive covers: the logger's own setLevel() and the level of the handler basicConfig installed. If you see log lines even without --verbose, that is expected for WARNING and above -- only DEBUG/INFO are gated behind the flag.
  • Your agent's diff touches pyproject.toml's dependencies list -- reject that part of the change; argparse and logging are both standard library, nothing new needed to add here.
  • aws_account rejected on a file that used to pass -- the pattern requires exactly 12 digits with no quotes stripped incorrectly; check the value in your YAML is a quoted string of digits, e.g. aws_account: "111122223333".

Teardown​

Nothing in this lab starts a service, a container or a cluster -- there is nothing to stop. Remove any stray permission-denied file if one is still lying around:

chmod 644 ~/platformops/service-noperm.yaml 2>/dev/null
rm -f ~/platformops/service-noperm.yaml

Keep ~/platformops; it carries forward into every later module.

cd ~
rm -rf platformops

Run that only if you want to remove the project and rebuild it from the checkpoint.
