Errors, Logging and Debugging

Module slides​

Walk this short whiteboard deck for the big picture, or open it fullscreen.

▶ M7 — Errors, Logging and DebuggingOpen fullscreen ↗

A validation tool checks a service.yaml file before a deploy runs. Someone mistypes an AWS account number, and runs the check. The tool prints OK and exits with a success code. The deploy goes ahead. Nothing in that tool lied on purpose -- it just never checked the one thing that mattered, and never said so. This module closes exactly that gap: telling apart a script that crashes loudly, one that fails quietly, and one you can trust because it tells the truth about what it found, every time.

1. Three kinds of errors, and when each one shows up​

Think about following a recipe. A step written in gibberish stops you before you even start. A step that says "add the sugar" when there is no sugar in the kitchen stops you partway through, the moment you reach it. And a step you follow perfectly, using salt instead of sugar by mistake, never stops you at all -- the cake looks fine coming out of the oven, and you only find out something was wrong when someone tastes it.

Python code fails the same three ways:

  • Syntax errors -- the code is not valid Python at all. Python catches these before your program runs a single line, the same way a gibberish recipe step stops you before you start.
  • Runtime errors (exceptions) -- the code is valid, but something goes wrong the moment a specific line executes: a file is not there, a value is the wrong type. Python stops right at that line.
  • Logic errors -- the code runs from start to finish with no error at all, and produces a wrong answer. Nothing stops. You only find out when the answer is checked against reality -- sometimes right away, sometimes long after the deploy already happened.

Logic errors are the most dangerous of the three precisely because nothing announces them. The lab's broken tool has one: it validates a file, finds a real problem, and still reports success.

2. Reading a traceback bottom-up​

When Python hits a runtime error it cannot handle, it prints a traceback -- a report of exactly where things went wrong. Read it the way you would read a traffic accident report: the last line names what actually hit you -- the error type and its message. The lines above it are the route that led there -- which function called which function, working backwards from the crash to where the program started.

Traceback (most recent call last):
  File "diagnostics.py", line 40, in <module>
    main()
  File "diagnostics.py", line 35, in main
    exit_code = diagnose(path)
  File "diagnostics.py", line 23, in diagnose
    result = validate_service(data)
UnboundLocalError: cannot access local variable 'data' where it is not associated with a value

Start at the bottom: UnboundLocalError, a variable used before it was ever set. Then look one line up to see exactly where -- diagnose, calling validate_service(data). The frames above that just show how the program got there. Most learners try to read this top-down, get lost in main(), and never reach the one line that actually explains the failure. Bottom-up, every time.

Eight real incident tickets, each with a genuine traceback captured from a running Python script -- nothing hand-typed. For each one, predict which frame actually crashed before you click, call whether it is a syntax, runtime or logic error, and pick where the real fix belongs. The crashing frame and the guilty frame are often two different lines -- sometimes the guilty one is a library you do not own, sometimes it is not in the traceback at all. One ticket has no traceback whatsoever and still hides a real bug -- that is the trap.

3. try / except / else / finally -- and the narrow-catch rule​

try:
    data = load_yaml_dict(path)
except ConfigError as exc:
    print(f"{path}: ERROR -- {exc}")
else:
    print(f"{path}: loaded cleanly")
finally:
    print("done checking this file")

try holds the code that might fail. except runs only for a matching error -- ConfigError, not everything. else runs only if nothing went wrong, keeping the success path separate from the failure path. finally always runs, error or not -- the right place for cleanup like closing a file.

The rule that matters most here: only catch what you know how to handle. A doctor doing triage sorts patients by what is actually wrong, and routes accordingly. except ConfigError is that sorting: it catches the file problems this code understands and lets everything else -- a real bug, a typo in the code itself -- keep propagating, so it gets noticed instead of buried. except Exception (or a bare except:) catches everything, including bugs nobody wrote on purpose. It does not fix those bugs -- it hides them until they resurface somewhere far more confusing, later.

4. Raising your own exceptions -- the ConfigError family​

A crime scene does not put every piece of evidence into one bag labeled "something happened." It labels each bag by what it actually is, so the right specialist looks at the right one. Your own exception types do the same job for errors:

class ConfigError(Exception):
    """A problem with the config file itself."""

class ConfigNotFoundError(ConfigError):
    """The path does not exist."""

class ConfigPermissionError(ConfigError):
    """This process cannot read the file."""

Code that only cares "was there a config problem" catches ConfigError and handles every kind of file trouble in one place. Code that needs to react differently to a missing file versus a permissions problem catches the specific subclass instead. Either way, nothing has to catch bare Exception -- your own types are exactly as narrow, or as broad, as the moment calls for.

When you raise a custom exception inside an except block, chain it to the original with from exc so the full story stays visible:

except yaml.YAMLError as exc:
    raise ConfigParseError(f"invalid YAML in {path}: {exc}") from exc

Without from exc, Python discards the original traceback -- whoever debugs the failure next sees your wrapper but not the parser error that caused it. With from exc, both tracebacks print together, and the __cause__ link is preserved for any code that inspects the chain programmatically. The Deep Dive explores chaining in more detail, including the from None form that explicitly suppresses the original when it would only add noise.

5. Exit codes -- the contract a machine actually reads​

A print statement is for a person reading the screen right now. An exit code is for whatever runs your script next -- CI, a cron job, another script -- and none of those read English. They read one number.

0 means go ahead. 1 means this run found something actually wrong -- a missing field, an invalid file. 2 is different again: the tool was called incorrectly (a missing argument), not a problem with the thing it checked. A pipeline that only checks "did it print an error" instead of the exit code is exactly the kind of pipeline the lab's broken tool would fool -- it can print whatever it wants and still exit 0.

6. Logging -- a note for right now versus an entry in the log​

print() is a note handed to whoever is watching the screen right now. A log line (logger.warning(...)) is an entry in a ship's log -- written down whether or not anyone is watching, for whoever reads it later: an incident responder, a log search tool, you tomorrow. Use print() for the answer your tool exists to give. Use logging for everything else -- what it noticed, in case someone needs to reconstruct the run afterward.

Log levels say how loud an entry is: DEBUG for detail only someone actively investigating wants, INFO for a normal note, WARNING for something worth a second look, ERROR for something that broke. A --verbose flag typically turns DEBUG on; without it, only WARNING and above show.

One more habit worth building now: structured logging. Instead of burying a value inside a sentence ("validation failed for field deployment_name"), a structured log line carries the file path and the field name as separate, named pieces of data a log search tool can filter on directly, without parsing a sentence. And at any level: never log the actual value of a field that could be sensitive -- log the file path and the field name, never the contents.

7. The debugging ladder​

Facing a failure, resist changing code immediately. Climb one step at a time:

  1. Read the error, fully. The traceback usually already names the problem.
  2. Reproduce it. Get the same failure, on demand, before touching anything.
  3. Look inside. A print() at the right spot, or a breakpoint() into Python's debugger, to see the actual values at the moment things went wrong.
  4. Write a failing test. Once you understand the bug, capture it in a test, then fix the code until that test passes -- now the bug cannot silently come back.

Skipping straight to step 3 is how an hour disappears changing code that was never the problem.

Common pitfalls
  • A bare except: or except Exception:. It catches the error you expected to see and every bug you did not. Catch the specific type you know how to handle.
  • Swallowing an exception with except: pass. The failure did not go away -- it just stopped being visible, often producing a confusing, unrelated error somewhere else instead.
  • Logging a field's value instead of its name. A log line meant to help debugging should never be the place a secret or sensitive value leaks out.
  • Leaving print() debugging statements in shipped code. They clutter every future run's output. Convert anything worth keeping into a real logger.debug() call, gated behind --verbose, and delete the rest.
