Cloud Governance and Compliance Automation

Every AWS module so far in this course either shows you what exists (Module 21's inventory, Module 23's multi-region scan) or does something to a resource (Module 22's report upload, queue send). This module does neither. It checks what already exists against a set of rules written down in a file, and produces a list of exactly what breaks those rules — nothing more. It is the platformops project's first audit tool, and audits have one job: find and report, never fix.

Why this matters at work

A cloud account grows one resource at a time — a bucket here for a one-off export, an instance there for a proof of concept — and nobody remembers every rule that was supposed to apply. Then a customer asks for a compliance report, or a security review flags an S3 bucket that turned out to be public, and someone has to answer: which of our resources actually follow policy, right now, with evidence? Checking that by hand, resource by resource, does not scale past a handful of buckets. This module builds the tool that answers it on demand, with a paper trail an auditor can check independently.

1. The inspector's checklist, not the repair crew​

Picture a building inspector who visits a construction site with a written checklist: smoke detectors installed, fire exits clear, wiring up to code. The inspector's job stops at the checklist. They walk the site, mark every item pass or fail, write down exactly what they saw — "exit on the third floor blocked by stored furniture," not just "fail" — and hand the building owner a citation report. The inspector does not move the furniture. A separate maintenance crew does that, on their own schedule, using the citation report as their work order.

Keeping those two roles apart is not bureaucracy for its own sake. An inspector who also fixes problems on the spot has a reason to look the other way on a minor issue to save time, and a building owner has no independent record of what was actually found before it got fixed. A written report, produced by someone whose only job is to look and record, is worth more precisely because the inspector cannot also make the problem disappear.

This module's cloudaudit.py is the inspector. It checks real AWS resources against a written policy — required tags, approved regions, age, encryption, public exposure — and produces a findings report with exact evidence for every violation. It never deletes a bucket, never changes a tag, never locks down a public ACL. A later module, Safe Cloud Remediation, is the maintenance crew — a separate tool, reading this module's findings as its work order, run deliberately and on its own schedule. This module ships no code that calls a write-mode AWS API (put_*, delete_*, create_*, modify_*) against a resource it is auditing — the Deep Dive proves that mechanically, not just by description.

The dashed box is deliberate: this module's diagram stops at the audit report. Remediation is someone else's job, in a later module.

2. Policy as data — rules you can read without reading Python​

cloudaudit.py's rules do not live in if statements scattered through the code. They live in a YAML file, policy.yaml, that a compliance lead who has never opened Python can read and reason about:

rules:
  - id: required-tags
    check: required_tags
    severity: high
    required_tags: [team_owner, environment]

  - id: no-public-exposure
    check: no_public_exposure
    severity: critical
    applies_to: [s3-bucket]

exceptions:
  - resource_id: platformops-legacy-reports
    rule_id: required-tags
    reason: "legacy bucket predates the tagging policy -- cleanup tracked in OPS-4021"
    expires: "2026-12-31"

Each rule has an id (matched against exceptions), a check (which built-in check function runs — required_tags, approved_regions, max_age_days, require_encryption, no_public_exposure), and a severity. applies_to is optional: leaving it out means the rule applies to every resource type this module gathers evidence for; naming resource types ([s3-bucket]) keeps a rule like "require encryption" from being silently meaningless against a resource type this module has no encryption evidence for at all.

Changing what counts as a violation — adding a region to the approved list, raising the maximum age from 90 days to 180 — means editing this file, not shipping a code change. That is the entire point of "policy as data": the rule and the code that enforces it are two different things, and only one of them needs a pull request to change.

3. Evidence composes with the inventory, it does not duplicate it​

Module 23's multiregion.py already discovers S3 buckets — list_s3_buckets() returns each bucket's resource_id, region and tags as a ResourceRecord. This module's policy checks need more than that: whether a bucket is encrypted with a customer-managed key, whether its ACL exposes it publicly, how old it is. Two ways to get there were on the table: add those fields directly onto ResourceRecord, or build something new that wraps a ResourceRecord and adds only what this module needs.

Adding audit-only fields onto ResourceRecord would mean every other caller of that dataclass — a plain inventory report, a CSV export, any future module that just wants "what exists, with what tags" — carries fields it never fills in, always None. This module instead defines ResourceEvidence, which wraps one ResourceRecord and adds exactly encrypted, public and created_at. multiregion.list_s3_buckets() still does the one thing it always did; this module's own gather_bucket_evidence() is the only place that adds the extra evidence, and it is the only place in this module that makes AWS calls at all.

4. Detection is pure — provably, not just by convention​

evaluate_policy() takes a list of already-gathered ResourceEvidence and a loaded policy, and returns a list of Finding objects. It never builds a boto3 client, never mentions client anywhere in its body, and never touches the network. That is what makes it fully unit-testable without Floci running at all: every detection test in this module's test suite hand-builds evidence directly and asserts on the findings that come back, no live AWS emulator required.

Splitting evidence-gathering (gather_bucket_evidence(), the only network-touching function here) from detection (evaluate_policy(), pure) is the same "separate detection from remediation" idea from section 1, one layer deeper: even inside the inspector's own work, "go look at the site" and "decide whether what I saw violates the checklist" are kept apart. A bug in the detection logic should never require a live AWS connection to catch in a test; a bug in evidence-gathering should never be confused with a bug in what counts as a violation.

5. A finding carries evidence, not a bare verdict​

A Finding is not just "resource X failed rule Y." It carries the exact evidence that proved the violation, as a specific string:

{
  "resource_id": "platformops-audit-no-kms",
  "resource_type": "s3-bucket",
  "rule_id": "require-encryption",
  "severity": "high",
  "evidence": "encryption: not using a customer-managed KMS key (AWS-managed SSE-S3 default only)",
  "suppressed": false,
  "suppression_reason": null
}

That distinction matters more than it looks. Real AWS — and Floci, which matches this behavior — turns on default SSE-S3 encryption for every bucket automatically, the moment it is created, and has done so since January 2023. A check that only asks "does this bucket have any default encryption configured" would find zero violations on any real account today, because the answer is always yes. The actual compliance question worth auditing is narrower — does this bucket use a customer-managed KMS key, which many compliance frameworks specifically require for key rotation control and CloudTrail audit visibility, versus the AWS-managed default that gives you neither. evidence says exactly that ("not using a customer-managed KMS key"), not a bare false that would leave an auditor guessing which kind of "not encrypted" they were looking at. The Deep Dive shows this finding next to the real API response that produced it.

6. Exceptions suppress, they never delete​

A policy will always have legitimate exceptions — a legacy bucket scheduled for cleanup next quarter, a resource whose owner has an approved waiver. policy.yaml's exceptions list matches one (resource_id, rule_id) pair to a reason and an expiry date. When evaluate_policy() finds a violation that also matches an unexpired exception, it still creates the Finding — it just marks suppressed: true and fills in suppression_reason. The finding stays in the report, visible, not quietly dropped from a shorter list.

That distinction is the whole point of tracking exceptions at all. A report that silently excludes excepted resources looks identical to a report where those resources were never checked — an auditor reviewing it cannot tell "we know about this and decided to accept the risk until a deadline" from "nobody looked." A report that shows the suppressed finding, with its reason and expiry, makes that decision visible and reviewable.

An exception's expires date is not decorative. evaluate_policy() checks it against now on every run: an exception with a past expires date no longer suppresses anything, and the finding it used to excuse goes back to being active. Nothing has to happen for that switch to flip — the same exception, re-evaluated the day after it expires, produces a different result, because the policy was written to expect that.

Common pitfalls​

  • Conflating detection with remediation. The moment an "audit" script starts calling delete_bucket() or put_bucket_tagging() to fix what it finds, it stops being an audit — there is no longer an independent report of what was found before it changed. Keep the two as separate tools, even when it would be faster to combine them.
  • Silently dropping suppressed findings instead of showing them. A shorter report that hides excepted resources looks the same as a report that never checked them at all. Show every suppressed finding, with its reason, right alongside the active ones.
  • A policy rule with no severity. Every rule needs one — a report where every finding looks equally urgent is not more urgent, it is less useful; nobody can tell what to act on first.
  • Treating an expired exception as still valid. An exception's expires date has to be checked against the current date on every run, not just recorded once when the exception was written. A suppression that never re-checks its own expiry quietly becomes permanent.
  • Assuming "not encrypted" means the bucket has no encryption at all. On a real account today, it almost always does — the AWS-managed SSE-S3 default. The evidence has to say which kind of encryption is missing (a customer-managed key, specifically), or the finding is misleading.
