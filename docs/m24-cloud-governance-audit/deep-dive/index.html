Deep Dive — Cloud Governance and Compliance Automation

The lab proved cloudaudit.py finds real seeded violations and produces a report. This page goes one level deeper on three claims the lesson made but did not fully prove on their own: that detection really has zero write-mode AWS calls anywhere in it (not just "we didn't add any"), that an exception's expiry date genuinely flips a real finding's suppression state on a real date, and what a finding's evidence string looks like sitting next to the raw AWS API response that produced it.

Where this picks up

This page assumes ~/platformops at v1.9.0, with src/platformops/cloudaudit.py and the cloud-audit CLI command in place from the lab, and Floci running.

cd ~/platformops
uv run platformops version

Expected output

platformops 1.9.0

1. Detection has zero write-mode AWS calls — proven mechanically​

The lesson claimed evaluate_policy() never touches the network. "We didn't write a network call" is not the same claim as "there is no network call" — the same discipline Module 19 used to prove a service-readiness skill was genuinely read-only, not just written with that intent. Grep the whole module for the AWS SDK's write-mode call prefixes:

rg 'client\.(put_|delete_|create_|modify_)' src/platformops/cloudaudit.py; echo "exit=$?"

Expected output

exit=1

rg exits 1 when it finds zero matches — across the entire module, not just inside evaluate_policy(), there is no put_*, delete_*, create_* or modify_* call against a client. gather_bucket_evidence(), bucket_uses_kms_encryption() and bucket_is_public() — the only functions here that touch AWS at all — call list_buckets(), get_bucket_encryption() and get_bucket_acl(). Every one of those is a Get/List/Describe-class read.

A narrower, stronger version of the same proof: evaluate_policy() does not merely avoid write calls, it never references a client at all.

awk '/^def evaluate_policy\(/{p=1} p{print} /^def build_report\(/{exit}' src/platformops/cloudaudit.py | rg 'client'; echo "exit=$?"

Expected output

exit=1

evaluate_policy()'s entire body — walking every rule against every piece of evidence, matching exceptions, building Finding objects — never mentions the word client. It cannot make an AWS call, write or read, because it never holds a reference to anything capable of making one. That is a stronger guarantee than "this function happens not to call a write API today" — a future edit to this function would have to introduce a client from nothing to make it capable of touching AWS at all, which is a much larger, much more visible change than adding one more line to an existing function that already has a client in scope.

2. Suppression and expiry, proven with real dates​

The lesson claimed an exception with a past expires date stops suppressing, on its own, with no other change. Here is the same exception, evaluated twice — once with a real future expiry, once with a real past one — with everything else held identical.

cat > /tmp/m24_expiry_demo.py << 'PYEOF'
from datetime import UTC, datetime

from platformops.cloudaudit import ResourceEvidence, evaluate_policy

NOW = datetime.now(UTC)
print("now:", NOW.date().isoformat())

evidence = [
    ResourceEvidence(
        resource_type="s3-bucket", resource_id="demo-bucket", region="us-east-1", tags={}
    )
]
rules = [
    {
        "id": "required-tags",
        "check": "required_tags",
        "severity": "high",
        "required_tags": ["team_owner"],
    }
]

unexpired_policy = {
    "rules": rules,
    "exceptions": [
        {
            "resource_id": "demo-bucket",
            "rule_id": "required-tags",
            "reason": "waiver approved by security",
            "expires": "2026-12-31",
        }
    ],
}
expired_policy = {
    "rules": rules,
    "exceptions": [
        {
            "resource_id": "demo-bucket",
            "rule_id": "required-tags",
            "reason": "waiver approved by security",
            "expires": "2026-01-01",
        }
    ],
}

f_unexpired = evaluate_policy(evidence, unexpired_policy, now=NOW)[0]
f_expired = evaluate_policy(evidence, expired_policy, now=NOW)[0]

print("\nexception expires 2026-12-31 (unexpired):")
print(f"  suppressed={f_unexpired.suppressed} reason={f_unexpired.suppression_reason!r}")
print("\nexception expires 2026-01-01 (expired):")
print(f"  suppressed={f_expired.suppressed} reason={f_expired.suppression_reason!r}")
PYEOF
uv run python /tmp/m24_expiry_demo.py

Expected output

now: 2026-08-05

exception expires 2026-12-31 (unexpired):
  suppressed=True reason='waiver approved by security'

exception expires 2026-01-01 (expired):
  suppressed=False reason=None
This output is point-in-time

now is today's real date, not a fixed value — run this next year and the "unexpired" exception above will itself have expired. The shape stays the same: whichever expires date is still in the future suppresses; whichever has passed does not.

Same resource, same rule, same violation, same reason string — the only thing that changed between the two policies is the expires date, and that alone is what flips suppressed from True to False and clears suppression_reason back to None. Nothing about the exception's row in policy.yaml has to be edited or removed for it to stop working; it simply stops matching the day after its expires date, because _exception_is_active() compares against now on every single call, not once when the exception was written.

3. Evidence, not just a verdict — the finding next to the real API response​

The lesson's require-encryption finding says "not using a customer-managed KMS key," not a bare false. Here is that exact finding sitting next to the raw AWS response it came from, against a real, freshly created Floci bucket.

cat > /tmp/m24_evidence_demo.py << 'PYEOF'
import json

from platformops.awsclient import get_aws_client
from platformops.cloudaudit import (
    ResourceEvidence,
    bucket_uses_kms_encryption,
    evaluate_policy,
)
from platformops.multiregion import list_s3_buckets

client = get_aws_client("s3", region="us-east-1", endpoint_url="http://localhost:4566")

bucket = "platformops-deepdive-demo"
client.create_bucket(Bucket=bucket)

print("--- raw get_bucket_encryption() response ---")
raw = client.get_bucket_encryption(Bucket=bucket)
print(json.dumps(raw["ServerSideEncryptionConfiguration"], indent=2))

print("\n--- bucket_uses_kms_encryption() result ---")
print(bucket_uses_kms_encryption(client, bucket))

records = [r for r in list_s3_buckets(client) if r.resource_id == bucket]
evidence = [
    ResourceEvidence.from_record(
        records[0], encrypted=bucket_uses_kms_encryption(client, bucket)
    )
]
policy = {
    "rules": [{"id": "require-encryption", "check": "require_encryption", "severity": "high"}],
    "exceptions": [],
}
findings = evaluate_policy(evidence, policy)

print("\n--- resulting Finding.evidence ---")
print(findings[0].evidence)

client.delete_bucket(Bucket=bucket)
PYEOF
uv run python /tmp/m24_evidence_demo.py

Expected output

--- raw get_bucket_encryption() response ---
{
  "Rules": [
    {
      "ApplyServerSideEncryptionByDefault": {
        "SSEAlgorithm": "AES256"
      },
      "BucketKeyEnabled": false
    }
  ]
}

--- bucket_uses_kms_encryption() result ---
False

--- resulting Finding.evidence ---
encryption: not using a customer-managed KMS key (AWS-managed SSE-S3 default only)

The raw response is the fact: SSEAlgorithm is AES256, not aws:kms. bucket_uses_kms_encryption() turns that fact into one boolean. evaluate_policy() turns that boolean into a sentence an auditor can act on without re-running any code — "not using a customer-managed KMS key (AWS-managed SSE-S3 default only)" says exactly what was checked and exactly what was found, in a way "encrypted: false" never could, since a bare false here would actually be wrong: the bucket is encrypted, just not with the specific kind of key this policy requires. An auditor who needs to verify a finding independently later has, in the finding itself, enough information to know which raw API call to go re-run — they do not have to trust the verdict, they can check the evidence.
