Designing a High-Quality SKILL.md

Module 16 gave you the main idea: a skill is a recipe card. An agent reads it in full only when a task matches it, not a standing rule every task pays for. Module 16's lab stopped at a planning document. skills/CATALOGUE.md names five candidate skills, but none of them exist as a real SKILL.md file yet. This module writes the first one: service-readiness-review, the skill that walks a service.yaml file through PlatformOps's checks before it ships.

Knowing a skill's two parts (frontmatter, body) is not the same as writing a skill that actually works well. A skill can have the right shape and still fail in practice. It loads for tasks it should not touch, it never loads for the task it was written for, or its steps only make sense to one specific coding agent. This lesson covers the discipline that avoids all three.

1. The runbook analogy​

Every operations team already writes a version of this document. So what do you do when the database fills up? Nobody improvises. They open the runbook for "disk full on the primary database." A good runbook has five parts: a trigger condition that says when to open it, the access or tools you need before you start, numbered steps, a clear description of what "resolved" looks like, and what to do if a step does not work as expected.

A SKILL.md is a runbook written for a coding agent instead of an on-call engineer. The discipline is the same. Only the reader changes:

Runbook partSKILL.md equivalent
Trigger condition ("use this when...")The description field in the frontmatter
Access and tools needed before you startPreconditions
Numbered stepsThe Steps section
What "resolved" looks likeThe Output section
What to do if a step failsFailure handling

An on-call engineer who opens the wrong runbook, or never finds the right one, wastes minutes during an incident. An agent that loads the wrong skill, or never finds the one it needed, makes the same mistake at machine speed, and across every task, not just incidents. The rest of this lesson builds service-readiness-review one runbook part at a time.

2. Trigger descriptions — a misfire vs a miss​

The description field is the only part of a skill an agent reads before deciding whether the current task matches it. Get this wrong and one of two things happens.

A misfire is a skill that loads for a task it should not touch. A vague description like "helps review service files" could match almost any task that mentions "service", including one about a completely different kind of file.

A miss is a skill that never loads for a task it should. The same vague description also fails the opposite way: a request phrased as "is service.yaml ready to deploy?" does not obviously match "helps review service files" either, so the skill sits unused.

A precise description fixes both problems at once, because it states the trigger condition directly, in the reader's own words, instead of describing the skill in general terms:

# Vague — causes both misfires and misses
description: Helps review service files.

# Precise — states when to use it, and when not to
description: >
  Review a PlatformOps service definition file (service*.yaml) for
  readiness before it ships, merges, or deploys. Use this when asked to
  review a service*.yaml file, check whether a service is ready to
  deploy, or look over a change to a service definition before it
  merges. Do not use this for Kubernetes manifests, CI workflow files,
  or any YAML file that is not a PlatformOps service definition.

The precise version names the exact file pattern (service*.yaml), the exact trigger phrase ("use this when..."), and the exact exclusion ("do not use this for..."). Anyone, agent or teammate, reading only this paragraph can decide whether today's task qualifies, without opening the rest of the file. This is the frontmatter for service-readiness-review, and it is the first piece of the worked example this lesson assembles.

3. Structuring the body — five parts, five reasons​

A runbook that only lists steps, with nothing else, fails the first time reality does not match what the writer imagined. The same is true of a skill's body. Each part below exists because of a specific way a review would go wrong without it.

Preconditions. State what has to be true before Step 1 makes sense: a working project, a file that exists and can be read. Skip this, and the agent starts executing steps against a project that is not even set up, and reports a false failure instead of a missing precondition.

## Preconditions

- You are working inside a PlatformOps project: a `pyproject.toml` and
  `src/platformops/` are present, and `uv sync` has already been run.
- The target file exists and you can read it.
- The target file is a service definition, named `service*.yaml`, or
  explicitly identified as one by whoever asked for the review.

Numbered steps. Each step should be one clear action, in order, that leads to the next one. Too few steps and the agent has to guess the missing detail every time; too many and a step gets skipped because the list stopped reading like a procedure. service-readiness-review's steps run uv run platformops validate <path> --json, read the result, and check two things a passing validation can still hide (an empty observability field, a namespace value worth quoting back). Notice what the steps do not do. They never reimplement validate_service() in the skill file. They call the existing command and interpret its result, the same boundary rule Module 16 taught for a skill and a library.

Tools this skill may use. Name exactly which commands and read operations are in scope. Without this, nothing stops the agent from deciding, mid-task, that fixing the file is also part of "reviewing" it, which is a different, riskier task than the one the skill promises.

## Tools this skill may use

- Run `uv run platformops validate <path> --json`.
- Read the target `service*.yaml` file.
- Search within the file for field names and values.

This skill does not write, edit, or delete any file. It only reads and reports.

Output. Describe the exact shape of what the skill produces. Without this, two runs of the same skill can report the same finding in two different formats, and nothing downstream, be it another skill, a script, or a human reading the result, can rely on it looking the same way twice.

Failure handling. State what happens when a step cannot complete: the command is not available, the file is not valid YAML at all, the file cannot be found. Without this, a skill either crashes on the first real-world edge case, or worse, produces a confident-looking report built on a failure it never checked for.

4. An agent-neutral core, with extensions kept separate​

service-readiness-review's steps run a shell command and read a text file. Nothing in that requires one specific coding agent. Claude Code, Codex, and OpenCode can all read a file and run uv run platformops validate. Writing the required Steps, Tools, Output and Failure handling sections in agent-neutral language is what makes the same SKILL.md file usable by whichever agent your team runs, without a rewrite.

Some agents do offer conveniences that others do not, say a TodoWrite tool that turns a numbered list into a visible checklist. Those conveniences belong in a section clearly separated from the required core, never mixed into the steps themselves:

## Optional extensions

The steps above work with any coding agent that can run a shell command
and read a file. Nothing above assumes a specific harness. This
section is for a convenience specific to one agent; skip it entirely
with any other agent.

- **Claude Code only:** if you have the `TodoWrite` tool available, you
  may use it to track Steps 1-7 above as a checklist while you work
  through them. This is a display convenience. It changes nothing
  about what the steps do or what the report contains.

If you remove the "Optional extensions" section entirely, the skill still works, end to end, with any agent. That is the test for whether a convenience belongs there: the skill must not depend on it.

5. A skill's lifecycle​

Putting the pieces together, a skill moves through the same five states every time it is used, whether the task that triggers it comes up once a week or five times a day:

Most of a skill's life is spent in the first box: dormant, costing nothing, the same way most runbooks sit in a binder untouched most days. The description is the only thing standing between "dormant" and "loaded." Get it precise, and the transition happens exactly when it should.

6. The complete skill​

Every section above is a real piece of service-readiness-review. Assembled, it is the actual file this module's lab creates at .claude/skills/service-readiness-review/SKILL.md:

.claude/skills/service-readiness-review/SKILL.md
---
name: service-readiness-review
description: >
  Review a PlatformOps service definition file (service*.yaml) for
  readiness before it ships, merges, or deploys. Runs the project's
  validator, then checks two things a passing validation can still miss:
  empty observability fields and a namespace value worth quoting back to
  the reviewer. Use this when asked to review a service*.yaml file, check
  whether a service is ready to deploy, or look over a change to a service
  definition before it merges. Do not use this for Kubernetes manifests,
  CI workflow files, or any YAML file that is not a PlatformOps service
  definition. Do not use it to edit the file, only to report on it.
---

# Service Readiness Review

## When to use this
## When NOT to use this
## Preconditions
## Steps
## Tools this skill may use
## Output
## Failure handling
## Optional extensions

The lab has you write the full version of every section, including the numbered Steps this outline only names. Once it is in place, the lab tests it against two coding agents on the same test file, with no changes to the skill file between the two runs. That is the actual proof that "agent-neutral core" is not just a claim in the frontmatter.

Common pitfalls​

Common pitfalls
  • A trigger description that describes the skill instead of stating when to use it. "Reviews service files" is a description of the skill; "use this when asked to review a service*.yaml file" is a trigger condition. Only the second one lets an agent match a task against it without reading the rest of the file.
  • Steps that assume one specific agent. A step that says "use the Read tool" or references a tool-call syntax specific to one harness breaks the moment a different agent reads the same file. Say what to do ("read the target file"), not which button to press.
  • A step that is secretly code. If a step reads more like a program than an instruction, several lines of logic pasted into the Steps section, that logic belongs in src/platformops/ or scripts/, called by name, the same boundary rule Module 16 already taught for a skill and a library.
  • Missing failure handling. A skill that only describes the happy path produces a confident report even when a step silently failed: a file that could not be read, a command that was not on PATH. State what happens when a step does not complete, not just what happens when it does.
