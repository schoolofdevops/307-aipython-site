Deep Dive — Measuring a Skill Instead of Guessing About It

The lab wrote service-readiness-review, tested it against two coding agents on the same file, and shipped it as v1.2.1. That proves the skill works once. This page turns the lesson's three claims -- a precise trigger costs little to scan, a review-shaped skill wants 4-8 steps, and an agent-neutral core is a checkable property, not a feeling -- into commands you can run against the real file and get a number back. The same three checks apply the next time you write a skill and want to know, before you ship it, whether it actually meets the bar this module set.

Where this picks up

You need ~/platformops at v1.2.1, with .claude/skills/service-readiness-review/SKILL.md in place from the lab. Every example on this page runs in its own scratch copy -- nothing here touches your real project:

rm -rf /tmp/m17-dd-scratch
cp -r ~/platformops /tmp/m17-dd-scratch
cd /tmp/m17-dd-scratch
rm -rf .venv
uv sync

The rm -rf .venv && uv sync step is needed because copying a uv-managed virtual environment breaks the internal symlinks that point at your Python install. Removing the copy and rebuilding it takes a few seconds and gives you a working environment. The skill file itself came along with the copy, unchanged -- this page only reads it.

Re-running any command on this page is safe.

1 — What a trigger description costs, against what the whole skill costs​

The lesson's rule is that a precise description states a trigger condition in a sentence or two. Put a number on "a sentence or two," the same way Module 16's Deep Dive put a number on progressive disclosure:

cd /tmp/m17-dd-scratch
F=.claude/skills/service-readiness-review/SKILL.md
wc -w "$F"

Expected output

     833 .claude/skills/service-readiness-review/SKILL.md

Now pull out only the frontmatter -- the part every task pays to scan, whether service-readiness-review ends up relevant to that task or not:

cd /tmp/m17-dd-scratch
F=.claude/skills/service-readiness-review/SKILL.md
sed -n '/^---$/,/^---$/p' "$F" | wc -w

Expected output

     113

The frontmatter comes in well under a fifth of the full file's word count. That ratio is the actual number behind a rule of thumb worth keeping: if a trigger description runs past roughly 20% of the skill's total word count, it has stopped stating a trigger condition and started re-explaining the procedure it is supposed to only point at. A description that long defeats its own purpose -- the whole reason progressive disclosure works is that scanning the description is supposed to be cheap. Check the ratio the same way any time you write a new skill: wc -w the whole file, wc -w the frontmatter, and see whether the second number stays a small fraction of the first.

Confirm the trigger phrase itself is actually there, not just short:

cd /tmp/m17-dd-scratch
F=.claude/skills/service-readiness-review/SKILL.md
grep -ci 'use this when' "$F"

Expected output

1

A short description with no "use this when" phrasing is not automatically a good one -- it is just a short, vague one. The ratio check and the trigger-phrase check answer two different questions: the ratio asks whether the description stayed a description; the phrase check asks whether it actually said when to use the skill at all. A precise trigger needs to pass both.

2 — Step granularity, checked against the skill you actually wrote​

The lesson names a sweet spot for a review-shaped skill: 4 to 8 numbered steps. Too few, and the agent fills in a missing detail differently every time it runs the skill. Too many, and a step gets skipped somewhere in the middle, because the list stopped reading like a short procedure and started reading like documentation. Check where service-readiness-review actually lands:

cd /tmp/m17-dd-scratch
F=.claude/skills/service-readiness-review/SKILL.md
grep -cE '^[0-9]+\. ' "$F"

Expected output

7

The count lands inside the 4-8 range -- this is not a coincidence, it is what the lesson's Step 3 walked through building: confirm the file matches the pattern, read the fields up front, run validate, branch on the exit code, check the two things a pass can still hide, and write the report. Seven actions, each one a single, checkable move. If you ever find yourself writing a ninth or tenth step for a skill this size, that is the signal to look for two steps that could collapse into one -- or a second skill hiding inside the first.

3 — Proving the core is agent-neutral, not just claiming it​

The lesson's fourth objective -- an agent-neutral core with documented optional extensions -- is a claim you can check mechanically, the same way Module 16 checked for the two boundary-rule anti-patterns. Split the file at the ## Optional extensions heading and search each half separately for agent-specific language:

The lab already showed this working end to end with two real agents. This section checks why it worked -- by confirming the required core never mentions one agent by name, the same way you would check a shipping label for a country-specific part number before assuming a package could go anywhere:

cd /tmp/m17-dd-scratch
F=.claude/skills/service-readiness-review/SKILL.md
sed -n '1,/^## Optional extensions/p' "$F" > /tmp/m17-core.txt
grep -ci 'claude' /tmp/m17-core.txt

Expected output

0

Zero. Every section a coding agent needs to actually run the review -- Steps, Tools this skill may use, Output, Failure handling -- never names one agent by product name. Now check the other half:

cd /tmp/m17-dd-scratch
F=.claude/skills/service-readiness-review/SKILL.md
sed -n '/^## Optional extensions/,$p' "$F" > /tmp/m17-opt.txt
grep -ci 'claude' /tmp/m17-opt.txt
rm -f /tmp/m17-core.txt /tmp/m17-opt.txt

Expected output

1

One mention, and it is inside "Optional extensions," introduced with "Claude Code only" so a reader on any other agent knows to skip straight past it. This is the actual, runnable version of what "agent-neutral core, with documented optional extensions" means: not a section title, a result you can grep for. The same two-part check works on any skill you write next -- split it at wherever the agent-specific section starts, and confirm the required part above that line comes back with a zero.

Teardown​

rm -rf /tmp/m17-dd-scratch

This removes only this page's scratch copy. Nothing on this page touched ~/platformops -- .claude/skills/service-readiness-review/SKILL.md, the v1.2.1 version bump, and the CHANGELOG.md entry from the lab are the only real additions this module makes to your project, and they are already there before this page starts.

Where you will use this
  • A description's word count, checked against the full skill's word count, catches a trigger that has quietly turned into a re-explanation of the procedure. Use it when: you are reviewing a skill someone else on your team wrote and its description reads longer than a sentence or two -- run the ratio before deciding whether to trim it.
  • 4-8 numbered steps is where a review-shaped skill stays reliable -- fewer and the agent improvises, more and a step gets skipped. Use it when: a skill's Steps section keeps growing every time someone finds a new edge case -- that is the moment to look for two steps that should collapse into one, instead of adding a ninth.
  • Agent-neutral portability is a grep away, not a guess -- split the file at the agent-specific section and confirm the required core comes back with zero hits. Use it when: you are about to hand a skill to a team that standardizes on a different coding agent than you do, and you want proof it will work before the first person on that team tries it.
  • A single agent-specific mention, walled off under a clearly named "Optional extensions" heading, does not break portability -- it is what keeping it separate is for. Use it when: a teammate's editor-specific shortcut sneaks into a skill's required Steps during a quick edit -- move it under Optional extensions instead of removing the convenience entirely.
