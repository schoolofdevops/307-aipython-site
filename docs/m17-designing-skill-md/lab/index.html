Lab — Designing a High-Quality SKILL.md

This lab has two phases. In Phase 1, you write service-readiness-review by hand -- the first real SKILL.md file for PlatformOps, turning the catalogue entry from Module 16 into an actual skill. In Phase 2, you test it: you create a service definition with two deliberate problems, then ask two different coding agents to use the skill on it, with no changes to the skill file between the two runs. The module closes by bumping platformops to v1.2.1 -- the Service Review Skill release.

Before you start

You need ~/platformops at v1.2, with CLAUDE.md, scripts/verify.sh, and skills/CATALOGUE.md in place from Modules 15 and 16, and the labs repo cloned at ~/307-aipython-labs.

cd ~/platformops
git log --oneline -1

Expected output

a928763 M16: Agent Skills: The Correct Mental Model — lesson, lab, quiz, deep dive, decks, narration

Your commit hash and message will differ; what matters is that it references v1.2 or Module 16.

Phase 1 — Write the skill by hand​

Step 1 — Create the skill file​

cd ~/platformops
mkdir -p .claude/skills/service-readiness-review
cat > .claude/skills/service-readiness-review/SKILL.md << 'EOF'
---
name: service-readiness-review
description: >
  Review a PlatformOps service definition file (service*.yaml) for
  readiness before it ships, merges, or deploys. Runs the project's
  validator, then checks two things a passing validation can still miss:
  empty observability fields and a namespace value worth quoting back to
  the reviewer. Use this when asked to review a service*.yaml file, check
  whether a service is ready to deploy, or look over a change to a service
  definition before it merges. Do not use this for Kubernetes manifests,
  CI workflow files, or any YAML file that is not a PlatformOps service
  definition -- and do not use it to edit the file, only to report on it.
---

# Service Readiness Review

## When to use this

Use this skill when someone asks you to review a `service*.yaml` file, decide whether a
service is ready to deploy, or check a change to a service definition before it merges. The
trigger is the request, not the file extension alone -- a `.yaml` file that is not a service
definition does not qualify.

## When NOT to use this

- Not for Kubernetes manifests, Helm values files, or CI workflow YAML -- these are not
  PlatformOps service definitions, even though they are also YAML.
- Not as a substitute for `scripts/verify.sh` before a code change. That script gates changes
  to `src/platformops/`; this skill reviews one service definition file.
- Not to fix or edit the file. This skill only reports what it finds -- it does not write to
  the reviewed file or to any other file.

## Preconditions

- You are working inside a PlatformOps project: a `pyproject.toml` and `src/platformops/` are
  present, and `uv sync` has already been run.
- The target file exists and you can read it.
- The target file is a service definition -- named `service*.yaml`, or explicitly identified
  as one by whoever asked for the review.

## Steps

1. Confirm the target file matches `service*.yaml` (or was explicitly named as a service
   definition) and note its path.
2. Read the file and check which top-level fields are present: `name`, `repository`,
   `environment`, `team_owner`, `kubernetes_namespace`, `deployment_name`, `aws_account`,
   `region`, and `observability` with its `dashboard_url` and `alert_channel`. This first pass
   is so you already know what to expect before the formal check runs.
3. From the project root, run `uv run platformops validate <path> --json` and capture the full
   output and exit code.
4. If the command exits non-zero, read the `errors` list in the JSON output. Each entry names
   the field (`loc`) and the problem (`msg`). Skip to Step 7 and report these as the reason the
   file is not ready.
5. If the command exits 0, the file passed schema validation. Still check
   `observability.dashboard_url` and `observability.alert_channel` for yourself -- the schema
   accepts an empty string for either one, so a passing validation can hide a missing on-call
   channel.
6. Also quote back the exact `kubernetes_namespace` value in your report, even on a pass. The
   validator has already rejected an invalid one; restating the value that was checked makes
   the report useful to a reviewer who has not opened the file.
7. Write the readiness report in the format described under Output, whether the file passed or
   failed.

## Tools this skill may use

- Run `uv run platformops validate <path> --json`.
- Read the target `service*.yaml` file.
- Search within the file for field names and values.

This skill does not write, edit, or delete any file. It only reads and reports.

## Output

A short readiness report, in this shape:

```
Service Readiness Review -- <file>

- Validation: PASS | FAIL
- Problems found: <one per line, field + message -- or "none">
- Observability: dashboard_url set (yes/no), alert_channel set (yes/no)
- Namespace checked: <the exact kubernetes_namespace value>
- Recommendation: ready to ship | fix required before shipping
```

## Failure handling

- If `uv run platformops validate` cannot run at all (wrong directory, `uv` not found, project
  not synced), stop and report the environment problem. Do not guess at the file's validity
  from reading the YAML alone.
- If the file is not valid YAML, `validate` reports a parse error and exits non-zero. Report
  this as "cannot be reviewed" -- a parse failure is not the same as a schema failure, and the
  report should say which one happened.
- If the target file cannot be found, stop before Step 3 and report the missing precondition
  instead of reviewing a different file.

## Optional extensions

The steps above work with any coding agent that can run a shell command and read a file --
nothing above assumes a specific harness. This section is for a convenience specific to one
agent; skip it entirely with any other agent.

- **Claude Code only:** if you have the `TodoWrite` tool available, you may use it to track
  Steps 1-7 above as a checklist while you work through them. This is a display convenience --
  it changes nothing about what the steps do or what the report contains.
EOF

No output from this command — it writes the file silently. The next step confirms it landed correctly.

Step 2 — Confirm the skill's structure​

The skill's shape matters as much as its content. Check that all eight sections are present, that the trigger phrase from the lesson is really there, that the step count lands in the 4-8 range the lesson recommends, and that no step is secretly a Python program:

cd ~/platformops
grep -c '^## ' .claude/skills/service-readiness-review/SKILL.md

Expected output

8
grep -cE '^[0-9]+\. ' .claude/skills/service-readiness-review/SKILL.md

Expected output

7

You should see 7 -- inside the 4-8 range the lesson recommends for a review-shaped skill.

grep -ci 'use this when' .claude/skills/service-readiness-review/SKILL.md

Expected output

1
grep -c '```python' .claude/skills/service-readiness-review/SKILL.md

Expected output

0

You should see 0 -- this skill points at uv run platformops validate, it does not reimplement it.

Phase 2 — Test the skill with two coding agents​

Step 3 — Create a test service definition with two deliberate problems​

Use a throwaway filename -- do not overwrite service-bad.yaml, which the earlier modules already use:

cd ~/platformops
cat > test-service.yaml << 'EOF'
name: checkout-api
repository: github.com/example/checkout-api
environment: prod
team_owner: payments-team
kubernetes_namespace: Checkout-API
aws_account: "111122223333"
region: us-east-1
observability:
  dashboard_url: https://grafana.example.com/d/checkout-api
  alert_channel: "#checkout-alerts"
EOF

This file has two problems on purpose: kubernetes_namespace contains uppercase letters (Checkout-API), which breaks the RFC-1123-style pattern ServiceDefinition enforces, and deployment_name is missing entirely.

Step 4 — Confirm the problems manually, before asking any agent​

Run the same command the skill's Steps 3-4 describe, so you know what a correct review should find before you delegate the review itself:

cd ~/platformops
uv run platformops validate test-service.yaml --json

Expected output

WARNING platformops.cli: test-service.yaml failed validation: 2 field(s)
{
  "status": "error",
  "errors": [
    {
      "type": "string_pattern_mismatch",
      "loc": [
        "kubernetes_namespace"
      ],
      "msg": "String should match pattern '^[a-z0-9]([-a-z0-9]*[a-z0-9])?$'",
      "input": "Checkout-API",
      "ctx": {
        "pattern": "^[a-z0-9]([-a-z0-9]*[a-z0-9])?$"
      },
      "url": "https://errors.pydantic.dev/2.13/v/string_pattern_mismatch"
    },
    {
      "type": "missing",
      "loc": [
        "deployment_name"
      ],
      "msg": "Field required",
      "input": {
        "name": "checkout-api",
        "repository": "github.com/example/checkout-api",
        "environment": "prod",
        "team_owner": "payments-team",
        "kubernetes_namespace": "Checkout-API",
        "aws_account": "111122223333",
        "region": "us-east-1",
        "observability": {
          "dashboard_url": "https://grafana.example.com/d/checkout-api",
          "alert_channel": "#checkout-alerts"
        }
      },
      "url": "https://errors.pydantic.dev/2.13/v/missing"
    }

Exit code 1. Two problems: the namespace pattern, and the missing deployment_name. This is the answer key you compare both agents' reviews against.

Step 5 — Invoke the skill explicitly with Claude Code​

cd ~/platformops
claude -p "Use the service-readiness-review skill to review test-service.yaml" --permission-mode bypassPermissions

Expected output (yours will differ in wording — what matters is the shape)

Example output from one real run
Service Readiness Review -- test-service.yaml

- Validation: FAIL
- Problems found:
  - kubernetes_namespace: "Checkout-API" does not match pattern `^[a-z0-9]([-a-z0-9]*[a-z0-9])?$`
  - deployment_name: missing, required field
- Observability: dashboard_url set (yes), alert_channel set (yes)
- Namespace checked: `Checkout-API`
- Recommendation: fix required before shipping

Claude Code matches "service-readiness-review skill" against the name in your skill's frontmatter and loads .claude/skills/service-readiness-review/SKILL.md in full. The exact wording of the report will differ from the example above — coding agents do not produce identical text on every run. What matters is that the report names both problems from Step 4 (the namespace pattern mismatch and the missing deployment_name) and follows the Output section's shape: a PASS/FAIL line, the problems found, the observability check, the namespace value, and a recommendation.

Step 6 — Invoke the same skill, unmodified, with Codex​

Codex does not use Claude Code's .claude/skills/ discovery mechanism, so point it at the file directly. This is still an explicit invocation of the same skill, not a different procedure -- the file codex reads is byte-for-byte the one you wrote in Step 1:

cd ~/platformops
codex exec --sandbox workspace-write "Read and follow the instructions in .claude/skills/service-readiness-review/SKILL.md exactly to review test-service.yaml. Report your findings in the Output format that file describes."

Expected output (yours will differ in wording — what matters is the shape)

Example output from one real run
Service Readiness Review -- test-service.yaml

- Validation: FAIL
- Problems found:
  kubernetes_namespace: String should match pattern `'^[a-z0-9]([-a-z0-9]*[a-z0-9])?$'`
  deployment_name: Field required
- Observability: dashboard_url set yes, alert_channel set yes
- Namespace checked: Checkout-API
- Recommendation: fix required before shipping

Step 7 — Compare what both agents found​

Read both reports side by side. They were produced by two different coding agents, but the skill file they followed did not change between Step 5 and Step 6. You should see:

  • Both name the same two problems -- the kubernetes_namespace pattern mismatch and the missing deployment_name.
  • Both reports follow the same Output shape from the skill: a PASS/FAIL line, a problems list, an observability check, the namespace value, and a recommendation.
  • Neither report needed you to explain the RFC-1123 pattern, the project's directory layout, or the meaning of --json -- the skill file carried all of that.

This is what "agent-neutral core" means in practice: the steps, not the agent, decided what got checked and how the result was reported.

Step 8 — Bump the version and record the release​

service-readiness-review is proven working against two agents. Record it as a release, the same way Module 15 recorded the harness.

Open CHANGELOG.md. Move whatever is sitting under ## [Unreleased] into a new release section, and add an entry for the skill itself:

CHANGELOG.md
## [Unreleased]

## [1.2.1] - Service Review Skill
### Added
- `.claude/skills/service-readiness-review/SKILL.md` — a skill that runs
  `platformops validate` against a service definition file and reports its
  readiness, including two checks a passing validation alone does not
  cover: an empty observability field, and the exact `kubernetes_namespace`
  value that was checked.
- `platformops version --json` — outputs version and Python runtime as JSON.

If your [Unreleased] section already had a different entry in it (from work you did after Module 15), keep that entry too -- move it into [1.2.1] rather than deleting it. Keep a Changelog's rule is that nothing sits under [Unreleased] once it ships in a release.

Open pyproject.toml and change the version line:

version = "1.2.1"
cd ~/platformops
uv sync
uv run platformops version

Expected output

platformops 1.2.1
cd ~/platformops
uv run pytest -q

Expected output

139 passed in 1.37s

Your exact timing will differ; the count should not.

rm -f test-service.yaml
git add -A
git commit -m "platformops v1.2.1 -- Service Review Skill"
git tag v1.2.1

.claude/skills/service-readiness-review/SKILL.md and the version bump are now a permanent part of your project.

Troubleshooting
  • grep -c '^## ' reports something other than 8. A section heading was pasted with the wrong number of # characters, or a line inside the Output template's code fence was miscounted -- check that the fenced report template does not itself start with ## .
  • claude -p ... never mentions service-readiness-review or does not produce a readiness report. Confirm the file is really at .claude/skills/service-readiness-review/SKILL.md (not .claude/skill/... or missing the .md extension) and that its description still contains the trigger phrase from Step 1 -- a typo there is the most common reason a skill never loads. Also confirm you used --permission-mode bypassPermissions -- a weaker mode like acceptEdits does not authorize the shell command the skill needs to run the validator.
  • codex exec reports it cannot find .claude/skills/service-readiness-review/SKILL.md. Run the command from inside ~/platformops -- codex exec resolves the path you gave it relative to your current directory, the same as any other command in this lab.
  • The two agents' reports name different problems. Re-run Step 4's manual validate command -- if it still reports the same two errors, the skill file is fine and the disagreement is in how one agent read or summarized the result; re-read that agent's report against the skill's Output section before assuming the skill itself is at fault.
  • uv run platformops version still reports 1.2.0. uv sync needs to run after you edit pyproject.toml -- the installed package's version comes from the last uv sync, not from the file on disk.

Teardown​

test-service.yaml was already removed in Step 8, before the commit -- it does not appear in the project's git history. .claude/skills/service-readiness-review/SKILL.md, the v1.2.1 version bump, and the CHANGELOG.md entry all stay -- they are permanent additions to the project, and later modules build on this skill existing.

If you get stuck

If your ~/platformops diverges from what this lab expects and you cannot recover it, compare against the frozen checkpoint for this module in your labs clone: ~/307-aipython-labs/labs/checkpoints/v1.2.1/.... Do not compare against labs/platformops inside that clone -- that copy keeps moving as later modules add to it, and it will not match this module's expected end state.
