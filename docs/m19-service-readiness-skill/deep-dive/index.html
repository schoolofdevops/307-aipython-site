Deep Dive — Project: PlatformOps Service Readiness Skill

The lab proved scripts/service_readiness.py works — the tests pass, two coding agents relay matching reports, and overall_confidence never claims more than it should. This page proves why that holds, in three places a reviewer would actually check before trusting this report in a real pipeline: the exact arithmetic behind overall_confidence (not a hand-wave, a function you can call with any input), the mechanical proof that the orchestrator never reimplements what it calls, and the mechanical proof that nothing in this skill ever writes anywhere. These are the questions a security-minded reviewer, or a teammate deciding whether to trust this report on a release gate, asks before wiring it into anything that matters.

Where this picks up

This page assumes ~/platformops at v1.4.0, with scripts/service_readiness.py and .claude/skills/platformops-service-readiness/SKILL.md in place from the lab. If the lab's Teardown already removed test-service.yaml, that is fine — nothing here depends on it. Re-run this to recreate it if you want a file to point commands at; it is safe to run again:

cd ~/platformops
cp service-bad.yaml test-service.yaml

1 — Confidence as a function of coverage, not vibes​

compute_confidence() takes three plain values — how many sections came back known, how many sections exist in total, and whether anything failed — and returns one of three strings. Nothing about it depends on wording, phrasing, or which agent is reading the report. Call it directly with every possible known-count, and the table below is what actually comes back — not a description of the function, its real output:

cd ~/platformops
uv run python3 -c "
import importlib.util, sys
spec = importlib.util.spec_from_file_location('service_readiness', 'scripts/service_readiness.py')
m = importlib.util.module_from_spec(spec)
sys.modules['service_readiness'] = m
spec.loader.exec_module(m)
for known in range(0, 6):
    print(known, '/5 known ->', m.compute_confidence(known, 5, has_failure=False))
print('with a failure, 5/5 known ->', m.compute_confidence(5, 5, has_failure=True))
"

Expected output

0 /5 known -> low
1 /5 known -> low
2 /5 known -> medium
3 /5 known -> medium
4 /5 known -> high
5 /5 known -> high
with a failure, 5/5 known -> low

Read the middle rows carefully: 2/5 and 3/5 both land on "medium" — the same tier. 4/5 and 5/5 both land on "high". Today, cloud and kubernetes are pinned to "unknown" forever, which caps the known count at 3 no matter what config, source control and CI report. 3/5 is 0.6, and 0.6 falls in the "medium" band (≥ 0.4), never the "high" band (≥ 0.8). The last line shows the other half of the rule: even a perfect 5/5 known count drops straight to "low" the moment has_failure is True. A concrete failure always outranks a good ratio — there is no number of passing sections that buys back a real problem.

This is also a pure function in the strict sense: same inputs, same output, every time, with nothing but arithmetic between them. Run the full report twice against an unchanged file and the output is byte-identical — use cmp, not diff, to prove it, since a shell alias or a misconfigured hook can make plain diff report two different files as identical without you noticing:

cd ~/platformops
uv run python scripts/service_readiness.py service.yaml --repo octocat/Hello-World > /tmp/m19-run1.json
uv run python scripts/service_readiness.py service.yaml --repo octocat/Hello-World > /tmp/m19-run2.json
cmp /tmp/m19-run1.json /tmp/m19-run2.json && echo identical || echo differs
rm -f /tmp/m19-run1.json /tmp/m19-run2.json

Expected output

identical

That determinism only holds between two runs against the same underlying state — a second run minutes later, after a commit or a new CI run landed, can legitimately differ. What cmp proves here is narrower and more useful: given the exact same evidence, the report is not rolling any dice.

2 — Composing evidence adapters, proven, not claimed​

Picture an old telephone switchboard. The operator does not generate the conversation on either end of the line — they only plug one existing line into another and let the two parties who already know how to talk to each other do the talking. service_readiness.py is that operator. It never runs git itself, never opens a socket to GitHub itself, and never parses YAML itself — it plugs into three lines that already exist (platformops.config, platformops.local_ops, platformops.httpclient) and relays what comes back.

That claim is checkable, not just stated. Grep the orchestrator for the raw imports the three underlying libraries need, and compare it against the adapters that actually do the low-level work:

cd ~/platformops
grep -c '^import subprocess' scripts/service_readiness.py; true
grep -c '^import httpx' scripts/service_readiness.py; true
grep -c '^import yaml' scripts/service_readiness.py; true

Expected output

0
0
0

Zero, zero, zero. Now the contrast — the same three imports, present exactly where the real work happens:

cd ~/platformops
grep -c 'import subprocess' src/platformops/local_ops.py
grep -c 'import httpx' src/platformops/httpclient.py
grep -c 'import yaml' src/platformops/config.py

Expected output

1
1
1

local_ops.py runs git through subprocess. httpclient.py talks to GitHub through httpx. config.py parses the file through yaml. service_readiness.py touches none of the three directly — its only connection to any of them is four from platformops... import lines:

cd ~/platformops
grep -c '^from platformops' scripts/service_readiness.py

Expected output

4

At work, this is the difference between a script you can trust and one you cannot. If a bug turns up in how git_status() reads a working tree, it gets fixed once, in local_ops.py, and every caller — service_readiness.py, any future script, the module's own tests — picks up the fix automatically. A script that reimplemented git status --porcelain parsing on its own would need that same fix applied a second time, somewhere a reviewer has to remember to look.

3 — What "read-only" means, and how it is enforced​

A museum tour guide narrates every exhibit in detail — history, provenance, what to notice — but never touches, rearranges, or removes anything on display. The value of that guide depends entirely on the visitor trusting that boundary holds. platformops-service-readiness makes the same promise about the service it reports on: it can say anything about what it observed, but it never changes what it observed.

That promise is checkable the same way the composition claim was — by grepping for the absence of the operations that would break it:

cd ~/platformops
grep -c "open(.*'w" scripts/service_readiness.py; true
grep -c 'git commit\|git push\|\.write_text(\|write_resolved_config' scripts/service_readiness.py; true

Expected output

0
0

Zero write-mode open() calls, zero commit/push/write calls of any kind. The same check against the skill file itself:

cd ~/platformops
grep -c "open(.*'w" .claude/skills/platformops-service-readiness/SKILL.md; true
grep -c 'git commit' .claude/skills/platformops-service-readiness/SKILL.md; true
grep -c 'git push' .claude/skills/platformops-service-readiness/SKILL.md; true

Expected output

0
0
0

And the skill states the same promise in plain language a reviewer can read without running anything:

cd ~/platformops
grep -c 'This skill does not write, edit, or delete any file' .claude/skills/platformops-service-readiness/SKILL.md

Expected output

1

Contrast this with platformops.config.write_resolved_config() — a real function in this toolkit, used by Module 6's CLI to write a resolved config back to disk. It exists, it is tested, and service_readiness.py could technically import it. It never does — grepping for it above is exactly how you would catch it if a future change accidentally introduced that import. "Read-only" here is not a comment or a docstring claim; it is an absence you can verify with the same two commands every time, on every future version of this script.

Where these three checks come from​

Teardown​

cd ~/platformops
rm -f test-service.yaml

Nothing else on this page adds anything permanent to the project — scripts/service_readiness.py, tests/test_service_readiness.py, and .claude/skills/platformops-service-readiness/SKILL.md are unchanged from where the lab left them.

Where you will use this
  • compute_confidence() is a pure function you can unit-test with plain numbers, independent of any real evidence source. Use it when: a teammate proposes changing the "high" threshold or adding a fourth confidence tier — you can verify the new behavior by calling the function directly with every known-count from 0 to N, the same table this page produced, before it ever touches a real report.
  • Grepping for the absence of raw subprocess/httpx/yaml imports is how you catch a script quietly turning into a second implementation. Use it when: reviewing a pull request that touches an orchestrator script like this one — a new raw import of a low-level library is the single clearest signal that logic is being duplicated instead of reused.
  • Grepping for the absence of write-mode open(), git commit, and git push is how a "read-only" claim in a skill or script description gets verified instead of just trusted. Use it when: you are asked to approve a coding-agent skill for use against a production repository or service — check what it can write before you check what it reports, because a report you can trust is only half the story if the tool producing it can also change what it is reporting on.
  • cmp, not diff, is the safe way to prove two command outputs are byte-identical. Use it when: verifying a script's determinism, or comparing two agents' raw output files — a shell alias or hook rewriting diff's behavior is a real failure mode this course has hit before, and cmp has no equivalent shortcut to misconfigure.
