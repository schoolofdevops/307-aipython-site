Deep Dive — What Actually Stops the Inspector From Writing

The lab proved workload-inspect reports a Deployment's real health across four scenarios. It never proved why you can hand this tool to anyone without worrying it might change something. This page proves that, mechanically: what request actually leaves your laptop when the Python client runs, what stops this module's code from ever calling a write method even by accident, what stops a compromised or buggy version of this code from writing even if the grep proof somehow stopped being true, and what actually separates a one-shot script like this one from a controller that never stops watching.

Where this picks up

This page builds its own cluster, separate from the lab's (the lab's Teardown already deleted platformops-m28). Re-running this block is safe.

cd ~/platformops
uv run platformops version
kind create cluster --name platformops-m28-dd
kubectl wait --for=condition=Ready node --all --timeout=90s
kubectl apply -f k8s/payments-namespace.yaml
kubectl apply -f k8s/payments-healthy.yaml
kubectl rollout status deployment/payments -n payments --timeout=60s

The kubectl wait --for=condition=Ready node line matters: applying the Deployment before the node finishes reporting Ready can produce a stray FailedScheduling warning event from that few-second window, which would otherwise show up as noise in Section 3's clean read-only inspection below. kind create cluster returns as soon as the control plane answers requests, not once the node is fully Ready — this line closes that gap explicitly instead of relying on timing.

1. The grep proof — read the code the way the Deep Dive's whole argument depends on​

cloudaudit.py's Deep Dive (Module 24) proved zero write-mode AWS calls the same way: grep the module, not the docstring's own claims about itself.

grep -nE "\.(create|patch|delete|replace)_" src/platformops/kubernetes_inspect.py
echo "grep exit code: $?"

Expected output

grep exit code: 1

Exit code 1 from grep means zero matches — not one write-verb method call anywhere in this file. A plain grep -c "create_\|patch_\|delete_\|replace_" (no leading dot) would actually find matches here — the module's own docstring uses those words in prose, explaining the very discipline this proof demonstrates. Anchoring the pattern on a leading . (a method call on a client object, apps_client.delete_...) is what makes the grep a real proof instead of a false positive against the module's own comments.

2. What request actually leaves your laptop​

kubectl and this module's Python code both end up as an HTTP client, and both hit the identical API surface. kubectl get --raw lets you see the raw response with no client-side formatting at all:

kubectl get --raw /apis/apps/v1/namespaces/payments/deployments/payments | python3 -m json.tool | head -8

Expected output

{
    "kind": "Deployment",
    "apiVersion": "apps/v1",
    "metadata": {
        "name": "payments",
        "namespace": "payments",
        "uid": "08d14581-eb9e-4e2c-b33c-0526b864f461",
        "resourceVersion": "3154",

Now turn on the Python client's own wire-level debug logging and make the exact call inspect_workload() makes internally:

uv run python3 - <<'EOF'
from kubernetes import client, config

config.load_kube_config()
c = client.Configuration.get_default_copy()
c.debug = True
client.Configuration.set_default(c)

apps = client.AppsV1Api()
apps.read_namespaced_deployment(name="payments", namespace="payments")
EOF

Expected output (trimmed to the request/response lines that matter)

send: b'GET /apis/apps/v1/namespaces/payments/deployments/payments HTTP/1.1\r\nHost: 127.0.0.1:62285\r\nAccept-Encoding: identity\r\nAccept: application/json\r\nUser-Agent: OpenAPI-Generator/36.0.3/python\r\nContent-Type: application/json\r\n\r\n'
reply: 'HTTP/1.1 200 OK\r\n'

Same path, /apis/apps/v1/namespaces/payments/deployments/payments, as the kubectl get --raw call above. The kubernetes Python package is generated (User-Agent: OpenAPI-Generator/36.0.3/python) straight from Kubernetes's own published OpenAPI schema — read_namespaced_deployment() is not a special programmatic shortcut into the cluster. It is the same plain GET any HTTP client could send, with the same bearer token or client certificate authenticating it that your kubeconfig already carries. This is exactly why a read-only inspector needs no special integration blessed by the platform team to exist — anyone who can already run kubectl get deployments has everything needed to write this module's equivalent themselves.

3. Two independent locks, not one​

A grep proof is strong evidence about this file, today. It says nothing about a future change, a bug, or a dependency that got compromised and tried to sneak in a write call. Production defense does not rely on one team member reading source code carefully forever — it puts a second lock at the identity level, enforced by the API server itself, regardless of what the code tries to do.

This page writes its own manifest, k8s/payments-readonly-rbac.yaml — a ServiceAccount scoped to exactly get/list/watch on Deployments, Pods and Events, in the payments namespace only, nothing else:

cat > k8s/payments-readonly-rbac.yaml << 'EOF'
# A least-privilege identity for the workload inspector: get/list/watch on
# exactly the three object kinds it reads (deployments, pods, events) in
# exactly one namespace -- nothing else. This is the identity a real
# monitoring or on-call tool should run as: it can never create, patch,
# delete or replace anything, even if a bug or a compromised dependency
# tried to make it. See below for a live proof that even a deliberate
# write attempt with this identity is refused by the API server itself,
# not just by this module's own code.
apiVersion: v1
kind: ServiceAccount
metadata:
  name: payments-inspector
  namespace: payments
---
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: payments-inspector-role
  namespace: payments
rules:
  - apiGroups: ["apps"]
    resources: ["deployments"]
    verbs: ["get", "list", "watch"]
  - apiGroups: [""]
    resources: ["pods", "events"]
    verbs: ["get", "list", "watch"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: payments-inspector-binding
  namespace: payments
subjects:
  - kind: ServiceAccount
    name: payments-inspector
    namespace: payments
roleRef:
  kind: Role
  name: payments-inspector-role
  apiGroup: rbac.authorization.k8s.io
EOF

Apply it and check what that identity can and cannot do, using kubectl auth can-i, which asks the API server's own authorization layer the question directly instead of guessing from the Role's YAML:

kubectl apply -f k8s/payments-readonly-rbac.yaml
kubectl auth can-i list pods -n payments --as=system:serviceaccount:payments:payments-inspector
kubectl auth can-i list deployments.apps -n payments --as=system:serviceaccount:payments:payments-inspector
kubectl auth can-i list events -n payments --as=system:serviceaccount:payments:payments-inspector
kubectl auth can-i delete pods -n payments --as=system:serviceaccount:payments:payments-inspector
kubectl auth can-i patch deployments.apps -n payments --as=system:serviceaccount:payments:payments-inspector
kubectl auth can-i list secrets -n payments --as=system:serviceaccount:payments:payments-inspector
kubectl auth can-i list pods -n default --as=system:serviceaccount:payments:payments-inspector

get/list/watch on the three object kinds this module reads: yes. Every mutation (delete pods, patch deployments), reading a Secret this Role was never granted, and even listing Pods in a different namespace: all no. This is not workload-inspect's own code refusing to try — it is the API server itself, checking a Role that was never granted a write verb in the first place. kubectl auth can-i is a real request against the same authorization path every other request goes through, not a static YAML read.

can-i answers "would this be allowed." The next command proves it with a real attempt, using the Python client directly, not kubectl, so this is unmistakably the same code path this module's own inspector runs through:

TOKEN=$(kubectl create token payments-inspector -n payments --duration=1h)
SERVER=$(kubectl config view --raw --minify -o jsonpath='{.clusters[0].cluster.server}')
CA=$(kubectl config view --raw --minify -o jsonpath='{.clusters[0].cluster.certificate-authority-data}')
cat > /tmp/payments-inspector-kubeconfig.yaml <<KCEOF
apiVersion: v1
kind: Config
clusters:
- name: kind-m28-dd
  cluster:
    server: ${SERVER}
    certificate-authority-data: ${CA}
contexts:
- name: payments-inspector
  context:
    cluster: kind-m28-dd
    namespace: payments
    user: payments-inspector
current-context: payments-inspector
users:
- name: payments-inspector
  user:
    token: ${TOKEN}
KCEOF

uv run platformops workload-inspect payments -n payments --kubeconfig /tmp/payments-inspector-kubeconfig.yaml

uv run python3 - <<'EOF'
from kubernetes import client, config
from kubernetes.client.exceptions import ApiException

config.load_kube_config(config_file="/tmp/payments-inspector-kubeconfig.yaml")
apps = client.AppsV1Api()

try:
    apps.delete_namespaced_deployment(name="payments", namespace="payments")
    print("UNEXPECTED: delete succeeded")
except ApiException as exc:
    print("status:", exc.status)
    print("reason:", exc.reason)
    print("body:", exc.body[:260])

The exact same identity that just ran workload-inspect successfully gets a real 403 Forbidden the moment it attempts delete_namespaced_deployment() — not because this module's code refused to call it (this test called it directly, bypassing kubernetes_inspect.py entirely), but because the API server itself checked the ServiceAccount's Role and refused the request before it ever touched the Deployment. Think of it the way a library issues a reading-room card: the card lets you pull any book off the shelf to read at your table, but the drop-box that removes or replaces books on the shelves does not recognize that card at all — not because a librarian is standing there stopping you, but because the card was never wired into that mechanism in the first place. Grep proves the code never tries. RBAC proves that even a version of the code that did try would still fail.

4. A script asks once; a controller never stops watching​

workload-inspect runs, prints one report, and exits — one GET per object kind, then done. The Deployment controller that keeps every Deployment in your cluster converged runs a fundamentally different kind of request: a watch, an HTTP connection the client holds open, over which the API server pushes one JSON event every time something changes — instead of the client asking again and again whether anything is new.

Think of the difference between staying on an open phone line where the other person speaks the moment there is news, versus hanging up and re-dialing every few seconds to ask "anything new yet?" A watch is the open line. This module's script is the second call: it asks once, gets today's answer, and hangs up.

(kubectl get --raw "/apis/apps/v1/namespaces/payments/deployments?watch=true&timeoutSeconds=8" &
 sleep 2
 kubectl annotate deployment payments -n payments demo-watch-trigger="$(date +%s)" --overwrite >/dev/null
 wait) 2>&1 | python3 -c "
import sys, json
for line in sys.stdin:
    line = line.strip()
    if not line:
        continue
    try:
        obj = json.loads(line)
        print(obj.get('type'), obj['object']['metadata']['name'], obj['object']['metadata'].get('resourceVersion'))
    except Exception:
        print('RAW:', line[:120])
"

Expected output

ADDED payments 495
MODIFIED payments 566
MODIFIED payments 568

This watches the whole deployments collection in the payments namespace (.../namespaces/payments/deployments?watch=true), not one named object — that distinction matters. A watch on a single named resource (.../deployments/payments?watch=true) does not speak this same envelope protocol on this Kubernetes version: it just streams the object itself, with no type/object wrapper at all, so the parser above would print nothing but RAW: lines against it. Watching a collection is what actually gives you the {"type": ..., "object": ...} envelope this section is about — the same shape a real controller's informer reads, watching every Deployment in a namespace at once, not one it already knows the name of.

One connection, three events, no re-polling. ADDED is the object's current state the instant the watch opens (Kubernetes's watch API always starts by replaying the current state, so a controller that just started still knows what it is looking at). Then kubectl annotate changed the object, and the API server pushed a MODIFIED event down the same open connection, unprompted — twice, because kubectl annotate itself makes two calls under the hood. workload-inspect never opens a connection like this: it calls read_namespaced_deployment() and list_namespaced_pod() once each, gets one answer, and is done. The resourceVersion values above are point-in-time — every fresh cluster starts its own counter, so yours will show different numbers; what should match is the shape: one ADDED, then two MODIFIED for the same object name.

Both paths hit the identical API server — a watch is not a different, more powerful API, just a different HTTP request (?watch=true, a long-held connection) against the same objects this module's GET calls already read. The real difference is operational, not technical: a controller runs unattended, forever, reacting to every change with no human approving each reaction. A script like workload-inspect only ever runs because a person (or a scheduled job standing in for one) decided to run it, once, right now. That gap is exactly why Module 29's governed rollout-restart — the first workload in this project that writes to a cluster — needs an approval gate, a dry-run, and an audit log before it acts: those guardrails exist to put a human decision back into a loop that would otherwise, like a real controller, keep acting on its own.

Common pitfalls​

  • Trusting a grep proof as permanent, unmonitored protection. A grep proof is a fact about the code today — re-run it after every change to this module, and treat RBAC as the layer that holds even when the grep proof stops being true.
  • Granting a monitoring ServiceAccount cluster-wide view instead of a scoped Role. The payments-inspector Role above is namespaced on purpose — the can-i list pods -n default check proves it cannot even read a namespace it was never granted.
  • Assuming can-i and an actual attempt always agree. They do here, because the RBAC Role is simple — but a webhook admission controller or a resource quota can refuse a request can-i would report as allowed. Trust a live attempt over a dry-run check where the two might diverge.
  • Reaching for a watch loop because it looks more "real-time." A watch that never terminates and reacts on its own is a controller — it needs the write-side guardrails Module 29 builds. A human-triggered, one-shot script has no business holding a connection open indefinitely.
Where you will use this
  • The dot-anchored grep proof (\.(create|patch|delete|replace)_). Use it when: you are reviewing a pull request against any "read-only" tool in your platform and want a five-second, mechanical check that no write verb crept in — not a promise in the PR description.
  • kubectl auth can-i --as=<serviceaccount>. Use it when: you are provisioning a new monitoring, dashboard or reporting identity and need to prove its Role grants exactly what you intended, before you hand out its kubeconfig or mount it into a pod.
  • A real write attempt against a restricted identity, not just a can-i check. Use it when: security review or an audit asks you to demonstrate least privilege — a live 403, captured from the actual client library your tool uses, is stronger evidence than a YAML file and a claim.
  • Recognizing a watch connection versus a one-shot GET/list in your own tools. Use it when: deciding whether a new piece of automation should be a script someone runs on demand, or a controller that needs its own set of write-side guardrails before it is allowed to run unattended.
