Kubernetes Automation with Python

Module 27 packaged platformops as a container and ran it as a Kubernetes Job (a workload that runs once, to completion, and stops). That Job's own manifest was clear about what it did not do: it never called kubectl, it never imported a Kubernetes client library, and it set automountServiceAccountToken: false so it could not reach the Kubernetes API even by accident. The lesson told you plainly that reading Kubernetes state from Python — a client library, a kubeconfig (the file that tells a tool which cluster to talk to and how to log in), listing Pods and Deployments in code instead of by hand — was this module's job, not that one's. So here we are. This is that module.

Why this matters at work

Picture an on-call engineer checking why a Deployment looks unhealthy. Normally they run kubectl get pods a few times and read the output with their own eyes. That works fine for one Deployment, once. It breaks down the moment you want the same check across fifty services, on a schedule, or as one signal inside a bigger incident report. At that point you need Python code asking the same questions kubectl asks, through the same API, and turning the answer into something another program can read.

1. The Kubernetes API is a live status board, and you are reading it, not touching it​

Imagine you are standing in front of an airport's departure board. It does not fly the planes, and it does not decide which gate a flight uses. It only shows what the airport's own systems already know: flight number, gate, status — "On Time", "Delayed", "Boarding". You read the board to decide what to do next. If a flight is delayed, the board does not fix that — a different system, run by different people, does.

A Kubernetes cluster's API server (the front door every tool, including kubectl, talks to) is the same kind of board for your workloads. It already knows every Deployment's desired and current replica count (how many copies of a Pod you asked for, versus how many are actually up), every Pod's phase and container state, every recent warning event — because the cluster's own controllers wrote that state there as things happened. This module's code is you, standing at the board: it asks the API server questions and reports what it finds. It never asks the API server to change anything. Module 29 builds the part that acts on what it reads — the equivalent of walking up to an airline desk and actually asking them to rebook your flight.

2. Two ways in: your laptop's kubeconfig, or a Pod's own identity​

Python code needs to prove who it is before the API server will answer it — the same way kubectl does. The kubernetes client library gives you two paths for that, and this module's k8sclient.py wraps both behind one function:

On your laptop, against the kind cluster this lab builds, config.load_kube_config() reads the same file kubectl already reads — ~/.kube/config, or whatever --kubeconfig points at — and uses whichever context (a saved cluster-plus-login combination) is current, unless you name one explicitly. That is the only path this module's lab uses. config.load_incluster_config() is the other path: it reads the token and certificate that Kubernetes itself places inside every Pod's filesystem. That is the identity a platformops container would carry if it ran as a scheduled Job or Deployment inside the cluster instead of on your laptop. Do keep this in mind: nothing downstream of get_kubernetes_clients() needs to know which path was used. Both hand back the same two client objects.

3. Two clients for two kinds of object​

AppsV1Api reads Deployments (and other "apps" objects like ReplicaSets and StatefulSets, which this module does not use). CoreV1Api reads Pods and Events (part of Kubernetes's oldest "core" API group). This module's inspector, kubernetes_inspect.py, takes both as plain function arguments and never builds either one itself. So this is the important point: because the client is just an argument, its logic can be tested against a fake client object with no real cluster running at all — you hand it a stand-in, not the real thing. This is the same pattern — call it passing the client in, rather than building it inside — that cloudaudit.py (Module 24) already used for its AWS client.

4. Reading a Deployment's real numbers — desired, ready, available​

A Deployment's spec.replicas is what you asked for. Its status.ready_replicas and status.available_replicas are what the cluster actually has right now. And here is the catch: the Kubernetes API returns None for either field, not 0, whenever a Deployment has never had any replica in that state at all. Code that assumes a missing field means zero, without checking, will crash the first time it meets a brand-new Deployment. This module's rollout_state() function turns those three numbers into one word — healthy, degraded, unavailable, or scaled-to-zero — so you never have to compare raw replica counts by hand.

5. One field name tells you which failure you are looking at​

Every container on a Pod is always in exactly one of three states: running, waiting, or terminated. A healthy container is running, with no reason attached. A struggling one is usually waiting, and its reason field is the exact short code you already read with your own eyes when you ran kubectl describe pod in Module 27 — CrashLoopBackOff, ImagePullBackOff, or ContainerCreating. This module's lab builds three failing Deployments so you see all three shapes for real. A container that starts and exits right away shows waiting / CrashLoopBackOff. A container whose image tag does not exist shows waiting / ImagePullBackOff. And a Pod that the scheduler can never place at all — because it asks for more memory than any node has — never gets a container status in the first place, because kubelet never even got a chance to try. Its phase alone (Pending, with an empty container list) is the whole signal.

A Pod's phase and a container's state answer different questions

pod.status.phase (Pending, Running, Succeeded, Failed) answers one question only: has this Pod's container ever started? A Pod stuck on ImagePullBackOff can still show phase Pending, even though it has already been placed on a node — it is the container's own state/reason fields that actually name the problem. Read both. Do not guess one from the other.

6. Warning events, filtered to what is still true​

Kubernetes keeps an Event record for almost everything that happens to an object — a Pod being scheduled, an image being pulled, a container backing off. Most are Normal. The ones worth your attention for troubleshooting are type: Warning. But here is the part that trips people up: events do not disappear the moment their cause is fixed. The cluster keeps them for about an hour by default. So if this module's code matched every Warning event whose name simply started with the Deployment's name, a Pod from a rollout you already fixed twenty minutes ago would still show up in a fresh report, describing a problem that no longer exists. Instead, list_warning_events() only keeps events tied to the Deployment's currently listed Pods — objects that exist right now — so a report reflects the cluster's actual state today, not its recent history.

7. Errors have a name too​

Two different things can go wrong when you ask the API server a question, and this module's code tells them apart — the same way cloudinventory.py tells NoCredentialsError apart from ClientError. A ConfigException means the client never even reached the cluster: no kubeconfig file, or a broken one. An ApiException means the API server did answer, but with a rejection — 404 for a Deployment that does not exist, 403 for a namespace this identity is not allowed to read. Catching each by its real type, rather than a bare except Exception, means a genuine bug in this module's own code will still crash loudly, instead of getting swallowed alongside an expected failure.

8. A script, not a controller — and why that difference matters​

workload-inspect runs once, prints a report, and exits. That makes it a script. A Kubernetes controller (the Deployment controller itself is one) runs forever, watching for changes and reacting to every one, continuously, with no human invoking it each time. An operator is a controller built for one specific application, packaged with its own custom object type. This module is, on purpose, the simplest of the three: it answers one question, once, when you ask it. The Deep Dive goes further into what actually separates a script from something that keeps reconciling state on its own — and why that difference is exactly what makes a read-only script safe to hand to anyone, while a controller with write access needs the guardrails Module 29 builds.

Common pitfalls​

  • Treating a missing ready_replicas as 0 without checking. The API returns None for a Deployment that has never had a ready replica — code that does arithmetic on it directly raises a TypeError the first time it meets a fresh Deployment.
  • Guessing a Pod's label selector instead of reading it from the Deployment. Hardcoding app=<deployment-name> breaks the moment a real Deployment uses different labels. Always read spec.selector.matchLabels from the Deployment object itself.
  • Assuming Pod phase alone tells you what's wrong. A Pending phase can mean "never scheduled" or "scheduled but the image will never pull" — you need the container's own state/reason to tell those apart.
  • Matching events by name prefix instead of by currently-live objects. A stale event from a Pod that no longer exists can still be sitting in the cluster's event history — filter against the Pods you just listed, not a guessed name pattern.
  • Catching Exception instead of ApiException/ConfigException by name. A bare except swallows a real bug in your own code the same way it hides an expected 404 — you lose the difference between "the cluster said no" and "this script has a bug."
  • Giving a read-only inspector's ServiceAccount more than get/list/watch. A tool that only ever reads should never be able to write, even by accident — the Deep Dive proves this is enforced by the API server itself, not just by this module's own code choosing not to call write methods.
