Deep Dive — What Actually Makes a Skill Worth Writing

The lab had you classify ten examples and write a planning document — no SKILL.md file exists yet. This page goes one level under the lesson's claims: what "read only when the task matches" actually costs in words, not just in theory; what separates a description an agent can act on from one that just sounds descriptive; and how to catch the two anti-patterns the lesson named — a skill that quietly duplicates CLAUDE.md, and a skill that quietly duplicates a library — with a check you can run, not just a feeling you get reading it.

Where this picks up

You need ~/platformops at v1.2, with skills/CATALOGUE.md in place from the lab. Every example on this page runs in its own scratch copy — nothing here touches your real project:

rm -rf /tmp/m16-dd-scratch
cp -r ~/platformops /tmp/m16-dd-scratch
cd /tmp/m16-dd-scratch
rm -rf .venv
uv sync
mkdir -p .claude/skills

The rm -rf .venv && uv sync step is needed because copying a uv-managed virtual environment breaks the internal symlinks that point at your Python install. Removing the copy and rebuilding it takes a few seconds and gives you a working environment.

Re-running any command on this page is safe.

1 — What progressive disclosure costs, in real words​

"The agent only loads a skill when it matches" is easy to say. Put a number on it.

Write the changelog-entry skill from the lesson into the scratch copy:

cd /tmp/m16-dd-scratch
mkdir -p .claude/skills/changelog-entry
cat > .claude/skills/changelog-entry/SKILL.md << 'EOF'
---
name: changelog-entry
description: >
  Write a CHANGELOG.md entry in Keep a Changelog format for a change you
  just made to the PlatformOps Toolkit. Use this whenever you finish a
  code change and need to record it, before reporting the task done.
---

# Changelog Entry

## When to use this

Use this skill right after you finish a change to the PlatformOps
Toolkit -- a new command, a bug fix, a dependency change -- and before
you tell the user the task is done.

## Steps

1. Read the last five entries in CHANGELOG.md to match the existing style.
2. Add a new line under `## [Unreleased]`, under the correct heading
   (`### Added`, `### Changed`, `### Fixed`).
3. Describe the change in one sentence, from the user's point of view --
   not implementation detail.
4. Do not create a new version number. That happens at release time.

## Tools this skill may use

- Read CHANGELOG.md
- Edit CHANGELOG.md

## Output

One new line in CHANGELOG.md, under `[Unreleased]`.
EOF
wc -w .claude/skills/changelog-entry/SKILL.md

Expected output

169 .claude/skills/changelog-entry/SKILL.md

Now pull out only the frontmatter — the part an agent has to weigh for every task, whether this skill ends up relevant or not:

cd /tmp/m16-dd-scratch
sed -n '/^---$/,/^---$/p' .claude/skills/changelog-entry/SKILL.md | wc -w

Expected output

43

The full skill runs to roughly 169 words. The frontmatter alone — the name and description that stand in for it on every task where the skill does not apply — is a small fraction of that. This is the actual mechanism behind the lesson's claim, not just an analogy: scanning one short description costs about 43 words; reading the full procedure costs 169, and that larger cost is only paid on the task where the skill is actually used.

Now scale it up to the catalogue you wrote in the lab. Five candidate skills, each in the same size range as changelog-entry, is roughly five times 169 — around 850 words of procedure. If all five were pasted directly into CLAUDE.md instead of kept as separate skills, CLAUDE.md would grow from its current size to several times that, on every single task, including the large majority of tasks that touch none of the five:

cd /tmp/m16-dd-scratch
wc -w CLAUDE.md

Expected output

325 CLAUDE.md

Compare that number against five times the full changelog-entry word count. CLAUDE.md stays close to its current size only because the five procedures live as skills, not as five more sections pasted into the file every task already reads in full.

2 — The trigger-phrase test for a description​

Not every description is equally useful to an agent trying to decide whether a skill applies. Two versions of the same skill's frontmatter, side by side:

cd /tmp/m16-dd-scratch
mkdir -p .claude/skills/vague-example
cat > .claude/skills/vague-example/SKILL.md << 'EOF'
---
name: changelog-helper
description: Helps with changelogs.
---
EOF
grep -c -iE 'use this (when|whenever)|use when' .claude/skills/changelog-entry/SKILL.md .claude/skills/vague-example/SKILL.md

Expected output

.claude/skills/changelog-entry/SKILL.md:1
.claude/skills/vague-example/SKILL.md:0

changelog-entry's description matches; vague-example's does not. "Helps with changelogs" is true, and useless — it does not say when to reach for it, so an agent (or a teammate reading the catalogue six months from now) has to guess whether a given task qualifies. "Use this whenever you finish a code change and need to record it" states the trigger condition directly, the same discipline Module 15 asked of a harness's approved commands: specific instructions produce specific behavior, and a description is the one part of a skill that has to do its job without the reader ever seeing the steps behind it.

This is a real, checkable difference, not a style preference. A grep for a trigger phrase like "use this when" is a rough proxy for a much more important property: could someone who has never read the skill's body decide, from the description alone, whether it applies to the task in front of them right now? If the answer requires opening the file and reading the steps, the description has not done its job.

3 — Catching the two anti-patterns with a real check​

The lesson named two ways a skill goes wrong: duplicating CLAUDE.md, or duplicating a library. Both are things you can actually check, not just sense.

Duplicating CLAUDE.md. Write a bad skill that is really just one line from the harness, dressed up as a procedure:

cd /tmp/m16-dd-scratch
mkdir -p .claude/skills/run-tests
cat > .claude/skills/run-tests/SKILL.md << 'EOF'
---
name: run-tests
description: Use this when you need to run the test suite.
---

# Run Tests

## Steps

1. Run `uv run pytest`.
EOF
grep -f <(grep -oE 'uv run [a-z]+' CLAUDE.md | sort -u) .claude/skills/run-tests/SKILL.md

Expected output

1. Run `uv run pytest`.

Every line of substance in run-tests/SKILL.md also appears, verbatim, inside CLAUDE.md's Approved commands section — a section already read on every task. There is no procedure here beyond "run one command that is already on the standing list." This is the first anti-pattern: a skill whose entire content is redundant with something the agent already always has, adding a second, on-demand copy of a rule instead of a genuinely task-specific one.

Duplicating a library. Write a second bad skill that inlines a full implementation instead of pointing at one:

cd /tmp/m16-dd-scratch
mkdir -p .claude/skills/audit-deps
cat > .claude/skills/audit-deps/SKILL.md << 'EOF'
---
name: audit-deps
description: Use this when you need to check for vulnerable dependencies.
---

# Audit Dependencies

## Steps

1. Run this Python code:

```python
import subprocess, json
result = subprocess.run(
    ["uvx", "pip-audit", "--format", "json"],
    capture_output=True, text=True, timeout=60,
)
data = json.loads(result.stdout)
for dep in data.get("dependencies", []):
    for vuln in dep.get("vulns", []):
        print(f"{dep['name']}: {vuln['id']}")

EOF grep -c '```python' .claude/skills/audit-deps/SKILL.md


**Expected output**

```text
1

audit-deps/SKILL.md contains a working Python implementation of the exact logic the lesson's dependency-audit-report catalogue entry described. That logic already belongs in scripts/check-deps.sh and, once Module 17 or later builds it, in platformops check-deps itself — tested, reviewed, and maintained as code. A skill that reimplements it inline has two untested copies of the same logic where there should be one tested one, and the skill's "steps" have quietly turned into a program instead of a procedure. The fix for both anti-patterns is the same: a real skill either points at a command from CLAUDE.md's Approved commands, or names a function to call in an existing module — it does not restate either one in full.

Teardown​

rm -rf /tmp/m16-dd-scratch

This removes only this page's scratch copy. Nothing on this page touched ~/platformops — skills/CATALOGUE.md from the lab is the only real addition this module makes to your project.

Where you will use this
  • A skill's frontmatter is the only part of it every task actually pays for — the full body is only read on a match. Use it when: you are deciding whether a procedure belongs in CLAUDE.md or in a skill — if it does not apply to most tasks, a skill keeps its cost off the tasks that do not need it.
  • A description without a stated trigger condition ("use this when...") cannot be matched against a task by anyone who has not already read the skill's body. Use it when: you are writing or reviewing a skill's description field — if it does not say when to reach for the skill, rewrite it before you write a single step.
  • A skill whose content already appears verbatim in CLAUDE.md is not a skill — it is a second copy of a standing rule. Use it when: a catalogue entry's steps turn out to be one already-approved command — cut the skill, and leave the rule where it already lives.
  • A skill whose "steps" are really a program is a library in disguise, and now you have two untested copies of the same logic. Use it when: a skill's step contains more than a couple of lines of real code logic — move that logic into the project's Python code or an existing script, and have the skill call it by name instead.
