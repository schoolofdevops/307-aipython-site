Lab — Agent Skills: The Correct Mental Model

This lab has two phases, and neither one touches platformops's Python code or bumps its version — it stays at v1.2 throughout. In Phase 1, you classify ten real examples from the project you have been building, using the five-way taxonomy from the lesson. In Phase 2, you write the project's first skill catalogue — a planning document that lists the skills PlatformOps could use, before you build any of them. Module 17 starts turning entries from this catalogue into real SKILL.md files.

Before you start

You need ~/platformops at v1.2, with CLAUDE.md and scripts/verify.sh in place from Module 15, and the labs repo cloned at ~/307-aipython-labs.

cd ~/platformops
git log --oneline -1

Expected output

321dfd8 M15: Building a Coding-Agent Harness — lesson, lab, quiz, deep dive, decks, narration

Your commit hash and message will differ; what matters is that it references v1.2 or Module 15.

Phase 1 — Classify ten examples​

Step 1 — Copy the worksheet​

cd ~/platformops
cp ~/307-aipython-labs/labs/m16/classification-worksheet.md classification.md

Step 2 — Confirm you have ten rows to fill in​

grep -c '^| [0-9]* |' classification.md

Expected output

10

You should see 10. If you see fewer, the file did not copy completely — re-run Step 1.

Step 3 — Classify each example​

Open classification.md. For each of the ten rows, write one of the five labels from the lesson's taxonomy (Section 4) into the Your answer column: repository instruction, skill, python library, cli command, or mcp tool.

Use the one-sentence test from the lesson: is the agent reading instructions and deciding what to do, or is it running something that already knows what to do? If it is reading instructions, ask a second question — is this read on every task, or only when the task matches it?

Step 4 — Check your answers​

Answer 1 — CLAUDE.md's Safety rules section

repository instruction. It is read by the agent on every task, without the agent having to decide whether it applies — the same way the whole ## Safety rules section works in Module 15.

Answer 2 — uv run pytest -q

cli command. It is a command you or the agent runs directly, exactly as listed under CLAUDE.md's Approved commands.

Answer 3 — the service-readiness SKILL.md

skill. It has a name, a description, and numbered steps — read in full only when a task matches "review a service definition," not on every task.

Answer 4 — httpclient.py

python library. The agent does not read check_health() or get_repo_info() as instructions to follow — code calls these functions, and they run.

Answer 5 — Typer

python library. A third-party package cli.py imports and calls. Nothing about Typer is read by the agent as a procedure to follow.

Answer 6 — scripts/verify.sh

cli command. A single script, run directly, the same way uv run pytest is — it is not read as a set of instructions the agent interprets; it executes.

Answer 7 — the changelog-entry SKILL.md

skill. Same shape as Answer 3 — a name, a description, and steps, read only when the task matches "record this change in CHANGELOG.md."

Answer 8 — CLAUDE.md's Definition of done checklist

repository instruction. Like Answer 1, this is part of CLAUDE.md — read on every task, not selectively loaded for a matching task.

Answer 9 — a future PlatformOps MCP server

mcp tool. check-security and check-deps already exist as CLI commands; wrapping them behind an MCP server exposes them as callable tools to any MCP-aware agent, reached over the protocol rather than by running the CLI or importing the Python package directly.

Answer 10 — a kubectl-wrapping MCP server

mcp tool. Same reasoning as Answer 9 — a capability outside the project's own Python code, reached by an agent over MCP, not by shelling out or importing anything itself.

Count how many you got right before reading the answers. Answers 3 and 7 (both skills) are the pair people mix up with a repository instruction most often — both are markdown files with step-by-step text, and the only real difference is when each one is read. If you got those two right, you have the core distinction this module teaches.

Phase 2 — Write the initial skill catalogue​

A skill catalogue is a planning document: the list of skills a project could use, written before any of them are built as real SKILL.md files. Writing it first forces a decision the lesson's boundary rules exist for — is this genuinely a recurring, task-specific procedure, or is it really a CLAUDE.md line, or a library function, in disguise?

Step 5 — Create the skills folder​

cd ~/platformops
mkdir -p skills

Step 6 — Write the catalogue​

Five candidate skills, each checked against the lesson's two boundary rules (not a CLAUDE.md line, not a library implementation in disguise) before it made the list:

cat > skills/CATALOGUE.md << 'CATALOGUE'
# PlatformOps Skill Catalogue

This is a planning document. It lists skills the PlatformOps Toolkit could
use -- not skills that exist yet. Module 17 starts turning these into real
`SKILL.md` files, one at a time.

Each entry passed the two boundary checks from Module 16 before it was
added here: it is not a single line that already belongs in CLAUDE.md, and
it is not a Python implementation that belongs in `src/platformops/`
instead.

## Candidate skills

| Name | Description | Trigger condition |
|------|-------------|--------------------|
| `changelog-entry` | Write a CHANGELOG.md entry in this project's exact Keep a Changelog format. | Right after finishing any code change, before reporting the task done. |
| `service-readiness-review` | Walk a service definition file (`service.yaml`) through the project's validation and readiness checks before it ships. | Before deploying, or merging a change to, a `service*.yaml` file. |
| `spec-writer` | Draft the seven-section spec (Goal, Functional requirements, Allowed files, Approved dependencies, Non-goals, Required tests, Acceptance criteria) for a described feature. | Before delegating a new feature to a coding agent, following the Module 14 spec shape. |
| `dependency-audit-report` | Turn a `check-deps --format json` result into a short, human-readable summary suitable for a pull-request comment. | When `check-deps` reports findings and a plain-language summary is needed for reviewers. |
| `incident-context-collector` | Gather the project's first-response context -- recent git history, container status, and the last failed health check -- into one short report. | When responding to a production incident and the first few minutes are spent gathering context by hand. |

## Boundary notes

- None of these five duplicate an existing CLAUDE.md rule -- each is a
  multi-step procedure for one recurring situation, not a standing rule
  every task needs.
- None of these five are a Python implementation in disguise -- each one's
  actual work (running `check-deps`, running `git log`, running the
  existing validation code) already exists as a command or a library
  function. The skill sequences and interprets that work; it does not
  reimplement it.
CATALOGUE

Step 7 — Confirm the catalogue has the shape it needs​

grep -c '^| \`' skills/CATALOGUE.md

Expected output

5

You should see 5 — one row per candidate skill. If you see fewer, a table row did not paste correctly.

grep -c '^## ' skills/CATALOGUE.md

Expected output

2

Two ## sections: Candidate skills and Boundary notes.

Step 8 — Confirm nothing else in the project changed​

The catalogue is a planning document, not a release. Confirm the version, the source code, and the test suite are all exactly where Module 15 left them:

grep -c 'version = "1.2.0"' pyproject.toml
uv run pytest -q

Expected output

1
139 passed in 2.07s

You should see 1 for the version check, and 139 passed (your exact timing will differ) for the test suite — unchanged from the end of Module 15. This module adds a planning document; it does not touch src/platformops/, pyproject.toml, or the test count.

Troubleshooting
  • **grep -c '^| \' skills/CATALOGUE.mdreports something other than5.** A markdown table row that does not start with | `` (a pipe, then a backtick) will not match — check that each candidate skill's name is still wrapped in backticks at the start of its row.
  • uv run pytest -q reports a different count than 139 passed. If the count differs but the run still says passed with no failed, your project has drifted slightly from the checkpoint this lab assumes — that is fine, the important thing is failed does not appear. If you see failed, stop and compare src/platformops/ against ~/307-aipython-labs/labs/checkpoints/v1.2/src/platformops/ before continuing.
  • You are unsure whether one of your own classifications in Phase 1 was closer to "skill" or "repository instruction." Re-read the lesson's one-sentence test in Section 4: the deciding question is not what the text says, but when it gets read — every task, or only a matching one.

Teardown​

cd ~/platformops
rm -f classification.md

skills/CATALOGUE.md stays — it is a real, permanent addition to the project, and Module 17 builds directly on it. There is no version bump and no tag for this module; platformops stays at v1.2 going into Module 17.

If you get stuck

If your ~/platformops diverges from what this lab expects and you cannot recover it, compare against the frozen checkpoint for this module in your labs clone: ~/307-aipython-labs/labs/checkpoints/v1.2/.... Do not compare against labs/platformops inside that clone — that copy keeps moving as later modules add to it, and it will not match a past module's expected state.
