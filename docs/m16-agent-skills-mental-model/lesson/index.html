Agent Skills: The Correct Mental Model

In Module 15 you wrote CLAUDE.md — a file a coding agent reads in full before it touches a single line of code. That works well for rules every task needs: which commands are approved, what the agent must never delete, what "done" means. But not every rule is like that. A step-by-step procedure for reviewing one specific kind of change — say, checking a service definition file before it ships — is not something every task needs. Most tasks will never touch a service definition at all.

If you paste that procedure into CLAUDE.md anyway, every task now reads it, whether it is relevant or not. Your harness grows longer, and — as you already saw in Module 15's Deep Dive — a longer file is a file that gets skimmed, not read. This module gives that procedure a proper home: a skill, a file the agent reads only when the task actually calls for it. You will also learn where a skill's boundary sits against four things it is easy to confuse it with: project instructions, a Python library, a CLI command, and an MCP (Model Context Protocol) server.

1. The kitchen analogy — house rules vs. a recipe card​

Imagine a professional kitchen. Pinned to the wall by the door is a house-rules poster: wash your hands before you start, label every container you put in the fridge, never substitute an ingredient without asking the head chef first. Every cook reads that poster at the start of every shift, no matter what they are cooking that day. It applies to all of them, all the time.

In a drawer near the stove sits a recipe box. Each card in it covers one dish — the exact steps for that dish, and only that dish. A cook does not read every card in the box before starting a shift. They pull out the card for tonight's special only when tonight's special is actually on the menu, follow its steps, and put it back. The rest of the box stays untouched.

Now look around the rest of the kitchen. The stand mixer on the counter is an appliance — a tool code (or a cook) operates, not something anyone "reads" as instructions. A specific knife is an instrument — you pick it up and use it directly for one job. And the phone line to the produce supplier is a connection to somewhere outside this kitchen entirely — you call it when you need something the kitchen itself does not have on hand.

A coding agent's world maps onto this almost exactly:

KitchenCoding-agent equivalent
House-rules poster (always read)CLAUDE.md — project instructions
One card from the recipe box (read on demand, for one task)A skill (SKILL.md)
The stand mixer (an appliance, not instructions)A Python library
One knife (a specific tool you use directly)A CLI command
The line to an outside supplierAn MCP server — an outside capability the agent calls

The house rules and the recipe card are both "instructions the agent follows." The difference that matters is when each one gets read.

2. Inside a SKILL.md​

A skill is a plain markdown file, conventionally named SKILL.md, saved once per skill in its own folder. It has two parts.

The frontmatter — discovery metadata. A short name and description at the top of the file, between --- lines. This is the only part of the skill an agent looks at before deciding whether the skill is relevant to the task in front of it right now.

The body — the procedure itself. When to use the skill, the exact steps to follow, which tools or commands the skill is allowed to use, and what it should produce when it is done. This part is only read once the agent has already decided, from the metadata, that this skill applies.

Here is a real skill you could write for the PlatformOps Toolkit today, without changing a single line of its Python code:

.claude/skills/changelog-entry/SKILL.md
---
name: changelog-entry
description: >
  Write a CHANGELOG.md entry in Keep a Changelog format for a change you
  just made to the PlatformOps Toolkit. Use this whenever you finish a
  code change and need to record it, before reporting the task done.
---

# Changelog Entry

## When to use this

Use this skill right after you finish a change to the PlatformOps
Toolkit, that is a new command, a bug fix, or a dependency change, and
before you tell the user the task is done.

## Steps

1. Read the last five entries in CHANGELOG.md to match the existing style.
2. Add a new line under `## [Unreleased]`, under the correct heading
   (`### Added`, `### Changed`, `### Fixed`).
3. Describe the change in one sentence, from the user's point of view,
   not implementation detail.
4. Do not create a new version number. That happens at release time.

## Tools this skill may use

- Read CHANGELOG.md
- Edit CHANGELOG.md

## Output

One new line in CHANGELOG.md, under `[Unreleased]`.

Notice what this skill does not do. It does not restate the project's tech stack or its safety rules — those live in CLAUDE.md and stay there. It does not write Python code — it tells the agent which existing file to edit and how. It is narrow, on purpose: one task, done the same way, every time it comes up.

3. Progressive disclosure — why the agent does not load every skill at once​

If a project ends up with fifteen skills, and the agent read every skill's full body before every task, you would be right back where Module 15 warned you not to be: a wall of text so long that the part that matters gets skimmed. Skills avoid this through progressive disclosure — a two-step read, not a one-step read.

The name and description are cheap to read — a sentence or two, for every skill, every time. The full body of a skill is only pulled in when its description matches what the task actually needs. This is the same reasoning as a cook not reading the whole recipe box before a shift: scanning fifteen card titles costs nothing; reading fifteen full recipes when you are only cooking one dish would waste real time. A well-written description is what makes this work — vague wording like "helps with project tasks" gives the agent nothing to match against, and the skill either never gets picked, or gets picked for tasks it was never meant for.

4. The five-way taxonomy — where the line actually falls​

Five kinds of things can sit inside (or alongside) a coding-agent project, and it is easy to lump them together because an agent can "use" all five in some sense. The test that actually separates them: is the agent reading instructions and deciding what to do, or is it running something that already knows what to do?

KindThe agent...Read/run whenPlatformOps example
Repository instruction (CLAUDE.md)reads it, in fullevery task"Never delete uv.lock"
Skill (SKILL.md)reads it, in fullonly when the task matchesthe changelog-entry skill above
Python libraryruns it (does not read it as instructions)whenever code calls ithttpclient.py
CLI commandruns it directlywhen you, or the agent, invoke ituv run pytest
MCP server / toolcalls it over a protocolwhen the task needs a capability outside the project's own codea server exposing check-security to any MCP-aware agent

CLAUDE.md and a skill both fall on the "reads instructions" side — the difference between them is only when they get read, which Section 3 already covered. A Python library, a CLI command, and an MCP server all fall on the "runs something" side — the agent does not read their internal code as a set of instructions to follow; it executes them and works with the result. An MCP server is really a CLI command or a library's capability, made reachable from outside the project, over a standard protocol, instead of by importing a package or running a local script.

The one-sentence test

If you can point at the exact spot in a diff where "following instructions" turns into "running code," that spot is the boundary between a skill and everything else on this list. A skill's job ends where a command, a library call, or an MCP tool call begins.

5. What makes a good skill boundary​

Not every repeated procedure deserves its own SKILL.md. Two boundary rules keep a skill catalogue useful instead of cluttered:

A skill should not duplicate CLAUDE.md. If a skill's entire content is "run uv run pytest," that is not a task-specific procedure — it is one line from the Approved commands section, already read on every task. Turning it into a skill adds a second, on-demand copy of a rule the agent already always has.

A skill should not duplicate a library. If a skill's "steps" are really a full Python implementation pasted into a markdown file, the actual logic belongs in src/platformops/ (or a script in scripts/), tested the way the rest of the project's code is tested. The skill should describe the procedure and point at the command or module that does the work — not contain the work itself.

What is left, once you subtract both of those, is the actual shape of a good skill: a specific, recurring task, done the same disciplined way each time, that is not itself a single command and does not belong inside every task's standing instructions. "Review a service definition before it ships." "Draft a changelog entry in this project's exact format." "Gather the first round of context when responding to an incident." Each of these is a real procedure, invoked only when that specific situation comes up — not a rule every task needs, and not something one command already does on its own.

Common pitfalls​

Common pitfalls
  • Turning every CLAUDE.md line into its own skill. A safety rule or an approved command belongs in the harness, read every task. Wrapping it in a SKILL.md on top does not make it more effective — it just adds a second copy the agent may or may not find.
  • A skill with a vague description. "Helps with the project" gives the agent nothing to match the task against. A description should name the specific situation and, ideally, say "use this when..." in plain words — the same specificity Module 15 asked of a harness.
  • A skill that is really a Python script wearing a markdown extension. If the "steps" are dozens of lines of code logic rather than a short, readable procedure, that logic belongs in the codebase, tested like the rest of it — the skill should point at it, not contain it.
  • Assuming a skill and an MCP tool are the same thing. A skill is instructions the agent reads and follows itself. An MCP tool is a capability the agent calls and gets a result back from, without reading or following anything internal to it. Confusing the two leads to writing a skill that tries to "be" a server, or a server that tries to "explain" itself in prose.
  • Writing a skill before you have used the procedure by hand at least once. A skill written from imagination, before anyone has actually done the task the way the skill describes, tends to skip a step that only shows up in practice. Do the procedure yourself first.
