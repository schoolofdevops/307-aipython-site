Local AWS Automation with Floci

Module 21 taught you Boto3 (the Python library for talking to AWS), and tested every line of it against moto — a library that fakes AWS entirely inside your own Python process, in memory, for the length of one test. That is the right tool for a unit test. It is the wrong tool the moment you want to run your own script by hand, watch a queue fill up over several separate commands, or check a bucket's contents after your script has already exited — moto's fake AWS account disappears the instant the decorated function returns.

This module uses a different kind of fake AWS: Floci, a small program that runs on your own laptop and answers real network requests exactly the way AWS's S3, DynamoDB and SQS do. Floci keeps running between commands, so you can upload a report in one command and list it in the next — something moto cannot do at all.

Why this matters at work

A platform engineer testing a deployment script against a brand-new AWS feature does not want to create a real AWS account, wait for it to provision, and pay for it, just to check the script's logic is right. Running the same script against a local stand-in first — free, instant, and safe to break — is normal practice before it ever touches a real account.

1. A flight simulator, not the real plane​

Imagine a flight simulator used to train pilots. It has the same controls as a real cockpit — the same throttle, the same instrument panel, the same radio. A trainee can practice a landing, an engine failure, a crosswind approach, over and over, without risking a real aircraft or a real runway. Most of what a pilot needs to learn, a simulator teaches well.

But a simulator crash does not ground the real fleet. It cannot reproduce every possible failure a real aircraft in real weather can have. At some point, every pilot still needs real flight hours in a real plane before flying passengers.

Floci is a flight simulator for AWS. It has the same "controls" — the same S3, DynamoDB and SQS APIs, answering the same way real AWS does for the operations this module covers. You can practice uploading a report, storing a finding, sending a message, over and over, for free, without a real AWS account. But a script that works against Floci is not automatically proven safe against real AWS — the Deep Dive covers exactly what a "pass" against Floci does and does not prove.

2. Installing and starting Floci​

Floci is a real, free, open-source program you install once, like docker or kind. It runs the same emulated AWS services inside a Docker container.

brew install floci-io/floci/floci   # macOS
# or: curl -fsSL https://floci.io/install.sh | sh   (Linux)
floci start

floci start needs Docker running — it pulls a small container image the first time, then starts it. Once it prints "Floci AWS is ready", it is listening at http://localhost:4566 for every AWS service it emulates, including S3, DynamoDB and SQS.

Check its health any time with:

floci doctor

A healthy Floci prints a checklist with every line showing a green check, ending in something like endpoint.reachable ✓ http://localhost:4566 is reachable. Two warning lines about the AWS CLI (aws.cli.endpoint, aws.cli.s3.pathstyle) are normal and safe to ignore for this module — they only matter if you also want the separate aws command-line tool to talk to Floci, and this module's code never uses that tool.

floci stop removes the container — and every bucket, table and queue in it

floci stop does not pause Floci — it stops and removes the container. The next floci start creates a brand-new, empty container: every S3 bucket, DynamoDB table and SQS queue Floci was holding is gone, not just the ones this module's lab created. This lab confirmed that behavior live before writing it here. Leave Floci running between lab sessions and between modules — later modules in this course use it too. This lab's own Teardown deletes only the specific bucket, table and queue it created, using the AWS API, never floci stop.

3. Credentials — any non-empty string works​

Floci does not check whether your AWS credentials are real — it only checks that boto3 sent something. Real AWS credentials would work too (Floci ignores them either way), but the normal practice is to export obviously-fake placeholder values so nobody mistakes them for real ones:

export AWS_ACCESS_KEY_ID=test
export AWS_SECRET_ACCESS_KEY=test

This project's rule from Module 1 still holds without exception: never write a real AWS key into code, a committed file, or a log line. These two values are not real keys, are safe to put in a shell profile, and would not grant access to anything even if they leaked.

4. The endpoint_url — the one thing that changes​

Every AWS SDK call goes to a URL. Against real AWS, boto3 already knows the right URL for every service and region. endpoint_url is boto3's way of overriding that — pointing every subsequent call at a different address instead, such as Floci's http://localhost:4566.

import boto3

# real AWS
s3 = boto3.client("s3", region_name="us-east-1")

# Floci, running on your own laptop
s3 = boto3.client("s3", region_name="us-east-1", endpoint_url="http://localhost:4566")

That one extra argument is the entire difference between "this code talks to real AWS" and "this code talks to a local stand-in." Nothing else about the code changes — same method names, same request shapes, same responses.

5. One client factory, not endpoint_url scattered everywhere​

The naive way to use endpoint_url is to type endpoint_url="http://localhost:4566" into every single boto3.client(...) call across every module that talks to AWS. That works for one lab. It falls apart the moment this project needs to switch back to real AWS: you would have to find and edit every one of those scattered literal strings, and it is easy to miss one.

src/platformops/awsclient.py adds one function, get_aws_client(), that every AWS-backed module in this project now goes through instead — the same discipline cloudinventory.get_client() already established for EC2 alone, generalized to any service:

def get_aws_client(
    service_name: str,
    *,
    region: str,
    profile: str | None = None,
    endpoint_url: str | None = None,
) -> Any:
    ...

Left at its default, endpoint_url=None means "no override — talk to real AWS", exactly like every function this project wrote before this module. Pass endpoint_url="http://localhost:4566" explicitly, and every call the returned client makes goes to Floci instead. reportstore.py, findingsstore.py and workqueue.py all build their clients through this one function — none of them ever calls boto3.client(...) directly, and none of them ever writes endpoint_url="http://localhost:4566" as a literal string. The Deep Dive proves that with a grep, not just a claim.

6. Explicit argument, then an environment variable — never silent global behavior​

boto3 itself already reads an AWS_ENDPOINT_URL environment variable and applies it automatically to every client any code in the whole process creates, with no code change needed at all. That sounds convenient, and for a quick one-off script it is. get_aws_client() deliberately does not rely on that global behavior. It reads the same environment variable, but only as a fallback inside this one function — an explicit endpoint_url= argument passed to get_aws_client() always wins.

The reason is locality. If this project simply let boto3's own environment-variable handling do the work, then any boto3 client created anywhere in the same process — including one built by some other library this project imports later — would be silently redirected to Floci too, the moment AWS_ENDPOINT_URL happened to be set in a learner's shell. Routing every client through get_aws_client() instead means the answer to "is this call hitting real AWS or Floci?" is always "read this one function's arguments" — not "trace every environment variable through the whole process." It is also easier to test: a unit test can assert exactly which endpoint_url value reached session.client(), the same way test_awsclient.py does.

7. S3, DynamoDB and SQS — three different shapes of storage​

This module builds one small piece of domain logic against each of three AWS services, because each one solves a different storage problem:

  • S3 (reportstore.py) — an object store. Good for whole files: a JSON report, uploaded under a unique, timestamped key, downloaded back later exactly as it was written.
  • DynamoDB (findingsstore.py) — a key-value / document database. Good for individual records you want to look up fast by a known key — here, "every finding for this service, most recent first." Unlike a SQL table, DynamoDB's key structure (which field to look records up by) is fixed when you create the table, not something you add later on a whim — the Deep Dive covers why that matters.
  • SQS (workqueue.py) — a message queue. Good for "something needs doing" work items a separate process picks up on its own schedule, with a way to handle a message that keeps failing instead of retrying it forever or losing it silently (a dead-letter queue, covered below).

8. Dead-letter queues — what happens when processing keeps failing​

A queue only stays useful if a message that cannot be processed has somewhere to go besides two bad outcomes: retried forever (one broken message blocks every message behind it), or dropped silently (the failure leaves no trace). SQS's answer is a dead-letter queue (DLQ) — an ordinary queue a main queue is configured to redirect a message to, once that message has been received (and not deleted) too many times.

Two settings make this real, not just a definition:

  • VisibilityTimeout — how long a received message stays hidden from other receivers while one receiver is (supposedly) processing it. If that receiver never deletes it before the timeout expires, the message becomes visible again — SQS's own signal that the previous attempt did not finish successfully.
  • maxReceiveCount — how many times a message can be received (and left undeleted) before SQS moves it to the DLQ instead of handing it out again.

workqueue.ensure_queue() wires both into a real RedrivePolicy on the queue. The lab receives the same message twice without deleting it, watches its ApproximateReceiveCount climb (SQS's own count of how many times a message has been delivered), and then finds that exact message sitting in the DLQ — real, captured output, not a diagram.

Common pitfalls​

  • Hardcoding endpoint_url="http://localhost:4566" inline in every module. Go through get_aws_client() instead — one place to change when switching between Floci and real AWS.
  • Forgetting Floci needs Docker running. floci start fails immediately if Docker itself is not up; floci doctor names the exact reason.
  • Running floci stop between lab sessions. It removes the container along with every bucket, table and queue Floci was holding — not a pause. Leave it running.
  • Assuming a pass against Floci means the code is production-ready. It proves your code calls the right operations with the right shapes. It does not prove an IAM permission boundary, a real service quota, or real network failure modes — see the Deep Dive.
  • Never checking ApproximateReceiveCount or wiring a RedrivePolicy. Without a DLQ, a message that keeps failing either blocks the queue forever or disappears with no record of why.
