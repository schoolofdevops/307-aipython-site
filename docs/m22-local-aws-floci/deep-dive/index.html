Deep Dive — Local AWS Automation with Floci

The lab proved reportstore.py, findingsstore.py and workqueue.py work against Floci. This page goes one level deeper on three things the lesson claimed but the lab did not have to prove directly: exactly where the "flight simulator" analogy breaks down (with a real, live test, not a guess), exactly how mechanically checkable "no endpoint_url scatter" really is, and exactly how a message's ApproximateReceiveCount climbs from 1 to a redirect into the dead-letter queue.

Where this picks up

This page assumes ~/platformops at v1.7.0, with src/platformops/awsclient.py, reportstore.py, findingsstore.py and workqueue.py in place from the lab, and Floci running.

cd ~/platformops
uv run platformops version

Expected output

platformops 1.7.0

1. What Floci proves, and what it does not -- tested live, not assumed​

Floci answers S3, DynamoDB and SQS API calls with the right shapes and the right ordinary behavior. That is genuinely useful: every test in this module's lab exercised a real network round trip, a real paginator, a real RedrivePolicy. But "answers the right shape" is not the same as "enforces every rule a real AWS account enforces." The clearest gap is IAM.

On real AWS, attaching an explicit Deny statement for s3:PutObject to the identity making a request blocks that request, full stop -- no exception, regardless of any Allow elsewhere. This session tested that exact scenario against Floci, live:

cat > /tmp/m22_iam_demo.py << 'PYEOF'
import json

import boto3

iam = boto3.client("iam", region_name="us-east-1", endpoint_url="http://localhost:4566")
s3 = boto3.client("s3", region_name="us-east-1", endpoint_url="http://localhost:4566")

s3.create_bucket(Bucket="iam-test-bucket")
iam.create_user(UserName="deny-test-user")

deny_policy = {
    "Version": "2012-10-17",
    "Statement": [{"Effect": "Deny", "Action": "s3:PutObject", "Resource": "*"}],
}
iam.put_user_policy(
    UserName="deny-test-user", PolicyName="deny-put", PolicyDocument=json.dumps(deny_policy)
)
print("put_user_policy: succeeded (Floci accepted the Deny policy)")

try:
    s3.put_object(Bucket="iam-test-bucket", Key="test.txt", Body=b"hello")
    print("put_object with an explicit Deny policy present: SUCCEEDED (not blocked)")
except Exception as exc:
    print(f"put_object blocked: {exc}")

s3.delete_object(Bucket="iam-test-bucket", Key="test.txt")
s3.delete_bucket(Bucket="iam-test-bucket")
iam.delete_user_policy(UserName="deny-test-user", PolicyName="deny-put")
iam.delete_user(UserName="deny-test-user")
PYEOF
uv run python /tmp/m22_iam_demo.py

Expected output

put_user_policy: succeeded (Floci accepted the Deny policy)
put_object with an explicit Deny policy present: SUCCEEDED (not blocked)

Floci's iam service accepted the policy call without complaint -- and then let the denied put_object through anyway. This is not a bug report against Floci; it is Floci's community edition being honest about its scope: it emulates operations, not the full authorization engine behind them. A script that passes every test in this lab, including one that (accidentally or on purpose) ignores IAM entirely, tells you nothing about whether that same script would be correctly blocked -- or correctly allowed -- against a real account with real permission boundaries.

The same gap applies, by the same reasoning, to:

  • S3 bucket policies (resource-based access rules) -- same category as the IAM test above, not re-tested here since the mechanism (a rule that should block a request) is the same one just proven not to be enforced.
  • Service quotas -- real AWS limits how fast you can create resources, how many buckets an account can hold, how many requests per second a table's partition can absorb. A loop that creates 10,000 objects against Floci in a tight local loop only tells you the loop's logic is correct, not that it survives real AWS throttling SlowDown (S3) or ProvisionedThroughputExceededException (DynamoDB) responses -- this lab's code never had to handle either, because Floci never sends them.
  • DynamoDB hot partitions -- the lesson's "pick the partition key up front" advice is not just about query convenience. A real DynamoDB partition has a physical throughput ceiling; a poorly chosen partition key (for example, one fixed value shared by every item) concentrates all traffic onto one partition and throttles far below the table's overall provisioned capacity, even while the table as a whole looks nowhere near its limit. This lab's findingsstore.py spreads load across a service-keyed partition on purpose, but nothing in this lab's tests proves that choice under real production traffic -- proving it would need a real DynamoDB table and a real load test, both outside a local lab's scope.

The flight-simulator analogy holds precisely here: everything Floci got right in this lab (the API shapes, the pagination, the RedrivePolicy mechanics in Section 3 below) is real training. The IAM gap is the simulator crash that does not ground the real fleet -- it teaches you nothing false about how to call the API, and it teaches you nothing at all about whether the permission boundary around that call is correct. That second question still needs a real AWS sandbox account before this code is production-ready.

2. "No endpoint_url scatter" is a checkable property, not just a design intention​

The lesson claimed reportstore.py, findingsstore.py and workqueue.py never hardcode endpoint_url="http://localhost:4566", and never call boto3.client() directly. That claim is mechanically checkable with grep -- run it yourself against your own ~/platformops:

grep -n 'endpoint_url\s*=\s*"http' src/platformops/reportstore.py src/platformops/findingsstore.py src/platformops/workqueue.py

Expected output

src/platformops/reportstore.py:14:here ever hardcodes `endpoint_url="http://localhost:4566"`. Point

The only match is a docstring sentence describing the rule, in a code comment -- not an actual literal argument in real code. findingsstore.py and workqueue.py have zero matches at all.

grep -c 'get_aws_client(' src/platformops/reportstore.py src/platformops/findingsstore.py src/platformops/workqueue.py

Expected output

src/platformops/reportstore.py:3
src/platformops/findingsstore.py:1
src/platformops/workqueue.py:3

reportstore.py (3) and workqueue.py (3) each build a client through get_aws_client() in exactly one function apiece -- upload_report_to_bucket() and send_to_queue()/ receive_from_queue(), the CLI-facing wrappers -- plus one docstring mention each, matching the count. findingsstore.py's single match is its docstring mention only; the module has zero actual call sites, because none of ensure_table(), put_finding(), get_finding() or query_findings() ever builds its own client at all. Every one of them takes client as its first parameter instead -- the same dependency-injection style cloudinventory.list_instances(client, ...) already established in Module 21. This module never needed a CLI-facing wrapper for DynamoDB (the lab exercises findingsstore.py directly, from a script), so there was nothing that needed to call get_aws_client() in the first place. Both are correct answers to "how does this module avoid endpoint_url scatter": build it in exactly one place when you need a client of your own, or accept an already-built one as a parameter and avoid the question entirely.

3. Dead-letter-queue mechanics, traced through a real redirect​

The lesson's sequence diagram showed the shape. Here is the same sequence, captured from a real run against your own Floci, with ApproximateReceiveCount visible at every step:

cat > /tmp/m22_dlq_trace.py << 'PYEOF'
import json
import time

from platformops.awsclient import get_aws_client
from platformops import workqueue

client = get_aws_client("sqs", region="us-east-1", endpoint_url="http://localhost:4566")

dlq_url, dlq_arn = workqueue.ensure_dead_letter_queue(client, "deepdive-poison-dlq")
main_url = workqueue.ensure_queue(
    client,
    "deepdive-poison-queue",
    dead_letter_arn=dlq_arn,
    max_receive_count=2,
    visibility_timeout=1,
    wait_time_seconds=1,
)

policy = client.get_queue_attributes(QueueUrl=main_url, AttributeNames=["RedrivePolicy"])
print("RedrivePolicy on the main queue:")
print(json.dumps(json.loads(policy["Attributes"]["RedrivePolicy"]), indent=2))
print()

workqueue.send_message(client, main_url, "poison message")

for attempt in range(1, 4):
    received = workqueue.receive_messages(client, main_url, max_messages=1, wait_time_seconds=2)
    if received:
        print(f"attempt {attempt}: ApproximateReceiveCount={received[0]['approximate_receive_count']}")
    else:
        print(f"attempt {attempt}: main queue empty -- message already redirected")
    time.sleep(1.5)

dlq_messages = workqueue.receive_messages(client, dlq_url, max_messages=1, wait_time_seconds=2)
print(f"\non the DLQ: {dlq_messages[0]['body']!r}")

client.delete_queue(QueueUrl=main_url)
client.delete_queue(QueueUrl=dlq_url)
PYEOF
uv run python /tmp/m22_dlq_trace.py

Expected output

RedrivePolicy on the main queue:
{
  "deadLetterTargetArn": "arn:aws:sqs:us-east-1:000000000000:deepdive-poison-dlq",
  "maxReceiveCount": 2
}

attempt 1: ApproximateReceiveCount=1
attempt 2: ApproximateReceiveCount=2
attempt 3: main queue empty -- message already redirected

on the DLQ: 'poison message'

Reading this trace against the RedrivePolicy it printed: maxReceiveCount: 2 means a message may be delivered and left undeleted twice before SQS treats the next delivery attempt as the one that exceeds the limit. Attempt 1 shows count 1 -- the first delivery. Attempt 2 shows count 2 -- the second delivery, now equal to maxReceiveCount. By attempt 3, the main queue has nothing left to deliver: SQS redirected the message to deepdive-poison-dlq instead of handing it out a third time, and the final read confirms it landed there with its body intact.

This output is point-in-time

The ARN account ID (000000000000) is Floci's fixed placeholder account, the same on every run. The receive counts and the redirect point (after the 2nd delivery, since maxReceiveCount=2) are deterministic given this exact configuration -- but the precise number of attempts SQS/Floci needs internally before the redirect becomes externally visible can vary by one, the same margin the lab built into its own DLQ test.

Where you will use this
  • Use it when: a script passes every test against Floci and someone asks "is this ready for production?" — the honest answer is "the logic is proven; the permissions are not," until it has also run once against a real AWS sandbox account under the actual IAM policy it will use in production.
  • Use it when: you are reviewing someone else's automation that talks to AWS and cannot tell whether a client is pointed at real AWS or a local stand-in — grep for get_aws_client( (or this project's equivalent) rather than trusting a comment; a mechanically checkable property beats a claim in a docstring.
  • Use it when: you are designing a new DynamoDB table and choosing a partition key — pick the field your most common query filters by, not the field that happens to be unique, and decide it before the first put_item(), since the key schema cannot be changed after the table exists.
  • Use it when: a queue-based worker keeps reprocessing the same failing message — check whether a RedrivePolicy with a maxReceiveCount is even wired up; without one, a poison message either blocks every message behind it forever or gets silently dropped, with no DLQ to show it ever existed.

Teardown​

cd ~/platformops
rm -f /tmp/m22_iam_demo.py /tmp/m22_dlq_trace.py

No AWS state, real or faked, survives past these scripts' own runs -- each one deletes the bucket/user/queues it created before exiting -- nothing else to clean up.
