Deep Dive — How Coding Agents Actually Read Your Project

The lab had you write a spec, then watch a rigged diff fail at the first import it tried to run. This page goes one level under that: why an agent reads only part of your project at all, why a written spec holds up better than a conversation across a long task, what a real diff's shape tells you about how carefully it was built, and a five-second check that would have caught the lab's hallucinated import before you ever opened the diff. You will use this the next time you scope a delegation to an agent, the next time you triage a PR an agent opened, and the next time someone on your team asks why "the agent said it works" is not something you can act on directly.

Where this picks up

You need ~/platformops at v1.1. Nothing in the lab modified it -- Phase 2 ran entirely in /tmp/m14-scratch, which you already removed at Teardown. Every command on this page runs in its own fresh scratch copy too, so it does not matter whether that directory still exists.

rm -rf /tmp/m14-dd-scratch
cp -r ~/platformops /tmp/m14-dd-scratch
cd /tmp/m14-dd-scratch

Re-running any command on this page is safe -- each one starts from this same fresh copy.

1 — What the agent actually reads, in numbers​

"The agent has a limited context window" is easy to say and easy to wave past. Put a real number on your own project instead:

find src/platformops -name '*.py' | xargs wc -l | tail -1

<expected output — folded in during live lab validation>

platformops runs a bit over two thousand lines across thirteen files today. That comfortably fits inside a single agent's working context, so for a project this size "the agent could not see the file" is rarely the honest excuse for a mistake. Real production repositories run into the hundreds of thousands of lines, across hundreds of files -- at that size, an agent genuinely cannot hold everything at once, and it has to choose. It chooses using the same signals you would if you were dropped into an unfamiliar repository with five minutes to find the right file: file and directory names, a CLAUDE.md or AGENTS.md at the root if one exists, and whatever the task description itself names directly.

This is the real mechanism behind the hallucinated import you watched fail in the lab. platformops.config, platformops.httpclient, platformops.local_ops -- the agent that produced the rigged diff had seen this naming pattern somewhere in its training or its own partial read of the project, and generated platformops.cloud because the name fit the pattern. It never actually opened src/platformops/ and confirmed a file named cloud.py existed there. A plausible name generated from a pattern is not the same thing as a name read from a directory listing -- and nothing in the diff itself tells you which one you are looking at.

2 — A five-second check that beats reading the whole diff​

The lab had you apply the rigged diff and run the full CLI to watch it fail. There is a faster, narrower check that catches the same class of mistake before you even start reading line by line: try importing the new module on its own, nothing else.

cd /tmp/m14-dd-scratch
git apply ~/307-aipython-labs/labs/m14/rigged-diff.patch
uv sync -q
uv run python3 -c "import platformops.depcheck"

This is the same failure the lab surfaced, reached in one line instead of a full --help or pytest run. The value of a check like this is not that it replaces reading the diff -- it does not tell you anything about the logged credential or the swallowed exception. It tells you, before you spend ten minutes reading carefully, whether the code the diff claims to add can even be imported. Run it first. If it fails, you already have your first finding before you have read a single line of logic.

3 — What a diff's own shape tells you, before you read a single line​

The lab pointed out that the diff touches pyproject.toml, which was never on the spec's Allowed files list. git can show you the complete shape of what changed in one line, which is worth doing before you read anything -- it tells you where to look first:

cd /tmp/m14-dd-scratch
git add -A
git diff --stat --cached

Expected output

<expected output — folded in during live lab validation>

Read this against the spec you wrote in the lab, file by file. cli.py and depcheck.py were both on the Allowed files list -- expected. pyproject.toml was not -- a finding, the same one the lab already named. But look at what is missing from this list entirely: CHANGELOG.md. Your spec's Allowed files section asked for an [Unreleased] entry there. The diff does not touch it at all.

This is a second, quieter failure mode alongside "touched a file it should not have": silently dropping a requirement the spec did ask for. An agent under-delivering on part of a spec is just as real a finding as over-delivering outside it -- and git diff --stat surfaces both in one command, before you have read a single line of what actually changed inside any file.

4 — The verification gap, in the order failures actually happen​

"It works" from an agent collapses several different claims into one sentence. Unpacked, in the order a real run would hit them:

  1. Does it import? The lab's diff fails here -- before any logic runs, before any test executes. This is the cheapest thing to check and the first thing that should be checked, by the agent itself, before it ever reports success.
  2. Does the test suite collect? One broken import in a file every test transitively imports (cli.py, in this diff) takes down collection for the entire suite, not just tests that exercise the new command. A hundred and thirty-eight passing tests and zero results are two very different outcomes that both start from "run the tests."
  3. Do the tests that run actually cover the risk? Even a suite that collects and passes only proves the paths its tests exercise. None of this diff's six flaws would be caught by a test that only checks the happy path -- a missing timeout needs a slow-server test, a logged credential needs a test that inspects log output, a swallowed exception needs a test for the failure case specifically.
  4. Did anyone run it at all? Some agent setups execute nothing -- they generate code and report based on what the code should do, not what it did do when run. You cannot tell which of these four levels a claim of "it works" actually reached just by reading the claim.

The lab already proved level 1 fails outright for this diff. That is the fastest, cheapest level to check, and it is exactly why Section 2's one-line import check earns a place before the full review: it tells you immediately whether you are dealing with a diff that never ran, before you invest time on levels 3 and 4.

Teardown​

rm -rf /tmp/m14-dd-scratch

This removes only this page's scratch copy. Your real ~/platformops was never touched by anything on this page.

Where you will use this
  • A project's real size in lines tells you whether "the agent could not see that file" is a plausible excuse or a convenient one. Use it when: an agent's mistake looks like it came from missing context on a small project -- check the actual size first; on a project this size, the more likely explanation is a name it inferred, not a file it never reached.
  • A one-line import check catches a broken diff faster than a full test run or a line-by-line read. Use it when: you receive any agent-generated diff that adds a new module -- try importing it in isolation before you invest in a full review; if it fails here, you already have your first finding.
  • git diff --stat shows you both what a diff added outside its scope and what it silently skipped inside its scope, in one command. Use it when: reviewing any diff against a written spec -- check the file list both ways, for files that should not be there and for required files that are missing.
  • "It works" collapses four different claims (imports, collects, tests cover the risk, someone actually ran it) into one sentence. Use it when: a teammate or an agent reports a change as done -- ask which of the four levels was actually verified, especially before merging anything security- or safety-sensitive.
