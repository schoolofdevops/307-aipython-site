Lab — Working Effectively with Coding Agents

This lab has two phases. In Phase 1, you write a real specification for a small feature -- platformops check-deps, a CLI command that reports the dependency audit as text or JSON -- the same kind of document you would hand a coding agent before it starts work. In Phase 2, you review a pre-written diff that simulates what an agent might hand back against a looser version of that same request, and find six flaws hidden in it.

No coding agent runs during this lab. The diff is a file you read, review, and document findings against -- the same discipline you would use on a real pull request.

Before you start

You need ~/platformops at v1.1 from Module 13, and the labs repo cloned at ~/307-aipython-labs.

cd ~/platformops
git log --oneline -1

Expected output

e377830 fix(m13): narration voice refinements + expand M14 plan

Your commit hash will differ; the message should reference v1.1 or Module 13.

Phase 1 — Write a spec​

A good spec draws a hard line around what an agent may touch and what it may not, before it writes a single line. You are going to write one for a real, small feature: platformops check-deps, a CLI command (following the same shape as check-security, already in src/platformops/cli.py) that wraps uvx pip-audit and reports the result as plain text or --format json.

Step 1 — Read the existing pattern first​

Before you write the spec, look at the command your new one has to match:

grep -n -A 5 '@app.command("check-security")' src/platformops/cli.py

Expected output

552:@app.command("check-security")
553-def check_security(
554-    ctx: typer.Context,
555-    path: Annotated[
556-        str,
557-        typer.Option("--path", help="source tree to scan (defaults to 'src')"),

(Line numbers will differ slightly if your cli.py has changed; the shape -- decorator, ctx, an Annotated option -- will not.)

check-security already shows the pattern: a Typer @app.command(), a --json (or here, --format) option, output routed through _fail() on error, --json-shaped output going only to stdout with nothing else mixed in. Your spec is going to point the agent at this exact pattern, by name, instead of describing the CLI conventions from scratch.

Step 2 — Create the spec directory​

mkdir -p specs

Step 3 — Write the spec file​

Create specs/check-deps-json.md. This is the seven-section shape every spec in this course uses from here on: Goal, Functional requirements, Allowed files, Approved dependencies, Non-goals, Required tests, Acceptance criteria.

cat > specs/check-deps-json.md << 'SPEC'
# Feature: platformops check-deps

## Goal

Add a `check-deps` command to the `platformops` CLI that runs the dependency
security audit (`uvx pip-audit`) already used in `scripts/check-deps.sh`, and
reports the result the same disciplined way every other command in this CLI
does: plain text for a human, `--format json` for a script or a CI job.

## Functional requirements

- `platformops check-deps` (no options) runs the audit and prints a plain-text
  report: "check-deps: OK -- no known vulnerabilities found" on a clean run,
  or "check-deps: FAIL -- N finding(s)" followed by one line per finding.
- `platformops check-deps --format json` prints ONE JSON object to stdout and
  nothing else: `{"status": ..., "clean": ..., "findings": [...]}`, following
  the exact envelope `check-security --json` already uses.
- Exit code 0 when clean, 1 when findings exist, 2 for an invalid `--format`
  value -- the same 0/1/2 contract every other command in `cli.py` uses.
- Errors route through the existing `_fail()` helper. No command adds its own
  ad hoc error path.

## Allowed files

- `src/platformops/cli.py` -- add the `check-deps` command only
- `src/platformops/depcheck.py` -- new module, the audit logic itself
- `CHANGELOG.md` -- add an `[Unreleased]` entry

Nothing else changes. Not `pyproject.toml`, not `scripts/check-deps.sh`, not
any existing command, not any existing test file's assertions (new tests may
be added).

## Approved dependencies

None. `uvx pip-audit` is already the approved external tool -- it stays a
throwaway `uvx` invocation, never a project dependency. Any subprocess call
follows the exact safe pattern already established in `local_ops.py`:
argument list, no `shell=True`, an explicit `timeout`. No new HTTP calls, no
new PyPI packages.

## Non-goals

- No new persistent dependency of any kind
- No web server, dashboard, or anything that listens on a port
- No change to any existing command's behavior or output shape

## Required tests

- A test asserting `check-deps --format json` produces output that
  `json.loads()` accepts, using the `CliRunner` + `monkeypatch` pattern
  `tests/test_cli.py` already uses for the `check-security` tests.
- A test asserting `check-deps` (no flag) produces the plain-text report.
- Existing tests are untouched and still pass.

## Acceptance criteria

- [ ] `platformops check-deps` runs with no arguments and reports text
- [ ] `platformops check-deps --format json` outputs one valid JSON object
- [ ] Exit codes match: 0 clean, 1 findings, 2 bad `--format` value
- [ ] `uv run pytest -q` passes, same count as before plus the new tests
- [ ] No new entries in `pyproject.toml` under `[project] dependencies`
SPEC

Step 4 — Verify the spec file​

grep -c '^## ' specs/check-deps-json.md

Expected output

7

Seven ## headings -- one per required section. If your count is off, a section got merged with its neighbor or dropped; open the file and check against the list above.

What the spec deliberately leaves out

Notice the spec never says how to parse --format in Python, or which dataclass shape to use inside depcheck.py. It states the behavior (what the command prints, what it exits with) and the constraints (which files, which dependencies, which tests) -- and leaves the implementation to whoever picks it up. That is the right level of detail: a contract, not pseudocode. An agent that has to guess at behavior drifts; an agent that has to guess at implementation style is exactly where you want it to use its own judgment.

Phase 2 — Review a rigged diff​

The file ~/307-aipython-labs/labs/m14/rigged-diff.patch is a unified diff that looks like what an agent produced for a looser version of the spec you just wrote -- one that never nailed down "allowed files" or "approved dependencies" as tightly. It adds the check-deps command to cli.py (that part is real and it works), a new src/platformops/depcheck.py, and a pyproject.toml change. It also contains six seeded flaws, one from each category the lesson named: a missing timeout, a logged credential, a swallowed exception, a hallucinated import, a needless dependency, and a destructive default.

+"""platformops.depcheck -- dependency security audit, wrapped for the CLI.
+
+Runs `pip-audit` through `uvx` and turns the result into a small object the
+`check-deps` command can print as text or JSON. Also checks PyPI for a
+newer `pip-audit` release, and serves a small dashboard so the audit result
+can be viewed in a browser.
+"""
+
+from __future__ import annotations
+
+import logging
+import os
+import subprocess
+from dataclasses import dataclass, field
+
+import requests
+from flask import Flask, jsonify
+
+from platformops.cloud import get_registry_client
+
+logger = logging.getLogger("platformops.depcheck")
+
+PIP_AUDIT_RELEASES_URL = "https://pypi.org/pypi/pip-audit/json"
+
+
+@dataclass
+class DependencyAuditResult:
+    """The outcome of one `run_dependency_audit()` call."""
+
+    clean: bool
+    findings: list[str] = field(default_factory=list)
+
+
+def _check_for_newer_pip_audit() -> None:
+    """Warn in the log if a newer pip-audit release is available on PyPI."""
+    response = requests.get(PIP_AUDIT_RELEASES_URL)
+    latest = response.json()["info"]["version"]
+    logger.info("latest pip-audit release available on PyPI: %s", latest)
+
+
+def run_dependency_audit() -> DependencyAuditResult:
+    """Run `uvx pip-audit` and translate its result into a DependencyAuditResult."""
+    _check_for_newer_pip_audit()
+
+    index_token = os.environ.get("PLATFORMOPS_INDEX_TOKEN", "")
+    logger.info("running dependency audit (index token: %s)", index_token)
+
+    try:
+        result = subprocess.run(
+            ["uvx", "pip-audit", "--format", "json"],
+            capture_output=True,
+            text=True,
+            timeout=60,
+            check=False,
+        )
+    except:
+        pass
+
+    findings = _parse_pip_audit_output(result.stdout)
+
+    if findings:
+        logger.warning(
+            "%d finding(s) -- deleting uv.lock to force a clean re-resolve",
+            len(findings),
+        )
+        os.remove("uv.lock")
+
+    return DependencyAuditResult(clean=not findings, findings=findings)
+
+
+def _parse_pip_audit_output(raw_output: str) -> list[str]:
+    """Turn pip-audit's JSON report into one human-readable line per finding."""
+    import json as _json
+
+    data = _json.loads(raw_output) if raw_output else {"dependencies": []}
+    findings = []
+    for dep in data.get("dependencies", []):
+        for vuln in dep.get("vulns", []):
+            findings.append(f"{dep['name']}=={dep['version']}: {vuln['id']}")
+    return findings
+
+
+def serve_dashboard(result: DependencyAuditResult) -> None:
+    """Serve a small web page showing the latest dependency audit result."""
+    app = Flask(__name__)
+
+    @app.route("/dependencies")
+    def dependencies():
+        return jsonify({"clean": result.clean, "findings": result.findings})
+
+    app.run(port=5055)

Do not skim. For every hunk, ask the same three questions the lesson gave you:

  1. Is this what the spec asked for?
  2. Is this safe?
  3. Is every new line necessary?

Already, before you find a single seeded flaw, one answer should jump out: the diff touches pyproject.toml. Your own spec's Allowed files section names exactly three files -- cli.py, depcheck.py, CHANGELOG.md -- and pyproject.toml is not one of them. That is a scope violation on its own, independent of what the change to pyproject.toml actually contains.

A rigged training file is only useful if it looks like a genuine diff, not a hand-wavy example. Prove that to yourself against a throwaway copy of your project -- never your real one:

cd /tmp/m14-scratch

Step 8 — Copy the review template and document your findings​

cp ~/307-aipython-labs/labs/m14/review-template.md review-findings.md

Open review-findings.md and fill in one row per flaw. The six categories:

CategoryWhat to look for
missing-timeoutAn HTTP call with no timeout parameter
leaked-credentialA credential value printed, logged, or included in output
swallowed-exceptionAn exception caught and silently discarded
hallucinated-apiAn import or call to something that does not exist
needless-dependencyA new dependency the feature does not need
destructive-defaultAn action that deletes data without confirmation
Hints if you are stuck
  • depcheck.py's _check_for_newer_pip_audit() -- it calls requests.get(...). Does that call set a timeout? Was this check even in the spec you wrote?
  • depcheck.py's run_dependency_audit(), the logger.info call -- read every argument passed to it. What does PLATFORMOPS_INDEX_TOKEN hold?
  • The try/except around subprocess.run(...) -- what happens if uvx is not installed? What does the except clause actually do with that failure?
  • The new import at the top of depcheck.py -- you already saw it fail at runtime in Step 7. Where does the name platformops.cloud come from if it does not exist?
  • The pyproject.toml hunk -- two packages were added. Does the project already have a library that does the same job as one of them? What is the other one even for?
  • The end of run_dependency_audit() -- what happens to uv.lock when a finding is found, and who approved that?

Step 9 — Check your findings​

Compare against all six:

Flaw 1 — missing-timeout

File: src/platformops/depcheck.py Line: response = requests.get(PIP_AUDIT_RELEASES_URL) in _check_for_newer_pip_audit() Problem: No timeout=. If PyPI is slow or unreachable, this call -- which nobody asked for in the first place -- hangs the whole audit indefinitely. It is also scope creep: nothing in the spec asked for a "check for a newer pip-audit release" step. Fix instruction: Remove the version-check step entirely -- it is out of scope. If it stays, give it timeout=httpclient.DEFAULT_TIMEOUT the way every other HTTP call in this project does.

Flaw 2 — leaked-credential

File: src/platformops/depcheck.py Line: logger.info("running dependency audit (index token: %s)", index_token) Problem: The literal value of PLATFORMOPS_INDEX_TOKEN -- a private package-index token -- is passed as a %s argument. Every log destination this runs in now carries the credential. Fix instruction: Log that a token was read, never its value: logger.info("running dependency audit (index token present: %s)", bool(index_token)).

Flaw 3 — swallowed-exception

File: src/platformops/depcheck.py Line: except: / pass around the subprocess.run(...) call Problem: A bare except: catches everything, including uvx not being installed, and discards it silently. The function then reads result.stdout on a result that was never assigned, which is its own separate bug hiding behind the first one. Fix instruction: Follow local_ops.py's pattern exactly: catch FileNotFoundError and subprocess.TimeoutExpired specifically, log a warning, and return a result with error set -- never a bare except: pass.

Flaw 4 — hallucinated-api

File: src/platformops/depcheck.py Line: from platformops.cloud import get_registry_client Problem: platformops.cloud does not exist anywhere in this project. You already watched this fail at runtime in Step 7 -- and get_registry_client is never even called anywhere in the file. Fix instruction: Delete the import. It is unused dead weight that breaks every command in the CLI the moment depcheck.py is imported.

Flaw 5 — needless-dependency

File: pyproject.toml Lines: "flask>=3.1.0" and "requests>=2.32.0" added to dependencies Problem: The project already uses httpx for every HTTP call it makes -- requests is a second library doing the same job. flask backs a serve_dashboard() function nobody asked for: a permanent web-framework dependency for what the spec described as a CLI-only feature. Both also violate the spec's Allowed files list -- pyproject.toml was never on it. Fix instruction: Remove both dependencies and serve_dashboard() entirely. If an HTTP call is genuinely needed later, it goes through the existing httpx client.

Flaw 6 — destructive-default

File: src/platformops/depcheck.py Line: os.remove("uv.lock") inside run_dependency_audit(), run whenever findings is non-empty Problem: Finding a vulnerability is common and expected -- it is what the audit is for. This code responds to a normal, healthy outcome by silently deleting the project's lockfile, with no confirmation and no dry run. The next uv sync re-resolves from scratch, discarding the exact, hash-verified versions the lockfile pinned. Fix instruction: Delete this block entirely. A finding is something to report, not an automatic trigger to mutate the project's dependency lock.

Step 10 — Reflect on the review​

Count how many of the six you found before checking the answers. Most people catch the hallucinated import and the needless dependency fastest -- Step 7 already proved the import wrong for you, and two new packages in one small diff stands out on a read-through. The logged credential and the swallowed exception are the two that hide best, because both look like ordinary, even helpful code at a glance.

This is the point of the exercise: a diff can add a real, working command -- the check-deps addition to cli.py in this diff is genuinely correct -- and still ship six ways to make things worse in production, in the same patch. Trusting "it looks reasonable" is not review. Reading every line against the spec is.

Troubleshooting
  • git apply --check in Step 6 reports a conflict. Confirm the scratch copy was made from a clean ~/platformops at v1.1, with no uncommitted changes (git status should be clean before you copy). A diff built against the pattern this course established only applies cleanly against that same starting point.
  • uv sync in Step 7 tries to install packages you do not want on your real machine. That is exactly why Step 6 and 7 happen in /tmp/m14-scratch, never in ~/platformops. Confirm your shell's working directory before running uv sync or uv run.
  • You do not see the ModuleNotFoundError in Step 7 -- the command seems to run. Confirm git apply in Step 7 actually reported no output (silence means success) and that src/platformops/depcheck.py exists in /tmp/m14-scratch afterward. If the apply silently failed, the old, unmodified cli.py is still what is running.
  • grep -n -A 5 in Step 1 returns nothing. Confirm you are in ~/platformops (not /tmp/m14-scratch) and that your project is genuinely at v1.1 -- check-security was added in Module 11 and should already be present.

Teardown​

rm -rf /tmp/m14-scratch
cd ~/platformops
rm -rf specs review-findings.md

This removes the scratch copy from Phase 2 and the practice spec and findings files from Phase 1. Your real ~/platformops project is untouched and still at v1.1 -- this module never bumps the version or tags a new release.

Recovery

If you need a clean starting point at any step, ~/platformops itself was never modified by this lab -- there is nothing to restore. If you suspect it was, compare it against ~/307-aipython-labs/labs/checkpoints/v1.1/.
