Working Effectively with Coding Agents

Since M3, every lab has included an "agent-extended" phase: you wrote a precise description of what you wanted, a coding agent implemented it, and you reviewed the result. That pattern — describe, delegate, review — is the one real skill this module teaches. Everything else is a variation on it.

A coding agent is not a colleague who understands your project. It is closer to a contractor you hired for one specific job: the quality of what you get back depends almost entirely on how clearly you described the work, what constraints you set, and how carefully you inspect the result. This module makes that process explicit and repeatable, so you can use it on any task, with any agent, and catch the mistakes agents make most often before those mistakes reach your tests or your users.

1. A spec is a contract, not a conversation​

Think about hiring a contractor to add a room to your house. You would not just say "add a room" and hope for the best. You would hand them a written scope: what the room is for, where it connects to the existing structure, which materials are approved, what the building code requires, and how you will inspect the result. A specification for a coding agent works the same way. It is a short, written document that answers four questions before the agent writes a single line:

  1. What does it do? A plain description of the feature or fix, stated as behavior the user can observe, not as implementation steps.
  2. What can change? The exact list of files the agent is allowed to modify or create. Anything not on this list is off limits.
  3. What is approved? Dependencies, patterns, and approaches the agent may use. If Flask is not on this list, the agent should not add it.
  4. How do I know it worked? Acceptance criteria, that is, concrete checks the result must pass. "All existing tests still pass" is always one of them.

The reason a written spec works better than a conversation is not about formality. It is about anchoring. When an agent has a written constraint list, it refers back to that list while it works. When it only has a conversational prompt, it drifts. The constraint you mentioned three messages ago fades from its working context the same way a verbal instruction fades from a contractor's memory after lunch.

2. Small changes, tight scope​

Imagine reviewing a one-page memo versus a fifty-page report. The memo takes two minutes; you catch every mistake. The fifty-page report takes an hour, your attention drifts halfway through, and you miss a factual error on page thirty-seven.

Agent-generated code works the same way. A diff that touches three files and adds forty lines is something you can read carefully, verify against the spec, and accept or reject with confidence. A diff that touches fifteen files, adds a new dependency, reorganizes two modules, and "improves" code you did not ask it to touch is almost impossible to review well, and the mistakes hide in the parts you skim.

The rule is simple: one feature per request, with an explicit list of files that may change. If the agent's diff touches a file you did not list, that is a finding, regardless of whether the change looks correct. Scope creep in an agent's output is exactly as dangerous as scope creep in a contractor's invoice.

3. The six flaws agents produce reliably​

Coding agents are good at producing code that compiles, passes a basic smoke test, and looks reasonable at first glance. They are systematically weak at six specific things, because those things require context the agent either does not have or does not prioritize:

  1. Missing timeouts. The agent calls an HTTP endpoint or runs a subprocess without setting a timeout. The code works in testing (where the server answers fast) and hangs in production (where the server is overloaded or unreachable).
  2. Logged credentials. The agent adds a log line that includes a token or key value. It is trying to be helpful ("here is what we sent"), but the credential now appears in every log file, every CI output, every terminal session that runs this code.
  3. Swallowed exceptions. The agent writes except Exception: pass or except: pass to "handle" an error. The error is now invisible. The function returns None or an empty result, and the caller has no way to know something went wrong.
  4. Hallucinated APIs. The agent imports a module or calls a function that does not exist in your project or in any installed package. It looks correct because the name is plausible ("of course there would be a platformops.cloud module"), but it fails on the first import.
  5. Needless dependencies. The agent adds a package to solve a problem that existing tools already handle. Adding requests when the project already uses httpx, or adding flask for a feature that is entirely CLI-based, are both real examples.
  6. Destructive defaults. The agent writes a cleanup function that deletes a directory without asking for confirmation, or a reset function that drops data without a dry-run option. The code works as written, and the first time someone runs it on the wrong directory, it destroys real data.

None of these are rare. You will see at least one of them in almost every non-trivial agent diff. The lab gives you practice finding all six in a single, realistic patch.

4. Reading a diff is the actual skill​

When you delegate implementation to an agent, your job shifts from "write code" to "review code critically." The output of that delegation is a diff, that is, a line-by-line record of what changed. Every line in that diff needs a reason to exist, and your job is to ask three questions of each change:

  1. Is this what I asked for? Does the change match the spec? If the spec said "modify scripts/check-deps.sh" and the diff also modifies src/platformops/cli.py, that is a scope violation.
  2. Is this safe? Does the change introduce any of the six common flaws? A missing timeout, a logged credential, a swallowed exception?
  3. Is this necessary? Does every new line serve the feature? A new dependency, a new import, a refactored function you did not ask to refactor. Each one is a question, not an automatic accept.

This is the same discipline code review has always required. The difference is that an agent produces code faster than a human does, so the review queue fills up faster. If you let review quality drop to keep up with the agent's output speed, you lose the entire benefit of having the agent in the first place.

Common pitfalls
  • Reviewing at the speed the agent writes. An agent can produce a 200-line diff in thirty seconds. Reviewing it properly still takes ten minutes. If you accept without reading, you are not delegating. You are rubber-stamping.
  • Trusting "all tests pass" as proof of correctness. Tests verify the paths they cover. A missing timeout, a logged credential, or a swallowed exception can all coexist with a green test suite. The review catches what tests do not.
  • Skipping the scope check. The agent modified a file you did not list in the spec. It might be a legitimate need, or it might be scope creep. Ask why before you accept.
  • Accepting a hallucinated import because the name looks right. platformops.cloud sounds like it should exist. It does not. Verify every new import against the actual codebase.
  • Not writing the spec at all. A conversational prompt ("add JSON output to check-deps") drifts faster than a written spec. The five minutes you save by skipping the spec cost you thirty minutes of review when the agent's output does not match what you had in mind.
